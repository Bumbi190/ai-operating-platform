# Chapter 4 — Canonical Concepts and Object Model

<a id="section-4-1"></a>
## 4.1 Chapter Status

This chapter defines the canonical concepts, objects, relationships, identifiers, lifecycle rules and state boundaries of the Omnira Intelligence Fabric.

It establishes the common language through which Omnira shall represent:

- intent,

- identity,

- scope,

- authority,

- capabilities,

- providers,

- models,

- tools,

- agents,

- execution plans,

- executions,

- outputs,

- costs,

- approvals,

- evidence,

- provenance,

- evaluations,

- incidents,

- learning,

- and memory candidates.

The object model defined in this chapter is normative after formal approval.

It does not require every object to be implemented as a separate database table or service.

An implementation may combine storage structures where this does not collapse canonical meaning, authority or lifecycle boundaries.

An implementation shall not merge concepts merely because they appear operationally similar.

The canonical distinctions in this chapter must remain observable and enforceable.

<a id="section-4-2"></a>
## 4.2 Purpose of the Canonical Object Model

The Intelligence Fabric coordinates many systems that use different terminology.

A provider may call an operation:

- generation,

- completion,

- prediction,

- render,

- inference,

- run,

- task,

- job,

- request,

- or agent execution.

Omnira requires a stable internal language that does not change whenever a provider changes its interface.

The canonical object model exists to:

- separate Omnira concepts from provider terminology,

- make execution traceable,

- preserve authority and scope,

- support provider replacement,

- normalise lifecycle state,

- enable cost attribution,

- preserve provenance,

- support audit and recovery,

- and provide stable contracts for humans and machines.

Provider objects may be translated into canonical objects.

Provider terminology shall not redefine the canonical model.

<a id="section-4-3"></a>
## 4.3 Canonical Meaning Before Storage Design

The object model defines meaning before storage design.

A canonical object may be represented through:

- a database row,

- an immutable event,

- a document,

- a structured log,

- an in-memory object,

- a graph entity,

- a queue message,

- or a derived view.

Storage form does not determine canonical meaning.

For example:

- an Approval may be stored in a relational table,

- an Execution Receipt may be an immutable document,

- a Provider Job may be represented as part of an Execution Attempt,

- and a relationship may be projected into the Intelligence Graph.

The implementation must preserve:

- identity,

- ownership,

- scope,

- lifecycle,

- provenance,

- authority,

- and version.

Canonical boundaries must survive storage optimisation.

<a id="section-4-4"></a>
## 4.4 Object, Record, Event and View

The Fabric shall distinguish between an object, a record, an event and a view.

An object represents a canonical entity with identity and lifecycle.

A record represents persisted evidence or state about an object.

An event represents something that occurred at a specific time.

A view represents a derived interpretation of one or more objects, records or events.

For example:

- an Execution is an object,

- an Execution Receipt is a record,

- ExecutionStarted is an event,

- and ActiveExecutionsByProject is a view.

A view shall not become the authoritative source merely because it is convenient to query.

Events shall not be treated as mutable current state.

Records shall not silently replace the object whose evidence they preserve.

<a id="section-4-5"></a>
## 4.5 Canonical Identity

Every canonical object that persists beyond a single local operation shall have a stable identifier.

Identifiers shall be:

- unique within their canonical namespace,

- immutable after creation,

- safe to reference across services,

- independent of display names,

- and separate from provider identifiers.

An object may also have:

- human-readable name,

- slug,

- external identifier,

- provider identifier,

- version identifier,

- and correlation identifier.

These shall not replace the canonical identifier.

A provider job ID identifies a provider-side object.

It does not replace the Omnira Execution ID.

<a id="section-4-6"></a>
## 4.6 Identifier Requirements

Canonical identifiers should be generated using a collision-resistant format.

The exact implementation may use:

- UUID,

- ULID,

- another time-sortable identifier,

- or an equivalent approved scheme.

Identifiers must not encode sensitive information.

Identifiers must not depend on:

- project names,

- user email addresses,

- provider names,

- or mutable business labels.

An identifier may be globally unique while access remains scope-restricted.

Knowledge of an identifier does not grant authority to access the object.

<a id="section-4-7"></a>
## 4.7 Canonical Metadata

Persistent canonical objects should include common metadata where applicable.

Expected metadata includes:

- id,

- objectType,

- schemaVersion,

- createdAt,

- createdBy,

- updatedAt,

- updatedBy,

- tenantId,

- projectId,

- environmentId,

- lifecycleStatus,

- classification,

- provenanceReference,

- and version.

Not every object requires every field.

Absence must be deliberate.

Missing tenant or project scope must not be interpreted as global scope without an explicit global-scope declaration.

<a id="section-4-8"></a>
## 4.8 Canonical Envelope

Objects exchanged between Fabric components should use a canonical envelope.

A conceptual envelope may contain:

Object Envelope

- objectType

- objectId

- schemaVersion

- tenantId

- projectId

- environmentId

- correlationId

- causationId

- traceId

- createdAt

- createdBy

- classification

- payload

- provenance

- integrityMetadata

The envelope supports consistent transport and evidence.

The envelope shall not be used to hide ambiguous payload meaning.

Payload schemas must remain explicit and versioned.

<a id="section-4-9"></a>
## 4.9 Correlation and Causation

The Fabric shall distinguish correlation from causation.

Correlation identifies objects and events that belong to the same broader operation or production.

Causation identifies the specific object or event that caused another object or event to exist.

For example:

- a monthly Nova and Pling production may have one Production Correlation ID,

- each scene Execution may belong to that correlation,

- and a retry Attempt may be caused by a specific failed Attempt.

Correlation supports grouping.

Causation supports explanation.

Both should be preserved through asynchronous boundaries.

<a id="section-4-10"></a>
## 4.10 Object Versioning

Canonical object schemas shall be versioned.

Versioning may include:

- schema version,

- object revision,

- provider resource version,

- policy version,

- capability version,

- and adapter version.

Schema version describes the shape and meaning of the object.

Object revision describes changes to a specific object instance.

Provider or model version describes the external resource used.

These concepts must not be collapsed into one generic version field.

<a id="section-4-11"></a>
## 4.11 Immutable and Mutable Objects

The Fabric shall distinguish immutable evidence from mutable operational state.

Objects such as the following should normally be immutable once finalised:

- Approval Decision,

- Execution Receipt,

- Cost Receipt,

- Provider Response Evidence,

- Evaluation Result,

- Policy Decision Record,

- and Publication Verification Record.

Operational objects such as the following may evolve through controlled lifecycle transitions:

- Capability Request,

- Execution Plan,

- Execution,

- Provider Connection,

- Budget Reservation,

- and Incident.

Immutable records may be superseded by new records.

They should not be rewritten to erase history.

<a id="section-4-12"></a>
## 4.12 Canonical Lifecycle Model

Canonical objects shall use explicit lifecycle states appropriate to their type.

A lifecycle transition should record:

- previous state,

- new state,

- transition time,

- actor,

- reason,

- related evidence,

- and policy basis where applicable.

Objects must not transition directly between states that bypass required approval, validation or reconciliation.

The canonical lifecycle shall distinguish:

- creation,

- activation,

- execution,

- completion,

- failure,

- cancellation,

- supersession,

- deprecation,

- and archival.

State names shall have defined meaning.

<a id="section-4-13"></a>
## 4.13 Principal

A Principal is an identity that may act within Omnira.

A Principal may represent:

- human user,

- service,

- agent,

- Manager,

- workflow,

- system process,

- external integration,

- or delegated runtime identity.

A Principal shall include:

- principalId,

- principalType,

- tenantId,

- status,

- authentication relationship,

- and authority references.

A Principal shall not receive authority merely because it is authenticated.

Authentication proves identity.

Authorisation determines permitted action.

<a id="section-4-14"></a>
## 4.14 Human Principal

A Human Principal represents a person using or governing Omnira.

A Human Principal may hold roles such as:

- owner,

- administrator,

- project owner,

- approver,

- operator,

- reviewer,

- developer,

- auditor,

- or customer user.

Roles shall remain scoped.

A person may be:

- owner in one tenant,

- project approver in another project,

- and ordinary operator elsewhere.

Human identity must not be inferred only from an email address or provider account.

<a id="section-4-15"></a>
## 4.15 Service Principal

A Service Principal represents a non-human system component.

Examples include:

- routing service,

- execution worker,

- callback processor,

- evaluation service,

- asset ingestion service,

- or publication service.

A Service Principal shall have:

- explicit purpose,

- limited permissions,

- credential identity,

- environment scope,

- and lifecycle.

Service Principals must not share one unrestricted platform identity merely for implementation convenience.

<a id="section-4-16"></a>
## 4.16 Agent Principal

An Agent Principal represents an Omnira-governed agent identity.

An Agent Principal shall remain separate from:

- the model it uses,

- the provider that hosts execution,

- the prompt version,

- and the runtime process.

The Agent Principal may reference:

- role definition,

- behavioural policy,

- authority,

- project assignments,

- memory access,

- tools,

- and capability permissions.

The agent’s current model may change without changing the Agent Principal.

<a id="section-4-17"></a>
## 4.17 Tenant

A Tenant is the highest ordinary isolation boundary for users, organisations, projects, credentials, budgets, evidence and policy.

A Tenant shall have:

- tenantId,

- ownership relationship,

- lifecycle status,

- governance policy,

- region where applicable,

- billing relationships,

- and administrative principals.

Tenant absence shall not imply shared access.

Platform-global objects must declare global scope explicitly.

<a id="section-4-18"></a>
## 4.18 Project

A Project is a governed operational scope within a Tenant.

A Project may represent:

- Familje-Stunden,

- The Prompt,

- GainPilot,

- Omnira,

- a customer initiative,

- or another bounded business or product context.

A Project shall define or reference:

- projectId,

- tenantId,

- name,

- slug,

- status,

- project policies,

- budgets,

- assets,

- agents,

- workflows,

- memories,

- provider restrictions,

- and approval rules.

Project names are display properties.

Project IDs are authoritative identifiers.

<a id="section-4-19"></a>
## 4.19 Project Relationship

Projects may have explicit relationships.

Examples include:

- parent and child,

- shared brand,

- supplier and consumer,

- portfolio membership,

- approved asset sharing,

- or cross-project reporting.

A Project Relationship shall define:

- participating projects,

- relationship type,

- permitted data,

- permitted capabilities,

- authority,

- duration,

- and revocation.

Common ownership does not automatically create a Project Relationship.

<a id="section-4-20"></a>
## 4.20 Environment

An Environment represents an operational deployment or execution context.

Expected environments include:

- local development,

- test,

- simulation,

- preview,

- staging,

- production,

- recovery,

- and sandbox.

An Environment shall influence:

- credentials,

- provider accounts,

- policies,

- data,

- budgets,

- callbacks,

- and publication eligibility.

Environment must remain explicit across the full execution chain.

<a id="section-4-21"></a>
## 4.21 Scope

A Scope defines the boundary within which an object, permission, execution or learning is valid.

A Scope may include:

- tenant,

- project,

- environment,

- user,

- agent,

- workflow,

- production,

- capability,

- resource,

- data class,

- and time.

Scope is not a single universal string.

It is a structured boundary.

The Fabric shall support both:

- narrow scopes,

- and explicitly declared composite scopes.

Scope expansion requires authority.

<a id="section-4-22"></a>
## 4.22 Scope Resolution

Scope Resolution is the process of determining the authoritative scope for a request or object.

Scope Resolution may use:

- authenticated principal,

- project route,

- explicit request envelope,

- delegated authority,

- workflow assignment,

- and tenant membership.

Scope shall not be resolved solely from:

- prompt text,

- visual branding,

- filename,

- or provider workspace name.

A Scope Resolution Record should preserve:

- source information,

- resolved scope,

- policy version,

- and resolution confidence or failure.

<a id="section-4-23"></a>
## 4.23 Caller

A Caller is the Principal that submits a Capability Request.

The Caller may be:

- human,

- Atlas,

- Manager,

- agent,

- workflow,

- service,

- or approved external client.

Caller identity shall be preserved even when the request is delegated.

The Caller is not always the original authority source.

The Fabric shall distinguish:

- caller,

- initiating user,

- delegating principal,

- and approving principal.

<a id="section-4-24"></a>
## 4.24 Initiator

The Initiator is the Principal or event that originated the broader objective.

For example:

- a user may initiate a media production,

- Atlas may create a Capability Request,

- a Manager may create execution steps,

- and a worker may invoke the provider.

The user remains the Initiator.

The worker is the immediate technical caller.

Both relationships should remain traceable.

<a id="section-4-25"></a>
## 4.25 Delegation

A Delegation is a governed transfer of bounded authority from one Principal to another.

A Delegation shall define:

- delegator,

- delegate,

- permitted actions,

- scope,

- capability,

- budget,

- data access,

- validity,

- re-delegation permission,

- and revocation state.

A Delegation must not exceed the delegator’s authority.

Delegation chains shall remain traceable.

<a id="section-4-26"></a>
## 4.26 Authority

Authority represents permission to perform an action.

Authority shall not be modelled as a single unrestricted boolean.

An Authority object or rule should include:

- principal,

- action,

- capability,

- scope,

- data classification,

- provider restrictions,

- budget limit,

- time validity,

- approval requirement,

- and conditions.

Authority may be:

- direct,

- role-based,

- delegated,

- approved,

- policy-derived,

- or emergency-limited.

Technical access without Authority is insufficient.

<a id="section-4-27"></a>
## 4.27 Authority Envelope

An Authority Envelope is the effective authority attached to a specific request or production.

It may include:

- authorised principals,

- approved capabilities,

- allowed providers,

- prohibited actions,

- maximum budget,

- retry limit,

- output restrictions,

- publication prohibition,

- data boundaries,

- expiry,

- and approval references.

The Authority Envelope is evaluated before execution and at material execution boundaries.

It shall not be expanded by the Fabric.

<a id="section-4-28"></a>
## 4.28 Approval

An Approval is a governed decision that permits, rejects or conditions a proposed action.

An Approval shall include:

- approvalId,

- requestType,

- subject,

- approver,

- decision,

- scope,

- constraints,

- validity,

- createdAt,

- decidedAt,

- evidence reviewed,

- and reason where appropriate.

Approval decisions may include:

- approved,

- rejected,

- approved with conditions,

- expired,

- revoked,

- superseded,

- or cancelled.

Approval state must not be inferred from conversation tone alone.

<a id="section-4-29"></a>
## 4.29 Production Envelope

A Production Envelope defines the approved operational boundaries for a multi-step production.

It may contain:

- productionId,

- projectId,

- objective,

- permitted capabilities,

- approved providers,

- maximum cost,

- maximum credits,

- scene count,

- variation count,

- retry limits,

- input assets,

- output formats,

- review requirements,

- publication restrictions,

- deadline,

- and validity.

The Production Envelope allows bounded autonomy across multiple executions.

It does not grant unlimited project authority.

<a id="section-4-30"></a>
## 4.30 Policy

A Policy is a governed rule that constrains or guides Fabric behaviour.

Policies may govern:

- provider eligibility,

- model eligibility,

- data placement,

- cost,

- retries,

- fallback,

- rights,

- publication,

- retention,

- and learning.

A Policy shall have:

- policyId,

- policyType,

- scope,

- version,

- status,

- effective time,

- precedence,

- conditions,

- decision logic,

- and provenance.

Natural-language policy may exist.

Operational policy must have sufficiently structured meaning to be enforceable.

<a id="section-4-31"></a>
## 4.31 Policy Context

Policy Context is the structured input used to evaluate policies for a request.

Policy Context may include:

- principal,

- tenant,

- project,

- environment,

- capability,

- data classification,

- provider candidates,

- budget,

- quality,

- rights,

- time,

- and current system state.

Policy Context shall be immutable for a single policy decision.

Material changes require re-evaluation.

<a id="section-4-32"></a>
## 4.32 Policy Decision

A Policy Decision records the result of evaluating one or more policies.

It shall include:

- policyDecisionId,

- evaluated policies,

- policy versions,

- input context reference,

- decision,

- allowed actions,

- denied actions,

- conditions,

- explanation,

- and timestamp.

Policy Decision states may include:

- allow,

- deny,

- allow with conditions,

- require approval,

- require local execution,

- require manual review,

- or unresolved.

An unresolved mandatory policy condition must fail closed.

<a id="section-4-33"></a>
## 4.33 Data Classification

A Data Classification describes the required protection of information.

Canonical classifications are expected to include:

- Public,

- Project Internal,

- Confidential,

- Local Only,

- and Prohibited.

A Data Classification object or value may also include:

- reason,

- source,

- classifier,

- confidence,

- inherited restrictions,

- retention,

- and review date.

Classification applies to both input and output.

Classification may change only through governed transition.

<a id="section-4-34"></a>
## 4.34 Data Item

A Data Item is a bounded unit of information used or created by the Fabric.

A Data Item may represent:

- text,

- document,

- image,

- audio,

- video,

- metadata,

- memory,

- prompt,

- transcript,

- code,

- or structured dataset.

A Data Item should include or reference:

- owner,

- tenant,

- project,

- classification,

- rights,

- storage location,

- checksum,

- format,

- and provenance.

Providers should receive Data Item references or transformed representations rather than uncontrolled raw project context.

<a id="section-4-35"></a>
## 4.35 Data Use Grant

A Data Use Grant authorises specific use of a Data Item.

It may define:

- permitted Principal,

- purpose,

- capability,

- provider class,

- duration,

- transformations,

- output restrictions,

- and retention.

A Data Use Grant may be required for:

- voice assets,

- likeness assets,

- confidential documents,

- customer data,

- or cross-project references.

Ownership alone does not imply unlimited use.

<a id="section-4-36"></a>
## 4.36 Consent Record

A Consent Record preserves permission related to personal data, voice, likeness or other consent-sensitive use.

It should include:

- subject,

- consenting party,

- permitted use,

- project,

- provider restrictions,

- commercial-use permission,

- validity,

- revocation,

- evidence,

- and jurisdiction where relevant.

A Consent Record must remain separate from provider terms.

Provider capability does not prove subject consent.

<a id="section-4-37"></a>
## 4.37 Rights Profile

A Rights Profile describes the legal and contractual conditions attached to an input, output or provider capability.

It may include:

- ownership,

- licence,

- commercial-use permission,

- attribution requirement,

- territorial restriction,

- derivative-use permission,

- publication restriction,

- provider terms version,

- and uncertainty.

A Rights Profile may be:

- confirmed,

- conditionally valid,

- disputed,

- unknown,

- or prohibited.

Unknown material rights shall trigger review when the use is consequential.

<a id="section-4-38"></a>
## 4.38 Intent

Intent represents the desired outcome or purpose behind a request.

Intent shall remain separate from:

- execution plan,

- provider choice,

- model parameters,

- and output.

An Intent object may include:

- objective,

- business context,

- desired effect,

- constraints,

- success definition,

- and initiating Principal.

Intent may be broad.

Capability Requests must translate it into executable requirements.

<a id="section-4-39"></a>
## 4.39 Intent Envelope

An Intent Envelope is the canonical structure through which a caller submits the desired result and constraints.

It may include:

- intentId,

- objective,

- tenantId,

- projectId,

- requester,

- beneficiary,

- required capabilities,

- inputs,

- desired outputs,

- quality expectations,

- data restrictions,

- rights requirements,

- budget,

- deadline,

- routing profile,

- authority reference,

- and review requirements.

The Intent Envelope describes what must be achieved.

It does not prescribe provider implementation unless pinned.

<a id="section-4-40"></a>
## 4.40 Capability

A Capability is a canonical description of an operation or result that an intelligence resource can perform.

A Capability shall have:

- capabilityId,

- canonical name,

- description,

- modality,

- input contract,

- output contract,

- quality dimensions,

- execution characteristics,

- risk classification,

- lifecycle,

- and version.

Examples include:

- text.reasoning,

- code.generate,

- image.edit,

- image.generate,

- video.image_to_video,

- speech.synthesise,

- speech.transcribe,

- retrieval.embed,

- retrieval.rerank,

- research.verify_sources,

- and media.character_consistency_evaluate.

Capability names should be stable and provider-independent.

<a id="section-4-41"></a>
## 4.41 Capability Version

A Capability Version defines a specific contract revision.

A version may change when:

- input requirements change,

- output meaning changes,

- quality dimensions change,

- risk classification changes,

- or required evidence changes.

Backward-compatible metadata additions may not require a major capability version.

Callers and adapters shall declare supported versions.

<a id="section-4-42"></a>
## 4.42 Capability Requirement

A Capability Requirement describes one required capability within a request.

It may include:

- capabilityId,

- version constraint,

- required quality,

- required inputs,

- desired output,

- priority,

- mandatory or optional status,

- and dependency relationships.

A request may contain several Capability Requirements.

Optional capabilities may support graceful degradation.

<a id="section-4-43"></a>
## 4.43 Capability Request

A Capability Request is the canonical request submitted to the Fabric for intelligence work.

It shall include:

- requestId,

- caller,

- tenantId,

- projectId,

- environmentId,

- intent reference,

- capability requirements,

- input references,

- output contract,

- authority envelope,

- policy context,

- routing profile,

- budget envelope,

- quality contract,

- deadline,

- and lifecycle status.

A Capability Request is not the same as an Execution.

One Capability Request may produce:

- one Execution,

- multiple Executions,

- no Execution because it was denied,

- or a human-assisted workflow.

<a id="section-4-44"></a>
## 4.44 Capability Request Lifecycle

Expected Capability Request states include:

- draft,

- submitted,

- validating,

- awaiting approval,

- approved,

- planning,

- rejected,

- cancelled,

- executing,

- partially completed,

- completed,

- failed,

- and expired.

The request may complete even when one optional capability is not fulfilled, if the output contract permits it.

Completion requires acceptance criteria.

<a id="section-4-45"></a>
## 4.45 Requirement Constraint

A Requirement Constraint narrows eligibility or execution.

Constraints may include:

- maximum cost,

- maximum latency,

- minimum quality,

- allowed provider,

- prohibited provider,

- local-only placement,

- output format,

- resolution,

- language,

- commercial use,

- deterministic seed support,

- context capacity,

- or human-review requirement.

Constraints should be machine-evaluable where possible.

Unstructured constraints may require interpretation and evidence.

<a id="section-4-46"></a>
## 4.46 Routing Profile

A Routing Profile defines the optimisation posture for resource selection.

Canonical profiles include:

- Economy,

- Balanced,

- Premium,

- Private,

- and Pinned.

A Routing Profile may include:

- optimisation weights,

- default quality floor,

- latency preference,

- cost preference,

- provider restrictions,

- and fallback posture.

Routing Profiles are policy inputs.

They do not override mandatory constraints.

<a id="section-4-47"></a>
## 4.47 Quality Contract

A Quality Contract defines how acceptable output shall be judged.

It may include:

- quality dimensions,

- minimum thresholds,

- deterministic validations,

- evaluator requirements,

- human-review requirements,

- rejection conditions,

- retry allowance,

- and acceptance authority.

Quality Contracts shall be capability-specific.

A generic quality score is insufficient for many tasks.

<a id="section-4-48"></a>
## 4.48 Quality Dimension

A Quality Dimension represents one measurable or reviewable aspect of quality.

Examples include:

- factual accuracy,

- source completeness,

- code correctness,

- visual consistency,

- character identity,

- brand alignment,

- voice naturalness,

- child appropriateness,

- resolution,

- timing,

- and format compliance.

A Quality Dimension may be evaluated by:

- deterministic test,

- model evaluator,

- human reviewer,

- external metric,

- or composite method.

<a id="section-4-49"></a>
## 4.49 Acceptance Criterion

An Acceptance Criterion defines the proof required for a result to be accepted.

It shall include:

- criterion,

- evaluation method,

- threshold,

- required evidence,

- and mandatory or optional status.

Examples include:

- all tests pass,

- character-consistency score exceeds threshold,

- human reviewer approves,

- required citations are present,

- or publication is verified live.

Execution completion does not imply acceptance.

<a id="section-4-50"></a>
## 4.50 Budget Envelope

A Budget Envelope defines the economic limits for a request or production.

It may include:

- budgetId,

- currency,

- credit unit,

- maximum estimated cost,

- maximum actual cost,

- provider-account restrictions,

- project budget source,

- fallback candidates,

- trigger conditions,

- quality floor,

- cost limit,

- data restrictions,

- verifying,

- verified,

- rejected,

- duplicate,

- idempotency,

- provider request identifier,

- provider response,

- usage,

- cost,

- timestamps,

- status,

- and signature or integrity information where available.

Provider Receipts should be retained in their original form where possible.

Canonical interpretation may be stored separately.

<a id="section-4-112"></a>
## 4.112 Boundary Receipt

A Boundary Receipt records the critical scope and authority decisions applied to execution.

It may include:

- tenant,

- project,

- environment,

- caller,

- authority,

- data classification,

- provider account,

- policy version,

- budget source,

- approval,

- and restrictions.

Boundary Receipts help prove that the execution stayed within the intended scope.

<a id="section-4-113"></a>
## 4.113 Decision Evidence

Decision Evidence is evidence used by Atlas, Executive Intelligence, Managers or humans to support a decision.

It may include:

- research,

- evaluations,

- costs,

- provider performance,

- audience analytics,

- incidents,

- or previous outcomes.

Decision Evidence shall preserve:

- source,

- date,

- scope,

- confidence,

- and limitations.

Evidence is not itself the final decision.

<a id="section-4-114"></a>
## 4.114 Incident

An Incident is an event or condition that threatens:

- security,

- privacy,

- rights,

- reliability,

- cost control,

- project isolation,

- or truthful operation.

An Incident shall include:

- incidentId,

- severity,

- scope,

- detectedAt,

- detector,

- affected objects,

- containment,

- status,

- evidence,

- and resolution.

Incident lifecycle shall remain separate from ordinary Execution failure.

<a id="section-4-115"></a>
## 4.115 Incident Severity

Incident Severity may include:

- informational,

- low,

- moderate,

- high,

- critical,

- and catastrophic where needed.

Severity should consider:

- affected users,

- data sensitivity,

- financial impact,

- public consequence,

- duration,

- scope,

- and recoverability.

Severity shall not be determined only by technical error type.

<a id="section-4-116"></a>
## 4.116 Incident Lifecycle

Expected Incident states include:

- detected,

- triaged,

- contained,

- investigating,

- recovering,

- resolved,

- monitoring,

- and closed.

Closure requires sufficient evidence.

A temporary provider recovery does not automatically resolve the root cause.

<a id="section-4-117"></a>
## 4.117 Learning Candidate

A Learning Candidate is a proposed conclusion derived from execution evidence.

It shall include:

- claim,

- supporting evidence,

- scope,

- capability,

- conditions,

- confidence,

- creator,

- and proposed retention.

A Learning Candidate is not yet governed long-term memory.

<a id="section-4-118"></a>
## 4.118 Derived Learning

Derived Learning is a reviewed conclusion accepted for operational or decision support.

It may state:

- one provider performs better for a specific capability,

- one workflow configuration reduces cost,

- one quality failure occurs repeatedly,

- or one project audience responds better to a format.

Derived Learning shall include:

- evidence,

- scope,

- confidence,

- validity,

- contradiction handling,

- and review status.

<a id="section-4-119"></a>
## 4.119 Memory Candidate

A Memory Candidate is a structured proposal submitted to Atlas Memory or another governed memory system.

It may originate from:

- Derived Learning,

- user instruction,

- decision,

- preference,

- repeated pattern,

- or verified project fact.

A Memory Candidate shall include:

- proposed memory type,

- owner,

- project,

- source,

- confidence,

- sensitivity,

- retention,

- and supersession rules.

The Fabric shall not directly admit Memory Candidates into permanent memory without the memory-governance process.

<a id="section-4-120"></a>
## 4.120 Governed Memory Reference

A Governed Memory Reference links Fabric work to an approved memory object without making the Fabric the memory owner.

The reference may include:

- memoryId,

- version,

- scope,

- retrieval permission,

- and usage reason.

Memory access shall be minimised and evidenced when relevant.

<a id="section-4-121"></a>
## 4.121 Publication Package

A Publication Package is a structured set of approved or publication-ready assets and metadata.

It may include:

- media,

- caption,

- title,

- description,

- thumbnail,

- subtitles,

- target platform,

- scheduling preference,

- rights profile,

- approval state,

- and provenance.

A Publication Package is not proof of publication.

Publication requires a separate side-effect execution.

<a id="section-4-122"></a>
## 4.122 Publication Record

A Publication Record preserves evidence of an external publication action.

It may include:

- platform,

- account,

- asset,

- submittedAt,

- external post identifier,

- status,

- public URL reference,

- verification,

- and publication receipt.

Expected states include:

- prepared,

- scheduled,

- submitted,

- published,

- failed,

- removed,

- and verified live.

<a id="section-4-123"></a>
## 4.123 Health Observation

A Health Observation records the observed operational state of a Provider, Connection, Adapter, Model Deployment or Runtime Node.

It may include:

- target,

- time,

- status,

- latency,

- error rate,

- capacity,

- and source.

One observation does not permanently define health.

Health state is derived from observations.

<a id="section-4-124"></a>
## 4.124 Health State

Health State is the current derived operational condition of a resource.

Expected states may include:

- healthy,

- degraded,

- unavailable,

- unknown,

- maintenance,

- rate limited,

- authentication required,

- and exhausted.

Health State does not equal policy eligibility.

<a id="section-4-125"></a>
## 4.125 Benchmark

A Benchmark defines a repeatable evaluation used to measure resource performance.

It shall include:

- benchmarkId,

- capability,

- dataset or task,

- quality dimensions,

- execution conditions,

- scoring method,

- scope,

- and version.

Benchmarks may be:

- platform-wide,

- tenant-specific,

- project-specific,

- or provider-specific.

Benchmark results must remain contextual.

<a id="section-4-126"></a>
## 4.126 Benchmark Result

A Benchmark Result records one resource’s performance under defined conditions.

It should include:

- resource,

- model version,

- adapter version,

- benchmark version,

- cost,

- latency,

- quality,

- failures,

- date,

- and environment.

Benchmark Results may inform routing.

They do not override mandatory policy.

<a id="section-4-127"></a>
## 4.127 Registry

A Registry is a governed collection of canonical resource definitions.

The Fabric shall include or integrate with registries for:

- capabilities,

- providers,

- provider accounts,

- models,

- deployments,

- adapters,

- tools,

- external agents,

- and potentially evaluation methods.

A Registry shall support:

- identity,

- lifecycle,

- versioning,

- discovery,

- eligibility metadata,

- and historical interpretation.

A Registry is not merely a static configuration file.

<a id="section-4-128"></a>
## 4.128 Capability Registry

The Capability Registry is the authoritative catalogue of canonical capabilities.

It shall contain:

- capability definitions,

- versions,

- input and output contracts,

- risk classification,

- quality dimensions,

- supported resource mappings,

- and lifecycle.

Provider names must not define the Capability Registry structure.

<a id="section-4-129"></a>
## 4.129 Provider Registry

The Provider Registry is the authoritative catalogue of provider organisations and platform relationships.

It shall contain:

- Provider objects,

- trust metadata,

- terms references,

- service regions,

- lifecycle,

- and provider-level policy information.

Provider Accounts remain separate objects.

<a id="section-4-130"></a>
## 4.130 Model Registry

The Model Registry is the authoritative catalogue of Model, Model Version and Model Deployment objects.

It shall support:

- capability mapping,

- lifecycle,

- quality evidence,

- context limits,

- pricing references,

- and deprecation.

The Registry must preserve historical versions used by past executions.

<a id="section-4-131"></a>
## 4.131 Tool and Agent Resource Registry

The Tool and Agent Resource Registry represents executable non-model resources.

It may contain:

- tools,

- provider-hosted agents,

- workflows,

- local utilities,

- browser actions,

- repository tools,

- and publication tools.

Each resource shall declare:

- capability,

- action class,

- side effects,

- authority requirements,

- and integration maturity.

<a id="section-4-132"></a>
## 4.132 Canonical Status Vocabulary

Status values shall be defined per object type.

The Fabric must not use one generic status field with ambiguous values across all objects.

For example:

- active for a Provider Account,

- running for an Execution,

- approved for an Approval,

- and canonical for an Asset

represent different lifecycle concepts.

Status vocabularies shall be documented and versioned.

<a id="section-4-133"></a>
## 4.133 Terminal State

A Terminal State is a state after which ordinary lifecycle progression ends.

Examples include:

- completed,

- failed,

- cancelled,

- rejected,

- revoked,

- retired,

- and archived.

Unknown outcome may be temporarily terminal for automated execution but remain open to reconciliation.

Terminal does not always mean immutable.

A reconciliation event may supersede prior interpretation without rewriting evidence.

<a id="section-4-134"></a>
## 4.134 Unknown State

Unknown shall be treated as an explicit state where the system lacks sufficient evidence.

Unknown may apply to:

- provider job outcome,

- cost,

- health,

- rights,

- classification,

- or publication.

Unknown must not be silently converted into a favourable default.

Resolution may require:

- new evidence,

- human review,

- provider reconciliation,

- or blocking action.

<a id="section-4-135"></a>
## 4.135 Unavailable State

Unavailable means the resource or capability cannot currently be used.

Unavailable may result from:

- outage,

- policy,

- authentication,

- quota,

- deprecation,

- environment,

- or missing adapter.

Unavailable must preserve reason.

A capability may be architecturally defined while operationally unavailable.

<a id="section-4-136"></a>
## 4.136 Deprecated State

Deprecated means an object remains interpretable but should not be selected for new use.

Deprecation shall include:

- reason,

- effective date,

- replacement,

- migration plan,

- and retirement target where known.

Historical evidence must continue to resolve deprecated objects.

<a id="section-4-137"></a>
## 4.137 Retired State

Retired means the object is no longer available for active use.

Retired objects may remain queryable for:

- audit,

- provenance,

- historical cost,

- and incident review.

Retirement shall not erase identity or historical relationships.

<a id="section-4-138"></a>
## 4.138 Object Relationships

Canonical relationships shall be explicit.

Expected relationships include:

- belongs to Tenant,

- belongs to Project,

- initiated by,

- called by,

- delegated by,

- approved by,

- constrained by Policy,

- requires Capability,

- fulfilled by Execution,

- selected Provider,

- used Model Version,

- invoked through Adapter,

- charged to Budget Source,

- produced Output,

- created Asset,

- evaluated by,

- derived from,

- supported Decision,

- created Learning Candidate,

- and submitted Memory Candidate.

Relationships may be represented relationally or graphically.

Their meaning must remain stable.

<a id="section-4-139"></a>
## 4.139 Relationship Direction

Relationship direction shall reflect canonical meaning.

For example:

- Execution produced Output,

- Output derived Asset,

- Approval authorised Execution,

- and Learning derived from Evidence.

Inverse queries may be supported.

The canonical relationship direction should remain documented to avoid ambiguous graph semantics.

<a id="section-4-140"></a>
## 4.140 Relationship Scope

Relationships inherit or declare scope.

A relationship between objects in different Projects requires:

- an approved cross-project relationship,

- explicit authority,

- or a platform-global object type designed for that purpose.

The system shall not create cross-project relationships merely because identifiers are known.

<a id="section-4-141"></a>
## 4.141 Relationship Provenance

Meaningful relationships should preserve provenance.

The system should be able to determine:

- who created the relationship,

- what event caused it,

- when it became valid,

- and whether it remains active.

Derived relationships shall be distinguishable from explicitly approved relationships.

<a id="section-4-142"></a>
## 4.142 Canonical Time

Fabric objects shall use consistent time representation.

Timestamps should be:

- timezone-aware,

- stored in a canonical format,

- and attributable to a trusted clock source where consequence requires it.

The architecture shall distinguish:

- createdAt,

- submittedAt,

- acceptedAt,

- startedAt,

- completedAt,

- observedAt,

- effectiveAt,

- expiresAt,

- and verifiedAt.

One generic timestamp is insufficient.

<a id="section-4-143"></a>
## 4.143 Effective Time and Recorded Time

Effective Time describes when a fact or policy became valid.

Recorded Time describes when Omnira recorded it.

These may differ.

For example:

- provider terms may become effective before Omnira records them,

- a delayed callback may describe an earlier provider completion,

- and a human may record consent after the consent was originally given.

Both times may be important for audit and reconciliation.

<a id="section-4-144"></a>
## 4.144 Integrity Metadata

Important records should preserve integrity metadata.

This may include:

- checksum,

- signature,

- source system,

- immutable storage reference,

- schema version,

- and evidence chain.

Integrity metadata helps detect:

- corruption,

- accidental modification,

- duplicate ingestion,

- and disputed evidence.

Not every low-risk temporary object requires cryptographic signing.

Integrity controls should match consequence.

<a id="section-4-145"></a>
## 4.145 Classification Inheritance

Outputs and derived objects may inherit classification from their inputs.

Inheritance rules should consider:

- highest input classification,

- transformation,

- redaction,

- aggregation risk,

- and output content.

A derived public summary may be eligible for lower classification only through explicit declassification logic.

Classification shall not drop automatically because output is shorter or reformatted.

<a id="section-4-146"></a>
## 4.146 Rights Inheritance

Derivative outputs shall preserve relevant rights restrictions from source assets.

A generated animation based on a licensed character reference may remain subject to:

- character ownership,

- provider terms,

- commercial-use restrictions,

- and publication conditions.

Rights inheritance shall be evaluated through the full derivation chain.

<a id="section-4-147"></a>
## 4.147 Cost Attribution Chain

Cost shall remain attributable through:

- Capability Request,

- Execution Plan,

- Execution,

- Attempt,

- Provider Account,

- Budget Source,

- Project,

- and Tenant.

The cost chain must support:

- request-level reporting,

- production-level reporting,

- project reporting,

- provider reconciliation,

- and retry analysis.

Shared infrastructure cost may be allocated separately from direct provider cost.

<a id="section-4-148"></a>
## 4.148 Evidence Chain

An Evidence Chain links the objects required to explain an outcome.

A valid Evidence Chain may connect:

- Intent,

- Capability Request,

- Authority Envelope,

- Policy Decision,

- Selection Decision,

- Execution,

- Attempts,

- Provider Receipts,

- Outputs,

- Evaluations,

- Acceptance,

- Assets,

- and publication or memory outcomes.

The chain need not be stored in one document.

It must remain reconstructable.

<a id="section-4-149"></a>
## 4.149 Object Ownership

Each persistent object shall have an ownership model.

Ownership may belong to:

- user,

- tenant,

- project,

- platform,

- provider,

- or shared governed scope.

Ownership affects:

- access,

- retention,

- deletion,

- export,

- cost,

- and governance.

Ownership shall not be inferred only from who created the object.

<a id="section-4-150"></a>
## 4.150 Object Custody

Custody describes which system currently stores or controls an object.

Custody is separate from ownership.

A provider may have temporary custody of an input.

Omnira or the user may retain ownership.

A cloud storage system may have custody of an Asset.

The Project may own it.

Custody transitions should be evidenced for sensitive objects.

<a id="section-4-151"></a>
## 4.151 Object Authority

Object Authority defines who may:

- read,

- modify,

- approve,

- supersede,

- delete,

- publish,

- or administer an object.

Authority may vary by action.

The creator of an object does not automatically receive every authority over it.

<a id="section-4-152"></a>
## 4.152 Object Retention

Persistent objects shall have explicit or inherited retention.

Retention may depend on:

- object type,

- classification,

- legal requirement,

- project policy,

- provider terms,

- incident state,

- and memory status.

Evidence needed for unresolved incidents must not be deleted prematurely.

Temporary outputs should not remain indefinitely by default.

<a id="section-4-153"></a>
## 4.153 Object Deletion

Deletion shall distinguish:

- soft deletion,

- archival,

- revocation,

- logical removal,

- physical deletion,

- provider deletion,

- and cryptographic erasure where applicable.

Deletion of a canonical object must preserve required audit evidence without retaining prohibited content beyond policy.

Deletion propagation across providers and derivatives must be deliberate.

<a id="section-4-154"></a>
## 4.154 Object Export

Users or authorised systems may require export of:

- Assets,

- provenance,

- execution evidence,

- costs,

- policies,

- provider relationships,

- or memory candidates.

Export shall preserve:

- scope,

- classification,

- rights,

- integrity,

- and relationship references.

Export does not remove the original object unless deletion is separately authorised.

<a id="section-4-155"></a>
## 4.155 Object Redaction

Redaction creates a reduced representation that removes protected content while preserving necessary evidence.

Redaction should record:

- source object,

- redaction method,

- actor,

- reason,

- removed categories,

- and resulting classification.

Redaction must not silently modify the original immutable evidence.

<a id="section-4-156"></a>
## 4.156 Object Supersession

Supersession means a newer object or version replaces an older one for active use.

The superseded object remains part of history.

Supersession should record:

- superseding object,

- superseded object,

- reason,

- effective time,

- and migration impact.

Examples include:

- new Policy Version,

- new Prompt Version,

- new Model Version,

- or new Canonical Asset Version.

<a id="section-4-157"></a>
## 4.157 Object Contradiction

A Contradiction Relationship records that two claims, learnings, evaluations or memories conflict.

Contradiction does not require immediate deletion.

The system should preserve:

- both objects,

- conflict reason,

- evidence,

- scope,

- and resolution status.

Contradiction handling is especially important for Derived Learning and Memory Candidates.

<a id="section-4-158"></a>
## 4.158 Object Confidence

Confidence may be attached to:

- classification,

- derived learning,

- evaluation,

- source verification,

- rights interpretation,

- or health inference.

Confidence shall not replace evidence.

A high numerical confidence without transparent basis is insufficient.

Confidence scale and meaning must be versioned.

<a id="section-4-159"></a>
## 4.159 Canonical Object Minimalism

The canonical model should be expressive without becoming unnecessarily fragmented.

A new object type should be introduced when it has distinct:

- identity,

- lifecycle,

- ownership,

- authority,

- or evidence requirements.

A simple attribute may be sufficient when those distinctions do not exist.

The purpose is clarity, not maximum object count.

<a id="section-4-160"></a>
## 4.160 Canonical Object Extensibility

Canonical objects may support extension fields.

Extensions shall be:

- namespaced,

- versioned,

- provider- or project-specific,

- and prevented from redefining canonical fields.

Provider-specific extensions may preserve unique features.

They must not become hidden core semantics.

<a id="section-4-161"></a>
## 4.161 Provider Object Translation

Adapters shall translate provider objects into canonical objects.

Examples include:

- provider generation request into Execution Attempt,

- provider job into Provider Job,

- provider asset into Output or Asset Reference,

- provider credit usage into Usage Record,

- provider error into canonical Error,

- and provider callback into Callback.

Translation shall preserve provider identifiers for reconciliation.

<a id="section-4-162"></a>
## 4.162 Canonical Error

A Canonical Error represents a normalised failure or rejection.

It may include:

- errorId,

- category,

- source,

- provider code,

- message,

- retryability,

- permanence,

- user action required,

- scope,

- and evidence reference.

Canonical categories may include:

- validation,

- authentication,

- authorisation,

- policy,

- budget,

- unsupported capability,

- rate limit,

- provider outage,

- timeout,

- unknown outcome,

- rights,

- safety,

- data classification,

- quality,

- and internal defect.

<a id="section-4-163"></a>
## 4.163 Error Causality

Errors may have causal relationships.

For example:

- ProviderAuthenticationExpired may cause ExecutionAttemptFailed,

- which may cause ExecutionPaused,

- which may cause WorkflowRunAwaitingOperator.

The system should preserve root cause where known.

A generic top-level failure must not erase lower-level evidence.

<a id="section-4-164"></a>
## 4.164 Compensation

A Compensation is a corrective action intended to reverse or mitigate a completed side effect.

Examples include:

- deleting an unintended provider asset,

- releasing a budget reservation,

- removing a scheduled publication,

- or restoring a prior configuration.

Compensation shall include:

- triggering failure,

- target,

- authority,

- execution,

- result,

- and residual risk.

Compensation is not always equivalent to rollback.

<a id="section-4-165"></a>
## 4.165 Reconciliation

Reconciliation is the process of resolving discrepancies between Omnira and an external provider or subsystem.

It may compare:

- job state,

- cost,

- output existence,

- publication state,

- credits,

- or asset records.

A Reconciliation Record should include:

- source states,

- discrepancy,

- resolution,

- evidence,

- and remaining uncertainty.

Reconciliation may convert unknown outcome into completed or failed without rewriting prior evidence.

<a id="section-4-166"></a>
## 4.166 Simulation Object

A Simulation represents a non-production evaluation of:

- routing,

- cost,

- policy,

- provider choice,

- or execution plan.

A Simulation shall be clearly marked.

It may produce:

- simulated Selection Decision,

- simulated Cost Estimate,

- simulated Execution Plan,

- or test Output.

Simulation objects must not be included in production performance evidence without explicit classification.

<a id="section-4-167"></a>
## 4.167 Test Execution

A Test Execution is an Execution performed for conformance, benchmark or integration testing.

It shall include:

- test purpose,

- environment,

- synthetic or approved data,

- expected outcome,

- and test result.

Test Executions shall not use production side effects unless explicitly approved.

<a id="section-4-168"></a>
## 4.168 Experimental Object

An Experimental object or resource has not yet completed production admission.

Experimental status may apply to:

- Provider Account,

- Model Version,

- Adapter,

- Capability Mapping,

- Tool,

- or Workflow.

Experimental resources may have:

- reduced data eligibility,

- low spending limits,

- mandatory human review,

- and sandbox-only use.

<a id="section-4-169"></a>
## 4.169 Production Admission Record

A Production Admission Record documents the decision to permit a resource in production.

It should include:

- target resource,

- tested version,

- conformance evidence,

- security review,

- policy review,

- approved scope,

- restrictions,

- approver,

- and effective time.

Production admission is not permanent.

Material change may require re-certification.

<a id="section-4-170"></a>
## 4.170 Canonical Object Access Pattern

Fabric components should access objects through authorised services or repositories rather than uncontrolled direct storage access.

Access should enforce:

- tenant,

- project,

- environment,

- authority,

- classification,

- and object lifecycle.

A direct database query that bypasses these controls is not canonical merely because it reads canonical tables.

<a id="section-4-171"></a>
## 4.171 Object Query Scope

Every object query shall declare or resolve scope.

Queries should distinguish:

- one object by authorised ID,

- project-scoped collection,

- tenant-scoped collection,

- platform-global operational view,

- and cross-project governed query.

Missing scope shall not return all objects.

<a id="section-4-172"></a>
## 4.172 Object Mutation Contract

Mutations shall include:

- acting Principal,

- target object,

- expected version,

- requested transition,

- authority,

- reason,

- and correlation.

Optimistic or equivalent concurrency control should prevent silent overwrite.

Mutation failure must preserve current state.

<a id="section-4-173"></a>
## 4.173 Object Creation Contract

Creation shall validate:

- identity,

- ownership,

- scope,

- schema,

- classification,

- authority,

- and uniqueness.

Objects created by asynchronous callbacks must still resolve legitimate ownership and scope.

External input must not create unrestricted global objects.

<a id="section-4-174"></a>
## 4.174 Object Read Contract

Read access shall be evaluated separately from mutation access.

A Principal may be allowed to:

- see summary metadata,

- but not sensitive payload;

- inspect cost,

- but not prompts;

- review output,

- but not credentials;

- or view project status,

- but not another project’s assets.

Canonical services should support field-level or representation-level restriction where necessary.

<a id="section-4-175"></a>
## 4.175 Object Projection

A Projection is a derived read model created for a specific use.

Examples include:

- project execution dashboard,

- provider health summary,

- monthly cost report,

- agent activity view,

- or Intelligence Graph projection.

Projections shall identify:

- source objects,

- freshness,

- scope,

- and derivation.

A stale Projection must not be represented as current truth.

<a id="section-4-176"></a>
## 4.176 Object Freshness

Objects and views that represent changing external state shall include freshness information.

Freshness may include:

- observedAt,

- sourceUpdatedAt,

- retrievedAt,

- expected refresh,

- and stale threshold.

Unknown freshness shall be represented honestly.

<a id="section-4-177"></a>
## 4.177 Canonical Object Search

Search across Fabric objects must preserve scope and classification.

Search indexes shall not become cross-tenant leakage paths.

Index documents should include:

- tenant,

- project,

- classification,

- object type,

- and lifecycle.

Search results must re-check authorisation before content is returned.

<a id="section-4-178"></a>
## 4.178 Object Graph Projection

Canonical objects may be projected into the Intelligence Graph.

Graph projection shall preserve:

- object identity,

- relationship type,

- scope,

- provenance,

- and freshness.

The Graph may provide navigation and explanation.

It shall not become the only authoritative storage for objects whose lifecycle belongs elsewhere.

<a id="section-4-179"></a>
## 4.179 Canonical Object Event

Material object changes should emit or record canonical events.

Examples include:

- CapabilityRequestSubmitted,

- ApprovalGranted,

- ExecutionStarted,

- ProviderJobAccepted,

- OutputReceived,

- EvaluationFailed,

- AssetCanonicalised,

- LearningCandidateCreated,

- and IncidentDetected.

Events shall include:

- eventId,

- object reference,

- event type,

- occurredAt,

- recordedAt,

- actor,

- correlation,

- causation,

- scope,

- and payload version.

<a id="section-4-180"></a>
## 4.180 Event Idempotency

Event consumers shall handle duplicate delivery where the architecture uses at-least-once transport.

Consumers should use:

- event IDs,

- object versions,

- deduplication state,

- or idempotent mutation.

Duplicate event receipt shall not duplicate:

- cost,

- assets,

- memory candidates,

- or publication actions.

<a id="section-4-181"></a>
## 4.181 Event Ordering

The Fabric shall not assume global event ordering.

Ordering may be preserved within:

- one object,

- one execution,

- one provider job,

- or one partition.

Consumers shall use:

- object revision,

- occurred time,

- causation,

- and state-transition validation.

Late events must not silently revert newer confirmed state.

<a id="section-4-182"></a>
## 4.182 Object State and Event Evidence

Current object state and historical events shall remain consistent.

If they differ, the system must:

- identify projection delay,

- repair state,

- or open an Incident.

Events should not be deleted merely to make current state appear correct.

<a id="section-4-183"></a>
## 4.183 Canonical Object Security Label

Objects may include a security label beyond general Data Classification.

A security label may express:

- personal data,

- credential-adjacent,

- legal hold,

- child-related,

- financial,

- health,

- proprietary,

- or export-controlled.

Labels may trigger additional policy.

Security labels shall remain scoped and versioned.

<a id="section-4-184"></a>
## 4.184 Child-Facing Content Label

Outputs and Assets intended for children may receive a child-facing content label.

This label may require:

- stronger human review,

- age appropriateness,

- visual safety,

- voice suitability,

- advertising restrictions,

- and publication rules.

The label is especially relevant to Familje-Stunden.

It shall not be inferred only from project name when content purpose differs.

<a id="section-4-185"></a>
## 4.185 Commercial Asset Label

Commercially used Assets may receive a commercial asset label.

This may require:

- confirmed rights,

- stronger provenance,

- approved quality,

- canonical version,

- publication history,

- and retention.

Disposable experiments should not automatically receive commercial status.

<a id="section-4-186"></a>
## 4.186 Canonical Object Schema Governance

Schema changes shall follow governed evolution.

A schema change should include:

- motivation,

- compatibility analysis,

- migration,

- affected services,

- version,

- tests,

- and rollback.

Breaking changes require explicit version transition.

Providers must not force uncontrolled breaking changes into canonical schemas.

<a id="section-4-187"></a>
## 4.187 Canonical Naming Rules

Canonical object and field names should be:

- clear,

- stable,

- provider-independent,

- and consistent across services.

Provider terminology may be preserved in extension fields.

Ambiguous names such as:

- item,

- data,

- job,

- result,

- or status

should be avoided without context.

Names should communicate lifecycle and ownership.

<a id="section-4-188"></a>
## 4.188 Required and Optional Fields

Schema definitions shall clearly distinguish:

- required,

- conditionally required,

- optional,

- derived,

- and prohibited fields.

Conditionally required fields should state the condition.

For example:

- projectId is required for project-scoped execution,

- globalScopeReason is required for platform-global execution,

- approvalId is required when policy requires approval,

- and providerJobId is optional for synchronous providers.

<a id="section-4-189"></a>
## 4.189 Null, Unknown and Not Applicable

The Fabric shall distinguish:

- null or absent,

- unknown,

- not applicable,

- redacted,

- and unavailable.

These meanings must not be collapsed.

For example:

- cost unknown,

- cost not applicable for a simulation,

- cost redacted from a user view,

- and cost unavailable from the provider

represent different states.

9. Every Execution Attempt SHALL remain historically visible after retry.

10. Every Output SHALL reference the Execution that produced it.

11. Every durable Asset SHALL preserve provenance.

12. Every Approval SHALL identify approver, scope and decision.

13. Every Policy Decision SHALL identify evaluated policy versions.

14. Every delegated action SHALL preserve its authority chain.

15. Every external side effect SHALL preserve completion evidence.

16. Every Learning Candidate SHALL reference supporting evidence.

17. Every Memory Candidate SHALL remain separate from admitted memory.

18. Every cross-project relationship SHALL be explicit.

19. Every canonical state transition SHALL be valid and attributable.

20. Missing critical scope SHALL fail closed.

<a id="section-4-199"></a>
## 4.199 Stage 1 Object Acceptance Tests

Representative acceptance tests should include:

1. Provider and Provider Account remain distinct.

2. A Capability Request may exist without an Execution when rejected.

3. One Execution may contain multiple Attempts.

4. A failed Attempt does not erase a later successful Attempt.

5. An Output cannot be accepted without required Evaluation.

6. An Output does not become a canonical Asset automatically.

7. An Approval cannot be reused outside its scope.

8. A Budget Reservation cannot be charged to another Project.

9. A Local Only Data Item cannot be attached to an external Provider Execution.

10. A provider callback cannot mutate an unrelated Execution.

11. A duplicate callback does not duplicate an Output.

12. Unknown provider outcome remains represented as unknown until reconciled.

13. A Model Version may change without changing the Agent Principal.

14. A Learning Candidate does not enter permanent memory automatically.

15. Historical Executions remain interpretable after Model deprecation.

16. A missing Project does not default to global scope.

17. Provider terms and input rights remain separately represented.

18. Estimated and confirmed cost remain distinguishable.

19. Publication Package does not imply Publication Record.

20. Canonical Asset supersession preserves the previous version.

## 4.200 Conformance Requirements

An implementation conforms to this chapter only when:

- canonical object identities are stable,

- provider terminology is translated rather than leaked into core contracts,

- scope is explicit,

- ownership is explicit,

- authority is explicit,

- lifecycles are defined,

- state transitions are validated,

- evidence remains immutable where required,

- object relationships are reconstructable,

- and critical conceptual distinctions remain enforceable.

A database schema alone does not prove conformance.

Conformance requires runtime behaviour, tests and evidence.

<a id="section-4-201"></a>
## 4.201 Canonical Object Contract

The following requirements define the canonical object contract:

1. Canonical meaning SHALL remain independent of storage form.

2. Persistent objects SHALL have stable identity.

3. Canonical and provider identifiers SHALL remain distinct.

4. Objects SHALL carry explicit scope where applicable.

5. Schema and object versions SHALL remain distinguishable.

6. Immutable evidence SHALL NOT be silently rewritten.

7. Lifecycle transitions SHALL be explicit and attributable.

8. Principals SHALL remain separate from authority.

9. Tenants and Projects SHALL remain separate scopes.

10. Delegation SHALL preserve its authority chain.

11. Approval SHALL remain separate from general authority.

12. Intent SHALL remain separate from implementation.

13. Capabilities SHALL remain provider-independent.

14. Capability Requests SHALL remain separate from Executions.

15. Providers and Provider Accounts SHALL remain separate.

16. Models, Model Versions and Deployments SHALL remain separate.

17. Agents SHALL remain separate from Models.

18. Adapters SHALL preserve canonical meaning.

19. Execution Plans SHALL remain separate from active Executions.

20. Executions SHALL preserve all Attempts.

21. Provider Jobs SHALL remain external execution evidence.

22. Outputs SHALL remain separate from durable Assets.

23. Evaluations SHALL remain separate from Acceptance and Approval.

24. Estimated cost SHALL remain separate from confirmed cost.

25. Meaningful Outputs and Assets SHALL preserve provenance.

26. Side effects SHALL produce appropriate receipts.

27. Incidents SHALL remain separate from ordinary failures.

28. Learning Candidates SHALL remain separate from permanent memory.

29. Publication preparation SHALL remain separate from publication.

30. Unknown SHALL remain a valid explicit state.

31. Cross-project relationships SHALL require explicit authority.

32. Historical objects SHALL remain interpretable after deprecation.

33. Extensions SHALL NOT redefine canonical fields.

34. Canonical status vocabularies SHALL remain object-specific.

35. Object access SHALL enforce scope and authority.

<a id="section-4-202"></a>
## 4.202 Closing Statement

The Omnira Intelligence Fabric requires more than connections to models and providers.

It requires a stable internal language through which every request, resource, execution, output, cost, decision and learning can be understood.

The canonical object model provides that language.

Intent explains what should be achieved.

Capability defines what kind of intelligence is required.

Authority defines what may occur.

Policy defines the rules.

Scope defines where the work belongs.

Providers and models supply replaceable resources.

Plans define how the work may proceed.

Executions record what Omnira attempted.

Attempts preserve every technical submission.

Outputs preserve what was produced.

Evaluations determine quality.

Approvals preserve human authority.

Assets preserve durable value.

Provenance preserves origin.

Receipts preserve operational truth.

Evidence supports decisions.

Learning converts experience into future advantage.

Memory governance determines what should persist.

These objects form the semantic foundation of the Intelligence Fabric.

Without stable objects, routing becomes guesswork.

Without explicit relationships, provenance disappears.

Without lifecycle, state becomes ambiguous.

Without scope, shared infrastructure becomes a leakage risk.

Without authority, technical capability becomes uncontrolled power.

The canonical model shall therefore remain provider-independent, versioned, scoped, observable and governed.

Every future implementation of the Fabric shall preserve these meanings even as the underlying technology changes.
