# Chapter 5 — Capability Requests and Intent Envelopes

<a id="section-5-1"></a>
## 5.1 Chapter Status

This chapter defines the canonical architecture for expressing intent, translating intent into capability requirements and submitting governed work to the Omnira Intelligence Fabric.

It establishes:

- how humans and authorised systems express desired outcomes,

- how broad objectives become executable capability requests,

- how project context and constraints are attached,

- how ambiguity and missing information are handled,

- how quality, budget, time, rights, data and authority are declared,

- how requests are validated before planning,

- how request changes are versioned,

- how recurring and multi-step requests are represented,

- and how the Fabric preserves the difference between desired outcome and technical implementation.

This chapter is normative after formal approval.

It does not require every request to be entered through a single user interface.

Intent may originate through:

- conversation,

- project workflows,

- forms,

- schedules,

- APIs,

- approved automations,

- Managers,

- agents,

- or internal platform events.

Regardless of origin, governed intelligence execution shall converge on the canonical request contracts defined in this chapter.

A natural-language instruction alone is not sufficient authority for consequential execution unless it has been resolved into a valid scoped request and the required approval or delegated authority exists.

<a id="section-5-2"></a>
## 5.2 Purpose of Capability Requests

The Intelligence Fabric shall not accept unstructured intent as unrestricted execution authority.

Users should be able to communicate naturally.

The system must then transform that communication into a request that can be:

- understood,

- validated,

- authorised,

- costed,

- planned,

- routed,

- executed,

- evaluated,

- and audited.

The Capability Request is the canonical boundary between:

- what a caller wants,

- and what the Fabric is allowed to execute.

It shall capture the outcome without prematurely coupling the request to one provider or model.

It shall contain enough structure to prevent important requirements from being lost during translation.

<a id="section-5-3"></a>
## 5.3 Intent and Execution Are Different Objects

Intent describes the desired purpose or outcome.

Execution describes the technical work performed to fulfil that intent.

The Fabric shall not collapse these concepts.

For example, the intent may be:

Create a monthly Nova and Pling episode connected to the approved Familje-Stunden theme.

The execution may involve:

- script analysis,

- scene segmentation,

- asset retrieval,

- image editing,

- image-to-video generation,

- narration,

- sound effects,

- quality evaluation,

- file conversion,

- and human review.

The user owns the intent.

The Fabric constructs and governs the execution path.

A change in execution method does not necessarily change the intent.

A change in business outcome may require a new or revised intent.

<a id="section-5-4"></a>
## 5.4 Intent Object

An Intent object represents the purpose that motivates one or more Capability Requests.

An Intent should include:

- intentId,

- tenantId,

- projectId where applicable,

- initiating Principal,

- beneficiary,

- objective,

- business or user context,

- desired outcome,

- success definition,

- importance,

- timing expectations,

- and lifecycle status.

Intent may remain broader than one technical request.

A long-term intent may generate several requests over time.

For example:

Increase discovery and engagement for Familje-Stunden through recurring Nova and Pling video content.

This Intent may later produce:

- one monthly episode request,

- one trailer request,

- several social-media derivative requests,

- one performance-analysis request,

- and one routing-learning request.

The broader intent remains stable while individual requests change.

<a id="section-5-5"></a>
## 5.5 Intent Envelope

The Intent Envelope is the structured representation through which broad intent is prepared for translation into governed work.

The canonical Intent Envelope should support:

- intentId,

- tenantId,

- projectId,

- environmentId,

- initiator,

- caller,

- beneficiary,

- objective,

- background context,

- desired outputs,

- success conditions,

- priority,

- time horizon,

- budget posture,

- data classification,

- rights requirements,

- routing preference,

- approval posture,

- and unresolved questions.

The Intent Envelope may begin partially complete.

It must not be treated as execution-ready until required fields have been resolved.

<a id="section-5-6"></a>
## 5.6 Capability Request

A Capability Request is the canonical executable request submitted to the Intelligence Fabric.

It shall include or reference:

- requestId,

- intentId,

- request version,

- caller,

- initiator,

- tenant,

- project,

- environment,

- purpose,

- one or more Capability Requirements,

- inputs,

- output contract,

- quality contract,

- authority envelope,

- policy context,

- budget envelope,

- routing profile,

- data classification,

- rights profile,

- deadline,

- review requirements,

- side-effect restrictions,

- lifecycle state,

- and provenance.

The Capability Request defines what the Fabric may attempt.

It does not guarantee that an eligible execution path exists.

<a id="section-5-7"></a>
## 5.7 Request Origin

A Capability Request may originate from:

- direct human instruction,

- Atlas,

- Executive Intelligence,

- a Manager,

- a specialist agent,

- a workflow,

- a recurring schedule,

- a condition watch,

- a project event,

- an API client,

- or an approved external integration.

The request shall preserve its origin.

The origin shall not determine authority by itself.

A request created by Atlas must still be authorised.

A request created by a schedule must still satisfy current policy.

A request created by an external integration must still resolve tenant, project and caller identity.

<a id="section-5-8"></a>
## 5.8 Initiator, Caller and Executor

The Fabric shall distinguish:

- Initiator,

- Caller,

- Planner,

- Executor,

- Approver,

- and Beneficiary.

The Initiator is the Principal or event that began the broader objective.

The Caller submits the Capability Request to the Fabric.

The Planner translates the request into an Execution Plan.

The Executor performs one or more Execution Steps.

The Approver grants required authority.

The Beneficiary is the person, project or system intended to receive value from the result.

These roles may be held by the same Principal.

They must remain distinguishable where they differ.

<a id="section-5-9"></a>
## 5.9 Human Intent Capture

Human intent may be expressed through natural language.

The user should not be required to understand Fabric schemas.

The system may ask questions, infer non-consequential defaults and present structured summaries.

However, the final request must preserve the difference between:

- explicitly stated information,

- inferred information,

- defaulted information,

- retrieved project context,

- and unresolved assumptions.

Inferred information shall not silently become user-approved truth when it materially affects:

- cost,

- privacy,

- rights,

- quality,

- publication,

- or authority.

<a id="section-5-10"></a>
## 5.10 Intent Interpretation

Intent Interpretation is the process through which natural or broad instructions are translated into structured meaning.

Intent Interpretation may identify:

- objective,

- affected project,

- desired output,

- required capabilities,

- audience,

- constraints,

- timing,

- budget sensitivity,

- quality expectations,

- and risk.

The interpreting system shall preserve uncertainty.

It should distinguish:

- explicit requirement,

- likely preference,

- weak inference,

- and unknown.

The Fabric shall not convert an uncertain inference into a mandatory execution constraint without evidence or confirmation.

<a id="section-5-11"></a>
## 5.11 Clarification Threshold

The system shall not ask unnecessary questions.

It should ask for clarification when missing information could materially change:

- authority,

- privacy,

- cost,

- rights,

- external side effects,

- quality acceptance,

- project scope,

- or irreversible outcome.

It may proceed with safe defaults when the missing information is low-risk and reversible.

For example:

A draft summary may use a default document format.

A public video publication may not assume an account or publication date.

The clarification threshold shall reflect consequence rather than conversational perfection.

<a id="section-5-12"></a>
## 5.12 Minimum Necessary Questions

When clarification is required, the system should request the minimum information needed to make the next safe decision.

It should avoid large interview blocks when:

- project context already answers the question,

- a safe default exists,

- the decision can be deferred,

- or the missing detail does not affect the current stage.

For a Nova and Pling episode, the initial questions may only need to resolve:

- approved story,

- target duration,

- output channels,

- maximum budget,

- and publication authority.

Detailed provider selection should remain a Fabric responsibility.

<a id="section-5-13"></a>
## 5.13 Explicit and Inferred Requirements

Every meaningful request attribute should identify its origin where consequence requires it.

Possible origins include:

- user explicit,

- user preference,

- project policy,

- tenant policy,

- workflow definition,

- Fabric default,

- system inference,

- provider limitation,

- or legal requirement.

This origin supports:

- explanation,

- conflict resolution,

- approval,

- and revision.

A user-explicit requirement normally takes precedence over a soft system preference.

It does not override mandatory security or legal policy.

<a id="section-5-14"></a>
## 5.14 Requirement Confidence

Inferred requirements may include confidence.

Confidence should not be treated as authority.

A high-confidence inference may reduce clarification for reversible work.

It shall not authorise:

- spending,

- publication,

- cross-project access,

- voice cloning,

- or external use of confidential data.

Confidence informs interaction.

Authority governs execution.

<a id="section-5-15"></a>
## 5.15 Objective

The Objective describes the result the caller wants to achieve.

A good Objective should state:

- desired outcome,

- target context,

- intended audience or beneficiary,

- and relevant business or operational purpose.

Examples include:

Create the approved September Nova and Pling episode for Familje-Stunden.

Produce a two-minute verified AI-news segment for The Prompt.

Create a short GainPilot reel explaining progressive overload.

Audit the Omnira project media architecture for project-isolation defects.

The Objective should not be written only as a provider command such as:

Use OpenArt.

Provider selection may be a constraint or preference, but it is not the objective.

<a id="section-5-16"></a>
## 5.16 Purpose

Purpose explains why the request exists.

Purpose may influence:

- quality,

- risk,

- retention,

- evaluation,

- and provider eligibility.

For example, the same image-generation capability may be used for:

- disposable brainstorming,

- internal concept review,

- paid advertising,

- child-facing content,

- or canonical character reference.

The capability is similar.

The governance requirements differ because the purpose differs.

<a id="section-5-17"></a>
## 5.17 Beneficiary

The Beneficiary identifies who or what receives the intended value.

The Beneficiary may be:

- the user,

- a project,

- a customer,

- an audience,

- an internal team,

- an agent,

- or the Omnira platform.

Beneficiary identification helps determine:

- project ownership,

- rights,

- output destination,

- quality expectations,

- and cost attribution.

The Beneficiary is not automatically the Caller.

<a id="section-5-18"></a>
## 5.18 Success Definition

The request should define what successful fulfilment means.

Success may include:

- required output produced,

- quality threshold met,

- human approval received,

- cost within budget,

- deadline met,

- and side effects verified.

Success must be measurable or reviewable.

A vague success definition such as “make it good” may be translated into project-specific quality dimensions.

The system should preserve the user’s qualitative intent without pretending that all value can be reduced to one numerical score.

<a id="section-5-19"></a>
## 5.19 Completion Contract

The Completion Contract defines what evidence is required before the request may be considered complete.

It may require:

- output received,

- schema valid,

- quality evaluation passed,

- human review completed,

- asset stored,

- publication package prepared,

- or external action verified.

Completion differs from provider success.

A provider may complete a generation while the request remains incomplete because evaluation failed.

<a id="section-5-20"></a>
## 5.20 Capability Requirement

A Capability Requirement defines one type of intelligence or tool operation needed to fulfil the request.

It should include:

- capabilityId,

- capability version,

- mandatory or optional state,

- input requirements,

- output expectations,

- quality constraints,

- placement constraints,

- and dependency relationships.

A simple request may contain one Capability Requirement.

A complex request may contain many.

<a id="section-5-21"></a>
## 5.21 Mandatory Capability

A Mandatory Capability is required for successful completion.

If no eligible resource can fulfil it, the request must:

- fail,

- pause,

- degrade through approved revision,

- or escalate.

The Fabric shall not silently remove a mandatory capability.

For example, Swedish narration is mandatory when the approved output contract requires a Swedish audio track.

<a id="section-5-22"></a>
## 5.22 Optional Capability

An Optional Capability improves the result but is not required for minimum acceptance.

Optional capabilities may support:

- subtitles,

- additional variants,

- premium visual effects,

- extra research,

- or social-media derivatives.

Optional capabilities should have:

- priority,

- budget limit,

- and omission behaviour.

Their omission must not be represented as failure when the Completion Contract permits it.

<a id="section-5-23"></a>
## 5.23 Capability Dependency

Capability Requirements may depend on one another.

Examples include:

- animation depends on approved scene images,

- narration timing depends on final script,

- captions depend on narration or transcript,

- publication package depends on accepted assets.

Dependencies shall be explicit.

The planner shall not infer unsafe execution ordering from provider convenience.

<a id="section-5-24"></a>
## 5.24 Capability Alternatives

A request may permit alternative capabilities.

For example:

- image-to-video animation,

- motion-comic composition,

- or human-assisted editing

may all fulfil a broader visual storytelling requirement.

Alternative capabilities shall define:

- equivalence conditions,

- quality differences,

- cost differences,

- and approval requirements.

The Fabric may select among approved alternatives.

It shall not substitute a materially different outcome without disclosure.

<a id="section-5-25"></a>
## 5.25 Capability Composition

Complex intent may require capability composition.

Composition may include:

- sequential execution,

- parallel execution,

- conditional execution,

- iterative refinement,

- and human checkpoints.

The Capability Request may declare the high-level requirements.

The Execution Planner constructs the detailed graph.

The request should not be forced to contain provider-specific orchestration logic.

<a id="section-5-26"></a>
## 5.26 Input Contract

The Input Contract defines what information or assets the request may use.

It may include:

- Data Item references,

- Asset references,

- Memory references,

- source documents,

- structured parameters,

- user instructions,

- and external evidence.

Inputs shall be identified rather than copied unnecessarily.

The Input Contract should preserve:

- owner,

- project,

- classification,

- rights,

- version,

- and required transformation.

<a id="section-5-27"></a>
## 5.27 Required Input

A Required Input is necessary for valid execution.

Examples include:

- approved story manuscript,

- canonical character references,

- source document,

- code repository,

- target language,

- or publication platform.

If a Required Input is unavailable, stale or unapproved, the request must not proceed as if it were complete.

<a id="section-5-28"></a>
## 5.28 Optional Input

An Optional Input may improve execution.

Examples include:

- previous audience analytics,

- style examples,

- preferred music reference,

- or historical provider evidence.

Optional Inputs should be used only when:

- scope permits,

- classification permits,

- rights permit,

- and retrieval is relevant.

The Fabric shall not indiscriminately attach all available project data.

<a id="section-5-29"></a>
## 5.29 Input Version

Requests shall identify relevant input versions.

For canonical assets, the request should reference a specific Asset Version.

A request that uses “the Nova reference image” without version may become ambiguous after the asset changes.

Where the latest approved version is intended, that rule should be explicit.

Execution evidence shall preserve the actual version used.

<a id="section-5-30"></a>
## 5.30 Input Freshness

Time-sensitive Inputs may require freshness constraints.

Examples include:

- current news sources,

- pricing,

- provider terms,

- project status,

- availability,

- and analytics.

The request may define:

- maximum age,

- current-as-of time,

- or verification requirement.

Stale input must not be represented as current.

<a id="section-5-31"></a>
## 5.31 Input Classification

Each Input shall carry or inherit Data Classification.

The request-level classification should normally reflect the most restrictive relevant input unless an approved transformation changes it.

Mixed-classification inputs may require:

- segregation,

- local preprocessing,

- redaction,

- or separate execution paths.

The Fabric must not send a confidential Input merely because the request also includes public data.

<a id="section-5-32"></a>
## 5.32 Input Rights

Inputs shall preserve applicable Rights Profiles.

The request must identify whether the input may be:

- analysed,

- transformed,

- used for model generation,

- sent to external providers,

- used commercially,

- published,

- or retained.

Possession of a file does not prove all rights.

<a id="section-5-33"></a>
## 5.33 Input Consent

Voice, likeness and personal-data Inputs may require a Consent Record.

The request shall reference valid consent when required.

Consent validity must include:

- permitted use,

- project,

- duration,

- revocation,

- and commercial scope.

A provider’s technical support for cloning does not create consent.

<a id="section-5-34"></a>
## 5.34 Memory Inputs

The Capability Request may reference Governed Memory.

Memory retrieval shall be:

- scoped,

- purposeful,

- minimal,

- and evidenced where meaningful.

The request should identify the type of memory required rather than attaching the entire memory store.

Examples include:

- project brand rules,

- user preference,

- prior production learning,

- or approved agent role context.

Unreviewed execution logs shall not be treated as memory inputs.

<a id="section-5-35"></a>
## 5.35 Context Package

A Context Package is a scoped collection of information assembled for one request or execution step.

It may contain:

- project context,

- user instruction,

- relevant memory,

- selected assets,

- policy summaries,

- and task-specific evidence.

Context Packages should be:

- minimal,

- versioned,

- classified,

- and attributable.

The same Context Package should not be reused across unrelated projects without explicit authority.

<a id="section-5-36"></a>
## 5.36 Context Budget

Some models have limited context capacity.

The request or planner may define a Context Budget.

The Context Budget may constrain:

- token count,

- media count,

- document size,

- retrieval volume,

- or provider limits.

Context selection should prioritise relevance and authority.

It should not silently omit mandatory information to fit a model.

<a id="section-5-37"></a>
## 5.37 Context Reduction

When context exceeds capacity, the Fabric may use:

- retrieval,

- summarisation,

- chunking,

- staged analysis,

- local preprocessing,

- or another eligible model.

Reduction must preserve critical meaning.

The system shall record material transformations.

A summary derived from confidential source material may remain confidential.

<a id="section-5-38"></a>
## 5.38 Output Contract

The Output Contract defines the expected result.

It may include:

- output type,

- format,

- schema,

- language,

- dimensions,

- duration,

- resolution,

- count,

- classification,

- rights,

- destination,

- quality requirements,

- and acceptance method.

The Output Contract shall be provider-independent.

The adapter translates it into provider-specific parameters.

<a id="section-5-39"></a>
## 5.39 Output Type

Output types may include:

- text,

- structured data,

- code,

- image,

- audio,

- video,

- document,

- embedding,

- ranking,

- plan,

- evaluation,

- or side-effect receipt.

A request may require multiple output types.

Each output should have its own acceptance requirements.

<a id="section-5-40"></a>
## 5.40 Output Count

The request may define:

- exact number,

- minimum number,

- maximum number,

- or bounded range of outputs.

For generative work, output count affects:

- cost,

- review burden,

- quality probability,

- and storage.

The Fabric shall not generate unlimited variants when only one is required.

<a id="section-5-41"></a>
## 5.41 Output Format

The Output Contract may define required formats such as:

- DOCX,

- PDF,

- Markdown,

- JSON,

- PNG,

- SVG,

- MP4,

- WAV,

- subtitle format,

- or provider-independent structured schema.

Format conversion may be a separate capability.

The Fabric must not claim native format support when it actually relies on post-processing.

<a id="section-5-42"></a>
## 5.42 Output Destination

The request may define where accepted output should be delivered.

Destinations may include:

- temporary result store,

- project asset library,

- document workspace,

- repository branch,

- review queue,

- publication package,

- or user download area.

Delivery to a destination may require separate authority.

Output storage is not the same as canonicalisation.

<a id="section-5-43"></a>
## 5.43 Output Classification

Outputs shall receive an explicit or derived classification.

Output classification may be influenced by:

- source classification,

- content,

- rights,

- audience,

- and publication status.

A public-facing output may still have restricted provenance or internal draft status before approval.

<a id="section-5-44"></a>
## 5.44 Output Rights

The Output Contract shall define required rights such as:

- commercial use,

- modification,

- distribution,

- sublicensing,

- or public publication.

The request may be rejected when no eligible resource can satisfy the rights requirement.

Rights uncertainty must not be hidden behind successful generation.

<a id="section-5-45"></a>
## 5.45 Derivative Outputs

A request may require derivatives such as:

- short clips,

- thumbnails,

- resized images,

- translated versions,

- captions,

- or platform variants.

Derivative relationships shall remain traceable.

Derivatives may use cheaper capabilities than the master output when the quality contract permits it.

<a id="section-5-46"></a>
## 5.46 Master Output

A Master Output is the primary accepted result from which derivatives may be created.

The request should identify when a master is required.

Master Outputs may require:

- highest quality,

- strongest provenance,

- archival format,

- and human approval.

A social-media preview should not silently become the canonical master.

<a id="section-5-47"></a>
## 5.47 Quality Contract

The Quality Contract defines the conditions under which an Output is acceptable.

It should include:

- quality dimensions,

- thresholds,

- evaluation methods,

- mandatory checks,

- human-review requirements,

- rejection rules,

- and retry limits.

The request may reference a reusable project Quality Contract.

The actual version used must be preserved.

<a id="section-5-48"></a>
## 5.48 Quality Floor

The Quality Floor is the minimum acceptable level for mandatory quality dimensions.

A routing profile may influence optimisation above the floor.

It must not lower the floor.

Economy routing may select the cheapest resource that satisfies the Quality Floor.

It may not redefine acceptable quality.

<a id="section-5-49"></a>
## 5.49 Quality Target

The Quality Target describes the desired level beyond the minimum floor.

Premium routing may attempt to maximise performance toward the target.

The target remains bounded by budget and eligibility.

Failure to reach the ideal target does not always mean failure if the minimum contract is satisfied.

<a id="section-5-50"></a>
## 5.50 Evaluation Method

The request may specify or inherit Evaluation Methods.

Methods may include:

- deterministic validation,

- automated model evaluation,

- cross-model review,

- human review,

- benchmark comparison,

- source verification,

- unit tests,

- visual inspection,

- or audience performance analysis.

High-risk work may require independent evaluation.

<a id="section-5-51"></a>
## 5.51 Human Review Requirement

The request shall identify when Human Review is mandatory.

Examples include:

- child-facing media,

- public publication,

- voice cloning,

- strategic business decision support,

- security-sensitive code,

- and rights-sensitive commercial output.

Human Review may occur:

- before execution,

- during execution,

- before acceptance,

- or before side effect.

The stage must be explicit.

<a id="section-5-52"></a>
## 5.52 Revision Policy

A Revision Policy defines what happens when output fails quality.

It may include:

- prompt refinement,

- same-provider retry,

- model change,

- provider fallback,

- human correction,

- or request escalation.

Revision must remain inside:

- budget,

- retry limits,

- authority,

- and data policy.

Unlimited refinement is prohibited.

<a id="section-5-53"></a>
## 5.53 Budget Envelope

The Budget Envelope defines the economic boundary of the request.

It may specify:

- maximum estimated cost,

- maximum confirmed cost,

- credit limit,

- currency,

- provider-account restrictions,

- budget source,

- retry allowance,

- reservation policy,

- and escalation threshold.

The Fabric shall not infer unlimited budget from the absence of a stated amount.

A safe default or approval requirement must apply.

<a id="section-5-54"></a>
## 5.54 Budget Posture

The request may express a Budget Posture such as:

- minimise cost,

- balanced cost and quality,

- quality-first within limit,

- private regardless of higher cost,

- use included credits first,

- or use specific account capacity.

Budget Posture informs routing.

It does not replace a hard budget where spending is consequential.

<a id="section-5-55"></a>
## 5.55 Estimated Cost Approval

Where policy requires it, the Fabric shall present an Estimated Cost before execution.

The estimate should include:

- proposed execution path,

- expected range,

- assumptions,

- included retries,

- and uncertainty.

Approval should apply to a defined limit or envelope.

A material estimate increase requires renewed approval.

<a id="section-5-56"></a>
## 5.56 Actual Cost Limit

The Budget Envelope may define a maximum actual cost.

The Fabric shall stop before knowingly exceeding it.

When provider billing is delayed or uncertain, the Fabric may use conservative reservations.

Unknown or delayed cost must not be treated as zero.

<a id="section-5-57"></a>
## 5.57 Cost Variance

The request may define permitted variance between estimate and actual cost.

Small variance may be allowed automatically.

Material variance may require:

- pause,

- revised estimate,

- or approval.

Variance policy should reflect provider billing behaviour and production consequence.

<a id="section-5-58"></a>
## 5.58 Free and Included Capacity

The request may permit use of:

- free-tier capacity,

- included subscription credits,

- local compute,

- promotional credits,

- or bundled Omnira capacity.

The Fabric shall still record usage.

Free capacity may have:

- lower limits,

- weaker rights,

- unavailable API access,

- or reduced quality.

Eligibility remains requirement-based.

<a id="section-5-59"></a>
## 5.59 Time Constraint

The request may include:

- deadline,

- earliest start,

- preferred completion,

- maximum latency,

- scheduling window,

- or recurrence.

Time constraints affect:

- provider eligibility,

- queue priority,

- cost,

- and fallback.

The Fabric shall distinguish:

- hard deadline,

- preferred deadline,

- and estimated duration.

<a id="section-5-60"></a>
## 5.60 Hard Deadline

A Hard Deadline is a time after which the result is no longer valid or useful.

The planner shall consider:

- provider queue time,

- review time,

- retries,

- and publication preparation.

A provider that might produce high quality after the deadline may be ineligible.

If the deadline becomes impossible, the Fabric shall report it rather than continue silently.

<a id="section-5-61"></a>
## 5.61 Preferred Deadline

A Preferred Deadline expresses desired timing without automatic failure after the time passes.

The Fabric may continue when:

- policy allows,

- value remains,

- and no consequential side effect has become invalid.

Late completion should be evidenced.

<a id="section-5-62"></a>
## 5.62 Time Horizon

The Intent Envelope may define a broader Time Horizon such as:

- immediate,

- today,

- this week,

- monthly,

- campaign period,

- or long-term recurring.

Time Horizon helps planning.

It shall not replace exact schedule data where exact execution is required.

<a id="section-5-63"></a>
## 5.63 Scheduled Request

A Scheduled Request is created or activated at a defined future time.

It shall preserve:

- schedule source,

- timezone,

- recurrence,

- validity,

- project,

- authority,

- and current policy evaluation.

A schedule created months earlier must not bypass current:

- credentials,

- budget,

- data policy,

- or provider eligibility.

<a id="section-5-64"></a>
## 5.64 Recurring Request

A Recurring Request defines repeated intent.

Examples include:

- monthly Nova and Pling episode production,

- weekly AI-news research,

- periodic provider benchmarking,

- or daily project summaries.

A recurring definition should produce separate request instances.

Each instance shall have:

- request ID,

- current inputs,

- current policy,

- current budget,

- and execution evidence.

The recurring definition is not one permanently open execution.

<a id="section-5-65"></a>
## 5.65 Condition-Triggered Request

A request may activate when a condition becomes true.

Examples include:

- provider availability restored,

- registration opened,

- budget replenished,

- new source published,

- or approval received.

The condition shall be:

- explicit,

- observable,

- scoped,

- and evaluated at a reasonable cadence.

Condition satisfaction does not bypass authority.

<a id="section-5-66"></a>
## 5.66 Event-Triggered Request

An Event-Triggered Request originates from an internal or external event.

Examples include:

- new asset approved,

- workflow step completed,

- provider callback received,

- project incident detected,

- or publication failed.

Events are untrusted until validated.

The request shall preserve:

- triggering event,

- event source,

- correlation,

- causation,

- and deduplication state.

<a id="section-5-67"></a>
## 5.67 Request Priority

The request may include priority.

Priority may be:

- low,

- normal,

- high,

- urgent,

- critical,

- or another governed vocabulary.

Priority influences:

- queue ordering,

- resource reservation,

- notification,

- and escalation.

Priority does not override:

- authority,

- privacy,

- rights,

- or budget.

Agents shall not self-declare every request urgent.

<a id="section-5-68"></a>
## 5.68 Business Importance

Business Importance describes strategic value.

It may differ from operational urgency.

A long-term architecture review may have high importance but no immediate deadline.

A failed publication may be urgent but limited in strategic impact.

The Fabric may use both dimensions for scheduling and review.

<a id="section-5-69"></a>
## 5.69 Routing Profile

The request shall specify or inherit a Routing Profile.

Canonical profiles include:

- Economy,

- Balanced,

- Premium,

- Private,

- and Pinned.

The routing profile shall be visible in the request.

Default selection should normally be explicit at project or tenant level.

<a id="section-5-70"></a>
## 5.70 Economy Request

An Economy request asks the Fabric to minimise total eligible cost.

Economy still requires:

- mandatory quality,

- rights,

- privacy,

- reliability,

- and deadline compliance.

Economy may use:

- local resources,

- included credits,

- cheaper providers,

- fewer variants,

- or staged preview-first production.

It may not silently reduce required quality.

<a id="section-5-71"></a>
## 5.71 Balanced Request

A Balanced request optimises across:

- quality,

- cost,

- latency,

- reliability,

- and historical evidence.

Balanced may be the default for ordinary production.

The exact weighting should be versioned and explainable.

<a id="section-5-72"></a>
## 5.72 Premium Request

A Premium request prioritises the highest justified quality within the approved budget.

Premium does not mean unlimited generation.

It may use:

- stronger models,

- additional evaluation,

- more variants,

- or premium retries.

The request must still define limits.

<a id="section-5-73"></a>
## 5.73 Private Request

A Private request prioritises approved private, local or self-hosted execution.

The request should define what private means in the relevant context.

Private may require:

- Local Only processing,

- specified regional provider,

- no provider retention,

- self-hosted model,

- or user-controlled node.

Encryption alone does not make an external provider local.

<a id="section-5-74"></a>
## 5.74 Pinned Request

A Pinned request requires a specific:

- provider,

- provider account,

- model,

- model version,

- deployment,

- or adapter.

Pinning may be justified by:

- unique capability,

- contract,

- reproducibility,

- existing assets,

- or user choice.

Pinned requests shall define fallback behaviour.

No silent substitution is permitted when the pinned condition is mandatory.

<a id="section-5-75"></a>
## 5.75 Provider Preference

A request may express a soft Provider Preference.

Preference differs from pinning.

The Fabric may choose another provider when:

- the preferred provider is unavailable,

- more expensive than permitted,

- ineligible,

- or materially weaker for the request.

Preference origin and override reason should be preserved.

<a id="section-5-76"></a>
## 5.76 Provider Allowlist

The request or policy may define permitted Providers or Provider Accounts.

The allowlist constrains candidate selection.

It does not prove that every listed provider is eligible.

Capability, data, rights, health and budget must still be evaluated.

<a id="section-5-77"></a>
## 5.77 Provider Denylist

The request or policy may prohibit:

- provider,

- account,

- model,

- region,

- or protocol.

A denied resource shall not be selected through fallback.

Denylist precedence should be explicit.

<a id="section-5-78"></a>
## 5.78 Data Classification Requirement

The request shall declare or resolve Data Classification before external processing.

Classification may be inherited from:

- Inputs,

- Project policy,

- User instruction,

- or automatic classification.

The most restrictive mandatory rule shall apply.

An unresolved classification shall block protected execution.

<a id="section-5-79"></a>
## 5.79 Processing Location Constraint

The request may restrict execution to:

- local device,

- private rig,

- tenant server,

- approved region,

- Omnira-managed infrastructure,

- or specific external provider class.

Location constraints shall be machine-evaluable where possible.

<a id="section-5-80"></a>
## 5.80 Retention Constraint

The request may define how providers and Omnira may retain:

- prompts,

- inputs,

- outputs,

- logs,

- and temporary files.

Provider retention capability must be verified where consequential.

A request requiring zero retention may be ineligible for providers that cannot support it.

<a id="section-5-81"></a>
## 5.81 Training-Use Constraint

The request may prohibit provider use of data for:

- training,

- service improvement,

- or human review.

Provider policy evidence shall determine eligibility.

The Fabric shall not rely on assumption.

<a id="section-5-82"></a>
## 5.82 Rights Requirement

The request shall define required rights for Inputs and Outputs.

Examples include:

- internal use,

- commercial use,

- public distribution,

- modification,

- sublicensing,

- or archival.

The request may include a Rights Profile or Rights Constraint.

Unknown rights may require review.

<a id="section-5-83"></a>
## 5.83 Attribution Requirement

Some inputs or providers may require attribution.

The request shall preserve attribution requirements into:

- Output Contract,

- Asset Provenance,

- and Publication Package.

Attribution must not be lost during derivative creation.

<a id="section-5-84"></a>
## 5.84 Consent Requirement

The request may require valid consent for:

- voice,

- likeness,

- personal data,

- biometric data,

- or child-related information.

Consent shall be verified before execution or before the relevant capability step.

Missing consent must fail closed.

<a id="section-5-85"></a>
## 5.85 Child-Facing Request

A Child-Facing Request shall receive stronger governance.

It may require:

- age appropriateness,

- visual safety,

- voice suitability,

- advertising restrictions,

- stronger human review,

- and protected publication workflow.

Familje-Stunden content may frequently receive this classification.

The classification should reflect actual purpose, not project name alone.

<a id="section-5-86"></a>
## 5.86 Commercial Request

A Commercial Request is intended to support:

- sales,

- subscriptions,

- advertising,

- paid products,

- or brand distribution.

Commercial requests may require:

- confirmed rights,

- stronger provenance,

- cost attribution,

- approved brand assets,

- and durable retention.

An internal prototype should not automatically be classified as commercial.

<a id="section-5-87"></a>
## 5.87 Research Request

A Research Request may require:

- current sources,

- source authority,

- citations,

- fact-opinion distinction,

- date range,

- domain restrictions,

- and uncertainty handling.

The request shall distinguish:

- exploratory research,

- decision support,

- public reporting,

- and high-stakes research.

Evaluation requirements increase with consequence.

<a id="section-5-88"></a>
## 5.88 Code Request

A Code Request may define:

- repository,

- branch,

- language,

- framework,

- architecture constraints,

- test requirements,

- allowed file scope,

- and side-effect permissions.

Generating a patch is separate from:

- writing files,

- committing,

- pushing,

- opening a pull request,

- merging,

- or deploying.

Each side effect requires appropriate authority.

<a id="section-5-89"></a>
## 5.89 Image Request

An Image Request may include:

- generation or editing capability,

- dimensions,

- style,

- reference images,

- text rendering,

- transparency,

- count,

- brand requirements,

- rights,

- and quality criteria.

Reference images shall preserve:

- version,

- project,

- rights,

- and classification.

<a id="section-5-90"></a>
## 5.90 Video Request

A Video Request may include:

- source image or text,

- duration,

- frame ratio,

- resolution,

- motion,

- character consistency,

- voice,

- sound,

- scene count,

- transition requirements,

- and output derivatives.

Video cost can vary significantly.

The request should define:

- preview strategy,

- retry limits,

- and master-output requirements.

<a id="section-5-91"></a>
## 5.91 Voice Request

A Voice Request may include:

- language,

- voice identity,

- tone,

- pacing,

- pronunciation,

- emotional style,

- format,

- and consent.

Synthetic voice selection shall remain distinct from voice cloning.

Voice cloning requires explicit rights and consent.

<a id="section-5-92"></a>
## 5.92 Music and Sound Request

A Music or Sound Request may include:

- duration,

- mood,

- tempo,

- instrumentation,

- loopability,

- commercial use,

- source restrictions,

- and publication context.

Music rights and provider terms require explicit tracking.

<a id="section-5-93"></a>
## 5.93 Multimodal Request

A Multimodal Request combines several modalities.

It should define:

- master objective,

- required modality outputs,

- shared context,

- asset dependencies,

- quality coordination,

- and final composition rules.

The Fabric may construct several linked Capability Requests or one composite request.

The relationship must remain traceable.

<a id="section-5-94"></a>
## 5.94 Composite Request

A Composite Request contains several Capability Requirements under one objective and authority envelope.

It may be appropriate when:

- steps share budget,

- outputs depend on one another,

- one approval covers the full production,

- and completion requires combined results.

The planner may decompose it into child requests.

The parent request retains overall completion state.

<a id="section-5-95"></a>
## 5.95 Parent Request

A Parent Request represents the broader governed objective.

It shall track:

- child requests,

- shared budget,

- shared authority,

- overall status,

- and completion rules.

Parent completion may depend on:

- all mandatory children,

- selected optional children,

- or an approved degraded result.

<a id="section-5-96"></a>
## 5.96 Child Request

A Child Request represents one bounded part of a Parent Request.

It shall inherit only the parent constraints that apply.

A child may have:

- narrower scope,

- smaller budget,

- separate quality contract,

- different provider eligibility,

- or separate review.

A child shall not expand the parent authority.

<a id="section-5-97"></a>
## 5.97 Request Dependency

Requests may depend on other requests.

Dependency types may include:

- output dependency,

- approval dependency,

- temporal dependency,

- budget dependency,

- or policy dependency.

Dependencies shall be explicit to avoid race conditions and incorrect execution order.

<a id="section-5-98"></a>
## 5.98 Production Request

A Production Request governs a multi-step creative or operational production.

It may reference a Production Envelope defining:

- objective,

- scope,

- approved assets,

- budget,

- allowed capabilities,

- retry limits,

- required outputs,

- and publication restrictions.

Production Requests are especially relevant to:

- Familje-Stunden episodes,

- The Prompt news segments,

- GainPilot campaigns,

- and Omnira product demonstrations.

<a id="section-5-99"></a>
## 5.99 Production Envelope Relationship

The Production Envelope authorises the broader production.

Individual Capability Requests consume bounded portions of that authority.

Each child request shall reference:

- productionId,

- applicable budget,

- allowed providers,

- remaining retry allowance,

- and publication restrictions.

The Fabric shall prevent cumulative work from exceeding the production envelope.

<a id="section-5-100"></a>
## 5.100 Cross-Project Request

A Cross-Project Request involves more than one Project.

It shall explicitly declare:

- participating Projects,

- purpose,

- permitted Inputs,

- permitted Outputs,

- shared budget or attribution,

- memory scope,

- and authority.

Common ownership is not sufficient.

Cross-project requests require explicit policy.

<a id="section-5-101"></a>
## 5.101 Platform-Global Request

A Platform-Global Request operates at Omnira platform scope.

Examples include:

- provider health monitoring,

- adapter conformance,

- model benchmarking,

- global cost analysis,

- or infrastructure maintenance.

It shall include:

- global scope reason,

- authorised Principal,

- permitted data types,

- and project-content restrictions.

Global scope shall not be inferred from missing project ID.

<a id="section-5-102"></a>
## 5.102 User-Private Request

A User-Private Request belongs to the user but not necessarily to a project.

It may involve:

- private planning,

- personal files,

- or user-owned local resources.

User-private scope shall remain separate from project and tenant-global scope.

The request must still define data placement and authority.

<a id="section-5-103"></a>
## 5.103 Human-Assisted Request

A Human-Assisted Request includes one or more required human actions.

It may involve:

- manual provider interface use,

- manual file upload,

- visual editing,

- rights confirmation,

- or final review.

The request shall identify:

- which steps are human,

- what instructions are provided,

- how output is returned,

- and how evidence is recorded.

The workflow must not be represented as fully automated.

<a id="section-5-104"></a>
## 5.104 Manual External Request

A Manual External Request prepares work for a provider that lacks governed integration.

Omnira may still manage:

- prompt,

- assets,

- cost estimate,

- review checklist,

- output ingestion,

- and provenance.

The execution state shall distinguish:

- prepared for manual use,

- handed to operator,

- external work underway,

- output returned,

- and verified.

Omnira must not claim provider control it does not possess.

<a id="section-5-105"></a>
## 5.105 Simulation Request

A Simulation Request evaluates what would happen without executing production work.

It may simulate:

- provider selection,

- cost,

- routing,

- policy,

- fallback,

- or expected quality.

Simulation shall be explicitly marked.

Simulation may not create:

- actual provider charges,

- real publication,

- or production evidence.

<a id="section-5-106"></a>
## 5.106 Dry-Run Request

A Dry-Run Request validates request structure and execution plan without consequential side effects.

It may:

- resolve scope,

- evaluate policy,

- estimate cost,

- select candidates,

- and validate Inputs.

Dry run must not be represented as actual execution.

<a id="section-5-107"></a>
## 5.107 Preview Request

A Preview Request produces a lower-cost or lower-resolution result for review before full production.

Preview strategy may reduce risk for:

- video,

- design,

- animation,

- and complex multimodal work.

The request shall define whether preview approval is required before full execution.

<a id="section-5-108"></a>
## 5.108 Exploratory Request

An Exploratory Request supports experimentation.

It should normally use:

- restricted data,

- limited budget,

- experimental providers,

- sandbox environment,

- and mandatory review.

Exploratory output shall not become canonical or public without separate admission.

<a id="section-5-109"></a>
## 5.109 High-Risk Request

A High-Risk Request may involve:

- confidential data,

- substantial spending,

- public consequence,

- children,

- voice or likeness,

- security-sensitive code,

- legal or medical context,

- or irreversible action.

High-risk requests may require:

- stronger identity verification,

- explicit human approval,

- independent evaluation,

- narrower providers,

- and enhanced evidence.

<a id="section-5-110"></a>
## 5.110 Consequential Request

A Consequential Request can materially affect:

- finances,

- public reputation,

- legal position,

- user access,

- external communication,

- production systems,

- or canonical assets.

Consequence classification shall drive:

- approval,

- evidence,

- reversibility,

- and verification.

Not every expensive request is consequential.

Not every low-cost request is low-risk.

<a id="section-5-111"></a>
## 5.111 Side-Effect Request

A Side-Effect Request asks the Fabric or a connected tool to change external or durable state.

Examples include:

- publish content,

- send message,

- create provider asset,

- delete file,

- commit code,

- schedule media,

- or modify configuration.

Side effects shall be explicit Capability Requirements.

They must not be hidden inside ordinary generation.

<a id="section-5-112"></a>
## 5.112 Generation and Publication Separation

A request to generate content shall not imply publication authority.

A request may include both generation and publication.

When it does, the two capabilities must remain separately represented.

Publication may require:

- separate approval,

- accepted asset,

- verified target account,

- schedule,

- and publication receipt.

<a id="section-5-113"></a>
## 5.113 Draft and Final Separation

The request shall distinguish:

- draft,

- review candidate,

- final candidate,

- approved final,

- and canonical output.

A model-generated result should normally begin as a draft or candidate.

Final or canonical status requires the appropriate process.

<a id="section-5-114"></a>
## 5.114 Request Authority Envelope

Every Capability Request shall carry or reference an effective Authority Envelope.

It should define:

- authorised Principal,

- capability,

- scope,

- project,

- provider restrictions,

- data classes,

- cost limit,

- action class,

- side effects,

- retry limit,

- validity,

- and approval reference.

The request shall not proceed when authority cannot be resolved.

<a id="section-5-115"></a>
## 5.115 Direct Authority

Direct Authority originates from a user or role that already possesses the required permission.

It may allow low-risk execution without a new approval.

Direct Authority shall still be:

- scoped,

- current,

- and policy-compliant.

<a id="section-5-116"></a>
## 5.116 Delegated Authority

Delegated Authority originates from another Principal.

The request shall preserve:

- delegator,

- delegate,

- original authority,

- permitted re-delegation,

- scope,

- expiry,

- and revocation.

The effective authority cannot exceed the delegation chain.

<a id="section-5-117"></a>
## 5.117 Approval-Based Authority

Some requests require an Approval before execution.

The request shall identify:

- approval type,

- requested scope,

- approver,

- status,

- and validity.

An approved request may still be blocked by changed policy or unavailable budget.

<a id="section-5-118"></a>
## 5.118 Authority Expiry

Authority may expire before execution begins or while a long-running request is active.

The Fabric shall define when authority must be revalidated.

Material boundaries may include:

- provider submission,

- spending threshold,

- publication,

- data export,

- or retry after extended delay.

<a id="section-5-119"></a>
## 5.119 Approval Summary

Before requesting human approval, the Fabric should present a concise Approval Summary.

It may include:

- objective,

- project,

- proposed execution,

- providers or provider classes,

- data used,

- estimated cost,

- maximum cost,

- retries,

- expected outputs,

- risks,

- and prohibited actions.

The summary should support informed approval without unnecessary technical noise.

<a id="section-5-120"></a>
## 5.120 Approval Granularity

Approval may apply to:

- one request,

- one execution,

- one production,

- one recurring instance,

- one budget period,

- or one bounded autonomy envelope.

Granularity must be explicit.

Approval to one monthly episode does not automatically approve future episodes unless recurrence is explicitly included.

<a id="section-5-121"></a>
## 5.121 Conditional Approval

An Approval may include conditions such as:

- only approved providers,

- maximum two retries,

- no publication,

- manual review required,

- or use only specified assets.

The request shall convert conditions into enforceable constraints.

Conditions must not remain only as human-readable comments.

<a id="section-5-122"></a>
## 5.122 Approval Revocation

Approval may be revoked before completion.

The Fabric shall define safe behaviour for:

- not-yet-started work,

- running work,

- irreversible provider jobs,

- partial outputs,

- and incurred cost.

Revocation cannot always undo completed side effects.

The system shall report residual consequences.

<a id="section-5-123"></a>
## 5.123 Request Validation

Before planning, the Fabric shall validate the Capability Request.

Validation should include:

- schema,

- identity,

- tenant,

- project,

- environment,

- capability existence,

- input availability,

- classification,

- rights,

- authority,

- budget,

- deadline,

- output contract,

- and internal consistency.

Validation failure shall identify actionable reasons.

<a id="section-5-124"></a>
## 5.124 Structural Validation

Structural Validation checks whether the request conforms to the schema.

It may verify:

- required fields,

- data types,

- identifier format,

- version,

- enum values,

- and reference shape.

Structural validity does not prove semantic or policy validity.

<a id="section-5-125"></a>
## 5.125 Semantic Validation

Semantic Validation checks whether the request meaning is coherent.

Examples include:

- output duration compatible with capability,

- required input type present,

- deadline after earliest start,

- budget currency known,

- publication requested with target platform,

- and child-facing classification consistent with review policy.

Semantic conflicts shall not be ignored.

<a id="section-5-126"></a>
## 5.126 Scope Validation

Scope Validation confirms:

- caller belongs to tenant,

- project exists,

- environment is valid,

- Inputs belong to permitted scope,

- and cross-project references are authorised.

Scope failure must fail closed.

<a id="section-5-127"></a>
## 5.127 Authority Validation

Authority Validation determines whether the caller may request the capability and action.

It shall consider:

- direct roles,

- delegation,

- approval,

- scope,

- cost,

- data,

- provider restrictions,

- and time.

Authentication alone is insufficient.

<a id="section-5-128"></a>
## 5.128 Budget Validation

Budget Validation confirms:

- budget source exists,

- request may use it,

- amount is available,

- currency or credits are compatible,

- and reservation rules can be satisfied.

Budget validation may produce:

- valid,

- insufficient,

- approval required,

- or unknown.

<a id="section-5-129"></a>
## 5.129 Rights Validation

Rights Validation determines whether:

- Inputs may be used,

- provider terms are compatible,

- output use is permitted,

- consent exists,

- and attribution can be satisfied.

Complex legal uncertainty may require human review.

The Fabric shall not invent legal certainty.

<a id="section-5-130"></a>
## 5.130 Capability Validation

Capability Validation confirms that each requested Capability exists and the requested version is supported.

It may also identify:

- deprecated capability,

- experimental capability,

- unsupported constraint,

- or no current resource mapping.

Architectural definition does not guarantee operational availability.

<a id="section-5-131"></a>
## 5.131 Request Consistency

The request shall be checked for conflicting requirements.

Examples include:

- Local Only data with external-only provider pin,

- Premium quality with budget below known minimum,

- public publication with unconfirmed rights,

- zero retention with provider that retains data,

- or deadline shorter than minimum production time.

Conflicts should be surfaced before execution.

<a id="section-5-132"></a>
## 5.132 Conflict Resolution

Conflicting request attributes shall be resolved according to:

1. law and mandatory policy,

2. explicit authority,

3. data classification,

4. rights,

5. hard constraints,

6. user-explicit requirements,

7. project defaults,

8. routing preference,

9. system inference.

The Fabric shall not silently discard the stricter requirement.

When no valid resolution exists, the request must pause or fail.

<a id="section-5-133"></a>
## 5.133 Missing Information

Missing information shall be classified as:

- safely defaultable,

- retrievable,

- clarifiable,

- deferrable,

- or blocking.

The system should retrieve known project context before asking the user.

It should not retrieve unrelated private context merely to avoid a question.

<a id="section-5-134"></a>
## 5.134 Safe Default

A Safe Default is a pre-approved value that does not materially expand risk or authority.

Examples may include:

- Balanced routing,

- no publication,

- bounded retries,

- temporary output storage,

- and manual review for child-facing content.

Safe Defaults shall be:

- documented,

- versioned,

- and scoped.

<a id="section-5-135"></a>
## 5.135 Unsafe Default

Unsafe Defaults include:

- unrestricted provider account,

- global scope,

- public classification,

- unlimited budget,

- automatic publication,

- automatic memory admission,

- or permission to overwrite canonical assets.

Unsafe Defaults are prohibited.

<a id="section-5-136"></a>
## 5.136 Assumption

An Assumption is a proposition used for planning when certainty is unavailable.

Assumptions shall be:

- explicit,

- scoped,

- and reviewable.

Material assumptions should be included in approval summaries.

An assumption that fails during execution may require replanning.

<a id="section-5-137"></a>
## 5.137 Assumption Register

Complex requests may maintain an Assumption Register.

It may record:

- assumption,

- source,

- confidence,

- consequence if false,

- validation method,

- and status.

The planner shall not bury material assumptions inside prompts.

<a id="section-5-138"></a>
## 5.138 Unknown Requirement

An Unknown Requirement represents unresolved information that may matter later.

Unknowns may be allowed when:

- execution can safely begin with reversible steps,

- the unknown is not yet relevant,

- and the request defines a checkpoint before consequence.

Unknowns must not disappear silently.

<a id="section-5-139"></a>
## 5.139 Deferred Decision

A Deferred Decision is intentionally postponed until more evidence exists.

Examples include:

- choose final video model after preview comparison,

- select publication date after review,

- or decide premium retry after first evaluation.

The request shall define:

- decision point,

- required evidence,

- decision authority,

- and default if unresolved.

<a id="section-5-140"></a>
## 5.140 Request Amendment

A Request Amendment changes an existing request.

Amendments shall identify:

- request version,

- changed fields,

- reason,

- actor,

- impact,

- and approval requirement.

Material changes may invalidate:

- cost estimate,

- execution plan,

- authority,

- or provider selection.

<a id="section-5-141"></a>
## 5.141 Material Amendment

A Material Amendment includes changes to:

- objective,

- project,

- data classification,

- rights,

- budget,

- deadline,

- providers,

- output,

- quality,

- side effects,

- or authority.

Material Amendments require revalidation.

They may require renewed approval.

<a id="section-5-142"></a>
## 5.142 Non-Material Amendment

A Non-Material Amendment may include:

- spelling correction,

- display label,

- or metadata that does not alter execution meaning.

Non-material amendments should still be versioned when persisted.

<a id="section-5-143"></a>
## 5.143 Request Version

Every material request revision shall create a new Request Version.

Executions shall reference the exact version they used.

A revised request shall not rewrite the meaning of an execution already in progress.

<a id="section-5-144"></a>
## 5.144 Request Supersession

A new request may supersede an older request.

Supersession shall define:

- replaced request,

- new request,

- reason,

- effective time,

- and treatment of existing execution.

Supersession does not automatically cancel active work.

<a id="section-5-145"></a>
## 5.145 Request Cancellation

A request may be cancelled by an authorised Principal.

Cancellation shall preserve:

- who cancelled,

- reason,

- time,

- remaining execution,

- incurred cost,

- and retained outputs.

Cancellation may not stop provider work that has already become irreversible.

The system shall report what could and could not be cancelled.

<a id="section-5-146"></a>
## 5.146 Request Expiry

A request may expire when:

- deadline passes,

- approval expires,

- Inputs become stale,

- budget period closes,

- or recurring validity ends.

Expired requests shall not start new execution.

Active work may require explicit policy.

<a id="section-5-147"></a>
## 5.147 Request Reopening

A completed, failed or expired request should not normally be reopened by mutating its history.

A new Request Version or related request should be created.

Reopening may be permitted only when lifecycle semantics remain clear.

<a id="section-5-148"></a>
## 5.148 Request Deduplication

The Fabric shall detect duplicate requests where repeated submission would create unnecessary cost or side effects.

Deduplication may use:

- idempotency key,

- caller,

- project,

- objective,

- input versions,

- time window,

- and production reference.

Similarity alone is insufficient to suppress legitimate repeated work.

<a id="section-5-149"></a>
## 5.149 Idempotent Request

An Idempotent Request uses a stable key to represent the same intended operation.

Repeated submission should return or reference the existing request when appropriate.

Idempotency scope shall be explicit.

A monthly recurring request must not reuse one key for every month.

<a id="section-5-150"></a>
## 5.150 Duplicate Candidate

When the system suspects duplication but cannot prove it, it should identify a Duplicate Candidate.

It may:

- ask for confirmation,

- display existing work,

- or proceed under separate authority.

Uncertain similarity must not silently discard user intent.

<a id="section-5-151"></a>
## 5.151 Request Correlation

Related requests should share a Correlation ID or Production ID.

Correlation supports:

- grouping,

- progress,

- cost reporting,

- and evidence.

Correlation does not merge lifecycle or authority.

<a id="section-5-152"></a>
## 5.152 Request Causation

A request may be caused by:

- user command,

- workflow step,

- failed evaluation,

- incident,

- recurring schedule,

- or prior request output.

Causation shall be preserved.

A retry request caused by quality failure should reference the failed evaluation.

<a id="section-5-153"></a>
## 5.153 Request Lifecycle

Canonical Capability Request states may include:

- draft,

- interpreting,

- incomplete,

- validating,

- awaiting clarification,

- awaiting approval,

- approved,

- planning,

- queued,

- executing,

- awaiting review,

- partially completed,

- completed,

- rejected,

- failed,

- cancelled,

- expired,

- and superseded.

The exact state vocabulary shall remain versioned.

States shall have defined entry and exit criteria.

<a id="section-5-154"></a>
## 5.154 Draft State

Draft means the request has been created but is not ready for validation or execution.

Draft requests may be edited.

They shall not consume production budget or provider resources.

<a id="section-5-155"></a>
## 5.155 Interpreting State

Interpreting means natural-language or broad intent is being translated into structured requirements.

This stage may use AI reasoning.

Interpretation does not create execution authority.

<a id="section-5-156"></a>
## 5.156 Incomplete State

Incomplete means required information is missing.

The request should identify:

- missing fields,

- why they matter,

- and how they may be resolved.

<a id="section-5-157"></a>
## 5.157 Validating State

Validating means the request is undergoing structural, semantic, scope, policy, rights and authority checks.

No provider execution should begin before required validation completes.

<a id="section-5-158"></a>
## 5.158 Awaiting Clarification State

Awaiting Clarification means human or authoritative system input is required.

The request should preserve:

- question,

- blocking reason,

- current assumptions,

- and response deadline where relevant.

<a id="section-5-159"></a>
## 5.159 Awaiting Approval State

Awaiting Approval means the request is valid enough to present for decision but lacks required authority.

The approval summary shall identify the exact scope requested.

<a id="section-5-160"></a>
## 5.160 Approved State

Approved means required approval exists for the current request version and conditions.

Approval does not prove:

- budget availability,

- provider availability,

- or successful planning.

These must still be resolved.

<a id="section-5-161"></a>
## 5.161 Planning State

Planning means the Fabric is constructing an eligible Execution Plan.

Planning may produce:

- candidate resources,

- cost estimates,

- fallback paths,

- and additional approval requirements.

<a id="section-5-162"></a>
## 5.162 Queued State

Queued means a valid plan exists and execution is waiting for capacity, schedule or dependency.

Queue position shall not imply guaranteed completion time.

<a id="section-5-163"></a>
## 5.163 Executing State

Executing means one or more Execution Steps are active.

The request may contain several concurrent Executions.

Current state should reflect partial progress truthfully.

<a id="section-5-164"></a>
## 5.164 Awaiting Review State

Awaiting Review means technical execution has produced candidate output but acceptance or human review remains incomplete.

The request is not completed.

<a id="section-5-165"></a>
## 5.165 Partially Completed State

Partially Completed means some required or optional results exist, but the full Completion Contract is not satisfied.

The request should identify:

- completed outputs,

- missing outputs,

- cost incurred,

- and recovery options.

<a id="section-5-166"></a>
## 5.166 Completed State

Completed means the Completion Contract has been satisfied.

Completion shall reference:

- accepted Outputs,

- Evaluations,

- required Approvals,

- cost evidence,

- and unresolved limitations.

Completed does not automatically mean published.

<a id="section-5-167"></a>
## 5.167 Rejected State

Rejected means authority or approval was explicitly denied.

A rejected request may later produce a new request.

The rejection evidence shall remain immutable.

<a id="section-5-168"></a>
## 5.168 Failed State

Failed means the request cannot satisfy its Completion Contract under the current approved conditions.

Failure should identify:

- failed requirement,

- attempts,

- cost,

- outputs preserved,

- and recovery options.

<a id="section-5-169"></a>
## 5.169 Cancelled State

Cancelled means an authorised Principal ended the request.

Cancellation evidence shall remain.

Residual external work or cost must be identified.

<a id="section-5-170"></a>
## 5.170 Expired State

Expired means the request is no longer valid because of time, approval, Inputs or policy.

Expired requests shall not resume without renewed authority.

<a id="section-5-171"></a>
## 5.171 Superseded State

Superseded means another request version or request has replaced the current one for future work.

Historical evidence remains valid for work performed under the superseded request.

<a id="section-5-172"></a>
## 5.172 Request Planning Handoff

A validated request shall be handed to the Intelligence Planning layer.

The handoff should include:

- exact request version,

- effective scope,

- authority,

- policy decision,

- budget envelope,

- routing profile,

- Input references,

- Output Contract,

- Quality Contract,

- deadline,

- and unresolved permitted assumptions.

The planner shall not reconstruct these from conversation history when canonical request data exists.

<a id="section-5-173"></a>
## 5.173 Planner Responsibility

The Planner may:

- decompose the request,

- select execution pattern,

- create child requests,

- identify resource candidates,

- estimate cost,

- define evaluation,

- and propose fallback.

The Planner shall not change mandatory request constraints.

Material conflict must return to request amendment or approval.

<a id="section-5-174"></a>
## 5.174 Planner Feedback

The Planner may return feedback such as:

- no eligible resource,

- budget insufficient,

- deadline impossible,

- required capability unavailable,

- rights unresolved,

- or quality requires human-assisted execution.

The request may then:

- amend,

- escalate,

- reject,

- or remain incomplete.

<a id="section-5-175"></a>
## 5.175 Request Explainability

The Fabric should be able to explain a request in human-readable form.

A Request Summary may answer:

- What are we trying to achieve?

- Which project does it belong to?

- What data will be used?

- What outputs are expected?

- What quality is required?

- What may it cost?

- What providers may be used?

- What actions are prohibited?

- What approval is required?

- What remains unknown?

Explainability supports trust and review.

<a id="section-5-176"></a>
## 5.176 Machine-Readable Request

The request shall also have a machine-readable representation.

The schema should support:

- deterministic validation,

- policy evaluation,

- routing,

- versioning,

- and audit.

Natural-language descriptions may supplement but not replace required structured fields.

<a id="section-5-177"></a>
## 5.177 Request Schema Evolution

The Capability Request schema shall be versioned.

Schema changes shall preserve:

- backward compatibility where possible,

- migration,

- validation,

- and historical interpretation.

Adapters shall not define the core request schema.

<a id="section-5-178"></a>
## 5.178 Extension Fields

Requests may support namespaced extensions for:

- project-specific requirements,

- provider-specific optional features,

- or experimental capabilities.

Extensions shall not redefine canonical fields.

A provider-specific extension must remain optional unless the request is explicitly pinned.

<a id="section-5-179"></a>
## 5.179 Request Integrity

Important requests should preserve integrity metadata such as:

- checksum,

- signature,

- immutable version reference,

- and creator.

Integrity requirements should increase with:

- cost,

- rights,

- public consequence,

- and security sensitivity.

<a id="section-5-180"></a>
## 5.180 Request Audit Trail

The request shall preserve an Audit Trail including:

- creation,

- interpretation,

- clarification,

- amendments,

- approvals,

- validation,

- planning,

- cancellation,

- and completion.

The audit trail shall remain scoped and privacy-aware.

<a id="section-5-181"></a>
## 5.181 Privacy of Request Content

Capability Requests may contain sensitive information.

Access shall be restricted by:

- tenant,

- project,

- role,

- data classification,

- and field-level need.

Operational dashboards may display summaries without exposing full prompts or Inputs.

<a id="section-5-182"></a>
## 5.182 Request Redaction

A redacted request representation may be created for:

- audit,

- support,

- analytics,

- or cross-team review.

Redaction shall not modify the canonical original.

The redacted representation must identify:

- redaction method,

- removed fields,

- and resulting classification.

<a id="section-5-183"></a>
## 5.183 Prompt Injection and Request Integrity

External content referenced by a request may contain instructions.

Those instructions shall not redefine:

- user intent,

- policy,

- authority,

- or provider selection.

The system must distinguish:

- canonical request instructions,

- trusted project instructions,

- and untrusted content.

Retrieved instructions should be treated as data unless explicitly admitted as policy.

<a id="section-5-184"></a>
## 5.184 Malicious Request

A request may be malicious, compromised or policy-violating.

The Fabric shall validate:

- action,

- target,

- scope,

- data,

- and authority.

A trusted user account does not guarantee every request is safe.

Suspicious requests may trigger:

- rejection,

- additional approval,

- incident,

- or restricted execution.

<a id="section-5-185"></a>
## 5.185 Request Rate Limits

The Fabric may apply request-level rate limits by:

- Principal,

- tenant,

- project,

- capability,

- provider,

- or budget.

Rate limits support:

- reliability,

- cost control,

- abuse prevention,

- and fair capacity.

Rate limits shall not be represented as provider failure.

<a id="section-5-186"></a>
## 5.186 Request Quota

A Request Quota defines permitted request volume over a period.

Quota differs from monetary budget.

A free provider account may have sufficient budget but exhausted request quota.

Quota state shall be considered during planning.

<a id="section-5-187"></a>
## 5.187 Request Concurrency

The Fabric may limit concurrent requests by:

- project,

- provider account,

- capability,

- runtime node,

- or production.

Concurrency limits protect:

- capacity,

- cost,

- ordering,

- and provider terms.

Requests waiting on concurrency shall remain queued rather than failed when appropriate.

<a id="section-5-188"></a>
## 5.188 Request Ordering

Some requests require ordering.

Examples include:

- final narration after script approval,

- publication after asset acceptance,

- and canonicalisation after review.

Ordering should be expressed through dependencies.

The Fabric shall not rely solely on submission time.

<a id="section-5-189"></a>
## 5.189 Request Batch

A Request Batch groups similar requests for efficient execution.

Examples include:

- generate five social variants,

- transcribe several files,

- or evaluate multiple scenes.

Batching may reduce cost.

Each item should preserve:

- scope,

- input,

- output,

- failure state,

- and cost attribution.

<a id="section-5-190"></a>
## 5.190 Partial Batch Failure

A Batch Request may partially succeed.

The Completion Contract shall define whether:

- all items are mandatory,

- a minimum count is acceptable,

- or failed items may be retried separately.

The Fabric shall not discard successful items automatically.

<a id="section-5-191"></a>
## 5.191 Streaming Request

A Streaming Request produces incremental output.

Examples include:

- text stream,

- live transcription,

- real-time voice,

- or progressive media generation.

Streaming shall preserve:

- partial-state meaning,

- cancellation,

- cost,

- and final acceptance.

Partial stream receipt does not prove completion.

<a id="section-5-192"></a>
## 5.192 Interactive Request

An Interactive Request allows multiple turns or real-time input.

It shall define:

- session identity,

- authority duration,

- context scope,

- tool permissions,

- cost boundary,

- and termination.

Interactive sessions must not accumulate unbounded authority or context.

<a id="section-5-193"></a>
## 5.193 Long-Running Request

A Long-Running Request may remain active for minutes, hours or longer.

It shall support:

- durable state,

- callback correlation,

- polling,

- policy revalidation,

- authority expiry,

- cancellation,

- and reconciliation.

Long-running work must not depend on one chat connection remaining open.

<a id="section-5-194"></a>
## 5.194 Request Notification Policy

The request may define when users should be notified.

Examples include:

- approval required,

- budget threshold reached,

- failure,

- unknown outcome,

- review ready,

- or completion.

Notification policy shall not expose sensitive content.

<a id="section-5-195"></a>
## 5.195 Request Escalation

Escalation occurs when the Fabric cannot continue safely.

Escalation may be triggered by:

- missing authority,

- insufficient budget,

- rights uncertainty,

- repeated quality failure,

- provider outage,

- or deadline risk.

The request should identify the appropriate escalation recipient.

<a id="section-5-196"></a>
## 5.196 Request Recovery

A failed or partial request may support recovery.

Recovery options may include:

- retry,

- fallback,

- amend request,

- supply missing Input,

- increase budget,

- human-assisted completion,

- or accept partial result.

Recovery must preserve prior evidence and cost.

<a id="section-5-197"></a>
## 5.197 Request Compensation

If a request caused side effects before failure, compensation may be required.

The request or plan should identify:

- compensatable actions,

- compensation authority,

- and residual risk.

Compensation does not erase the original evidence.

<a id="section-5-198"></a>
## 5.198 Request Outcome Record

A Request Outcome Record summarises the final result.

It may include:

- final state,

- accepted Outputs,

- rejected Outputs,

- cost,

- evaluations,

- approvals,

- side effects,

- unresolved issues,

- and learning candidates.

The Outcome Record should be immutable once finalised.

Later reconciliation may append or supersede interpretation.

<a id="section-5-199"></a>
## 5.199 Request Receipt

A Request Receipt provides a human- and machine-readable summary of the governed request lifecycle.

It may include:

- request identity,

- project,

- caller,

- purpose,

- version,

- authority,

- policy,

- plan,

- executions,

- outputs,

- cost,

- quality,

- and final state.

The Request Receipt complements individual Execution Receipts.

<a id="section-5-200"></a>
## 5.200 Request and Memory

The Capability Request may become relevant to future memory.

The Fabric may produce Memory Candidates such as:

- approved recurring preference,

- stable production requirement,

- or repeated routing learning.

The request itself shall not automatically become long-term memory.

Operational history may remain in evidence storage.

<a id="section-5-201"></a>
## 5.201 Request and Intelligence Graph

The Capability Request may be projected into the Intelligence Graph.

Relationships may include:

- initiated by,

- belongs to Project,

- requires Capability,

- authorised by,

- fulfilled by Execution,

- produced Output,

- supported Decision,

- and created Learning Candidate.

Graph visibility does not grant request authority.

<a id="section-5-202"></a>
## 5.202 Request and Asset Library

Requests may reference Assets and produce Output candidates.

The Asset Library remains responsible for durable asset lifecycle.

The request shall preserve:

- input Asset Versions,

- output destination,

- canonicalisation prohibition or authority,

- and derivative relationships.

<a id="section-5-203"></a>
## 5.203 Request and Publication System

A request may prepare a Publication Package.

Publication shall remain a separate capability or child request.

The original generation request must not be marked fully complete when publication verification is part of its Completion Contract and has not occurred.

<a id="section-5-204"></a>
## 5.204 Request and Repository Workflow

A Code Capability Request may produce a patch.

Repository actions such as:

- write,

- commit,

- push,

- pull request,

- merge,

- and deploy

shall remain separate capability requirements with separate authority.

The request shall declare which actions are permitted.

<a id="section-5-205"></a>
## 5.205 Request and External Provider UI

Some requests may require manual use of a provider interface.

The Fabric may prepare an Operator Package containing:

- instructions,

- approved Inputs,

- provider account,

- budget,

- expected settings,

- review checklist,

- and upload destination.

The request shall remain human-assisted until output is returned and evidenced.

<a id="section-5-206"></a>
## 5.206 Request Policy Precedence

When several policies apply, the request shall preserve the effective result.

Potential policy sources include:

- platform,

- tenant,

- project,

- user,

- capability,

- provider,

- environment,

- and production.

The most restrictive mandatory policy should normally prevail.

Conflicts must be explicit.

<a id="section-5-207"></a>
## 5.207 Request Default Resolution

Defaults may be resolved in the following order where appropriate:

1. request-explicit value,

2. approved Production Envelope,

3. project policy,

4. tenant policy,

5. user preference,

6. capability default,

7. platform safe default.

Mandatory policy may override any lower source.

The effective source should be recorded.

<a id="section-5-208"></a>
## 5.208 Request Normalisation

The Fabric may normalise equivalent user expressions into canonical values.

Examples include:

- “cheap” into Economy,

- “keep it private” into a Private profile requiring clarification of placement,

- “use OpenArt only” into Pinned Provider constraint,

- or “do not publish” into publication prohibition.

Normalisation shall preserve original wording for provenance where useful.

<a id="section-5-209"></a>
## 5.209 Request Localisation

User-facing request summaries may be translated.

Canonical technical fields should remain stable.

Translation must not change:

- authority,

- constraints,

- rights,

- or quality meaning.

The original user instruction may be preserved alongside the canonical representation.

<a id="section-5-210"></a>
## 5.210 Request Accessibility

Request interfaces should support users who do not understand provider terminology or technical schemas.

The system should explain:

- cost,

- privacy,

- quality,

- and approval

in accessible language.

Technical detail may remain available for expert review.

Accessibility must not hide consequence.

Stage 1 should support representative request types such as:

<a id="section-5-218"></a>
## 5.218 Stage 1 Clarification Behaviour

Stage 1 should implement focused clarification.

It shall ask when missing information affects:

- project,

- data classification,

- provider eligibility,

- spending,

- publication,

- rights,

- or required quality.

It should use approved project defaults for low-risk fields.

It shall not present users with exhaustive technical questionnaires.

<a id="section-5-219"></a>
## 5.219 Stage 1 Approval Summary

Stage 1 should produce an approval summary for paid or consequential work.

The summary should include:

- project,

- objective,

- proposed providers or classes,

- maximum cost,

- data used,

- expected outputs,

- retries,

- human review,

- and prohibited actions.

Approval shall bind to the exact request version.

<a id="section-5-220"></a>
## 5.220 Stage 1 Request Validation Tests

Representative validation tests should include:

1. Missing tenant scope is rejected.

2. Missing project scope does not default to global.

3. Unknown Capability is rejected.

4. Local Only input cannot be used with an external provider requirement.

5. Publication requires explicit authority.

6. Paid execution requires a Budget Source.

7. Voice cloning requires valid consent.

8. Child-facing media requires the configured review policy.

9. Pinned provider conflict with policy is rejected.

10. Expired approval blocks execution.

11. Request amendment invalidates prior cost approval when material.

12. Required Input version is preserved.

13. Output Contract is validated before execution.

14. Optional Capability omission does not fail a compatible request.

15. Mandatory Capability omission does fail the request.

16. Duplicate idempotency key returns the existing request.

17. Cross-project Inputs require explicit authority.

18. A dry run does not create provider charges.

19. A human-assisted request is labelled truthfully.

20. Generation approval cannot be reused for publication.

<a id="section-5-221"></a>
## 5.221 Stage 1 Lifecycle Tests

Representative lifecycle tests should include:

1. Draft cannot transition directly to executing.

2. Incomplete transitions to validating only after blocking fields are resolved.

3. Awaiting Approval cannot execute before valid approval.

4. Approved may return to awaiting approval after material amendment.

5. Cancelled does not restart automatically.

6. Expired cannot execute without renewal.

7. Partially Completed preserves accepted Outputs.

8. Superseded preserves historical evidence.

9. Failed may create a related recovery request.

10. Completed requires the Completion Contract to be satisfied.

<a id="section-5-222"></a>
## 5.222 Stage 1 Security Tests

Representative security tests should include:

1. Request Inputs cannot be read across Projects.

2. Caller identity cannot be replaced through prompt text.

3. Raw credentials cannot appear in the request payload.

4. External content cannot modify the Authority Envelope.

5. Provider callbacks cannot create new unrestricted requests.

6. Global scope requires explicit reason and permission.

7. Redacted request views do not expose protected Inputs.

8. Request search remains tenant- and project-scoped.

9. Approval conditions become enforceable request constraints.

10. Request logs do not expose sensitive prompt content broadly.

<a id="section-5-223"></a>
## 5.223 Request Conformance Requirements

An implementation conforms to this chapter only when:

- intent remains separate from execution,

- requests are provider-independent,

- project and tenant scope are explicit,

- capability requirements are structured,

- authority is resolvable,

- budget is bounded,

- quality is defined,

- Input and Output contracts are explicit,

- request changes are versioned,

- lifecycle transitions are valid,

- and consequential work cannot begin from unvalidated natural-language text alone.

A user-friendly interface is not sufficient proof of conformance.

The canonical request must exist beneath it.

<a id="section-5-224"></a>
## 5.224 Canonical Intent Contract

The following requirements define the canonical Intent contract:

1. Intent SHALL describe desired purpose and outcome.

2. Intent SHALL remain separate from provider implementation.

3. Intent SHALL preserve initiator and beneficiary.

4. Intent SHALL preserve project and tenant scope where applicable.

5. Intent MAY generate multiple Capability Requests.

6. Intent MAY remain broader and longer-lived than one execution.

7. Inferred Intent details SHALL remain distinguishable from explicit user statements.

8. Material uncertainty SHALL be preserved.

9. Human-readable Intent SHALL be translatable into machine-readable requests.

10. Intent SHALL NOT create execution authority by itself.

<a id="section-5-225"></a>
## 5.225 Canonical Capability Request Contract

The following requirements define the canonical Capability Request contract:

1. Every governed intelligence execution SHALL originate from a valid Capability Request or approved equivalent object.

2. Every request SHALL have stable identity and version.

3. Every request SHALL identify caller and initiating context.

4. Every request SHALL resolve tenant and project scope where applicable.

5. Global scope SHALL require explicit declaration and reason.

6. Every request SHALL declare one or more Capability Requirements.

7. Mandatory and optional capabilities SHALL remain distinguishable.

8. Every request SHALL define permitted Inputs.

9. Input versions, classifications and rights SHALL be preserved.

10. Every request SHALL define an Output Contract.

11. Every request SHALL define or inherit a Quality Contract.

12. Every paid request SHALL define a Budget Envelope and Budget Source.

13. Every request SHALL define or inherit a Routing Profile.

14. Every request SHALL carry or reference an Authority Envelope.

15. Consequential requests SHALL require the appropriate approval.

16. Generation authority SHALL remain separate from publication authority.

17. Missing critical information SHALL fail closed.

18. Safe defaults MAY be applied only when they do not expand authority or risk.

19. Material assumptions SHALL be explicit.

20. Material amendments SHALL create a new Request Version.

21. Executions SHALL reference the exact Request Version used.

22. Request lifecycle transitions SHALL be valid and attributable.

23. Duplicate requests SHALL be handled through scoped idempotency or explicit review.

24. Cancellation SHALL preserve incurred cost and residual external state.

25. Request completion SHALL require the Completion Contract.

26. Requests SHALL preserve correlation and causation.

27. Request summaries SHALL be explainable to human approvers.

28. Request schemas SHALL remain provider-independent.

29. Extensions SHALL NOT redefine canonical fields.

30. Requests SHALL remain subject to current policy at execution time.

<a id="section-5-226"></a>
## 5.226 Request Invariants

The following invariants shall remain true:

- No request executes without resolvable identity.

- No project request executes without explicit project scope.

- No paid request executes without budget attribution.

- No protected Input is routed before classification.

- No provider is selected before capability and policy evaluation.

- No Output is accepted without required quality evidence.

- No publication occurs under generation-only authority.

- No request silently expands its own scope.

- No amendment rewrites prior execution history.

- No optional omission is misrepresented as mandatory success.

- No mandatory omission is hidden as complete.

- No human-assisted process is represented as autonomous.

- No simulation is represented as production execution.

- No external content becomes request authority.

- No request becomes permanent memory merely because it existed.

<a id="section-5-227"></a>
## 5.227 Anti-Pattern — Provider Command as Intent

The request must not be reduced to:

Use Provider X.

This omits:

- purpose,

- quality,

- data,

- rights,

- cost,

- and output.

A provider may be pinned.

The objective must still remain explicit.

<a id="section-5-228"></a>
## 5.228 Anti-Pattern — Conversation as the Only Contract

A conversation may contain relevant instructions.

It shall not remain the only authority source for consequential execution.

Important constraints must be resolved into the Capability Request.

Otherwise, the system cannot reliably:

- validate,

- audit,

- reproduce,

- or enforce them.

<a id="section-5-229"></a>
## 5.229 Anti-Pattern — Infinite Clarification

The system must not block progress by asking every imaginable question before reversible work.

Clarification should be consequence-driven.

Safe planning and draft work may proceed when authority permits.

<a id="section-5-230"></a>
## 5.230 Anti-Pattern — Hidden Assumptions

The system must not silently assume:

- project,

- budget,

- provider account,

- rights,

- publication,

- or data classification.

Material assumptions must be explicit.

<a id="section-5-231"></a>
## 5.231 Anti-Pattern — One Giant Request

A request should not contain an unbounded mixture of:

- strategy,

- production,

- publication,

- analytics,

- and future optimisation

without clear child boundaries.

Complex intent should be decomposed while preserving the parent objective.

<a id="section-5-232"></a>
## 5.232 Anti-Pattern — Request Per Model Call

The canonical request should not be forced to mirror every low-level provider call.

One request may produce many executions.

The request represents governed intent, not transport granularity.

<a id="section-5-233"></a>
## 5.233 Anti-Pattern — Approval Without Version

Approval must not apply vaguely to a request that can later change.

Approval shall bind to:

- request version,

- scope,

- budget,

- and conditions.

Material amendments require renewed authority.

<a id="section-5-234"></a>
## 5.234 Anti-Pattern — Budget as Optional Metadata

Paid work must not treat budget as an afterthought.

Cost is part of execution eligibility and approval.

The request shall include budget before paid execution.

<a id="section-5-235"></a>
## 5.235 Anti-Pattern — Quality After Generation

Quality requirements must be defined before resource selection.

Evaluating quality only after generation prevents correct routing and cost planning.

<a id="section-5-236"></a>
## 5.236 Anti-Pattern — Output Exists Therefore Request Completed

An Output may exist while:

- quality failed,

- review is pending,

- rights are unclear,

- or required derivatives are missing.

Completion requires the Completion Contract.

<a id="section-5-237"></a>
## 5.237 Anti-Pattern — Project Inferred From Folder Name

A request shall not rely on:

- file path,

- visual page,

- prompt wording,

- or provider workspace

as the sole project authority.

Project scope must resolve canonically.

<a id="section-5-238"></a>
## 5.238 Anti-Pattern — Recurrence as Permanent Approval

A recurring definition shall not create permanent unrestricted authority.

Each instance remains subject to:

- current policy,

- budget,

- credentials,

- and validity.

<a id="section-5-239"></a>
## 5.239 Anti-Pattern — Retry as New Unrelated Request

Retries should remain linked to the original request and execution where semantically appropriate.

Creating unrelated requests for every retry destroys cost and failure traceability.

<a id="section-5-240"></a>
## 5.240 Anti-Pattern — Silent Degradation

The Fabric must not silently:

- lower quality,

- change provider class,

- omit mandatory output,

- reduce privacy,

- or alter rights.

Material degradation requires disclosure and appropriate approval.

<a id="section-5-241"></a>
## 5.241 Future Evolution

Future versions of the request architecture may support:

- richer natural-language negotiation,

- automatic requirement extraction,

- dynamic contracts,

- market-based resource bidding,

- multi-tenant procurement,

- advanced condition triggers,

- real-time interactive production,

- and collaborative approvals.

Future capability must preserve:

- explicit scope,

- bounded authority,

- user ownership,

- truthful state,

- and versioned request meaning.

<a id="section-5-242"></a>
## 5.242 Closing Statement

The Capability Request is the point where human intention becomes governable system work.

It must be simple enough for ordinary users to create through natural conversation.

It must be precise enough for machines to validate, plan and execute.

It must preserve:

- purpose,

- scope,

- authority,

- quality,

- cost,

- privacy,

- rights,

- time,

- and expected outcome.

The Intent Envelope explains what the user is trying to achieve.

The Capability Request defines what the Fabric may do.

The Authority Envelope defines what is permitted.

The Budget Envelope defines what may be spent.

The Quality Contract defines what is acceptable.

The Input Contract defines what may be used.

The Output Contract defines what must be produced.

The Completion Contract defines what evidence proves success.

These contracts allow Atlas, Managers, agents, workflows and humans to work through one governed intelligence boundary without being forced to understand every provider or model.

The user should be able to describe a vision.

Omnira should be able to structure the work.

The Fabric should be able to execute it compliantly.

No provider should become the purpose.

No technical implementation should replace the intent.

No natural-language ambiguity should silently become authority.

No approved request should exceed its scope.

Intent remains human.

Execution becomes governed.

The Capability Request is the bridge between them.
