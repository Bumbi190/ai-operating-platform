# Chapter 6 — Capability Registry

<a id="section-6-1"></a>
## 6.1 Chapter Status

This chapter defines the canonical architecture, governance model, lifecycle, contracts and operational responsibilities of the Omnira Intelligence Fabric Capability Registry.

It establishes:

- what a capability is,

- how capabilities are identified and named,

- how capability contracts are versioned,

- how inputs and outputs are declared,

- how quality, risk, rights, placement and evidence requirements are attached,

- how models, providers, tools, agents and runtimes declare support,

- how support is verified,

- how capability discovery works,

- how compatibility is determined,

- how deprecated and unavailable capabilities remain historically interpretable,

- and how Stage 1 shall implement a bounded but extensible registry.

The Capability Registry is a foundational control-plane component of the Intelligence Fabric.

It is the authoritative catalogue of what kinds of governed intelligence work Omnira understands.

It is not, by itself, proof that a capability is currently available.

A capability may be:

- conceptually defined,

- contractually specified,

- mapped to resources,

- experimentally supported,

- operationally available,

- restricted,

- degraded,

- deprecated,

- or unavailable.

These states must remain distinct.

This chapter is normative after formal approval.

Runtime availability and conformance must be verified independently.

<a id="section-6-2"></a>
## 6.2 Purpose of the Capability Registry

The Intelligence Fabric shall not organise intelligence execution primarily around provider names or model brands.

It shall organise execution around capabilities.

A capability represents what Omnira needs a resource to accomplish.

Examples include:

- generate text,

- reason over evidence,

- create code,

- edit an image,

- animate an illustration,

- synthesise Swedish speech,

- transcribe audio,

- generate embeddings,

- rerank retrieved material,

- validate character consistency,

- or publish an approved media asset.

The Capability Registry provides the canonical language through which:

- users express desired outcomes,

- Atlas and Managers request intelligence work,

- agents declare required operations,

- workflows define execution steps,

- providers and models declare support,

- policies constrain use,

- quality contracts define acceptance,

- and routing identifies eligible resources.

Without a Capability Registry, provider terminology would leak into every caller.

The Registry prevents external vendor language from becoming Omnira’s permanent architecture.

<a id="section-6-3"></a>
## 6.3 Capability as a Canonical Contract

A capability is not merely a label.

It is a versioned canonical contract.

The contract defines:

- semantic purpose,

- allowed inputs,

- expected outputs,

- supported execution patterns,

- quality dimensions,

- risk classification,

- authority requirements,

- data-placement implications,

- rights implications,

- evidence requirements,

- and compatibility rules.

A resource may claim support for a capability only when it can satisfy the relevant contract under declared conditions.

A provider offering “video generation” does not automatically satisfy every Omnira video capability.

It may support:

- text-to-video,

- but not image-to-video;

- short clips,

- but not long-form scenes;

- generic subjects,

- but not reusable character references;

- generation,

- but not commercial-use requirements;

- or synchronous preview,

- but not reliable asynchronous production.

Capability declarations must preserve these distinctions.

<a id="section-6-4"></a>
## 6.4 Capability-First Architecture

Capability-first architecture means that Omnira callers express:

- what operation is required,

- what inputs are available,

- what output is expected,

- what quality is required,

- and what restrictions apply.

They should not need to begin with:

- provider name,

- model identifier,

- endpoint,

- API version,

- or vendor-specific parameter.

The Fabric may later select a provider or model.

Provider choice is a routing result.

It is not the canonical meaning of the request.

<a id="section-6-5"></a>
## 6.5 Capability Is Not Provider

A Capability describes an operation.

A Provider describes the organisation or platform supplying a resource.

The following are different concepts:

Capability

video.image_to_video

Provider

OpenArt

Model or Resource

A specific video-generation model exposed through OpenArt.

Adapter Mapping

The translation between video.image_to_video and the provider operation.

The Registry shall not create provider-specific capabilities merely because one provider uses unique terminology.

Provider-specific extensions may exist.

They must remain namespaced and must not redefine the canonical capability.

<a id="section-6-6"></a>
## 6.6 Capability Is Not Model

A Model may support several Capabilities.

A Capability may be supported by several Models.

The relationship is many-to-many.

For example, one model may support:

- text.generate,

- text.summarise,

- text.classify,

- and reasoning.general.

Another model may support only:

- retrieval.embed.

The Capability Registry describes the operation.

The Model Registry describes the resource.

A Capability Support Declaration connects them.

<a id="section-6-7"></a>
## 6.7 Capability Is Not Agent

An Agent has:

- identity,

- role,

- memory access,

- authority,

- behavioural policy,

- and project relationships.

A Capability is an operation the Agent may request or provide.

Arnold may request:

- reasoning.training_plan,

- content.exercise_explanation,

- image.generate,

- and speech.synthesise.

Those capabilities do not define Arnold’s identity.

The same capabilities may be used by other agents under different project policies.

<a id="section-6-8"></a>
## 6.8 Capability Is Not Tool

A Tool is an executable implementation or action surface.

A Capability describes what the Tool can achieve.

For example:

Capability

media.convert.video_format

Tool

A local FFmpeg-based conversion utility.

The Tool may implement the Capability.

The Capability remains independent of the Tool.

<a id="section-6-9"></a>
## 6.9 Capability Is Not Workflow

A Workflow composes several steps.

A Capability represents one canonical operation or bounded result.

A workflow may require:

- research.search,

- research.verify_sources,

- text.script_generate,

- speech.synthesise,

- video.avatar_generate,

- media.caption_generate,

- and publication.prepare.

The Capability Registry defines the step contracts.

The Workflow defines how they are sequenced.

<a id="section-6-10"></a>
## 6.10 Capability Identity

Every Capability shall have a stable canonical identifier.

The identifier shall remain independent of:

- provider,

- model,

- project,

- display language,

- and current implementation.

A Capability may also have:

- display name,

- description,

- aliases,

- deprecated names,

- and translated labels.

The stable identifier is authoritative.

Display labels may change without changing the Capability identity.

<a id="section-6-11"></a>
## 6.11 Capability Naming Convention

Capability identifiers should use a structured namespace.

The recommended pattern is:

domain.operation

or, where additional precision is required:

domain.subdomain.operation

Examples include:

- text.generate

- text.summarise

- reasoning.general

- code.generate

- code.review

- image.generate

- image.edit

- video.text_to_video

- video.image_to_video

- speech.synthesise

- speech.transcribe

- retrieval.embed

- retrieval.rerank

- research.verify_sources

- media.character_consistency.evaluate

- publication.prepare

- publication.submit

Names shall be:

- provider-independent,

- concise,

- semantically stable,

- and specific enough for meaningful routing.

<a id="section-6-12"></a>
## 6.12 Canonical Naming Language

Canonical Capability identifiers shall be written in English.

User-facing interfaces may translate:

- titles,

- explanations,

- examples,

- and guidance.

Translation must not create a second technical identifier.

A Swedish interface may display:

Skapa tal från text

while the canonical identifier remains:

speech.synthesise

<a id="section-6-13"></a>
## 6.13 Capability Namespace

The Capability Registry shall support namespaces.

Namespaces help separate broad domains such as:

- text,

- reasoning,

- code,

- research,

- retrieval,

- image,

- design,

- video,

- speech,

- audio,

- music,

- document,

- data,

- tool,

- agent,

- workflow,

- publication,

- evaluation,

- safety,

- and infrastructure.

Namespaces do not imply service ownership.

They are semantic organisation.

<a id="section-6-14"></a>
## 6.14 Reserved Namespaces

Core Omnira Capability namespaces should be governed centrally.

Projects and providers shall not create conflicting core identifiers.

Reserved namespaces may include:

- omnira.*

- atlas.*

- system.*

- governance.*

- publication.*

- credential.*

- provider.*

Project-specific extensions should use a namespaced pattern such as:

project.familje_stunden.*

Provider-specific extensions should use:

provider.openart.*

Extensions shall not replace canonical core capabilities.

<a id="section-6-15"></a>
## 6.15 Capability Display Name

Each Capability should include a human-readable display name.

Examples include:

- Text Generation

- Image Editing

- Image-to-Video Animation

- Swedish Speech Synthesis

- Source Verification

- Character Consistency Evaluation

Display names may be localised.

They must not carry unique semantic meaning absent from the canonical contract.

<a id="section-6-16"></a>
## 6.16 Capability Description

Each Capability shall include a concise canonical description.

The description should state:

- what the capability does,

- what it does not do,

- and the boundary of expected responsibility.

For example:

video.image_to_video transforms one or more approved image inputs into a generated video output under declared motion, duration, quality and rights constraints.

It does not automatically include:

- narration,

- music,

- final editing,

- publication,

- or character-consistency guarantees

unless those are explicitly included in the Capability Version.

<a id="section-6-17"></a>
## 6.17 Capability Definition

A Capability Definition shall include or reference:

- capabilityId,

- namespace,

- canonical name,

- display name,

- description,

- Capability Version,

- modality,

- input contract,

- output contract,

- execution pattern,

- quality dimensions,

- risk class,

- side-effect class,

- authority requirements,

- data-placement considerations,

- rights considerations,

- evidence requirements,

- lifecycle state,

- ownership,

- and provenance.

Not every Capability requires every field.

Omissions must be deliberate and valid for the capability type.

<a id="section-6-18"></a>
## 6.18 Capability Version

A Capability Version defines one specific revision of the canonical contract.

It shall have stable identity separate from the Capability family.

A new Capability Version may be required when:

- input meaning changes,

- output meaning changes,

- quality semantics change,

- authority requirements change,

- risk classification changes,

- evidence requirements change,

- or compatibility expectations change materially.

Historical Executions must remain linked to the Capability Version used.

<a id="section-6-19"></a>
## 6.19 Semantic Versioning

Capability Versions should use a governed versioning strategy.

A semantic approach may distinguish:

Major version

Breaking change in meaning or compatibility.

Minor version

Backward-compatible addition or refinement.

Patch version

Correction that does not change operational meaning.

The exact format may differ.

The distinction between breaking and compatible change must remain explicit.

<a id="section-6-20"></a>
## 6.20 Capability Revision

A Capability Revision may represent metadata updates that do not create a new semantic contract.

Examples include:

- improved description,

- translated label,

- corrected documentation,

- or additional examples.

Revisions must not silently alter:

- input eligibility,

- output meaning,

- quality requirements,

- or authority.

Material semantic change requires a new Capability Version.

<a id="section-6-21"></a>
## 6.21 Capability Family

A Capability Family groups related operations.

For example:

video.generation

may be a family containing:

- video.text_to_video

- video.image_to_video

- video.video_to_video

- video.extend

- video.edit

- video.character_replace

A Capability Family may support discovery and user explanation.

It shall not be used as an executable Capability unless it has its own valid contract.

<a id="section-6-22"></a>
## 6.22 Abstract Capability

An Abstract Capability describes a broad desired outcome that requires further resolution.

Examples include:

- media.create

- research.perform

- content.produce

Abstract Capabilities may help intent interpretation.

They are not necessarily directly executable.

The Registry shall mark whether a Capability is:

- abstract,

- compositional,

- or executable.

<a id="section-6-23"></a>
## 6.23 Executable Capability

An Executable Capability has a contract precise enough for resource matching and execution planning.

It must define:

- valid inputs,

- expected outputs,

- mandatory constraints,

- and execution evidence.

An Executable Capability may still require decomposition by the planner when one provider call is insufficient.

<a id="section-6-24"></a>
## 6.24 Composite Capability

A Composite Capability represents a governed combination of lower-level capabilities.

For example:

media.episode_produce

may require:

- text.story_segment,

- image.reference_retrieve,

- video.image_to_video,

- speech.synthesise,

- audio.mix,

- video.compose,

- media.quality_evaluate,

- and publication.prepare.

Composite Capabilities shall define:

- required child capabilities,

- optional child capabilities,

- dependency rules,

- and Completion Contract.

They shall not hide consequential side effects.

<a id="section-6-25"></a>
## 6.25 Primitive Capability

A Primitive Capability represents the smallest canonical operation that the Fabric chooses to model independently.

Primitive does not necessarily mean one provider call.

It means the capability is not decomposed further at the canonical contract level for the current architecture.

What counts as primitive may evolve.

<a id="section-6-26"></a>
## 6.26 Capability Granularity

Capability definitions shall be neither too broad nor unnecessarily fragmented.

A Capability is too broad when resource eligibility cannot be determined meaningfully.

A Capability is too narrow when it only renames a provider parameter.

For example:

video.generate

may be too broad for reliable routing.

video.image_to_video.with_openart_motion_strength_07

is too provider-specific.

Appropriate granularity may be:

video.image_to_video

with constraints for:

- duration,

- aspect ratio,

- motion,

- reference support,

- and quality.

<a id="section-6-27"></a>
## 6.27 Capability Input Contract

Every Executable Capability shall define an Input Contract.

The Input Contract shall describe:

- accepted input types,

- required inputs,

- optional inputs,

- cardinality,

- format,

- size,

- classification limits,

- rights requirements,

- and validation rules.

The Input Contract shall remain canonical and provider-independent.

<a id="section-6-28"></a>
## 6.28 Input Type

Input Types may include:

- text,

- structured data,

- document,

- image,

- audio,

- video,

- code,

- repository reference,

- Asset reference,

- Data Item reference,

- Memory reference,

- tool state,

- or human instruction.

Each Input Type shall have a defined schema or media contract.

<a id="section-6-29"></a>
## 6.29 Required Input

A Required Input must be present for valid execution.

The Registry shall identify:

- input name,

- type,

- minimum count,

- format,

- and validation.

A resource cannot claim full support when it requires a missing input not represented in the Capability Contract.

<a id="section-6-30"></a>
## 6.30 Optional Input

An Optional Input may improve or modify execution.

Examples include:

- style reference,

- negative instruction,

- seed,

- brand profile,

- motion reference,

- pronunciation dictionary,

- or quality preference.

Optional inputs should declare:

- default behaviour,

- provider support variability,

- and whether absence changes quality.

<a id="section-6-31"></a>
## 6.31 Input Cardinality

Capabilities shall define whether inputs accept:

- exactly one,

- zero or one,

- one or more,

- bounded list,

- or unbounded collection subject to limits.

Examples include:

- one source image,

- up to five character references,

- one or more research documents,

- or a bounded set of code files.

Provider mappings may support narrower cardinality than the canonical Capability.

The limitation must be declared.

<a id="section-6-32"></a>
## 6.32 Input Format

The Registry shall define accepted canonical formats.

Examples include:

- UTF-8 text,

- Markdown,

- JSON,

- DOCX,

- PDF,

- PNG,

- JPEG,

- SVG,

- WAV,

- MP3,

- MP4,

- WebM,

- repository tree,

- or structured schema.

Adapters may perform format conversion where policy and quality permit.

Implicit conversion must be evidenced when it may affect meaning.

<a id="section-6-33"></a>
## 6.33 Input Size Constraints

Capability Definitions may declare:

- token limits,

- character limits,

- file size,

- image dimensions,

- duration,

- page count,

- media count,

- or repository scope.

The Registry may define canonical constraints.

Resource mappings may add narrower provider-specific limits.

The effective limit shall be the most restrictive applicable limit.

<a id="section-6-34"></a>
## 6.34 Input Classification Support

Capabilities may restrict which Data Classifications they can accept.

For example:

- publication.submit may accept Public or approved Project Internal packages.

- local.private_analysis may accept Local Only.

- external avatar generation may prohibit Confidential biometric data unless specifically approved.

Capability-level classification requirements shall be combined with resource-level placement policy.

<a id="section-6-35"></a>
## 6.35 Input Rights Requirements

Capabilities may require specific rights before execution.

Examples include:

- image editing requires modification rights,

- voice cloning requires voice consent,

- character animation requires rights to transform the reference asset,

- publication requires distribution rights,

- commercial music generation requires commercial-use eligibility.

Rights requirements shall be part of the Capability Contract.

<a id="section-6-36"></a>
## 6.36 Capability Output Contract

Every Executable Capability shall define an Output Contract.

It shall describe:

- output type,

- format,

- cardinality,

- semantic meaning,

- expected metadata,

- classification behaviour,

- provenance requirements,

- and completion evidence.

Provider output must be translated into this contract.

<a id="section-6-37"></a>
## 6.37 Output Type

Output Types may include:

- text,

- structured object,

- code,

- image,

- audio,

- video,

- embedding,

- ranking,

- evaluation,

- plan,

- decision support,

- tool receipt,

- or side-effect receipt.

A Capability may produce several Output Types.

Each must be explicit.

<a id="section-6-38"></a>
## 6.38 Output Cardinality

Capabilities shall declare whether they produce:

- one result,

- several variants,

- a stream,

- a batch,

- or a variable set.

Output count affects:

- cost,

- evaluation,

- storage,

- and Completion Contract.

<a id="section-6-39"></a>
## 6.39 Output Format Requirements

Capabilities may support one or more canonical output formats.

The Registry shall distinguish:

- native provider output,

- Fabric-normalised output,

- and post-processed output.

A Capability mapping must not claim native DOCX generation when the provider creates text that Omnira later converts into DOCX.

<a id="section-6-40"></a>
## 6.40 Output Classification Behaviour

The Capability Contract should define expected classification behaviour.

Possible behaviours include:

- inherit highest input classification,

- derive classification through policy,

- require explicit classification,

- or produce Public output only after approval.

Capabilities shall not automatically reduce classification.

<a id="section-6-41"></a>
## 6.41 Output Provenance Requirements

The Capability Registry shall define minimum provenance requirements.

A low-risk temporary summarisation may require:

- request,

- model,

- and timestamp.

A commercial video may require:

- source assets,

- prompts,

- provider,

- model,

- adapter,

- cost,

- rights,

- human review,

- and derivative chain.

Provenance requirements should be proportionate to consequence.

<a id="section-6-42"></a>
## 6.42 Output Acceptance Boundary

The Capability Contract shall define what technical evidence proves that an output was produced.

It may also reference a Quality Contract for acceptance.

Provider completion and Output acceptance shall remain separate.

A video file existing does not prove:

- character consistency,

- child appropriateness,

- or commercial usability.

<a id="section-6-43"></a>
## 6.43 Modality

Each Capability shall declare one or more Modalities.

Canonical Modalities may include:

- text,

- structured data,

- code,

- image,

- video,

- speech,

- audio,

- music,

- document,

- embedding,

- multimodal,

- tool action,

- agent action,

- and workflow action.

Capabilities may accept one modality and produce another.

<a id="section-6-44"></a>
## 6.44 Cross-Modal Capability

A Cross-Modal Capability converts or relates modalities.

Examples include:

- speech.transcribe,

- speech.synthesise,

- image.describe,

- video.caption,

- text_to_image,

- image_to_video,

- document.extract_structure,

- and audio_to_animation.

Cross-modal conversion shall preserve provenance and classification.

<a id="section-6-45"></a>
## 6.45 Multimodal Capability

A Multimodal Capability consumes or produces several modalities in one governed operation.

Examples include:

- analyse image and text together,

- answer questions over video and transcript,

- generate narrated visual story,

- evaluate audio-visual synchronisation.

Multimodal support must be declared precisely.

A text model that can receive one image is not automatically eligible for all multimodal capabilities.

<a id="section-6-46"></a>
## 6.46 Execution Pattern

Capabilities shall declare supported Execution Patterns.

Patterns may include:

- synchronous,

- asynchronous,

- streaming,

- interactive,

- batch,

- long-running,

- scheduled,

- human-assisted,

- local,

- or composite.

Execution pattern influences:

- state model,

- callbacks,

- retries,

- cancellation,

- and Completion Contract.

<a id="section-6-47"></a>
## 6.47 Synchronous Capability

A Synchronous Capability normally returns within one request-response interaction.

The Capability Definition should still account for:

- timeout,

- partial response,

- usage,

- and unknown outcome where possible.

Synchronous transport does not guarantee deterministic or immediate completion.

<a id="section-6-48"></a>
## 6.48 Asynchronous Capability

An Asynchronous Capability creates or submits work that completes later.

It shall require:

- Provider Job correlation,

- callback or polling strategy,

- durable state,

- cancellation behaviour,

- reconciliation,

- and unknown-outcome handling.

Video generation frequently belongs to this pattern.

<a id="section-6-49"></a>
## 6.49 Streaming Capability

A Streaming Capability produces incremental output.

It shall define:

- stream unit,

- ordering,

- interruption,

- partial-output handling,

- finalisation,

- and cost.

A partial stream is not automatically an accepted Output.

<a id="section-6-50"></a>
## 6.50 Interactive Capability

An Interactive Capability supports multiple turns or real-time feedback.

It shall define:

- session identity,

- context retention,

- authority duration,

- tool permissions,

- cost boundaries,

- and termination.

Interactive capability must not accumulate unrestricted context indefinitely.

<a id="section-6-51"></a>
## 6.51 Batch Capability

A Batch Capability processes several related items.

It shall define:

- item contract,

- maximum batch size,

- partial failure semantics,

- per-item output,

- cost attribution,

- and retry behaviour.

Batch success must not hide failed items.

<a id="section-6-52"></a>
## 6.52 Human-Assisted Capability

A Human-Assisted Capability requires a person to perform a material step.

The Registry shall declare:

- human role,

- required action,

- expected evidence,

- and automation maturity.

Human-assisted support is legitimate.

It must not be labelled as fully automated.

<a id="section-6-53"></a>
## 6.53 Side-Effect Capability

A Side-Effect Capability changes external or durable state.

Examples include:

- publication.submit,

- repository.commit,

- file.delete,

- message.send,

- provider.asset_create,

- schedule.create,

- configuration.modify.

Side-effect capabilities shall declare:

- action class,

- idempotency requirements,

- verification requirements,

- reversibility,

- and authority.

<a id="section-6-54"></a>
## 6.54 Read Capability

A Read Capability retrieves information without intentionally modifying external state.

Examples include:

- provider.asset_list,

- repository.read,

- memory.retrieve,

- research.search,

- provider.credit_balance_read.

Read access still requires:

- scope,

- privacy,

- and authority.

<a id="section-6-55"></a>
## 6.55 Generate Capability

A Generate Capability creates a new draft, media object, text result or provider-side asset.

Generation may consume credits and create durable provider state.

It is not equivalent to publication.

<a id="section-6-56"></a>
## 6.56 Modify Capability

A Modify Capability changes an existing object or asset.

It shall define:

- target version,

- mutation behaviour,

- overwrite or derivative semantics,

- and rollback.

Canonical assets should normally create new versions rather than destructive overwrite.

<a id="section-6-57"></a>
## 6.57 Delete Capability

A Delete Capability removes or requests removal of an object.

It shall define:

- deletion type,

- provider behaviour,

- retention effect,

- confirmation,

- reversibility,

- and verification.

Delete capabilities require stronger authority.

<a id="section-6-58"></a>
## 6.58 Publish Capability

A Publish Capability makes content externally visible or distributes it to an external audience.

It shall define:

- target platform,

- account,

- publication state,

- scheduling,

- verification,

- and removal behaviour.

Publishing is consequential and must remain separate from generation.

<a id="section-6-59"></a>
## 6.59 Administrative Capability

An Administrative Capability changes provider, account, policy, credential, registry or platform configuration.

Examples include:

- provider.connect,

- provider.disconnect,

- model.activate,

- routing_policy.modify,

- credential.rotate,

- capability.deprecate.

Administrative capability requires privileged authority and enhanced evidence.

<a id="section-6-60"></a>
## 6.60 Capability Risk Classification

Every Capability shall have a Risk Classification.

Risk may depend on:

- side effects,

- data sensitivity,

- public consequence,

- financial consequence,

- rights,

- identity,

- reversibility,

- and potential harm.

Risk classes may include:

- minimal,

- low,

- moderate,

- high,

- critical.

Risk classification shall guide:

- approval,

- evaluation,

- evidence,

- and monitoring.

<a id="section-6-61"></a>
## 6.61 Minimal-Risk Capability

Minimal-risk capabilities may include:

- local formatting,

- non-sensitive classification,

- preview generation with no external side effect,

- or simulation.

Minimal risk does not remove scope or evidence requirements entirely.

<a id="section-6-62"></a>
## 6.62 Low-Risk Capability

Low-risk capabilities may include:

- internal draft generation,

- public-source summarisation,

- or temporary image ideation.

Low-risk execution may receive broader bounded autonomy.

<a id="section-6-63"></a>
## 6.63 Moderate-Risk Capability

Moderate-risk capabilities may involve:

- paid generation,

- project-internal assets,

- commercial drafts,

- or external provider processing of ordinary project data.

They may require budget approval and stronger provenance.

<a id="section-6-64"></a>
## 6.64 High-Risk Capability

High-risk capabilities may involve:

- public publication,

- voice cloning,

- confidential data,

- security-sensitive code changes,

- canonical asset replacement,

- or substantial spending.

They normally require explicit approval and independent evaluation.

<a id="section-6-65"></a>
## 6.65 Critical Capability

Critical capabilities may affect:

- tenant administration,

- credential control,

- destructive deletion,

- production deployment,

- large financial commitment,

- or platform-wide policy.

Critical capabilities require the strongest authority and evidence.

<a id="section-6-66"></a>
## 6.66 Capability Consequence Class

Risk and consequence may be represented separately.

A capability may be:

- non-consequential,

- reversible,

- externally consequential,

- financially consequential,

- publicly consequential,

- destructive,

- or administrative.

Consequence Class helps determine:

- approval,

- idempotency,

- compensation,

- and verification.

<a id="section-6-67"></a>
## 6.67 Capability Reversibility

Capabilities shall declare reversibility.

Possible values include:

- fully reversible,

- partially reversible,

- compensatable,

- irreversible,

- unknown.

Generating a draft may be reversible through deletion.

Publishing publicly may be only partially reversible because copies or audience exposure may persist.

Reversibility claims shall be honest.

<a id="section-6-68"></a>
## 6.68 Capability Idempotency Profile

Capabilities shall declare expected idempotency properties.

Possible profiles include:

- naturally idempotent,

- idempotent with key,

- deduplicatable,

- non-idempotent,

- provider-dependent,

- unknown.

Retry policy shall use this information.

<a id="section-6-69"></a>
## 6.69 Capability Cost Profile

Capabilities may declare general Cost Profiles.

Examples include:

- zero incremental local,

- low,

- moderate,

- high,

- highly variable,

- provider-dependent,

- usage-metered,

- subscription-included.

Cost Profile is descriptive.

Actual cost is determined by resource, account and usage.

<a id="section-6-70"></a>
## 6.70 Capability Latency Profile

Capabilities may declare typical Latency Profiles such as:

- real-time,

- interactive,

- short,

- long-running,

- asynchronous,

- highly variable.

Latency Profile helps planning.

It does not replace current provider health and queue evidence.

<a id="section-6-71"></a>
## 6.71 Capability Capacity Profile

Capabilities may require different capacity properties.

Examples include:

- token context,

- image resolution,

- video duration,

- audio duration,

- batch size,

- tool-call depth,

- concurrency,

- or GPU memory.

The Capability Contract shall define required dimensions.

<a id="section-6-72"></a>
## 6.72 Capability Quality Dimensions

Every Capability shall define relevant Quality Dimensions.

Examples include:

Text

- correctness,

- relevance,

- coherence,

- tone,

- completeness.

Research

- source credibility,

- recency,

- citation coverage,

- uncertainty handling.

Code

- correctness,

- testability,

- security,

- maintainability,

- architecture conformance.

Image

- composition,

- character consistency,

- text accuracy,

- brand alignment,

- resolution.

Video

- temporal coherence,

- motion quality,

- character identity,

- artefact absence,

- audio synchronisation.

Speech

- intelligibility,

- naturalness,

- pronunciation,

- tone,

- identity consistency.

<a id="section-6-73"></a>
## 6.73 Mandatory Quality Dimension

A Mandatory Quality Dimension must meet the defined threshold for acceptance.

The Registry shall identify whether a dimension is:

- mandatory,

- recommended,

- optional,

- or informational.

A resource cannot be considered fully compatible when it cannot support a mandatory dimension.

<a id="section-6-74"></a>
## 6.74 Quality Measurement Type

Quality Dimensions may be evaluated through:

- deterministic test,

- quantitative metric,

- model evaluator,

- human review,

- external performance metric,

- or composite method.

The Registry should recommend valid evaluation types.

<a id="section-6-75"></a>
## 6.75 Quality Threshold

Capability Versions may define:

- default minimum threshold,

- project-overridable threshold,

- or request-defined threshold.

Project or request policy may raise the threshold.

It must not lower mandatory platform safety thresholds.

<a id="section-6-76"></a>
## 6.76 Capability Evaluation Requirement

A Capability may require evaluation before acceptance.

The Registry shall define:

- evaluation type,

- evaluator independence,

- required evidence,

- and acceptance authority.

For child-facing animation, human review may be mandatory.

For JSON extraction, deterministic schema validation may be sufficient.

<a id="section-6-77"></a>
## 6.77 Capability Safety Requirements

Capabilities may define safety requirements.

Examples include:

- child-facing content review,

- prompt-injection resistance,

- malware scanning,

- harmful-content controls,

- external-link validation,

- or secure code review.

Safety requirements must remain separate from provider marketing claims.

<a id="section-6-78"></a>
## 6.78 Capability Data Placement Requirements

Capabilities may impose placement constraints.

Examples include:

- Local Only analysis,

- region-restricted speech processing,

- no external biometric processing,

- private code review,

- public-source research.

The Capability Contract may define default placement posture.

Request and policy may impose stricter placement.

<a id="section-6-79"></a>
## 6.79 Capability Privacy Profile

A Capability Privacy Profile may describe:

- typical sensitive data,

- provider retention risk,

- training-use concerns,

- identity exposure,

- and recommended minimisation.

It supports policy evaluation and user explanation.

<a id="section-6-80"></a>
## 6.80 Capability Rights Profile

The Capability Registry shall define rights-related requirements for each Capability.

Examples include:

- modification rights,

- transformation rights,

- commercial-use requirement,

- attribution,

- consent,

- publication rights,

- derivative rights.

The Registry does not provide legal ownership itself.

It defines what must be verified.

<a id="section-6-81"></a>
## 6.81 Capability Consent Profile

Capabilities involving:

- voice,

- likeness,

- biometric transformation,

- personal data,

- or child-related content

may require explicit Consent Records.

The Consent Profile shall define:

- required subject,

- permitted use,

- commercial scope,

- expiry,

- and revocation behaviour.

<a id="section-6-82"></a>
## 6.82 Capability Authority Profile

Each Capability shall declare minimum Authority requirements.

The profile may include:

- permitted Principal types,

- required role,

- approval class,

- budget authority,

- project ownership,

- or administrative permission.

A resource being available does not imply that all Principals may use the Capability.

<a id="section-6-83"></a>
## 6.83 Capability Approval Profile

The Registry may define default Approval behaviour such as:

- no separate approval,

- approval required for paid execution,

- approval required for external processing,

- approval required for publication,

- approval required for destructive action,

- or approval required above threshold.

Project and tenant policy may be stricter.

<a id="section-6-84"></a>
## 6.84 Capability Evidence Profile

Each Capability shall define minimum evidence requirements.

Evidence may include:

- request reference,

- policy decision,

- selected resource,

- provider receipt,

- output checksum,

- evaluation,

- cost,

- approval,

- side-effect receipt,

- and verification.

High-risk Capabilities require stronger evidence.

<a id="section-6-85"></a>
## 6.85 Capability Retention Profile

Capabilities may define default retention for:

- execution records,

- temporary outputs,

- provider jobs,

- rejected attempts,

- and provenance.

Retention remains subject to:

- tenant policy,

- classification,

- legal requirements,

- and incidents.

<a id="section-6-86"></a>
## 6.86 Capability Observability Profile

The Registry should define which operational metrics matter.

Examples include:

- success rate,

- latency,

- queue time,

- retry rate,

- unknown outcomes,

- cost,

- quality failure,

- human rejection,

- provider fallback,

- and asset acceptance.

Metrics should remain capability-specific.

<a id="section-6-87"></a>
## 6.87 Capability Availability State

A Capability shall have an architectural Lifecycle State and an operational Availability State.

Lifecycle may be:

- proposed,

- experimental,

- approved,

- active,

- deprecated,

- retired.

Availability may be:

- available,

- partially available,

- restricted,

- degraded,

- unavailable,

- unknown.

These states shall remain separate.

<a id="section-6-88"></a>
## 6.88 Proposed Capability

Proposed means the concept exists but has not yet completed specification and approval.

A Proposed Capability must not be used for governed production execution.

<a id="section-6-89"></a>
## 6.89 Draft Capability

Draft means the contract is being authored.

It may be used for design discussion or simulation.

Draft status shall not imply resource support.

<a id="section-6-90"></a>
## 6.90 Experimental Capability

Experimental means the Capability Contract is sufficiently defined for controlled testing.

Experimental capabilities may have:

- restricted projects,

- sandbox-only execution,

- limited data classes,

- low spending limits,

- and mandatory review.

<a id="section-6-91"></a>
## 6.91 Approved Capability

Approved means the canonical contract has passed architecture approval.

Approved does not guarantee an active resource mapping.

<a id="section-6-92"></a>
## 6.92 Active Capability

Active means the Capability is approved and available through at least one production-admitted resource for an authorised scope.

Active state should identify:

- supported environments,

- supported projects or tenants,

- and current limitations.

<a id="section-6-93"></a>
## 6.93 Restricted Capability

Restricted means the Capability is active only under additional constraints.

Restrictions may include:

- selected projects,

- approved users,

- local execution,

- low volume,

- mandatory approval,

- or specific providers.

<a id="section-6-94"></a>
## 6.94 Degraded Capability

Degraded means the Capability remains usable but cannot meet its ordinary full contract or service expectation.

Examples include:

- fewer providers,

- longer latency,

- reduced resolution,

- temporary manual operation,

- or disabled fallback.

Degradation must be visible.

<a id="section-6-95"></a>
## 6.95 Deprecated Capability

Deprecated means the Capability remains historically interpretable but should not be used for new requests.

Deprecation shall identify:

- replacement,

- effective date,

- migration guidance,

- and retirement plan.

<a id="section-6-96"></a>
## 6.96 Retired Capability

Retired means the Capability cannot be selected for new execution.

Historical objects and evidence must remain resolvable.

<a id="section-6-97"></a>
## 6.97 Unavailable Capability

Unavailable means no eligible production resource currently satisfies the Capability for the request scope.

The canonical Capability may still exist.

Unavailable must preserve reason such as:

- no resource mapping,

- provider outage,

- policy restriction,

- account exhaustion,

- missing consent,

- or environment limitation.

<a id="section-6-98"></a>
## 6.98 Unknown Capability Availability

Unknown means Omnira cannot currently determine availability with sufficient confidence.

The system shall not present Unknown as Available.

<a id="section-6-99"></a>
## 6.99 Capability Owner

Every core Capability shall have an accountable Owner.

The Owner may be a platform architecture or governance role.

Ownership includes responsibility for:

- definition,

- versioning,

- review,

- lifecycle,

- conformance expectations,

- and deprecation.

The Owner does not automatically control every execution.

<a id="section-6-100"></a>
## 6.100 Capability Steward

A Capability Steward may maintain operational metadata such as:

- mappings,

- documentation,

- evaluation evidence,

- and lifecycle proposals.

Stewardship may be delegated.

Canonical approval remains governed.

<a id="section-6-101"></a>
## 6.101 Capability Provenance

Capability Definitions shall preserve provenance.

Provenance may include:

- original proposal,

- architecture decision,

- author,

- review,

- approval,

- change history,

- and related book section.

A Capability must not appear in production without a traceable origin.

<a id="section-6-102"></a>
## 6.102 Capability Registry Entry

A Capability Registry Entry should contain:

- Capability identity,

- active Capability Versions,

- lifecycle,

- owner,

- namespace,

- description,

- input and output contracts,

- modality,

- risk,

- authority,

- quality,

- evidence,

- privacy,

- rights,

- placement,

- supported execution patterns,

- aliases,

- dependencies,

- resource mappings,

- and documentation.

The Registry Entry may reference other canonical objects rather than embedding all details.

<a id="section-6-103"></a>
## 6.103 Registry Entry Integrity

Registry Entries shall be:

- versioned,

- attributable,

- testable,

- and protected from uncontrolled modification.

Material changes require:

- review,

- migration impact,

- and effective date.

<a id="section-6-104"></a>
## 6.104 Registry Source of Truth

The Capability Registry shall have an authoritative source.

Derived views may exist in:

- database,

- configuration cache,

- documentation,

- APIs,

- Atlas Knowledge,

- or Intelligence Graph.

No derived view shall silently become the source of truth.

The authoritative source must be known and versioned.

<a id="section-6-105"></a>
## 6.105 Registry API

The Fabric should expose a governed Capability Registry API.

The API may support:

- retrieve Capability,

- list Capabilities,

- query by modality,

- query by lifecycle,

- resolve version,

- discover required inputs,

- discover supported resources,

- validate Capability Request,

- and inspect current availability.

Administrative mutation shall require stronger authority.

<a id="section-6-106"></a>
## 6.106 Capability Discovery

Capability Discovery allows callers to determine what Omnira understands.

Discovery may be used by:

- Atlas,

- Managers,

- agents,

- workflows,

- developers,

- operator interfaces,

- and approval systems.

Discovery shall respect:

- tenant,

- project,

- environment,

- authority,

- and capability visibility.

Knowing that a Capability exists does not grant permission to use it.

<a id="section-6-107"></a>
## 6.107 Human Capability Discovery

Human-facing discovery should use understandable categories and examples.

A user may search for:

- create a video,

- generate Swedish narration,

- analyse a document,

- or publish a post.

The interface may map these phrases to canonical Capabilities.

It should not require knowledge of technical identifiers.

<a id="section-6-108"></a>
## 6.108 Machine Capability Discovery

Machine consumers shall receive structured Capability Definitions.

A machine-readable response should include:

- Capability ID,

- version,

- input schema,

- output schema,

- constraints,

- risk,

- approval requirements,

- and current availability.

Machine discovery must not include raw credentials or unrestricted provider details.

<a id="section-6-109"></a>
## 6.109 Capability Search

Search shall support:

- exact identifier,

- alias,

- description,

- modality,

- input type,

- output type,

- quality dimension,

- risk,

- and lifecycle.

Search results shall indicate confidence when natural-language matching is used.

<a id="section-6-110"></a>
## 6.110 Capability Alias

Aliases may improve discovery.

Examples include:

- TTS for speech.synthesise,

- STT for speech.transcribe,

- image animation for video.image_to_video.

Aliases shall not become independent identifiers.

Ambiguous aliases should require contextual resolution.

<a id="section-6-111"></a>
## 6.111 Deprecated Alias

When a Capability is renamed, the old identifier or alias may remain as a Deprecated Alias.

Requests using it should:

- resolve to the supported Capability Version where safe,

- emit migration guidance,

- and preserve original input for provenance.

<a id="section-6-112"></a>
## 6.112 Capability Recommendation

The Fabric may recommend Capabilities based on Intent.

For example:

Intent

Create an animated story episode.

Recommended Capabilities

- text.story_segment

- asset.reference_retrieve

- video.image_to_video

- speech.synthesise

- audio.mix

- video.compose

- media.quality_evaluate

- publication.prepare

Recommendations are planning assistance.

They are not authority.

<a id="section-6-113"></a>
## 6.113 Capability Resolution

Capability Resolution maps:

- user language,

- agent request,

- workflow step,

- or legacy identifier

to one or more canonical Capabilities.

Resolution shall preserve:

- original expression,

- selected Capability,

- confidence,

- alternatives,

- and unresolved ambiguity.

<a id="section-6-114"></a>
## 6.114 Ambiguous Capability Resolution

When one expression maps to several materially different Capabilities, the system should:

- use context,

- present alternatives,

- ask focused clarification,

- or defer the choice to planning.

For example:

“Make a video”

may mean:

- video.text_to_video,

- video.image_to_video,

- video.compose,

- video.avatar_generate,

- or media.motion_graphics_create.

The Fabric shall not guess when the difference affects cost or outcome materially.

<a id="section-6-115"></a>
## 6.115 Capability Dependency

Capabilities may depend on other Capabilities.

Examples include:

- video.compose may require media.decode and audio.mix.

- publication.submit may require publication.prepare.

- media.character_consistency.evaluate may require image.compare or video.frame_extract.

- research.verify_sources may require research.search and document.retrieve.

Dependencies shall be explicit.

<a id="section-6-116"></a>
## 6.116 Mandatory Dependency

A Mandatory Dependency must be available for the parent Capability to execute.

The Registry shall define:

- dependency version,

- ordering,

- and failure behaviour.

<a id="section-6-117"></a>
## 6.117 Optional Dependency

An Optional Dependency improves execution but is not required for minimum capability support.

Optional dependency omission must be represented in the effective execution contract.

<a id="section-6-118"></a>
## 6.118 Conditional Dependency

A Conditional Dependency applies only under defined conditions.

Examples include:

- speech.synthesise requires consent validation only when a cloned voice is used.

- publication.prepare requires subtitle generation only when the target channel requires captions.

- image.generate requires text-rendering evaluation only when the image contains visible text.

<a id="section-6-119"></a>
## 6.119 Capability Alternative

Capabilities may be declared alternatives when they can satisfy the same higher-level requirement under different conditions.

For example:

- video.image_to_video,

- media.motion_comic_create,

- and video.human_assisted_edit

may be alternatives for a visual storytelling step.

Alternative relationships must define:

- equivalence boundary,

- quality difference,

- cost difference,

- and approval impact.

<a id="section-6-120"></a>
## 6.120 Capability Superset

One Capability may be a superset of another.

For example, a multimodal model may support:

- text.generate,

- image.describe,

- and reasoning.multimodal.

Superset relationships shall not imply that every implementation of the broader Capability meets all specialised quality contracts.

<a id="section-6-121"></a>
## 6.121 Capability Specialisation

A specialised Capability refines a broader Capability.

Examples include:

speech.synthesise

specialised into:

- speech.synthesise.swedish

- speech.synthesise.cloned_voice

- speech.synthesise.realtime

Specialisation should be used only when the semantic contract differs materially.

Language or configuration may otherwise remain constraints.

<a id="section-6-122"></a>
## 6.122 Parameter Versus Capability

The Registry shall distinguish a Capability from a parameter.

Examples:

Capability

speech.synthesise

Parameters

- language,

- voice,

- speed,

- format.

A new Capability is not required for every language or setting unless the governance, input, output or risk contract changes materially.

<a id="section-6-123"></a>
## 6.123 Constraint Versus Capability

A constraint narrows execution.

It is not automatically a Capability.

Examples include:

- maximum cost,

- Local Only,

- Swedish language,

- 16:9 aspect ratio,

- no provider retention.

Capabilities define operations.

Constraints define acceptable execution.

<a id="section-6-124"></a>
## 6.124 Capability Feature

A Capability Feature describes optional support within a Capability.

For video.image_to_video, features may include:

- character reference support,

- motion reference,

- camera control,

- lip sync,

- first and last frame,

- transparent background,

- or seed control.

Features shall be declared by Resource Support Mappings.

<a id="section-6-125"></a>
## 6.125 Mandatory Feature

A request may require one or more Capability Features.

A resource that supports the base Capability but lacks a mandatory Feature is ineligible.

For Nova and Pling, character reference support may be mandatory for selected scenes.

<a id="section-6-126"></a>
## 6.126 Optional Feature

An Optional Feature may improve output.

The planner may prefer resources supporting it.

It must not reject otherwise eligible resources unless the request requires the Feature.

<a id="section-6-127"></a>
## 6.127 Capability Constraint Schema

Each Capability may define valid constraint fields.

For example, video.image_to_video may support:

- durationSeconds,

- aspectRatio,

- resolution,

- motionStrength,

- characterReferences,

- cameraInstruction,

- commercialUseRequired,

- maximumCost,

- and routingProfile.

Constraint schemas shall remain canonical.

<a id="section-6-128"></a>
## 6.128 Unsupported Constraint

When a Resource cannot satisfy one requested constraint, the Capability Support Mapping shall report:

- unsupported,

- partially supported,

- requires transformation,

- requires manual step,

- or unknown.

It must not silently ignore the constraint.

<a id="section-6-129"></a>
## 6.129 Capability Support Declaration

A Capability Support Declaration connects a Resource to a Capability Version.

The Resource may be:

- Model Version,

- Tool,

- External Agent Resource,

- Runtime Node,

- Workflow,

- or human-assisted provider process.

The declaration shall include:

- support status,

- supported Features,

- supported constraints,

- limits,

- quality evidence,

- execution pattern,

- pricing reference,

- known defects,

- and conformance state.

<a id="section-6-130"></a>
## 6.130 Claimed Support

Claimed Support means a provider or documentation states that the resource supports the Capability.

Claimed Support is not verified support.

It may be used for discovery or experimentation.

Production routing should require stronger evidence where consequence warrants it.

<a id="section-6-131"></a>
## 6.131 Observed Support

Observed Support means Omnira has successfully executed the Capability under known conditions.

Observed support should record:

- test,

- date,

- version,

- environment,

- inputs,

- outputs,

- and limitations.

One observed success may not prove full conformance.

<a id="section-6-132"></a>
## 6.132 Verified Support

Verified Support means the resource has passed the applicable conformance and quality checks for a defined scope.

Verification shall be:

- Capability Version-specific,

- Resource Version-specific,

- Adapter Version-specific,

- and environment-aware.

Material provider change may invalidate verification.

<a id="section-6-133"></a>
## 6.133 Restricted Support

Restricted Support means the resource supports the Capability only under declared limits.

Examples include:

- maximum five-second video,

- English speech only,

- no commercial use,

- public data only,

- specific project,

- or human review required.

Restrictions must remain visible to routing.

<a id="section-6-134"></a>
## 6.134 Partial Support

Partial Support means the resource satisfies some but not all canonical requirements.

Partial Support may be usable only when:

- the request does not require unsupported elements,

- an approved transformation fills the gap,

- or the planner composes multiple resources.

Partial must not be presented as full support.

<a id="section-6-135"></a>
## 6.135 Unsupported Capability

Unsupported means the resource cannot satisfy the Capability contract.

Unsupported resources shall not be selected.

Historical unsupported evidence may remain for future review.

<a id="section-6-136"></a>
## 6.136 Unknown Support

Unknown Support means Omnira lacks sufficient evidence.

Unknown may be permitted in sandbox experiments.

It should not be treated as production-verified support.

<a id="section-6-137"></a>
## 6.137 Capability Support Scope

Support declarations shall include Scope.

A resource may be verified for:

- one environment,

- one provider account,

- one region,

- one data class,

- one project,

- or one quality tier.

Support shall not be generalised beyond evidence.

<a id="section-6-138"></a>
## 6.138 Support Validity Period

Support evidence may expire.

Reasons include:

- model updates,

- provider API changes,

- adapter changes,

- pricing changes,

- terms changes,

- or quality drift.

The Registry shall support review and expiry dates.

<a id="section-6-139"></a>
## 6.139 Support Confidence

Support may include confidence based on evidence.

Confidence must not replace conformance state.

High confidence in provider marketing is not equivalent to verified support.

<a id="section-6-140"></a>
## 6.140 Capability Compatibility

Compatibility determines whether a request and a resource can satisfy one another.

Compatibility shall consider:

- Capability Version,

- input type,

- output type,

- required Features,

- constraints,

- quality,

- data placement,

- rights,

- authority,

- cost,

- latency,

- capacity,

- and execution pattern.

Compatibility is broader than technical API support.

<a id="section-6-141"></a>
## 6.141 Structural Compatibility

Structural Compatibility checks:

- input schemas,

- output schemas,

- formats,

- cardinality,

- and parameter support.

Structural compatibility does not prove quality or policy eligibility.

<a id="section-6-142"></a>
## 6.142 Semantic Compatibility

Semantic Compatibility checks whether the resource’s result meaning matches the Capability Contract.

A generic image model may structurally output PNG.

It may still be semantically incompatible with:

- character-consistent image generation,

- precise text rendering,

- or regulated medical illustration.

<a id="section-6-143"></a>
## 6.143 Policy Compatibility

Policy Compatibility determines whether the resource may be used under:

- tenant,

- project,

- data,

- rights,

- and authority rules.

A technically capable provider may remain policy-incompatible.

<a id="section-6-144"></a>
## 6.144 Quality Compatibility

Quality Compatibility determines whether evidence supports the required Quality Contract.

A low-resolution model may support image generation but fail a print-quality requirement.

<a id="section-6-145"></a>
## 6.145 Economic Compatibility

Economic Compatibility checks whether expected cost fits:

- request budget,

- provider account,

- credit availability,

- and permitted variance.

A capable resource may be economically ineligible.

<a id="section-6-146"></a>
## 6.146 Temporal Compatibility

Temporal Compatibility checks:

- expected latency,

- provider queue,

- deadline,

- schedule,

- and review time.

A high-quality provider may be incompatible with a hard deadline.

<a id="section-6-147"></a>
## 6.147 Rights Compatibility

Rights Compatibility checks:

- provider terms,

- input rights,

- output rights,

- commercial use,

- attribution,

- and consent.

Rights incompatibility must fail closed where required.

<a id="section-6-148"></a>
## 6.148 Placement Compatibility

Placement Compatibility checks whether the resource can execute in an allowed location.

A Local Only request requires:

- eligible local Runtime Node,

- compatible Model Deployment,

- and local Adapter.

External cloud support is irrelevant to that request.

<a id="section-6-149"></a>
## 6.149 Compatibility Decision

A Compatibility Decision shall record:

- request,

- Capability Version,

- resource,

- supported constraints,

- unsupported constraints,

- quality result,

- policy result,

- cost result,

- placement result,

- final decision,

- and explanation.

Compatibility may be:

- compatible,

- compatible with conditions,

- incompatible,

- unresolved,

- or requires transformation.

<a id="section-6-150"></a>
## 6.150 Transformation Requirement

A resource may require transformation to satisfy the Capability.

Examples include:

- DOCX converted to text before analysis,

- provider video converted to MP4,

- image resized,

- long document chunked,

- or output translated.

Transformations shall be explicit capabilities or governed adapter behaviour.

Material transformation must preserve provenance.

<a id="section-6-151"></a>
## 6.151 Capability Composition for Compatibility

When no single resource satisfies the full Capability, the planner may compose resources.

For example:

- one model generates an image,

- another evaluates character consistency,

- a local tool corrects format,

- and a human reviewer approves.

Composition must still satisfy the original Capability Contract.

The Capability Registry defines what Omnira understands.

The Provider Registry defines who supplies resources.

- Adapter Capability Mappings,

One Tool may implement several Capabilities.

<a id="section-6-195"></a>
## 6.195 Missing Capability

A Missing Capability is an operation requested by the user that the Registry cannot resolve.

The Fabric should record:

- original intent,

- project,

- requested outcome,

- urgency,

- likely domain,

- and possible alternatives.

Missing Capability records support roadmap planning.

<a id="section-6-196"></a>
## 6.196 Capability Gap

A Capability Gap occurs when:

- the Capability exists,

- but no eligible resource satisfies current requirements.

Gaps may be caused by:

- no provider,

- no local model,

- rights conflict,

- insufficient quality,

- cost,

- data placement,

- or missing integration.

The system should distinguish missing definition from missing execution support.

<a id="section-6-197"></a>
## 6.197 Capability Gap Resolution

Possible resolutions include:

- add provider mapping,

- add local resource,

- create Adapter,

- refine Capability,

- use composite execution,

- use human-assisted workflow,

- or decline the request.

Gap resolution must not weaken mandatory constraints silently.

<a id="section-6-198"></a>
## 6.198 Human-Assisted Gap Bridge

When automation is unavailable, a Human-Assisted Capability may temporarily bridge the gap.

For example:

- Atlas prepares OpenArt scene instructions,

- a human runs Director manually,

- output is uploaded,

- provenance and cost are recorded,

- and quality review continues in Omnira.

The Registry shall label the Capability maturity honestly.

<a id="section-6-199"></a>
## 6.199 Capability Fallback

Fallback occurs between resources supporting the same Capability or an approved alternative Capability.

The Registry shall expose:

- equivalent resources,

- partial alternatives,

- and prohibited substitutions.

Fallback remains subject to the original request.

<a id="section-6-200"></a>
## 6.200 Capability Degradation

A degraded capability may offer reduced:

- quality,

- speed,

- resolution,

- duration,

- automation,

- or provider diversity.

- previous version,

<a id="section-6-236"></a>
## 6.236 Stage 1 Acceptance Tests

Representative tests should include:

1. Capability identifiers remain provider-independent.

2. Unknown Capability is rejected.

3. Retired Capability cannot be selected.

4. Deprecated Capability returns migration guidance.

5. Input schema is validated.

6. Output schema is preserved.

7. Required Features affect eligibility.

8. Provider claims do not equal verified support.

9. Support is version-specific.

10. One Capability may map to several resources.

11. One resource may support several Capabilities.

12. Resource health does not override policy.

13. Available Capability state reflects at least one eligible resource.

14. Local Only requests exclude external resources.

15. Paid capabilities expose cost requirements.

16. Side-effect Capabilities require separate authority.

17. Publication remains distinct from generation.

18. Capability changes are versioned.

19. Historical Executions resolve old Capability Versions.

20. Missing Capability demand can be recorded.

<a id="section-6-237"></a>
## 6.237 Stage 1 Security Tests

Representative security tests should include:

1. Capability discovery does not grant execution permission.

2. Project-restricted Capabilities remain project-scoped.

3. Administrative Capability mutation requires privileged authority.

4. Provider Adapter cannot self-activate unrestricted Capability support.

5. Secret values never appear in Capability entries.

6. Capability search respects tenant visibility.

7. Cross-project Capability access requires explicit authority.

8. External content cannot redefine Capability contracts.

9. Unknown classification does not route externally.

10. Manual Capability maturity is represented honestly.

<a id="section-6-238"></a>
## 6.238 Stage 1 Conformance Tests

Representative conformance tests should include:

1. Provider-specific operation maps to canonical Capability.

2. Unsupported constraint produces incompatibility.

3. Partial Support is not treated as full support.

4. Capability Version mismatch is detected.

5. Adapter Version is recorded.

6. Output provenance references Capability Version.

7. Quality dimensions are Capability-specific.

8. Cost evidence remains resource-specific.

9. Resource fallback preserves Capability contract.

10. Capability availability reports freshness.

<a id="section-6-279"></a>
## 6.279 Capability Registry Success Criteria

The Capability Registry succeeds when:

- callers request outcomes without provider coupling,

- new providers can map to existing Capabilities,

- resource support can be compared honestly,

- policies can target stable operations,

- quality remains task-specific,

- availability is represented truthfully,

- historical Executions remain interpretable,

- and project workflows survive provider change.

<a id="section-6-280"></a>
## 6.280 Capability Registry Failure Conditions

The Registry is non-conformant when:

- provider names become canonical Capability identifiers,

- Capabilities lack input or output contracts,

- availability is treated as one global boolean,

- claimed support is treated as verified support,

- versions are rewritten,

- project scope is absent,

- capability discovery grants authority,

- manual execution is presented as autonomous,

- or runtime systems bypass Registry validation.

<a id="section-6-281"></a>
## 6.281 Canonical Capability Contract

The following requirements define the canonical Capability contract:

1. Every Capability SHALL have stable provider-independent identity.

2. Capability identifiers SHALL use governed namespaces.

3. Canonical identifiers SHALL remain language-independent.

4. Every Executable Capability SHALL have a versioned Input Contract.

5. Every Executable Capability SHALL have a versioned Output Contract.

6. Capabilities SHALL declare modality.

7. Capabilities SHALL declare execution pattern.

8. Capabilities SHALL declare risk and consequence.

9. Capabilities SHALL declare relevant Quality Dimensions.

10. Capabilities SHALL declare minimum evidence requirements.

11. Capabilities SHALL declare applicable authority requirements.

12. Capabilities SHALL declare data-placement considerations.

13. Capabilities SHALL declare rights and consent requirements where applicable.

14. Capabilities SHALL remain distinct from Providers, Models, Agents, Tools and Workflows.

15. Provider-specific behaviour SHALL remain in Adapters or namespaced extensions.

16. Capability Versions used by historical Executions SHALL remain interpretable.

17. Material semantic changes SHALL create new Capability Versions.

18. Claimed support SHALL remain distinct from verified support.

19. Partial support SHALL remain distinct from full support.

20. Availability SHALL remain distinct from lifecycle.

21. Capability discovery SHALL NOT grant execution authority.

22. Capability support SHALL be scoped and version-specific.

23. Resource compatibility SHALL include policy, quality, rights, placement and cost.

24. Unsupported constraints SHALL NOT be silently ignored.

25. Human-assisted execution SHALL be represented honestly.

26. Side-effect Capabilities SHALL declare authority and verification requirements.

27. Publication SHALL remain separate from generation.

28. Local resources SHALL be first-class Capability providers.

29. Capability changes SHALL be attributable and versioned.

30. Capability deprecation SHALL include migration guidance.

<a id="section-6-282"></a>
## 6.282 Canonical Registry Contract

The following requirements define the canonical Capability Registry contract:

1. The Capability Registry SHALL be the authoritative catalogue of canonical Capability definitions.

2. The Registry SHALL support versioned Capability entries.

3. The Registry SHALL preserve lifecycle history.

4. The Registry SHALL support Resource Support Mappings.

5. The Registry SHALL preserve support evidence.

6. The Registry SHALL distinguish architectural definition from operational availability.

7. The Registry SHALL expose governed discovery.

8. The Registry SHALL support request validation.

9. The Registry SHALL support compatibility evaluation.

10. The Registry SHALL remain provider-independent.

11. The Registry SHALL support project, tenant and provider extensions through namespaces.

12. Extensions SHALL NOT redefine core Capability semantics.

13. Administrative mutation SHALL require explicit authority.

14. Registry changes SHALL preserve provenance.

15. Registry caches and projections SHALL declare freshness.

16. Historical Capability Versions SHALL remain resolvable after retirement.

17. The Registry SHALL support explicit missing-capability and capability-gap records.

18. The Registry SHALL support Stage-based production admission.

19. The Registry SHALL NOT treat documentation as proof of runtime availability.

20. The Registry SHALL remain usable by both human and machine consumers.

<a id="section-6-283"></a>
## 6.283 Capability Registry Invariants

The following invariants shall remain true:

- No Provider becomes the canonical definition of a Capability.

- No Model becomes the identity of a Capability.

- No Agent gains identity from a Capability.

- No Capability grants authority merely by existing.

- No Capability is considered available without an eligible supporting resource.

- No Resource is considered compatible by technical format alone.

- No unsupported Feature is silently ignored.

- No provider claim becomes verified support without evidence.

- No Capability Version changes historical meaning.

- No retired Capability disappears from historical evidence.

- No project extension silently replaces a core Capability.

- No manual process is labelled fully automated.

- No availability projection hides its freshness.

- No quality judgment becomes universal across unrelated Capabilities.

- No fallback weakens the original Capability Contract.

<a id="section-6-284"></a>
## 6.284 Closing Statement

The Capability Registry is the semantic foundation through which Omnira understands intelligence work.

It defines what can be requested without defining who must provide it.

It separates human and project intent from provider implementation.

It allows Atlas, Managers, agents and workflows to communicate through one stable language.

It allows Providers, Models, Tools and local resources to remain replaceable.

It allows policy to target meaningful operations.

It allows quality to remain task-specific.

It allows cost, rights, privacy and authority to be evaluated before execution.

It allows capability gaps to be identified honestly.

It allows manual pilots to coexist with governed production without confusing their maturity.

For Familje-Stunden, it means that Nova and Pling production is defined through capabilities such as story segmentation, character-aware animation, Swedish narration and child-facing review rather than through one permanent vendor.

For The Prompt, it means that current research, source verification, scripting and reporter production remain separate governed capabilities.

For GainPilot, it means that lower-cost image, narration and short-form media resources can be used without creating a separate intelligence architecture.

For Omnira, it means that code, research, memory, media, voice and future modalities can all pass through one shared semantic contract.

The Capability Registry shall answer:

What kind of intelligence work does Omnira understand?

The Provider Registry shall answer:

Who may supply it?

The Model and Resource Registries shall answer:

Which resources can perform it?

Policy shall answer:

Which resources may be used here?

Routing shall answer:

Which eligible resource should be selected now?

Evidence shall answer:

What actually happened?

The Capability Registry gives stable meaning to every one of those decisions.

Without it, the Fabric would be a collection of connections.

With it, the Fabric becomes an intelligence architecture.
