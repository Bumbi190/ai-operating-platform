# Chapter 7 — Model Registry

<a id="section-7-1"></a>
## 7.1 Chapter Status

This chapter defines the canonical architecture, governance model, lifecycle, contracts and operational responsibilities of the Omnira Intelligence Fabric Model Registry.

It establishes:

- what a Model represents within Omnira,

- how Models differ from Providers, Deployments, Agents and Capabilities,

- how Model Families and Model Versions are identified,

- how provider aliases and silent provider updates are handled,

- how capabilities, context limits, modalities and execution properties are declared,

- how quality, cost, safety, privacy and rights evidence are attached,

- how local and externally hosted models are represented consistently,

- how model deployments are separated from abstract model identity,

- how model support is verified,

- how Models are activated, restricted, deprecated and retired,

- how historical Executions remain interpretable,

- and how Stage 1 shall implement a bounded but extensible registry.

The Model Registry is a foundational Intelligence Fabric control-plane component.

It is the authoritative catalogue of model identities, versions and deployment relationships known to Omnira.

It is not, by itself, proof that a Model can currently be used.

A Model may be:

- known,

- proposed,

- experimental,

- approved,

- active,

- restricted,

- degraded,

- deprecated,

- retired,

- or historically referenced.

Operational eligibility also depends on:

- Provider Account,

- Connection,

- Model Deployment,

- Adapter,

- Capability support,

- policy,

- data classification,

- authority,

- budget,

- health,

- region,

- and current availability.

This chapter is normative after formal approval.

Runtime implementation and conformance must be verified separately.

<a id="section-7-2"></a>
## 7.2 Purpose of the Model Registry

The Intelligence Fabric requires a stable internal understanding of the Models that may execute intelligence work.

Providers frequently expose Models through:

- changing names,

- aliases,

- preview labels,

- dated identifiers,

- deployment identifiers,

- product tiers,

- or generic endpoints that silently change their underlying implementation.

Without a canonical Model Registry, Omnira would be unable to determine reliably:

- which model performed an Execution,

- which capabilities the model actually supports,

- which version was tested,

- which limits applied,

- whether pricing changed,

- whether quality evidence remains valid,

- whether a workflow depends on a deprecated resource,

- whether a local deployment is equivalent to an external one,

- or whether a provider silently changed model behaviour.

The Model Registry provides a canonical layer between provider naming and Omnira execution.

It allows Models to be:

- understood,

- compared,

- governed,

- selected,

- replaced,

- benchmarked,

- deprecated,

- and historically interpreted.

<a id="section-7-3"></a>
## 7.3 Model as an Execution Resource

A Model is an intelligence execution resource.

It may perform operations such as:

- text generation,

- reasoning,

- code generation,

- image generation,

- image editing,

- speech synthesis,

- speech recognition,

- video generation,

- embedding,

- reranking,

- multimodal analysis,

- or evaluation.

The Model does not own:

- user intent,

- Agent identity,

- project context,

- long-term memory,

- authority,

- provider selection,

- budget,

- or strategic direction.

The Model receives a bounded execution context through the Fabric.

It returns output or execution evidence.

Omnira remains responsible for governance.

<a id="section-7-4"></a>
## 7.4 Model Is Not Provider

A Provider is the organisation or platform supplying access to a resource.

A Model is the intelligence resource itself.

One Provider may expose many Models.

The same Model Family may be available through:

- its original Provider,

- a third-party hosting platform,

- a local runtime,

- an Omnira-managed deployment,

- or a user-controlled private server.

Provider identity and Model identity shall remain separate.

For example:

Provider

NVIDIA-hosted service.

Model

A specific open or proprietary language Model Version.

Deployment

The provider-hosted operational endpoint through which that Model Version is accessed.

These concepts must not be collapsed.

<a id="section-7-5"></a>
## 7.5 Model Is Not Provider Account

A Provider Account represents a specific connected billing, credential or workspace relationship.

A Model may be accessible through several Provider Accounts.

The same Provider Account may expose many Models.

Model eligibility therefore requires both:

- eligible Model or Model Version,

- and eligible Provider Account.

The Model Registry shall not store account credentials or project billing authority as properties of the abstract Model.

<a id="section-7-6"></a>
## 7.6 Model Is Not Deployment

A Model represents a logical intelligence resource or family.

A Model Deployment represents one operational instance or access path.

The same Model Version may be deployed:

- in several regions,

- under several Provider Accounts,

- on different local nodes,

- with different quantisation,

- through different runtimes,

- or under different safety and performance configurations.

Deployment determines practical properties such as:

- endpoint,

- region,

- hardware,

- latency,

- context capacity,

- throughput,

- privacy boundary,

- and cost.

Model identity must remain stable across Deployments where semantic equivalence is sufficiently established.

<a id="section-7-7"></a>
## 7.7 Model Is Not Agent

A Model is not an Omnira Agent.

An Agent has:

- identity,

- role,

- purpose,

- behavioural policy,

- authority,

- project relationships,

- tools,

- and governed memory access.

A Model is one resource an Agent may use.

Atlas does not become a different Agent when a different reasoning Model is selected.

Arnold does not cease to be Arnold when GainPilot changes its execution provider.

The Model Registry shall never be used as the Agent Registry.

<a id="section-7-8"></a>
## 7.8 Model Is Not Capability

A Capability defines what kind of operation Omnira understands.

A Model declares support for one or more Capabilities.

One Model may support several Capabilities.

One Capability may be supported by many Models.

Capability identity remains provider- and Model-independent.

The Model Registry shall reference canonical Capability Versions from the Capability Registry.

<a id="section-7-9"></a>
## 7.9 Model Is Not Adapter

An Adapter translates between Omnira’s canonical contracts and a provider-specific interface.

A Model may be accessible through several Adapters.

An Adapter may support several Models.

Adapter behaviour may affect:

- supported parameters,

- error mapping,

- streaming,

- tool calling,

- usage reporting,

- and output normalisation.

Model identity shall not be tied permanently to one Adapter implementation.

<a id="section-7-10"></a>
## 7.10 Model Is Not Endpoint

A provider endpoint is an operational address or routing target.

An endpoint may expose:

- one Model,

- several Models,

- a moving alias,

- or a provider-managed router.

The endpoint shall belong to a Connection or Model Deployment.

It shall not become the canonical Model identifier.

<a id="section-7-11"></a>
## 7.11 Model Family

A Model Family groups related Model Versions that share a recognised lineage or product identity.

A Model Family may include:

- major generations,

- dated versions,

- preview versions,

- specialised variants,

- context variants,

- speed-optimised variants,

- or provider-managed releases.

The Model Family provides continuity.

It does not imply that all Versions are interchangeable.

<a id="section-7-12"></a>
## 7.12 Model

The canonical Model object represents the stable logical identity under which one or more Versions are grouped.

A Model shall include or reference:

- modelId,

- canonical name,

- Model Family,

- originating Provider where known,

- model type,

- primary modalities,

- broad purpose,

- ownership or licence class,

- lifecycle,

- and provenance.

The Model object should not contain volatile operational properties that belong to Versions or Deployments.

<a id="section-7-13"></a>
## 7.13 Model Version

A Model Version represents a specific release or materially distinct implementation of a Model.

It shall include or reference:

- modelVersionId,

- modelId,

- provider version identifier,

- release date where known,

- knowledge or training cutoff where declared,

- supported Capabilities,

- modality support,

- context limits,

- output limits,

- tool support,

- safety properties,

- pricing references,

- quality evidence,

- lifecycle,

- and provenance.

Historical Executions shall reference the exact Model Version used where this can be determined.

<a id="section-7-14"></a>
## 7.14 Model Variant

A Model Variant is a specialised form of a Model Version.

Variants may differ by:

- size,

- speed,

- quality,

- quantisation,

- context window,

- safety configuration,

- modality,

- region,

- or hardware optimisation.

Examples may include:

- small,

- medium,

- large,

- fast,

- reasoning,

- vision,

- instruct,

- code,

- real-time,

- or distilled.

A Variant may be modelled as:

- separate Model Version,

- Variant metadata,

- or Deployment property,

depending on whether the semantic behaviour differs materially.

The distinction must remain consistent.

<a id="section-7-15"></a>
## 7.15 Model Alias

A Model Alias is a provider or user-facing name that resolves to a Model Version or provider-managed target.

Aliases may include:

- latest,

- production,

- preview,

- default,

- fast,

- or dated shorthand.

Aliases are not stable evidence of Model Version.

The Registry shall record:

- alias,

- Provider,

- resolution state,

- observed target,

- and observation time.

Executions using a moving alias shall preserve the alias and any resolved Version evidence available.

<a id="section-7-16"></a>
## 7.16 Moving Alias

A Moving Alias may change its underlying Model Version without changing its name.

Moving aliases reduce reproducibility.

The Fabric shall:

- identify them explicitly,

- avoid treating historical quality evidence as automatically current,

- record observed provider metadata,

- and increase verification when material behaviour may have changed.

A moving alias must not be represented as a fixed Version.

<a id="section-7-17"></a>
## 7.17 Unknown Model Version

A Provider may not disclose the exact Model Version behind an endpoint or alias.

The Registry shall support an explicit Unknown Model Version state.

Execution evidence should preserve:

- Provider,

- endpoint or alias,

- observation time,

- declared product name,

- and any response metadata.

Unknown shall not be replaced with an assumed Version.

<a id="section-7-18"></a>
## 7.18 Model Identity

Every Model shall have a stable canonical identifier.

The identifier shall remain independent of:

- provider endpoint,

- display name,

- project,

- local filename,

- account,

- or mutable alias.

A Model may also have:

- provider names,

- community names,

- repository names,

- local runtime names,

- and deprecated names.

These shall be represented as aliases or external identifiers.

<a id="section-7-19"></a>
## 7.19 Model Version Identity

Every Model Version shall have a stable canonical identifier.

The identifier should distinguish:

- provider-declared releases,

- materially changed hidden releases where detectable,

- local builds,

- quantised builds where behaviour differs,

- and fine-tuned or adapted versions.

A checksum or artefact digest may assist identification for self-hosted Models.

<a id="section-7-20"></a>
## 7.20 Model Naming Convention

Canonical Model names should be:

- recognisable,

- stable,

- provider-aware where appropriate,

- and separate from mutable marketing labels.

The canonical identifier may use a structured namespace such as:

provider.model_family

or:

origin.model_family

Model Version identifiers may append a governed Version reference.

The exact naming syntax may evolve.

Meaning must remain stable.

<a id="section-7-21"></a>
## 7.21 Provider Model Name

The Provider Model Name is the identifier required by the Provider API or service.

It shall be stored separately from the canonical Model identifier.

Adapter code may use the Provider Model Name.

Callers and business logic should use canonical resource references or capability requests.

<a id="section-7-22"></a>
## 7.22 External Model Identifier

A Model may have external identifiers such as:

- provider API ID,

- model repository ID,

- NIM identifier,

- Hugging Face repository,

- Ollama tag,

- container image,

- or local artefact path.

Each external identifier shall include:

- source,

- identifier type,

- value,

- validity,

- and observed time where relevant.

<a id="section-7-23"></a>
## 7.23 Model Type

The Registry shall classify Models by Model Type.

Types may include:

- foundation language model,

- reasoning model,

- code model,

- embedding model,

- reranking model,

- image generation model,

- image editing model,

- video generation model,

- speech synthesis model,

- speech recognition model,

- music generation model,

- multimodal model,

- evaluator model,

- moderation model,

- classifier,

- or tool-routing model.

A Model may have several types when justified.

Types support discovery.

Capabilities remain the authoritative execution contract.

<a id="section-7-24"></a>
## 7.24 Model Modality

Each Model Version shall declare accepted and produced modalities.

Accepted Modalities may include:

- text,

- image,

- audio,

- video,

- document,

- code,

- structured data,

- or embedding vectors.

Produced Modalities may include:

- text,

- structured output,

- image,

- audio,

- video,

- embedding,

- ranking,

- or tool calls.

Multimodal must be represented precisely.

<a id="section-7-25"></a>
## 7.25 Input Modality

Input Modality describes what the Model Version can consume.

A Model accepting text and one image is not necessarily equivalent to a Model designed for:

- many images,

- video,

- audio,

- or interleaved multimodal context.

The Registry shall capture practical limits.

<a id="section-7-26"></a>
## 7.26 Output Modality

Output Modality describes what the Model Version can produce directly.

A text Model whose output is later converted to audio shall not be registered as a native speech synthesis Model.

Post-processing must remain explicit.

<a id="section-7-27"></a>
## 7.27 Native Capability

A Native Capability is performed directly by the Model Version.

Examples include:

- text generation,

- image generation,

- embedding,

- speech synthesis,

- or image understanding.

Native support should remain distinct from support created through:

- Adapter transformation,

- tool composition,

- workflow composition,

- or human assistance.

<a id="section-7-28"></a>
## 7.28 Composed Capability Support

A Model may participate in a composed Capability without performing the whole operation.

For example, a text Model may create:

- motion instructions for video generation,

- but not the video itself.

The Model Registry shall not claim support for the final video Capability merely because the Model contributed to the workflow.

<a id="section-7-29"></a>
## 7.29 Model Capability Declaration

A Model Capability Declaration connects one Model Version to one Capability Version.

It shall include:

- capabilityId,

- Capability Version,

- support state,

- supported Features,

- constraints,

- context limits,

- output limits,

- quality evidence,

- known limitations,

- and verification state.

Declarations may originate from:

- Provider documentation,

- Adapter metadata,

- testing,

- benchmark,

- or operational evidence.

<a id="section-7-30"></a>
## 7.30 Claimed Model Capability

Claimed support means a Provider or source states that the Model supports the Capability.

Claimed support may be used for:

- discovery,

- experimentation,

- and test planning.

It shall not automatically be treated as production-verified.

<a id="section-7-31"></a>
## 7.31 Observed Model Capability

Observed support means Omnira has executed the Capability successfully under recorded conditions.

Observed support shall identify:

- Capability Version,

- Model Version,

- Deployment,

- Adapter,

- inputs,

- environment,

- and output evidence.

One success does not prove universal compatibility.

<a id="section-7-32"></a>
## 7.32 Verified Model Capability

Verified support means the Model Version has passed the applicable Capability conformance and quality tests.

Verification shall be:

- Capability-specific,

- Version-specific,

- Deployment-aware where needed,

- Adapter-specific,

- and time-aware.

Verification may expire.

<a id="section-7-33"></a>
## 7.33 Partial Model Capability

Partial support means the Model Version satisfies only part of the Capability Contract.

Examples include:

- supports image input but not multiple images,

- supports speech synthesis but not Swedish,

- supports structured output but not strict schema adherence,

- supports image-to-video but not reusable character references.

Partial support must not be presented as full support.

<a id="section-7-34"></a>
## 7.34 Restricted Model Capability

Restricted support means the Capability is supported only under specific conditions.

Restrictions may include:

- Public data only,

- one Project,

- one region,

- one Provider Account,

- one duration limit,

- mandatory human review,

- or no commercial use.

Restrictions shall be routable metadata.

<a id="section-7-35"></a>
## 7.35 Unsupported Model Capability

Unsupported means the Model Version cannot satisfy the Capability contract.

Unsupported declarations may still be preserved to prevent repeated invalid selection.

<a id="section-7-36"></a>
## 7.36 Unknown Model Capability

Unknown support means insufficient evidence exists.

Unknown may be acceptable for controlled experimentation.

It should not be treated as verified production support.

<a id="section-7-37"></a>
## 7.37 Capability Feature Support

Model Capability Declarations shall identify supported Features.

For a text Model, Features may include:

- structured output,

- function calling,

- tool calling,

- streaming,

- reasoning mode,

- system instructions,

- image input,

- document input,

- citation output,

- or deterministic seed support.

For video, Features may include:

- image reference,

- multiple-character reference,

- first and last frame,

- camera control,

- motion control,

- lip sync,

- extension,

- or resolution options.

<a id="section-7-38"></a>
## 7.38 Mandatory Feature Compatibility

If a Capability Request requires a Feature, a Model lacking verified support is ineligible.

The Fabric must not assume that a Model supports a Feature because a related Model in the same Family supports it.

<a id="section-7-39"></a>
## 7.39 Tool-Calling Support

Tool-calling support shall describe:

- whether tools are supported,

- schema restrictions,

- parallel calls,

- streaming tool calls,

- tool-choice control,

- argument reliability,

- and provider limitations.

Tool support is not authority to use tools.

Authority remains a separate Fabric decision.

<a id="section-7-40"></a>
## 7.40 Structured Output Support

Structured output support shall describe:

- JSON mode,

- schema enforcement,

- response validation,

- retry requirements,

- maximum schema complexity,

- and known failure behaviour.

A Model producing JSON-like text is not equivalent to strict schema support.

<a id="section-7-41"></a>
## 7.41 Reasoning Support

Reasoning support may include:

- general reasoning,

- extended reasoning,

- hidden reasoning mode,

- visible rationale summary,

- planning,

- or specialised mathematical reasoning.

The Registry shall not require or store private chain-of-thought content.

It may record:

- reasoning mode,

- declared effort level,

- latency impact,

- cost impact,

- and quality evidence.

<a id="section-7-42"></a>
## 7.42 Grounding and Citation Support

Some Models or provider systems may support:

- web grounding,

- document grounding,

- source citations,

- or retrieval integration.

Grounding support shall identify:

- source type,

- freshness,

- citation traceability,

- provider control,

- and limitations.

Citation appearance alone does not prove source correctness.

<a id="section-7-43"></a>
## 7.43 Context Window

The Context Window describes the maximum amount of input context supported by a Model Version or Deployment.

The Registry should distinguish:

- advertised maximum,

- verified practical maximum,

- project-approved maximum,

- and recommended operating range.

Larger context does not guarantee better quality.

<a id="section-7-44"></a>
## 7.44 Input Token Limit

For token-based Models, the Registry shall record the maximum supported input size where known.

Provider counting methods may differ.

The Adapter shall preserve provider-specific token estimation where required.

<a id="section-7-45"></a>
## 7.45 Output Token Limit

The Registry shall record output limits separately from input limits.

A large context window does not imply equally large output support.

Output limits influence:

- Capability compatibility,

- planning,

- document generation,

- and cost.

<a id="section-7-46"></a>
## 7.46 Total Context Limit

Some Providers apply one total limit across input and output.

The Registry shall represent whether limits are:

- input-only,

- output-only,

- combined,

- dynamic,

- or unknown.

Adapters must not assume one universal counting model.

<a id="section-7-47"></a>
## 7.47 Media Limits

Multimodal Model Versions may have limits such as:

- image count,

- image dimensions,

- audio duration,

- video duration,

- frame count,

- file size,

- or document page count.

These limits belong to Version or Deployment metadata.

<a id="section-7-48"></a>
## 7.48 Context Quality Profile

The Registry may record practical evidence about performance across context lengths.

A Model may technically accept a long context while showing degraded:

- retrieval,

- instruction adherence,

- accuracy,

- or latency.

Routing should use measured quality where available.

<a id="section-7-49"></a>
## 7.49 Knowledge Cutoff

Where declared, the Registry may record a Model Version’s knowledge cutoff.

The cutoff is not evidence that every fact before that date is known or correct.

The Fabric shall still use current research tools for time-sensitive requests.

<a id="section-7-50"></a>
## 7.50 Training Data Disclosure

The Registry may preserve Provider-declared information about:

- training sources,

- licences,

- synthetic data,

- opt-out mechanisms,

- and limitations.

Unknown training provenance shall remain unknown.

The Registry shall not invent certainty.

<a id="section-7-51"></a>
## 7.51 Model Ownership Class

A Model may be classified as:

- proprietary,

- open-weight,

- open-source,

- source-available,

- research-only,

- custom private,

- fine-tuned,

- distilled,

- or unknown.

Ownership class affects:

- deployment options,

- rights,

- cost,

- privacy,

- and maintenance.

<a id="section-7-52"></a>
## 7.52 Model Licence

Open or self-hosted Models shall reference the applicable licence.

The Registry may record:

- licence name,

- version,

- commercial-use permission,

- redistribution terms,

- attribution,

- acceptable-use restrictions,

- and uncertainty.

Open weights do not automatically mean unrestricted commercial use.

<a id="section-7-53"></a>
## 7.53 Provider Terms Relationship

Externally hosted Model use may be governed by Provider terms in addition to Model licence.

The Registry shall preserve the distinction between:

- Model licence,

- Provider service terms,

- Provider Account agreement,

- and project input rights.

<a id="section-7-54"></a>
## 7.54 Commercial Use Eligibility

The Registry may record whether output from a Model Version is:

- eligible for commercial use,

- conditionally eligible,

- restricted,

- unknown,

- or prohibited.

Eligibility may vary by:

- Provider Account tier,

- Provider terms,

- region,

- use case,

- and input rights.

The Model Registry alone cannot prove the complete rights chain.

<a id="section-7-55"></a>
## 7.55 Data Retention Profile

A Model Deployment or Provider relationship may declare:

- prompt retention,

- output retention,

- abuse-monitoring retention,

- human-review possibility,

- training use,

- and deletion support.

Retention is often Deployment- or Account-specific rather than Model-specific.

The Registry shall place data at the correct object level.

<a id="section-7-56"></a>
## 7.56 Training-Use Profile

The Registry may record whether Provider-submitted data may be used for:

- model training,

- service improvement,

- safety review,

- or no such use.

This property may differ by:

- account tier,

- contract,

- region,

- and endpoint.

It shall not be assumed from general Provider reputation.

<a id="section-7-57"></a>
## 7.57 Safety Profile

A Model Safety Profile may include:

- built-in moderation,

- refusal behaviour,

- harmful-content controls,

- age-related restrictions,

- prompt-injection resilience,

- known jailbreak sensitivity,

- and Provider enforcement.

Safety claims require evidence.

A strict refusal profile may make a Model unsuitable for some benign tasks.

A permissive profile may require stronger Fabric controls.

<a id="section-7-58"></a>
## 7.58 Content Policy Profile

The Registry may preserve Provider- or Model-specific content restrictions.

Restrictions may affect:

- image generation,

- child-facing media,

- health,

- finance,

- politics,

- likeness,

- copyrighted characters,

- or voice cloning.

Policy restrictions influence eligibility.

They must not be confused with Omnira’s own policies.

<a id="section-7-59"></a>
## 7.59 Privacy Profile

A Model Deployment Privacy Profile may describe:

- execution location,

- Provider access,

- encryption,

- retention,

- training use,

- regional processing,

- local ownership,

- and auditability.

Privacy belongs primarily to Deployment and Provider Account context.

The abstract Model may support several privacy profiles through different Deployments.

<a id="section-7-60"></a>
## 7.60 Risk Classification

Each Model Version may receive a Risk Classification based on:

- autonomy,

- tool use,

- modality,

- external side effects,

- data handling,

- output unpredictability,

- and known defects.

Risk classification informs:

- production admission,

- approval,

- evaluation,

- and monitoring.

Capability risk and Model risk shall both be considered.

<a id="section-7-61"></a>
## 7.61 Model Trust Level

The Registry may assign a Trust Level such as:

- untrusted,

- experimental,

- reviewed,

- production approved,

- restricted production,

- high assurance,

- or retired.

Trust Level shall be based on evidence.

It shall not be inherited automatically across Model Family Versions.

<a id="section-7-62"></a>
## 7.62 Model Maturity

Model Maturity may include:

- preview,

- beta,

- stable,

- generally available,

- legacy,

- or unknown.

Provider labels are evidence, not absolute truth.

Preview status may require:

- lower spending limits,

- stronger review,

- and reduced data eligibility.

<a id="section-7-63"></a>
## 7.63 Model Lifecycle

Canonical Model lifecycle states may include:

- proposed,

- discovered,

- experimental,

- approved,

- active,

- restricted,

- degraded,

- deprecated,

- disabled,

- retired,

- and archived.

Lifecycle shall be version-specific where appropriate.

<a id="section-7-64"></a>
## 7.64 Proposed Model

Proposed means the Model has been identified for possible addition.

It may have incomplete metadata.

It shall not be used for production execution.

<a id="section-7-65"></a>
## 7.65 Discovered Model

Discovered means the Model was detected through:

- Provider metadata,

- API listing,

- repository scan,

- user connection,

- or manual research.

Discovery does not imply trust or approval.

<a id="section-7-66"></a>
## 7.66 Experimental Model

Experimental means the Model Version may be used in bounded tests.

Experimental use should normally require:

- sandbox environment,

- restricted data,

- limited budget,

- mandatory evaluation,

- and no automatic publication.

<a id="section-7-67"></a>
## 7.67 Approved Model

Approved means architecture, policy and risk review have accepted the Model Version for defined use.

Approved does not mean every Deployment or Account is active.

<a id="section-7-68"></a>
## 7.68 Active Model

Active means the Model Version is available through at least one production-admitted Deployment and may be selected for eligible requests.

Active state shall include:

- supported environments,

- supported scopes,

- and restrictions.

<a id="section-7-69"></a>
## 7.69 Restricted Model

Restricted means the Model Version may be used only under declared conditions.

Restrictions may include:

- specific Capabilities,

- specific Projects,

- Public data,

- low budget,

- human review,

- or no side effects.

<a id="section-7-70"></a>
## 7.70 Degraded Model

Degraded means the Model remains selectable for limited use but current evidence shows reduced:

- quality,

- availability,

- latency,

- reliability,

- or capability support.

Degradation must be visible to routing.

<a id="section-7-71"></a>
## 7.71 Deprecated Model

Deprecated means the Model Version should not be selected for new ordinary work.

Deprecation shall identify:

- reason,

- replacement,

- affected Capabilities,

- migration plan,

- and retirement date where known.

<a id="section-7-72"></a>
## 7.72 Disabled Model

Disabled means selection is blocked immediately.

Reasons may include:

- security incident,

- rights issue,

- severe quality regression,

- Provider outage,

- cost anomaly,

- or administrative decision.

Disabled status may be temporary.

<a id="section-7-73"></a>
## 7.73 Retired Model

Retired means the Model Version is no longer eligible for new execution.

Historical evidence must remain resolvable.

<a id="section-7-74"></a>
## 7.74 Archived Model

Archived means the Model record is retained primarily for historical interpretation.

Archived Models may no longer appear in ordinary discovery.

<a id="section-7-75"></a>
## 7.75 Model Lifecycle Transition

Lifecycle transitions shall record:

- previous state,

- new state,

- actor,

- reason,

- evidence,

- effective time,

- and affected scopes.

A Model shall not move directly from discovered to active without required review.

<a id="section-7-76"></a>
## 7.76 Model Owner

Every Model Registry entry shall have an accountable governance Owner or Steward.

Responsibilities may include:

- metadata quality,

- lifecycle,

- capability mappings,

- benchmark coverage,

- deprecation,

- and review.

Ownership does not grant unrestricted execution authority.

<a id="section-7-77"></a>
## 7.77 Model Provenance

Model records shall preserve provenance such as:

- Provider documentation,

- repository metadata,

- Model card,

- licence,

- API observation,

- benchmark,

- test execution,

- and human review.

Conflicting source claims shall remain visible.

<a id="section-7-78"></a>
## 7.78 Model Card

The Registry may include or reference a Model Card.

A Model Card may describe:

- intended use,

- limitations,

- training information,

- safety,

- evaluation,

- licence,

- and known risks.

Provider or community Model Cards are evidence sources.

They are not automatically canonical truth.

<a id="section-7-79"></a>
## 7.79 Canonical Model Record

A canonical Model record should contain or reference:

- stable identity,

- Family,

- Provider origin,

- Model Type,

- modality,

- ownership class,

- licence,

- broad purpose,

- lifecycle,

- aliases,

- Versions,

- and provenance.

Volatile operational data should remain in Version or Deployment objects.

<a id="section-7-80"></a>
## 7.80 Canonical Model Version Record

A Model Version record should contain or reference:

- stable Version identity,

- Model identity,

- Provider version identifier,

- release date,

- Capability Declarations,

- Features,

- limits,

- quality evidence,

- cost references,

- safety profile,

- rights profile,

- lifecycle,

- and known limitations.

<a id="section-7-81"></a>
## 7.81 Model Deployment

A Model Deployment represents an operationally selectable instance or access path.

It shall include or reference:

- deploymentId,

- Model Version,

- Provider,

- Provider Account,

- Connection,

- region,

- endpoint reference,

- environment,

- configuration,

- runtime,

- capacity,

- health,

- privacy profile,

- pricing reference,

- and lifecycle.

Routing shall select a Deployment, not only an abstract Model.

<a id="section-7-82"></a>
## 7.82 External Model Deployment

An External Model Deployment executes on infrastructure controlled by an external Provider.

It shall identify:

- Provider,

- Provider Account,

- region,

- endpoint,

- service tier,

- account terms,

- retention profile,

- and current health.

<a id="section-7-83"></a>
## 7.83 Omnira-Managed Deployment

An Omnira-Managed Deployment executes on infrastructure controlled or operated by Omnira.

It may use:

- proprietary Models,

- licensed open Models,

- containerised NIM resources,

- or managed compute.

It shall still have:

- explicit ownership,

- budget,

- capacity,

- security,

- and operational evidence.

<a id="section-7-84"></a>
## 7.84 User-Managed Deployment

A User-Managed Deployment runs on infrastructure controlled by the user.

Examples include:

- local workstation,

- private rig,

- home server,

- or user cloud account.

The Fabric shall record:

- node owner,

- connectivity,

- capacity,

- trust,

- and permitted scope.

<a id="section-7-85"></a>
## 7.85 Local Model Deployment

A Local Deployment executes on a user-controlled device or private node.

It may provide:

- privacy,

- offline use,

- predictable ownership,

- and lower marginal cost.

It may also have:

- limited performance,

- energy cost,

- reduced availability,

- hardware dependency,

- and maintenance burden.

Local shall not be treated as automatically free or superior.

<a id="section-7-86"></a>
## 7.86 Edge Model Deployment

An Edge Deployment runs on a constrained device such as:

- mobile phone,

- tablet,

- vehicle,

- wearable,

- or embedded node.

Edge deployment may support:

- low latency,

- offline processing,

- privacy,

- and limited capabilities.

The Registry shall preserve hardware and battery constraints.

<a id="section-7-87"></a>
## 7.87 Deployment Configuration

Deployment Configuration may include:

- quantisation,

- precision,

- context setting,

- safety setting,

- system prompt layer,

- batching,

- concurrency,

- temperature defaults,

- or hardware allocation.

Configuration materially affecting behaviour shall be versioned.

<a id="section-7-88"></a>
## 7.88 Quantisation

For locally hosted Models, Quantisation may affect:

- memory use,

- speed,

- quality,

- and hardware compatibility.

Quantised variants should be represented at Version or Deployment level according to semantic impact.

Benchmark evidence shall identify the actual quantisation used.

<a id="section-7-89"></a>
## 7.89 Fine-Tuned Model

A Fine-Tuned Model is derived from another Model Version through additional training or adaptation.

The Registry shall record:

- base Model Version,

- training owner,

- training data provenance where governed,

- intended purpose,

- evaluation,

- licence compatibility,

- and scope.

Fine-tuned Models may be project-specific.

<a id="section-7-90"></a>
## 7.90 Adapter-Tuned or Prompt-Tuned Model

Some apparent specialisation may result from:

- system instructions,

- adapters,

- retrieval,

- or prompt templates

rather than changed Model weights.

The Registry shall not register a new Model Version when only execution configuration changed unless the behaviour is governed as a distinct Deployment or packaged resource.

<a id="section-7-91"></a>
## 7.91 Distilled Model

A Distilled Model derives behaviour from another Model or training process.

The Registry shall record available lineage.

Distillation does not guarantee equivalent quality or rights.

<a id="section-7-92"></a>
## 7.92 Model Lineage

Model Lineage may represent:

- derived from,

- fine-tuned from,

- distilled from,

- quantised from,

- converted from,

- or supersedes.

Lineage supports:

- rights,

- reproducibility,

- quality interpretation,

- and migration.

<a id="section-7-93"></a>
## 7.93 Model Artefact

A self-hosted Model may have one or more artefacts.

Artefact metadata may include:

- file or container reference,

- checksum,

- size,

- format,

- source,

- licence,

- and integrity verification.

Artefact identity supports secure deployment.

<a id="section-7-94"></a>
## 7.94 Model Checksum

Checksums should be preserved for self-hosted Model artefacts where practical.

Checksum mismatch may indicate:

- corruption,

- unapproved modification,

- or wrong version.

External hosted Models may not expose equivalent artefact verification.

<a id="section-7-95"></a>
## 7.95 Runtime

A Runtime is the software environment that loads or accesses a Model Deployment.

Examples include:

- Ollama,

- vLLM,

- NVIDIA NIM,

- provider-hosted API,

- custom inference server,

- mobile runtime,

- or browser runtime.

Runtime identity shall remain separate from Model identity.

<a id="section-7-96"></a>
## 7.96 Runtime Version

Runtime Version may materially affect:

- performance,

- supported context,

- tool calling,

- quantisation,

- and output.

Execution evidence should preserve Runtime Version for local or self-hosted Deployments where relevant.

<a id="section-7-97"></a>
## 7.97 Hardware Profile

Local and managed Deployments shall reference a Hardware Profile.

It may include:

- CPU,

- GPU,

- accelerator,

- RAM,

- VRAM,

- storage,

- architecture,

- and energy constraints.

Hardware Profile informs:

- compatibility,

- load time,

- throughput,

- and model placement.

<a id="section-7-98"></a>
## 7.98 Hardware Requirement

A Model Deployment may declare minimum and recommended hardware.

Requirements may include:

- VRAM,

- system RAM,

- storage,

- GPU compute capability,

- operating system,

- runtime,

- and driver.

The Fabric shall not schedule a Model to an incompatible node.

<a id="section-7-99"></a>
## 7.99 Node Compatibility

Node Compatibility determines whether a Runtime Node can operate the Model Deployment.

It shall consider:

- hardware,

- runtime,

- storage,

- power state,

- network,

- privacy,

- and environment.

Compatibility may change dynamically.

<a id="section-7-100"></a>
## 7.100 Model Load State

Local Models may have states such as:

- not installed,

- installed,

- loading,

- loaded,

- idle,

- unloading,

- unavailable,

- or corrupted.

Load State affects latency and availability.

<a id="section-7-101"></a>
## 7.101 Model Installation State

Installation shall preserve:

- source,

- artefact,

- checksum,

- licence acceptance,

- node,

- installedAt,

- and installer identity.

Automatic Model installation may require approval due to:

- storage,

- bandwidth,

- licence,

- and security.

<a id="section-7-102"></a>
## 7.102 Model Removal

Removing a local Model artefact shall require authority.

Removal must distinguish:

- unload,

- uninstall,

- archive,

- and physical deletion.

Historical execution evidence shall remain interpretable after removal.

<a id="section-7-103"></a>
## 7.103 Capacity

Model Deployment Capacity may include:

- concurrent requests,

- tokens per minute,

- images per minute,

- audio seconds per minute,

- video queue capacity,

- or local GPU availability.

Capacity is operational state.

It shall not be stored as a permanent abstract Model property.

<a id="section-7-104"></a>
## 7.104 Throughput

Throughput evidence may include:

- tokens per second,

- requests per second,

- images per minute,

- or media processing rate.

Throughput shall identify:

- Deployment,

- input conditions,

- hardware,

- Adapter,

- and time.

<a id="section-7-105"></a>
## 7.105 Latency

Latency evidence may include:

- queue latency,

- first-token latency,

- total response time,

- job completion time,

- and callback delay.

Latency is Capability- and Deployment-specific.

<a id="section-7-106"></a>
## 7.106 Availability

Model availability depends on:

- lifecycle,

- Deployment,

- Provider Account,

- Connection,

- health,

- capacity,

- quota,

- policy,

- and scope.

The Registry shall not expose one misleading universal available flag.

<a id="section-7-107"></a>
## 7.107 Model Health

Model Health is the current derived condition of a Model Deployment.

Expected states may include:

- healthy,

- degraded,

- unavailable,

- unknown,

- warming,

- rate limited,

- exhausted,

- authentication required,

- and maintenance.

Health is not the same as eligibility.

<a id="section-7-108"></a>
## 7.108 Health Observation

Health Observations may include:

- successful request,

- failed request,

- latency,

- rate limit,

- capacity,

- Provider status,

- or local node telemetry.

Health state shall be derived from observations with declared freshness.

<a id="section-7-109"></a>
## 7.109 Health Freshness

Health data shall include:

- observedAt,

- source,

- expected refresh,

- and stale threshold.

Stale health data must not be represented as current certainty.

<a id="section-7-110"></a>
## 7.110 Model Quality Evidence

Model quality shall be represented through capability-specific evidence.

Evidence may include:

- benchmarks,

- test executions,

- human review,

- project outcomes,

- error rates,

- acceptance rates,

- and operational learning.

The Registry shall not assign one universal quality score to every Model.

<a id="section-7-111"></a>
## 7.111 Benchmark Relationship

Benchmark Results shall reference:

- Model Version,

- Model Deployment,

- Capability Version,

- Adapter Version,

- test conditions,

- cost,

- latency,

- and date.

Results shall remain contextual.

<a id="section-7-112"></a>
## 7.112 External Benchmark

External Benchmarks may be useful evidence.

They shall preserve:

- source,

- methodology,

- date,

- tested Version,

- and limitations.

External rankings must not be treated as permanent or universally applicable.

<a id="section-7-113"></a>
## 7.113 Internal Benchmark

Internal Benchmarks shall reflect Omnira tasks and requirements.

Examples include:

- Nova and Pling character consistency,

- Swedish narration quality,

- TypeScript architecture conformance,

- source-grounded news synthesis,

- or local retrieval performance.

Internal benchmarks may be more useful for routing than generic leaderboards.

<a id="section-7-114"></a>
## 7.114 Project-Specific Benchmark

A Project may define benchmarks reflecting its own Quality Contracts.

Project-specific evidence shall not automatically become platform-wide ranking.

<a id="section-7-115"></a>
## 7.115 Human Evaluation Evidence

Human review may record:

- reviewer,

- criteria,

- score,

- comments,

- acceptance,

- and date.

Human evaluation should preserve reviewer scope and potential subjectivity.

<a id="section-7-116"></a>
## 7.116 Automated Evaluation Evidence

Automated evaluation may use:

- deterministic tests,

- another Model,

- rules,

- or external metrics.

The evaluator and Version shall be recorded.

<a id="section-7-117"></a>
## 7.117 Acceptance Rate

The Registry may derive Model acceptance rates by:

- Capability,

- Project,

- routing profile,

- and time period.

Acceptance rate shall not be interpreted without considering:

- task difficulty,

- reviewer standards,

- and retry policy.

<a id="section-7-118"></a>
## 7.118 Retry Rate

High retry rate may indicate:

- weak quality,

- unstable Provider,

- poor Adapter mapping,

- or unsuitable prompt strategy.

Retry evidence shall remain Capability-specific.

<a id="section-7-119"></a>
## 7.119 Unknown-Outcome Rate

Asynchronous or external Models may have unknown outcomes.

The Registry may track unknown-outcome frequency by Deployment.

This affects reliability ranking and retry policy.

<a id="section-7-120"></a>
## 7.120 Model Cost Profile

Cost belongs primarily to:

- Deployment,

- Provider Account,

- pricing version,

- and usage.

The Model Registry may reference cost profiles but shall not store one permanent universal price.

Cost may include:

- per token,

- per image,

- per second,

- per job,

- subscription capacity,

- local compute,

- energy,

- or bundled credits.

<a id="section-7-121"></a>
## 7.121 Pricing Reference

A Pricing Reference shall identify:

- Provider,

- Provider Account class,

- Model Deployment,

- pricing version,

- effective date,

- currency,

- usage units,

- and source.

Historical Executions shall preserve the pricing basis used for estimates where possible.

<a id="section-7-122"></a>
## 7.122 Cost Estimate Evidence

Model selection may use Cost Estimates based on:

- expected input,

- expected output,

- retries,

- conversion,

- and Provider pricing.

Estimates must remain separate from confirmed usage.

<a id="section-7-123"></a>
## 7.123 Local Execution Cost

Local execution may have:

- zero direct provider charge,

- energy cost,

- hardware depreciation,

- opportunity cost,

- and maintenance.

Stage 1 may initially report local cost as:

- zero marginal provider cost,

- estimated compute cost,

- or unknown internal cost.

It shall not claim universally free execution.

<a id="section-7-124"></a>
## 7.124 Subscription-Included Capacity

Some Provider Accounts include Model use within a subscription.

The Registry or Account state may record:

- included quota,

- reset period,

- API availability,

- and marginal cost.

Subscription inclusion does not make usage unbounded.

<a id="section-7-125"></a>
## 7.125 Free-Tier Model Access

Free-tier access may have:

- lower rate limits,

- reduced quality,

- watermarking,

- restricted commercial rights,

- or no API.

Free-tier status belongs to Provider Account and Deployment context.

It shall not define the abstract Model.

<a id="section-7-126"></a>
## 7.126 Model Selection Score

Routing may derive a Model Selection Score using:

- capability compatibility,

- policy,

- quality,

- cost,

- latency,

- reliability,

- privacy,

- and user preference.

The score shall not override mandatory eligibility.

A high-scoring ineligible Model remains unselectable.

<a id="section-7-127"></a>
## 7.127 Model Ranking

Rankings shall be scoped to:

- Capability,

- request conditions,

- Project,

- routing profile,

- and time.

The Fabric shall not maintain one simplistic global “best model” list.

<a id="section-7-128"></a>
## 7.128 Economy Suitability

A Model may be suitable for Economy routing when it:

- meets the Quality Floor,

- has acceptable reliability,

- satisfies rights and privacy,

- and offers lower total cost.

Economy suitability is Capability-specific.

<a id="section-7-129"></a>
## 7.129 Balanced Suitability

Balanced suitability considers:

- quality,

- cost,

- latency,

- reliability,

- and historical acceptance.

The weighting shall be versioned.

<a id="section-7-130"></a>
## 7.130 Premium Suitability

Premium suitability reflects evidence that the Model can produce superior required quality within budget.

Premium does not mean highest price.

<a id="section-7-131"></a>
## 7.131 Private Suitability

Private suitability depends on:

- local or approved private Deployment,

- data controls,

- retention,

- region,

- and ownership.

The same Model Family may have both private and external Deployments.

<a id="section-7-132"></a>
## 7.132 Pinned Suitability

A Pinned request may require a specific Model Version or Deployment.

Pinned selection must still verify:

- authority,

- availability,

- safety,

- rights,

- and budget.

Pinning does not convert an ineligible Model into an eligible one.

<a id="section-7-133"></a>
## 7.133 Model Fallback

Fallback may select another:

- Model Version,

- Model Family,

- Deployment,

- Provider,

- or composed Capability path.

Fallback shall preserve mandatory constraints.

Model fallback must be evidenced.

<a id="section-7-134"></a>
## 7.134 Same-Family Fallback

A newer or older Version in the same Family may be a fallback.

The Registry must not assume semantic equivalence.

Quality, cost and compatibility must be evaluated.

<a id="section-7-135"></a>
## 7.135 Cross-Provider Model Fallback

An equivalent or related Model may be hosted by another Provider.

Cross-Provider fallback changes:

- account,

- terms,

- region,

- pricing,

- and operational trust.

It must be evaluated as a distinct Resource Candidate.

<a id="section-7-136"></a>
## 7.136 Local Fallback

External failure may permit local fallback when:

- local Capability support exists,

- quality floor is met,

- deadline permits,

- and policy allows.

Local fallback may be slower or lower quality.

Material degradation must be disclosed.

<a id="section-7-137"></a>
## 7.137 External Fallback From Local

A local failure must not automatically route externally when data is Local Only.

External fallback requires compatible classification and authority.

<a id="section-7-138"></a>
## 7.138 Model Substitution

Model substitution occurs when a selected Model is replaced before or during execution.

Substitution shall record:

- original selection,

- replacement,

- reason,

- cost change,

- quality change,

- and approval impact.

Silent material substitution is prohibited.

<a id="section-7-139"></a>
## 7.139 Model Deprecation Trigger

Deprecation may be triggered by:

- Provider retirement notice,

- quality regression,

- high cost,

- security issue,

- licence change,

- better replacement,

- or unsupported Adapter.

Deprecation shall not erase historical evidence.

<a id="section-7-140"></a>
## 7.140 Model Retirement Migration

Retirement planning shall identify:

- affected Capabilities,

- Workflows,

- Agents,

- Provider Accounts,

- and stored prompts or configurations.

Migration should use Capability contracts rather than provider-specific rewrite where possible.

<a id="section-7-141"></a>
## 7.141 Model Version Drift

Version Drift occurs when observed behaviour changes while the declared Version remains stable.

Signals may include:

- benchmark regression,

- changed refusal behaviour,

- changed output format,

- pricing changes,

- or Provider announcement.

Drift may require creating an observed sub-version or restricting the alias.

<a id="section-7-142"></a>
## 7.142 Silent Provider Update

When a Provider silently updates a stable Model name, Omnira shall:

- preserve the alias used,

- record the observation period,

- re-run critical conformance tests,

- reduce reproducibility confidence,

- and update quality evidence.

The Registry shall not pretend that past and current behaviour are identical.

<a id="section-7-143"></a>
## 7.143 Model Behaviour Fingerprint

The Fabric may derive a Behaviour Fingerprint using controlled tests.

A fingerprint may help detect:

- silent update,

- Adapter change,

- or configuration drift.

A fingerprint is evidence.

It is not proof of underlying weights.

<a id="section-7-144"></a>
## 7.144 Model Reproducibility Profile

A Reproducibility Profile may include:

- fixed Version availability,

- seed support,

- deterministic settings,

- provider alias behaviour,

- local artefact checksum,

- and observed variance.

Reproducibility requirements may affect routing.

<a id="section-7-145"></a>
## 7.145 Determinism

Models may be:

- deterministic,

- configurable,

- stochastic,

- provider-dependent,

- or unknown.

Determinism claims shall identify conditions.

Temperature zero does not always guarantee identical output.

<a id="section-7-146"></a>
## 7.146 Seed Support

Generative media Models may support seeds.

Seed support may improve repeatability.

The Registry shall record:

- seed availability,

- seed range,

- provider consistency,

- and limitations.

Seed support does not guarantee identical output after a Model update.

<a id="section-7-147"></a>
## 7.147 Parameter Profile

Model Versions may support canonical parameters such as:

- temperature,

- top-p,

- maximum output,

- seed,

- aspect ratio,

- duration,

- guidance,

- voice settings,

- or reasoning effort.

Provider-specific parameter names belong in Adapter mappings.

<a id="section-7-148"></a>
## 7.148 Parameter Compatibility

A Model Capability Declaration shall identify which canonical parameters are:

- supported,

- ignored,

- transformed,

- bounded,

- or unsupported.

Adapters must not silently discard material parameters.

<a id="section-7-149"></a>
## 7.149 Default Parameter Set

Deployments may define safe default parameters.

Defaults shall be:

- versioned,

- Capability-specific,

- and scoped.

A Provider’s generic default is not automatically Omnira’s approved default.

<a id="section-7-150"></a>
## 7.150 Project Parameter Profile

Projects may define preferred parameter profiles.

For example:

- Familje-Stunden child-safe motion settings,

- The Prompt newsroom voice pacing,

- GainPilot short-form visual format.

Project profiles shall not alter canonical Model identity.

<a id="section-7-151"></a>
## 7.151 Model Prompt Compatibility

Models may respond differently to:

- system instructions,

- structured prompts,

- examples,

- long context,

- tool schemas,

- and multilingual input.

Prompt compatibility evidence may be captured in operational learning.

It should not become part of immutable Model identity unless contractually relevant.

<a id="section-7-152"></a>
## 7.152 Instruction Hierarchy Support

The Registry may record whether a Model or Provider supports:

- system instructions,

- developer instructions,

- user messages,

- tool messages,

- or equivalent roles.

Adapter mappings shall preserve the strongest available instruction hierarchy.

<a id="section-7-153"></a>
## 7.153 Multilingual Support

Model Versions may declare language support.

Support should distinguish:

- understands,

- generates,

- transcribes,

- synthesises,

- translates,

- and maintains quality.

“Supports Swedish” is too broad without capability context.

<a id="section-7-154"></a>
## 7.154 Swedish Quality Evidence

For Omnira, Swedish quality may require dedicated tests for:

- grammar,

- tone,

- pronunciation,

- transcription,

- child-facing language,

- technical terminology,

- and naturalness.

Generic multilingual claims are insufficient for critical workflows.

<a id="section-7-155"></a>
## 7.155 Model Locale Support

Locale support may include:

- language,

- regional spelling,

- date format,

- pronunciation,

- and cultural context.

Locale is often a request constraint rather than separate Capability.

<a id="section-7-156"></a>
## 7.156 Code Model Profile

Code Models may declare support for:

- languages,

- frameworks,

- repository size,

- tool use,

- patch generation,

- test generation,

- code review,

- and architecture reasoning.

Code quality shall be verified through tests and review.

<a id="section-7-157"></a>
## 7.157 Image Model Profile

Image Models may declare support for:

- text-to-image,

- image editing,

- inpainting,

- outpainting,

- text rendering,

- transparency,

- reference consistency,

- style control,

- and resolution.

Provider claims shall be tested for project-critical features.

<a id="section-7-158"></a>
## 7.158 Video Model Profile

Video Models may declare:

- text-to-video,

- image-to-video,

- video-to-video,

- duration,

- resolution,

- aspect ratio,

- reference support,

- motion control,

- camera control,

- lip sync,

- sound,

- extension,

- host,

- runtime,

- configuration,

- and observed behaviour.

<a id="section-7-213"></a>
## 7.213 Provider Router Deployment

Some Providers expose an automatic router rather than one fixed Model.

Such a Deployment shall be represented as:

- provider-managed routed resource,

- with declared candidate Models where known,

- routing opacity,

- cost behaviour,

- and reproducibility limits.

It must not be mislabelled as one fixed Model Version.

<a id="section-7-214"></a>
## 7.214 Ensemble Model Resource

An Ensemble combines several Models.

It may:

- vote,

- critique,

- route,

- or aggregate.

It shall not be registered as one ordinary Model unless it has a stable governed contract.

<a id="section-7-215"></a>
## 7.215 Mixture-of-Experts Model

Internal architecture does not require separate Fabric routing unless externally selectable.

<a id="section-7-216"></a>
## 7.216 Model-as-a-Service Product

A Provider product may bundle:

- Model,

- retrieval,

- tools,

- memory,

- and orchestration.

<a id="section-7-217"></a>
## 7.217 Provider Assistant Product

A Provider-hosted assistant may use a Model plus state and tools.

It should normally be represented as an External Agent Resource, not merely a Model.

The underlying Model may remain known or unknown.

<a id="section-7-218"></a>
## 7.218 Real-Time Model Session

- session limits,

- context retention,

- interruption,

- cost,

- tool permissions,

<a id="section-7-219"></a>
## 7.219 Ephemeral Model Session

An Ephemeral Session exists for one request or short task.

It should not become a hidden persistent memory store.

## 7.220 Persistent Provider Thread

The Registry or External Agent Resource shall record:

- owner,

- Project,

- retention,

<a id="section-7-325"></a>
## 7.325 Closing Statement

The Model Registry gives Omnira a stable understanding of the intelligence resources available beneath the Intelligence Fabric.

It allows the platform to distinguish:

- Provider from Model,

- Model from Version,

- Version from Alias,

- Model from Deployment,

- Deployment from Account,

- Model from Agent,

- and Capability from implementation.

This distinction is essential.

Providers will rename Models.

Aliases will move.

Prices will change.

Deployments will fail.

Local runtimes will differ.

Open Models will be quantised.

Provider routers will hide implementation.

Quality will vary by task.

New Models will appear faster than application code can safely absorb them.

The Model Registry ensures that this change occurs at the resource layer rather than inside every Agent, Project and Workflow.

For Familje-Stunden, it allows Omnira to compare video Models according to actual Nova and Pling character consistency instead of provider popularity.

For The Prompt, it allows research, editorial reasoning, avatar production and factual evaluation to use different specialised Models.

For GainPilot, it allows inexpensive local or external Models to handle routine content while stronger Models remain available for tasks that justify them.

For Omnira itself, it allows code, reasoning, retrieval, voice, image, video and future modalities to evolve without giving one vendor ownership of the platform.

The Capability Registry defines what must be done.

The Model Registry defines which intelligence resources may be capable of doing it.

The Provider Registry defines who supplies access.

The Deployment defines where and how execution occurs.

The Adapter translates the request.

Policy determines what is permitted.

Routing selects the eligible path.

Evidence records what actually happened.

The Model is powerful.

It is still only a resource.

Omnira retains identity.

The user retains direction.

The Fabric retains governance.
