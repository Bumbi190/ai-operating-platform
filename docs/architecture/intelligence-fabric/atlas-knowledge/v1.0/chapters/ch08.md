# Chapter 8 — Provider Registry

<a id="section-8-1"></a>
## 8.1 Chapter Status

This chapter defines the canonical architecture, governance model, lifecycle, contracts and operational responsibilities of the Omnira Intelligence Fabric Provider Registry.

It establishes:

- what a Provider represents within Omnira,

- how Providers differ from Provider Accounts, Models, Deployments, Connections, Adapters and credentials,

- how external, local, self-hosted, user-managed and Omnira-managed providers are represented,

- how provider identity and service boundaries are established,

- how provider accounts, workspaces, subscriptions and billing relationships are separated,

- how trust, privacy, rights, regional processing and operational maturity are recorded,

- how provider capability claims are evaluated,

- how provider health, availability, quotas and incidents are managed,

- how provider onboarding, restriction, deprecation and removal occur,

- how commercial relationships remain subordinate to user value,

- and how Stage 1 shall implement a bounded but extensible Provider Registry.

The Provider Registry is a foundational Intelligence Fabric control-plane component.

It is the authoritative catalogue of organisations, platforms, services and governed resource suppliers known to Omnira.

A Provider Registry entry does not prove that:

- a usable Provider Account exists,

- credentials are connected,

- a requested Capability is supported,

- a Model is eligible,

- current capacity is available,

- current pricing is known,

- current terms are acceptable,

- or the Provider may process the request’s data.

Those conditions must be evaluated through the appropriate canonical objects and runtime evidence.

This chapter is normative after formal approval.

Implementation and operational conformance must be verified separately.

<a id="section-8-2"></a>
## 8.2 Purpose of the Provider Registry

The Intelligence Fabric shall interact with many forms of intelligence and tool suppliers.

These may include:

- commercial AI companies,

- cloud platforms,

- model-hosting services,

- creative-production platforms,

- voice providers,

- search providers,

- self-hosted runtimes,

- local execution environments,

- user-controlled servers,

- Omnira-managed infrastructure,

- MCP servers,

- external agent platforms,

- human-assisted services,

- and future intelligence marketplaces.

Without a canonical Provider Registry, Omnira would risk representing provider relationships through:

- scattered environment variables,

- hard-coded endpoint names,

- undocumented subscriptions,

- agent-specific credentials,

- project-specific integrations,

- provider dashboards,

- and unverified assumptions.

The Provider Registry shall provide one governed representation of:

- who supplies a resource,

- under what operational relationship,

- through which accounts and connections,

- with which terms and restrictions,

- for which scopes,

- and under which lifecycle state.

<a id="section-8-3"></a>
## 8.3 Provider as a Canonical Entity

A Provider is a canonical entity representing an organisation, platform, runtime operator or bounded service source that supplies one or more resources to the Intelligence Fabric.

A Provider may supply:

- Models,

- Tools,

- External Agent Resources,

- search services,

- storage services,

- media-generation systems,

- local runtimes,

- self-hosted capabilities,

- or human-assisted execution.

A Provider shall have stable identity independent of:

- one account,

- one API key,

- one Model,

- one endpoint,

- one billing plan,

- one project,

- or one user.

The Provider represents the supplier relationship.

Operational access is represented through Provider Accounts, Connections, Deployments and credentials.

<a id="section-8-4"></a>
## 8.4 Provider Is Not Model

A Provider may expose many Models.

A Model may be available through several Providers.

The Provider Registry shall not use Model names as Provider identities.

For example:

Provider

A model-hosting platform.

Model

A specific language or image Model Version.

Provider Account

The user’s connected account at that platform.

Model Deployment

The specific endpoint or operational access path through which the Model is executed.

These objects remain distinct.

<a id="section-8-5"></a>
## 8.5 Provider Is Not Provider Account

A Provider represents the supplier.

A Provider Account represents a specific connected operational relationship with that supplier.

One Provider may have:

- personal account,

- project account,

- business account,

- sandbox account,

- production account,

- Omnira-managed account,

- and several future customer-owned accounts.

Each account may differ in:

- credentials,

- credits,

- billing,

- region,

- assets,

- terms,

- privacy,

- rate limits,

- and permissions.

The Provider Registry shall preserve the Provider independently from every account.

<a id="section-8-6"></a>
## 8.6 Provider Is Not Connection

A Connection represents the technical path through which Omnira communicates with a Provider or Provider Account.

Connection types may include:

- API,

- MCP,

- OAuth,

- webhook,

- queue,

- command-line runtime,

- local socket,

- file exchange,

- or human-assisted handoff.

A Provider may have several Connections.

A Connection may fail without changing Provider identity.

<a id="section-8-7"></a>
## 8.7 Provider Is Not Adapter

An Adapter translates between Omnira’s canonical contracts and Provider-specific behaviour.

A Provider may require:

- several Adapters,

- one Adapter per protocol,

- one Adapter per service family,

- or one human-assisted Adapter.

The Provider Registry identifies the supplier.

The Adapter Registry defines translation and execution behaviour.

<a id="section-8-8"></a>
## 8.8 Provider Is Not Credential

A credential authorises access to a Provider Account or Connection.

Credentials may include:

- API key,

- OAuth token,

- service token,

- certificate,

- signed request key,

- local runtime permission,

- or session relationship.

Credentials shall never become Provider identity.

The Provider Registry shall store only credential references or relationship metadata where necessary.

Raw secrets belong in an approved credential or secret-management service.

<a id="section-8-9"></a>
## 8.9 Provider Is Not Agent

A Provider may offer agent-like products.

Those products remain external Provider resources unless they are explicitly admitted into Omnira’s Agent architecture.

A Provider shall not become:

- Atlas,

- a Manager,

- Arnold,

- or another Omnira Agent identity.

Provider-hosted agents remain bounded external resources.

<a id="section-8-10"></a>
## 8.10 Provider Is Not Capability

A Capability defines what Omnira needs performed.

A Provider may claim or prove support for several Capabilities.

One Capability may be supported by several Providers.

The Provider Registry shall reference canonical Capabilities rather than inventing Provider-specific business logic.

<a id="section-8-11"></a>
## 8.11 Provider Is Not Project

A Project may use a Provider.

The Provider does not become part of that Project’s identity.

The same Provider may serve:

- Familje-Stunden,

- The Prompt,

- GainPilot,

- Omnira,

- and future customer Projects

through separate Provider Accounts, policies and budgets.

Shared Provider use must not collapse Project isolation.

<a id="section-8-12"></a>
## 8.12 Provider Identity

Every Provider shall have a stable canonical identifier.

The identifier shall remain independent of:

- website URL,

- current brand name,

- account email,

- endpoint,

- Provider Account,

- or Model catalogue.

The Provider may also have:

- legal name,

- trading name,

- former names,

- aliases,

- domains,

- external identifiers,

- and parent-company relationships.

Canonical identity must remain stable across ordinary rebranding.

<a id="section-8-13"></a>
## 8.13 Provider Naming

Provider display names should be recognisable to users.

Canonical identity shall remain separate from display name.

A Provider rename should normally update:

- display name,

- aliases,

- branding metadata,

- and documentation

without replacing the canonical Provider ID.

A legal entity change may require a new Provider or explicit successor relationship.

<a id="section-8-14"></a>
## 8.14 Provider Legal Entity

Where relevant, the Registry should record the legal entity supplying the service.

This may include:

- legal name,

- jurisdiction,

- registered address reference,

- contracting entity,

- and tax or billing entity.

The service brand and legal contracting entity may differ.

This distinction matters for:

- contracts,

- privacy,

- invoices,

- data processing,

- and disputes.

<a id="section-8-15"></a>
## 8.15 Provider Parent Relationship

A Provider may belong to a parent organisation.

Parent relationships may include:

- subsidiary of,

- operated by,

- acquired by,

- reseller of,

- infrastructure hosted by,

- or white-labelled from.

Relationships shall preserve:

- effective date,

- source,

- and impact.

A parent relationship does not automatically merge Provider identities.

<a id="section-8-16"></a>
## 8.16 Provider Successor Relationship

When one Provider replaces another through:

- merger,

- acquisition,

- service migration,

- or reorganisation,

the Registry shall preserve a successor relationship.

Historical Executions must continue to reference the original Provider identity used at the time.

<a id="section-8-17"></a>
## 8.17 Provider Service Family

A Provider may expose several Service Families.

Examples include:

- language Models,

- image generation,

- video generation,

- voice,

- search,

- embeddings,

- storage,

- external agents,

- or developer tools.

Service Families assist organisation.

They shall not replace canonical Capabilities.

<a id="section-8-18"></a>
## 8.18 Provider Product

A Provider Product is a commercial or technical offering.

Products may include:

- subscription plan,

- API platform,

- creative studio,

- enterprise workspace,

- model-hosting service,

- MCP package,

- or managed agent.

Products can change more frequently than Provider identity.

They should be represented separately when product differences materially affect:

- access,

- terms,

- pricing,

- capabilities,

- or privacy.

<a id="section-8-19"></a>
## 8.19 Provider Type

The Registry shall classify Providers by Provider Type.

Types may include:

- external commercial cloud,

- external specialised AI service,

- model-hosting platform,

- tool platform,

- local runtime provider,

- self-hosted platform,

- user-managed service,

- Omnira-managed service,

- infrastructure provider,

- human-assisted provider,

- marketplace,

- or simulation provider.

A Provider may have several relevant types.

Provider Type informs trust and placement but does not determine eligibility alone.

<a id="section-8-20"></a>
## 8.20 External Cloud Provider

An External Cloud Provider executes work on infrastructure outside the user’s and Omnira’s direct control.

It may offer:

- APIs,

- hosted Models,

- storage,

- processing,

- and managed agent systems.

External Providers remain outside Omnira’s trusted core.

They require explicit policy, account and data-placement evaluation.

<a id="section-8-21"></a>
## 8.21 Specialised AI Provider

A Specialised AI Provider focuses on one or several modalities or production areas.

Examples may include:

- voice,

- video,

- image,

- music,

- avatar,

- search,

- or document processing.

Specialisation may create strong Capability quality.

It may also create:

- narrow account terms,

- unique credit systems,

- limited fallback,

- and Provider lock-in.

The Registry shall preserve both strengths and restrictions.

<a id="section-8-22"></a>
## 8.22 Model-Hosting Provider

A Model-Hosting Provider exposes Models that may originate from:

- the Provider,

- third-party creators,

- open-weight communities,

- or customer deployments.

The Registry shall distinguish:

- Provider,

- Model creator,

- Model licence,

- hosted Deployment,

- and Provider terms.

<a id="section-8-23"></a>
## 8.23 Local Runtime Provider

A Local Runtime Provider supplies software that enables Models or Tools to run on user-controlled infrastructure.

Examples may include:

- local language-model runtime,

- inference server,

- media-processing runtime,

- or containerised execution system.

The Provider may supply runtime software without receiving user data externally.

The Deployment and Node determine the actual trust boundary.

<a id="section-8-24"></a>
## 8.24 Self-Hosted Provider

A Self-Hosted Provider represents a service deployed on infrastructure controlled by:

- user,

- Tenant,

- Omnira,

- or customer organisation.

The software supplier and infrastructure operator may differ.

The Registry shall distinguish:

- software Provider,

- deployment operator,

- Runtime Node,

- and data custodian.

<a id="section-8-25"></a>
## 8.25 User-Managed Provider

A User-Managed Provider is operated or contracted directly by the user.

Examples include:

- personal AI subscription,

- personal cloud account,

- local compute,

- or private server.

User management does not remove Fabric governance.

The Provider Account remains scoped and cost-attributed.

<a id="section-8-26"></a>
## 8.26 Omnira-Managed Provider

An Omnira-Managed Provider relationship uses infrastructure, credits or accounts controlled by Omnira.

It may support:

- bundled services,

- shared capacity,

- managed routing,

- or future customer plans.

Omnira-managed access shall still preserve:

- Tenant attribution,

- Project attribution,

- account isolation,

- privacy,

- terms,

- cost,

- and user authority.

<a id="section-8-27"></a>
## 8.27 Human-Assisted Provider

A Human-Assisted Provider requires a person to perform a material Provider operation.

Examples include:

- using a Provider web interface,

- uploading approved references,

- selecting generation settings,

- downloading output,

- or confirming billing.

The Registry shall classify integration maturity honestly.

Human-assisted support is valid.

It is not equivalent to a fully automated API integration.

<a id="section-8-28"></a>
## 8.28 Simulation Provider

A Simulation Provider exists for:

- tests,

- routing simulation,

- cost forecasting,

- failure injection,

- or development.

It shall never be represented as production execution.

Simulation Provider outputs and receipts must be explicitly marked.

<a id="section-8-29"></a>
## 8.29 Provider Trust Boundary

Every external Provider shall be treated as outside Omnira’s trusted core unless a more specific internal relationship has been established.

Provider approval does not imply unrestricted trust.

The Fabric shall control:

- what data is sent,

- what action is requested,

- which account is used,

- what cost is allowed,

- how output is validated,

- and how evidence is preserved.

The Provider controls its own infrastructure and internal behaviour.

This boundary must remain explicit.

<a id="section-8-30"></a>
## 8.30 Provider Trust Level

The Registry may assign Trust Levels such as:

- untrusted,

- discovered,

- experimental,

- reviewed,

- production approved,

- restricted production,

- strategic approved,

- suspended,

- or retired.

Trust Level shall be:

- evidence-based,

- scoped,

- and time-aware.

A trusted Provider may still be ineligible for a specific request.

<a id="section-8-31"></a>
## 8.31 Provider Trust Evidence

Trust evidence may include:

- security documentation,

- privacy terms,

- contractual commitments,

- operational history,

- incident response,

- audit reports,

- conformance tests,

- Provider reputation,

- and direct experience.

Trust evidence must preserve:

- source,

- date,

- scope,

- and limitations.

<a id="section-8-32"></a>
## 8.32 Provider Risk Classification

Provider Risk may consider:

- data handling,

- operational opacity,

- jurisdiction,

- security maturity,

- financial stability,

- rights uncertainty,

- account controls,

- destructive tools,

- and service dependency.

Risk may be classified as:

- minimal,

- low,

- moderate,

- high,

- critical,

- or unknown.

Unknown risk must not default to low.

<a id="section-8-33"></a>
## 8.33 Provider Criticality

Provider Criticality describes how strongly Omnira depends on the Provider.

A Provider may be:

- optional,

- useful,

- important,

- critical,

- or single-source.

Criticality affects:

- monitoring,

- fallback,

- contract review,

- incident planning,

- and migration.

<a id="section-8-34"></a>
## 8.34 Single-Source Provider

A Single-Source Provider supplies a Capability for which no approved equivalent currently exists.

Single-source dependence may be acceptable when explicit.

It shall require:

- dependency record,

- impact analysis,

- contingency plan,

- data-export plan,

- and regular review.

<a id="section-8-35"></a>
## 8.35 Provider Lock-In Profile

The Registry may record lock-in factors such as:

- proprietary asset format,

- Provider-hosted memory,

- irreversible project structure,

- unique reference system,

- non-exportable voices,

- non-transferable credits,

- proprietary workflow,

- or restricted API access.

Lock-in shall be visible rather than accidental.

<a id="section-8-36"></a>
## 8.36 Provider Exit Profile

A Provider Exit Profile may define:

- export support,

- asset download,

- metadata portability,

- account deletion,

- credential revocation,

- data deletion,

- workflow migration,

- and replacement options.

Exit readiness is part of long-term governance.

<a id="section-8-37"></a>
## 8.37 Provider Operational Maturity

Provider maturity may include:

- experimental,

- preview,

- beta,

- generally available,

- enterprise,

- legacy,

- or unknown.

Provider labels are evidence.

Omnira shall evaluate actual operational maturity separately.

<a id="section-8-38"></a>
## 8.38 Provider Integration Maturity

Integration maturity describes Omnira’s relationship with the Provider.

Canonical states may include:

- discovered,

- researched,

- manual external,

- human-assisted,

- experimental API,

- experimental MCP,

- partially automated,

- production API,

- production MCP,

- local production,

- restricted production,

- deprecated,

- and disconnected.

Integration maturity shall be truthful.

<a id="section-8-39"></a>
## 8.39 Provider Lifecycle

Canonical Provider lifecycle states may include:

- proposed,

- discovered,

- under review,

- experimental,

- approved,

- active,

- restricted,

- degraded,

- suspended,

- deprecated,

- disconnected,

- retired,

- and archived.

Lifecycle state is distinct from current health.

<a id="section-8-40"></a>
## 8.40 Proposed Provider

Proposed means the Provider is being considered for future use.

The Registry may contain incomplete information.

No production use is permitted.

<a id="section-8-41"></a>
## 8.41 Discovered Provider

Discovered means the Provider was identified through:

- user suggestion,

- web research,

- API metadata,

- installed connector,

- repository package,

- or existing account.

Discovery does not imply approval.

<a id="section-8-42"></a>
## 8.42 Provider Under Review

Under Review means governance is evaluating:

- capabilities,

- terms,

- privacy,

- security,

- rights,

- cost,

- integration,

- and operational need.

Testing may occur in a restricted environment.

<a id="section-8-43"></a>
## 8.43 Experimental Provider

Experimental means the Provider may be used in bounded tests.

Experimental use should normally require:

- sandbox or development environment,

- non-sensitive data,

- limited budget,

- no automatic publication,

- and enhanced review.

<a id="section-8-44"></a>
## 8.44 Approved Provider

Approved means the Provider may be used for defined scopes and service classes.

Approval shall identify:

- permitted Tenants,

- Projects,

- data classes,

- Capabilities,

- environments,

- and restrictions.

Approved does not mean a usable Provider Account currently exists.

<a id="section-8-45"></a>
## 8.45 Active Provider

Active means at least one production-admitted Provider Account and Connection exists for an approved scope.

Active state does not imply every Capability or account is available.

<a id="section-8-46"></a>
## 8.46 Restricted Provider

Restricted means use is permitted only under additional conditions.

Restrictions may include:

- Public data only,

- selected Projects,

- selected Capabilities,

- low spending limit,

- human review,

- manual operation,

- or no publishing.

<a id="section-8-47"></a>
## 8.47 Degraded Provider

Degraded means the Provider remains usable but has reduced:

- availability,

- quality,

- account access,

- API functionality,

- speed,

- or service coverage.

Degradation must be reflected in routing.

<a id="section-8-48"></a>
## 8.48 Suspended Provider

Suspended means new execution is temporarily blocked.

Reasons may include:

- security Incident,

- rights uncertainty,

- billing dispute,

- terms change,

- authentication compromise,

- severe outage,

- or governance review.

Historical records remain available.

<a id="section-8-49"></a>
## 8.49 Deprecated Provider

Deprecated means the Provider should not be selected for new ordinary work.

Deprecation shall identify:

- reason,

- replacement,

- affected accounts,

- affected Capabilities,

- migration plan,

- and retirement timing.

<a id="section-8-50"></a>
## 8.50 Disconnected Provider

Disconnected means no active governed Connection remains.

The Provider record may remain for:

- history,

- assets,

- cost,

- and provenance.

<a id="section-8-51"></a>
## 8.51 Retired Provider

Retired means the Provider is no longer eligible for new use.

Historical Executions and Assets must remain interpretable.

<a id="section-8-52"></a>
## 8.52 Archived Provider

Archived means the Provider record is retained primarily for historical and audit purposes.

It may be hidden from ordinary discovery.

<a id="section-8-53"></a>
## 8.53 Provider Lifecycle Transition

Lifecycle transitions shall preserve:

- previous state,

- new state,

- actor,

- reason,

- evidence,

- effective time,

- affected scope,

- and rollback or recovery plan where relevant.

No Provider shall move directly from discovered to unrestricted active use.

<a id="section-8-54"></a>
## 8.54 Provider Registry Entry

A Provider Registry entry should include or reference:

- providerId,

- canonical name,

- legal entity,

- aliases,

- Provider Type,

- Service Families,

- ownership relationships,

- trust level,

- risk classification,

- criticality,

- lifecycle,

- regions,

- terms,

- privacy,

- rights,

- security evidence,

- integration maturity,

- Provider Accounts,

- Connections,

- Adapters,

- capability claims,

- health references,

- incidents,

- and provenance.

<a id="section-8-55"></a>
## 8.55 Provider Provenance

Provider metadata shall preserve provenance.

Sources may include:

- official documentation,

- contracts,

- privacy policy,

- service terms,

- API metadata,

- user account information,

- operational tests,

- audit reports,

- and human review.

Conflicting sources shall remain visible.

<a id="section-8-56"></a>
## 8.56 Provider Metadata Freshness

Provider information changes frequently.

Metadata should include:

- observedAt,

- effectiveAt,

- source,

- expected review,

- and stale threshold.

Stale terms, pricing or privacy information must not be represented as current certainty.

<a id="section-8-57"></a>
## 8.57 Provider Region

The Registry shall record regions where the Provider:

- contracts,

- operates,

- processes data,

- stores data,

- bills,

- and offers service.

These regions may differ.

Provider marketing location does not prove data-processing location.

<a id="section-8-58"></a>
## 8.58 Data-Processing Region

Data-processing region identifies where request data may be processed.

It may be:

- fixed,

- configurable,

- account-dependent,

- model-dependent,

- routed dynamically,

- or unknown.

Unknown region may make the Provider ineligible for protected data.

<a id="section-8-59"></a>
## 8.59 Data-Storage Region

Data-storage region identifies where persistent or temporary Provider data may be stored.

Processing and storage regions must remain distinguishable.

<a id="section-8-60"></a>
## 8.60 Provider Jurisdiction

Provider jurisdiction may affect:

- contracts,

- privacy,

- law enforcement access,

- dispute resolution,

- and data transfer.

The Registry may preserve:

- legal jurisdiction,

- contracting entity,

- governing law,

- and dispute forum.

The Fabric does not replace legal review.

<a id="section-8-61"></a>
## 8.61 Regional Availability

A Provider may offer different:

- Models,

- Capabilities,

- pricing,

- terms,

- and quotas

by region.

Regional support shall be represented through Provider Product, Account or Deployment metadata as appropriate.

<a id="section-8-62"></a>
## 8.62 Provider Terms Record

A Provider Terms Record shall preserve material service terms.

It may include:

- terms identifier,

- source,

- version,

- effective date,

- accepted date,

- accepting Principal,

- applicable account class,

- commercial-use terms,

- data-use terms,

- retention,

- prohibited use,

- attribution,

- indemnity,

- and review status.

Terms history shall not be overwritten.

<a id="section-8-63"></a>
## 8.63 Terms Version

Terms shall be versioned where possible.

Executions may need to reference the applicable Terms Version.

If the Provider does not expose versions clearly, Omnira shall preserve:

- retrieval date,

- checksum,

- source snapshot,

- or equivalent evidence.

<a id="section-8-64"></a>
## 8.64 Terms Acceptance

Accepting new Provider terms is an administrative or contractual action.

It may require:

- owner authority,

- legal review,

- cost review,

- and policy update.

An Agent shall not accept materially changed terms autonomously unless explicitly authorised.

<a id="section-8-65"></a>
## 8.65 Terms Change

A Terms Change may affect:

- commercial rights,

- data retention,

- training use,

- pricing,

- acceptable use,

- or account ownership.

Material change may trigger:

- suspension,

- review,

- reapproval,

- migration,

- or provider restriction.

<a id="section-8-66"></a>
## 8.66 Privacy Policy Record

The Registry shall preserve Provider privacy-policy evidence.

It may include:

- policy version,

- collection practices,

- retention,

- subprocessors,

- training use,

- region,

- deletion,

- data-subject rights,

- and contact path.

Privacy claims must remain Account- and Product-aware where they differ.

<a id="section-8-67"></a>
## 8.67 Data Processing Agreement

Enterprise or managed Provider relationships may include a Data Processing Agreement.

The Registry may preserve:

- agreement identifier,

- scope,

- parties,

- effective date,

- subprocessors,

- regional terms,

- and review state.

The agreement itself may remain in a governed document system.

<a id="section-8-68"></a>
## 8.68 Provider Subprocessor

A Provider may rely on subprocessors.

The Registry may record material subprocessors where relevant.

Subprocessor changes may affect protected-data eligibility.

<a id="section-8-69"></a>
## 8.69 Training-Use Policy

The Registry shall record whether Provider data may be used for:

- training,

- service improvement,

- safety review,

- human review,

- or no such use.

The answer may vary by:

- Product,

- Account,

- enterprise agreement,

- API,

- web interface,

- region,

- and Model.

One general Provider flag is insufficient.

<a id="section-8-70"></a>
## 8.70 Retention Policy

Provider retention may differ for:

- prompts,

- Inputs,

- Outputs,

- logs,

- abuse review,

- assets,

- threads,

- and deleted content.

Retention shall be represented at the narrowest correct level.

<a id="section-8-71"></a>
## 8.71 Provider Deletion Support

The Registry may record whether the Provider supports:

A Sandbox Account is intended for:

- development,

- tests,

- previews,

- or experimentation.

A Production Account is approved for live governed execution.

It should have:

- appropriate owner,

- secure credential,

- monitoring,

- billing controls,

- incident path,

<a id="section-8-104"></a>

- connecting,

- revoked,

- disconnected,

- and archived.

<a id="section-8-105"></a>
## 8.105 Connecting State

Connecting means authentication or setup is underway.

The account must not be represented as ready before verification.

<a id="section-8-106"></a>
## 8.106 Connected State

Connected means the technical relationship exists.

Connected does not prove:

- eligible terms,

- available credits,

- correct scope,

- or production approval.

<a id="section-8-107"></a>
## 8.107 Active Account

Active means the account is eligible for defined governed use.

Eligibility remains request-specific.

<a id="section-8-108"></a>
## 8.108 Authentication Required

Authentication Required means the account relationship exists but current credentials cannot be used.

Reasons may include:

- expiry,

- revocation,

- user re-consent,

- changed OAuth scopes,

- or multi-factor requirement.

<a id="section-8-109"></a>
## 8.109 Payment Required

Payment Required means execution is blocked by:

- failed payment,

- expired subscription,

- required upgrade,

- or missing billing method.

The system shall not classify this as a generic Provider outage.

<a id="section-8-110"></a>
## 8.110 Exhausted Account

Exhausted means relevant credits or quota are unavailable.

Exhaustion may be temporary.

It shall affect account eligibility without retiring the Provider.

<a id="section-8-111"></a>
## 8.111 Suspended Account

A Provider or Omnira may suspend the account.

The Registry shall preserve:

- reason,

- detected time,

- affected workflows,

- and recovery path.

<a id="section-8-112"></a>
## 8.112 Revoked Account

Revoked means authorisation has been withdrawn.

No new execution may use the account.

Existing external jobs may require reconciliation.

<a id="section-8-113"></a>
## 8.113 Disconnected Account

Disconnected means Omnira no longer has an active Connection.

Provider-side assets or data may still exist.

The system shall not imply Provider deletion merely because local credentials were removed.

## 8.167 Provider Credit Conversion

- purchased credit cost,

- included credit source,

- Product usage rate,

- effective currency value,

- and uncertainty.

<a id="section-8-168"></a>
## 8.168 Provider Minimum Charge

Some Providers may round usage or impose minimum charges.

<a id="section-8-169"></a>
## 8.169 Provider Retry Cost

The Registry or pricing metadata should identify:

- failed-job charging,

- cancellation refund,

- retry policy,

- and credit return behaviour.

<a id="section-8-170"></a>
## 8.170 Provider Cancellation Economics

Cancellation may:

- prevent charge,

- partially charge,

- fully charge,

- or be unavailable.

The Fabric must not promise cost recovery without evidence.

<a id="section-8-171"></a>
## 8.171 Provider Refund Behaviour

Refunds or credit returns may be:

- automatic,

- manual,

- conditional,

- delayed,

- or unavailable.

Refund state belongs to cost reconciliation.

<a id="section-8-172"></a>
## 8.172 Provider Currency

Provider billing currency may differ from Project budget currency.

The cost system shall preserve exchange-rate assumptions separately.

<a id="section-8-173"></a>
## 8.173 Provider Tax Treatment

Taxes, VAT and invoice handling belong to financial systems.

The Registry may reference:

- invoice availability,

- tax region,

- and billing entity.

<a id="section-8-174"></a>
## 8.174 Provider Cost Transparency

Provider cost transparency may be classified as:

- exact pre-execution,

- estimated,

- usage-based,

- delayed,

- opaque,

- or unknown.

Opaque pricing increases approval and reservation risk.

<a id="section-8-175"></a>
## 8.175 Provider Economic Suitability

Economic suitability shall consider:

- direct price,

- retries,

- correction cost,

- Account capacity,

- subscription value,

- quality,

- and operational burden.

Cheapest advertised price is not sufficient.

<a id="section-8-176"></a>
## 8.176 Provider Routing Preference

A Provider may receive a preference based on:

- user choice,

- Project policy,

- quality evidence,

- cost,

- privacy,

- Product,

- Model,

- reason,

<a id="section-8-178"></a>
## 8.178 Provider Allowlist

Policies may define approved Providers or Accounts.

Allowlist membership does not prove current compatibility.

<a id="section-8-179"></a>
## 8.179 Provider Denylist

Deny reasons may include:

- privacy,

- rights,

- cost,

- security,

- quality,

- user preference,

- or Incident.

- Project Internal,

- Confidential,

- Account,

- Product,

- region,

- contract,

- and Connection.

Public data may use a wider Provider set.

- acceptable retention,

- no unauthorised training use,

<a id="section-8-183"></a>
## 8.183 Confidential Eligibility

- enterprise terms,

- approved region,

- private Deployment,

- zero or bounded retention,

<a id="section-8-184"></a>
## 8.184 Local Only Eligibility

External Providers are normally ineligible for Local Only data.

A local runtime Provider may be eligible when execution remains user-controlled.

<a id="section-8-185"></a>

The Provider Registry shall not create exceptions to prohibited classification.

<a id="section-8-186"></a>
## 8.186 Provider Rights Eligibility

Provider eligibility may depend on:

- derivative rights,

- attribution,

- watermarking,

- output ownership,

## 8.187 Provider Child-Facing Eligibility

Child-facing content may require:

- Provider policy compatibility,

- visual safety,

- stronger review,

- rights,

- and publication controls.

<a id="section-8-188"></a>
## 8.188 Provider Voice Eligibility

- voice ownership,

- cloning controls,

- account security,

<a id="section-8-189"></a>
## 8.189 Provider Code Eligibility

Code Providers may require:

- tool restrictions,

A coding Provider shall not gain repository-write authority automatically.

<a id="section-8-190"></a>
## 8.190 Provider Publication Eligibility

Providers exposing publication tools require:

- target account mapping,

- explicit publication authority,

- audit,

- idempotency,

- and verification.

<a id="section-8-191"></a>
## 8.191 Provider Administrative Eligibility

Administrative Provider operations include:

- changing billing,

- adding users,

- deleting workspace,

- accepting terms,

- rotating keys,

- Provider identity,

- intended Capabilities,

- Projects,

- expected value,

- access model,

- pricing,

- privacy,

- rights,

- integration method,

## 8.194 Provider Need Assessment

Before integration, Omnira should determine:

- which Capability gap exists,

- whether existing Providers can satisfy it,

- whether local execution is possible,

- whether the Provider creates meaningful value,

Provider count is not a success metric.

- official documentation,

- terms,

- privacy,

- pricing,

- API or MCP access,

- commercial rights,

- limits,

- operational maturity,

- rights,

- account controls,

- billing,

- lock-in,

- and operational dependency.

The Provider shall not redefine Omnira Capability names.

- account type,

- Project scope,

- environment,

- billing source,

- credential owner,

- and recovery owner.

## 8.199 Provider Credential Setup

## 8.200 Provider Connection Validation

- Account,

- permissions,

- environment,

- basic read operation,

- billing visibility,

<a id="section-8-201"></a>
## 8.201 Provider Adapter Validation

Adapter validation shall test:

- canonical request translation,

- output normalisation,

- errors,

- usage,

- retries,

- callbacks,

<a id="section-8-202"></a>
## 8.202 Provider Sandbox Test

Initial Provider testing should use:

- approved test data,

- low budget,

- no public publication,

<a id="section-8-203"></a>
## 8.203 Provider Conformance Review

Production admission shall require evidence that:

- scope,

- cost,

- data placement,

- rights,

<a id="section-8-206"></a>
## 8.206 Provider Offboarding

4. Migrate workflows.

9. Preserve historical records.

## 8.207 Stop-New-Execution Boundary

Offboarding should first prevent new ordinary work while allowing:

- reconciliation,

- export,

- recovery,

- and required deletion actions.

## 8.208 Running Job Reconciliation

Active Provider jobs must be classified as:

- cancellable,

- completing,

- failed,

- unknown,

- or requiring manual inspection.

<a id="section-8-209"></a>
## 8.209 Provider Asset Export

Provider-side Assets may need export before disconnection.

- files,

- metadata,

- Provider IDs,

- provenance,

- and ownership.

<a id="section-8-210"></a>
## 8.210 Provider Workflow Migration

- alternative Provider,

- alternative Model,

- human-assisted path,

- or retired Capability.

<a id="section-8-211"></a>
## 8.211 Credential Revocation

Credentials shall be revoked after the required operational steps.

<a id="section-8-212"></a>
## 8.212 Provider Data Deletion

- Inputs,

- Outputs,

- threads,

- requested,

- completed,

- verified,

- failed,

- and unknown.

- owner approval,

- asset export,

- Execution Receipts,

- terms approver,

<a id="section-8-219"></a>

<a id="section-8-220"></a>
## 8.220 Provider Visibility

Provider visibility may be:

- platform-wide,

- administrative,

- experimental,

## 8.221 Provider Discovery

- list Providers,

- query by Capability,

- get Products,

- list Provider Accounts,

- inspect terms status,

## 8.229 Provider Registry Export

- documentation,

- disaster recovery,

- audit,

- SDK generation,

## 8.230 Provider Registry Import

- validated,

- reviewed,

<a id="section-8-231"></a>
## 8.231 Provider Registry Federation

Future Omnira deployments may federate Provider metadata across:

- user nodes,

- Tenants,

- local Account privacy,

- restrictions,

- and authority.

<a id="section-8-232"></a>

<a id="section-8-233"></a>

A Project may use a specialised Provider relationship not visible elsewhere.

Its credentials, Accounts, Assets and cost remain Project-scoped.

<a id="section-8-234"></a>
## 8.234 Local Provider Registration

The Registry shall preserve:

- operator,

- Node,

- Runtime,

- scope,

- and trust.

Future integrations may be distributed as Provider Packages containing:

- Provider metadata,

- Adapter,

- Capability mappings,

- schemas,

- tests,

- and documentation.

- connect credentials,

- accept terms,

- grant permissions,

<a id="section-8-236"></a>
## 8.236 Provider Package Trust

- Omnira official,

- Provider official,

- verified partner,

- community,

- local private,

<a id="section-8-237"></a>
## 8.237 Provider Package Update

Updates may change:

- Adapter,

- tools,

- permissions,

- Capability mappings,

- or security.

<a id="section-8-238"></a>
## 8.238 Provider Package Removal

- quality,

- cost,

- privacy,

- reliability,

- commercial rights,

- and lock-in.

<a id="section-8-240"></a>
## 8.240 Provider Explanation

The system should be able to explain:

- why a Provider is eligible,

- why it was selected,

- which Account will be used,

- what data will be sent,

- what it may cost,

<a id="section-8-241"></a>
## 8.241 Provider Selection Decision

Provider selection shall be recorded through a Selection Decision.

- Capability,

- Provider Accounts,

- Models or Tools,

- policy,

- quality,

- cost,

- latency,

- health,

- lifecycle,

- Account,

- Connection,

- Capability support,

- data class,

- region,

- rights,

- authority,

- budget,

- health,

- and restrictions.

- data classification,

- rights,

- quality,

- budget,

- and approval.

- Model,

- Product,

- Account,

- Deployment,

## 8.246 Cross-Provider Fallback

Cross-Provider fallback changes:

- terms,

- Account,

- pricing,

- data processing,

<a id="section-8-247"></a>
## 8.247 Provider Substitution Disclosure

Material Provider substitution should be disclosed when it affects:

- user expectation,

- privacy,

- cost,

- quality,

- rights,

<a id="section-8-248"></a>

Omnira shall not prefer a Provider merely because Omnira receives:

- commission,

- margin,

- credit,

- referral benefit,

- or commercial partnership.

<a id="section-8-249"></a>
## 8.249 Provider Commercial Relationship

The Registry may record:

- partner,

- reseller,

- affiliate,

- customer,

- negotiated contract,

- or ordinary subscriber relationship.

<a id="section-8-250"></a>
## 8.250 Provider Conflict of Interest

<a id="section-8-251"></a>
## 8.251 Provider Marketplace Governance

A future Provider marketplace shall not:

- grant automatic production access,

- hide Provider margin,

- weaken quality,

<a id="section-8-252"></a>
## 8.252 Provider Competition

The Fabric should preserve multiple eligible Providers where this improves:

- resilience,

- cost,

- quality,

- and negotiation.

<a id="section-8-253"></a>
## 8.253 Provider Consolidation

Using fewer Providers may reduce:

- complexity,

- contracts,

- credentials,

- and maintenance.

<a id="section-8-254"></a>
## 8.254 Provider Portfolio

Omnira may maintain a Provider Portfolio balancing:

- local resources,

- user-owned Accounts,

- managed Providers,

- premium specialists,

- and fallback services.

<a id="section-8-255"></a>
## 8.255 Provider Portfolio Review

- unused Providers,

- duplicate subscriptions,

- cost,

- lock-in,

- security,

- quality,

- and current demand.

## 8.256 Unused Provider

- restricted,

- disconnected,

- or retired.

Credentials should not remain active without need.

<a id="section-8-257"></a>
## 8.257 Duplicate Provider Coverage

Several Providers may supply the same Capability.

<a id="section-8-258"></a>

The Fabric may recommend consolidation while respecting:

- fallback,

- rights,

- export format,

- metadata export,

- batch export,

- API support,

## 8.260 Provider Prompt Portability

<a id="section-8-261"></a>
## 8.261 Provider Voice Portability

Voice Assets may be:

- exportable,

- Provider-locked,

- reproducible,

- or legally restricted.

<a id="section-8-262"></a>
## 8.262 Provider Character-System Portability

Creative Providers may store:

- character references,

- style profiles,

- or project-specific training.

The Registry should record:

- exportability,

- ownership,

- reusability,

- and Provider lock-in.

<a id="section-8-263"></a>
## 8.263 Provider Thread Portability

Provider-hosted threads or assistants may contain useful context.

Export and deletion behaviour should be known.

<a id="section-8-264"></a>

- Inputs,

- Outputs,

- Assets,

- threads,

- or metadata.

- synchronous response,

- callback,

- download URL,

- Asset library,

- export,

<a id="section-8-266"></a>
## 8.266 Provider Download Link

- expiry,

- authentication,

- checksum where possible,

- correlation,

- reconciliation,

- manual inspection,

<a id="section-8-271"></a>

- rate limit,

- latency,

- cost,

- Provider guidance,

- and deadline.

<a id="section-8-272"></a>

- Omnira Execution state,

- Provider job state,

- Provider Assets,

- usage,

- and billing.

- authentication,

- quota,

- outage,

- malformed request,

- timeout,

- Provider failure,

- Account failure,

- Connection failure,

- Adapter defect,

- request defect,

<a id="section-8-275"></a>
## 8.275 Provider Retry Guidance

17. The Registry SHALL support local, external, managed and human-assisted Providers.

18. The Registry SHALL NOT contain raw secrets.

19. The Registry SHALL distinguish architectural definition from operational availability.

20. The Registry SHALL remain suitable for human and machine consumers.

<a id="section-8-356"></a>
## 8.356 Provider Registry Invariants

The following invariants shall remain true:

- No Provider becomes an Agent identity.

- No Provider Account becomes the Provider itself.

- No Connection becomes proof of production approval.

- No credential becomes Provider identity.

- No Provider claim becomes verified Capability support without evidence.

- No healthy Provider bypasses data, rights or authority policy.

- No shared Account hides Project usage.

- No personal Account becomes silent platform capacity.

- No development MCP session becomes a hidden production dependency.

- No manual Provider workflow is represented as autonomous.

- No Provider Workspace name replaces canonical Project scope.

- No Provider terms are treated as permanently stable.

- No Provider retirement deletes historical provenance.

- No commercial relationship silently overrides user value.

- No Provider-side Asset library becomes Omnira’s canonical Asset system.

- No Provider-hosted thread becomes the only long-term memory.

- No unknown region or retention state becomes favourable by default.

- No Provider fallback weakens the original request contract.

- No Provider disconnection is misrepresented as verified data deletion.

- No Provider receives authority beyond the bounded execution submitted to it.

<a id="section-8-357"></a>
## 8.357 Closing Statement

The Provider Registry gives Omnira a governed understanding of the organisations, services, runtimes and operational relationships that supply intelligence resources.

It separates:

- Provider from Account,

- Account from Connection,

- Connection from credential,

- Provider from Model,

- Model from Deployment,

- Provider from Adapter,

- and Provider access from execution authority.

This separation is essential because Provider relationships are not static.

Brands change.

Terms change.

Products change.

Prices change.

Models appear and disappear.

Credits expire.

Sessions break.

Accounts become suspended.

APIs evolve.

MCP servers expose new tools.

Provider workspaces accumulate Assets.

Commercial partnerships create incentives.

A development integration may appear functional long before it is safe for production.

The Provider Registry ensures that these changes remain governed at the supplier layer rather than leaking into every Project, Agent and Workflow.

For Familje-Stunden, it allows OpenArt, ElevenLabs and image Providers to support Nova and Pling production without owning the characters, the Project, the memory or the publication authority.

For The Prompt, it allows research, reasoning, avatar, voice and media Providers to remain separate from editorial truth.

For GainPilot, it allows economical Provider choices without creating an isolated provider architecture.

For Omnira, it allows local Models, user-owned subscriptions, managed credits and external services to coexist within one controlled intelligence portfolio.

The Capability Registry defines what must be done.

The Model Registry defines which intelligence resources may perform it.

The Provider Registry defines who supplies access and under which relationship.

The Provider Account defines whose access and billing are used.

The Connection defines how Omnira communicates.

The Adapter defines how canonical meaning is translated.

Policy defines whether the relationship is permitted.

Routing selects the eligible path.

Evidence records what actually occurred.

The Provider supplies capability.

The Provider does not own the intent.

The Provider does not own the Agent.

The Provider does not own the Project.

The Provider does not own Omnira’s intelligence architecture.

The user retains direction.

Omnira retains governance.

The Fabric retains the boundary.
