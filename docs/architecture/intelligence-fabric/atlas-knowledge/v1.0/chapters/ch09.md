# Chapter 9 — Agent, Tool and Execution Resource Registry

<a id="section-9-1"></a>
## 9.1 Chapter Status

This chapter defines the canonical architecture, object model, lifecycle, governance boundaries and Registry contracts for Agents, Tools and Execution Resources within the Omnira Intelligence Fabric.

It establishes:

- how Agents are represented as persistent Omnira identities rather than Model instances,

- how Agent identity remains independent from Provider, Model, Runtime and Session,

- how Tools are represented as governed executable resources,

- how deterministic Tools remain distinct from Models and Agents,

- how MCP-discovered Tools enter the same canonical Tool model,

- how local commands, APIs, browser actions, databases, search systems and device operations may become Tools,

- how execution infrastructure is represented independently from the intelligence it hosts,

- how Runtime Nodes, Runtime Services, Execution Environments and Resource Pools are registered,

- how local, cloud, private, edge and human-assisted resources coexist,

- how capabilities are bound to Agents, Tools and execution resources,

- how resource ownership, Project scope, Tenant scope and Environment remain explicit,

- how lifecycle, Version, availability, health and qualification remain separate concepts,

- how discovery differs from registration,

- how registration differs from approval,

- how approval differs from execution eligibility,

- how execution eligibility depends on current policy and context,

- how authority remains external to resource existence,

- how side effects are classified,

- how permissions and access requirements are represented without embedding raw Secrets,

- how resource dependencies are represented,

- how scheduling and placement metadata are exposed,

- how cost and capacity metadata are attached,

- how trust and certification evidence are represented,

- how resource drift is detected,

- how compromised or stale resources are suspended,

- how resources are deprecated and retired,

- how Agents may call Tools only through governed Plans and authority,

- how Tools may never self-authorise,

- how Tools may never become policy simply because they describe themselves as capable,

- how Agent-to-Agent execution resources are represented,

- how human operators and human-assisted execution are represented truthfully,

- how Stage 1 shall implement the minimum viable Registry foundation,

- and how future resources can be introduced without altering the canonical architecture.

This chapter is normative after formal approval.

Chapter 10 defines how registered capabilities and resources are assembled into Intelligence Plans and Execution Graphs.

Later chapters define Routing, cost, Quality, reliability, scheduling, integrations, Credentials, local intelligence, authority, observability and conformance in greater depth.

<a id="section-9-2"></a>
## 9.2 Purpose

Omnira must understand not only which Models and Providers exist.

It must also understand:

- which Agents exist,

- which Tools exist,

- where work may execute,

- which Runtime hosts which resource,

- which resources are available now,

- which resources are allowed for one Project,

- which resources produce side effects,

- which resources require approval,

- which resources are local,

- which resources are external,

- which resources are human-operated,

- and which resources remain safe and qualified for use.

Without canonical resource Registries, Omnira could:

- confuse an Agent with the Model currently powering it,

- grant new authority merely because a new Tool appears,

- expose arbitrary MCP Tools automatically,

- call local commands outside their intended Project,

- send a job to an offline Node,

- choose a Runtime that lacks required hardware,

- execute a publication Tool when only generation was authorised,

- mix personal and Project browser Sessions,

- treat a human-assisted service as autonomous,

- or allow a compromised resource to remain eligible because it still responds.

The Registry architecture exists so the Fabric can answer:

- What resource is this?

- Who owns it?

- What type of resource is it?

- What Version is active?

- What Capabilities does it expose?

- Under which conditions?

- In which Environment?

- For which Tenant and Project?

- Through which Runtime?

- With which dependencies?

- What side effects can it create?

- What authority is required?

- What data may it process?

- What does it cost?

- What capacity does it have?

- Is it healthy?

- Is it certified?

- Has it drifted?

- Is it currently eligible?

<a id="section-9-3"></a>
## 9.3 Resource

A Resource is a registered entity that may participate in intelligence planning or execution.

<a id="section-9-4"></a>
## 9.4 Resource Classes

Canonical Resource classes include:

- Agent Resource,

- Tool Resource,

- Model Resource,

- Provider Resource,

- Execution Resource,

- Runtime Node,

- Runtime Service,

- Human Resource,

- External Agent Resource,

- and Resource Pool.

<a id="section-9-5"></a>
## 9.5 Registry

A Registry is the canonical source of metadata describing one Resource class or related resource domain.

<a id="section-9-6"></a>
## 9.6 Resource Registration

Registration makes a Resource known to Omnira.

Registration does not make the Resource automatically eligible for production use.

<a id="section-9-7"></a>
## 9.7 Discovery

Discovery identifies a possible Resource.

Discovery is not registration.

<a id="section-9-8"></a>
## 9.8 Qualification

Qualification evaluates whether a registered Resource satisfies defined requirements.

<a id="section-9-9"></a>
## 9.9 Certification

Certification provides evidence-backed eligibility for defined scopes and uses.

<a id="section-9-10"></a>
## 9.10 Execution Eligibility

Execution Eligibility is a contextual Decision that a Resource may participate in one specific Plan or Attempt.

Eligibility is determined at execution time from:

- Registry state,

- policy,

- Classification,

- authority,

- health,

- capacity,

- certification,

- Budget,

- and Request constraints.

<a id="section-9-11"></a>
## 9.11 Resource Identity

Every canonical Resource shall have a stable Resource identity.

<a id="section-9-12"></a>
## 9.12 Resource Version

Every materially mutable Resource definition shall have a Version.

<a id="section-9-13"></a>
## 9.13 Resource Instance

A Resource Instance is one concrete operational instance of a Resource definition.

<a id="section-9-14"></a>
## 9.14 Resource Definition Versus Instance

A Tool definition may describe one operation.

Several deployed Tool Instances may implement it.

A Model definition may describe one Model.

Several Deployments may serve it.

An Agent definition may describe one Agent identity.

Several Sessions or Runtime processes may execute it.

<a id="section-9-15"></a>
## 9.15 Resource Ownership

Every Resource shall identify an ownership model.

<a id="section-9-16"></a>
## 9.16 Ownership Types

Ownership may include:

- user-owned,

- Project-owned,

- Tenant-owned,

- Omnira-owned,

- Provider-owned,

- device-owned,

- organisation-owned,

- and externally-operated.

<a id="section-9-17"></a>
## 9.17 Ownership Is Not Authority

Owning a Resource does not automatically authorise every operation through it.

<a id="section-9-18"></a>
## 9.18 Resource Scope

Resources may be scoped by:

- Tenant,

- Project,

- Environment,

- device,

- Account,

- Runtime,

- region,

- or Capability.

<a id="section-9-19"></a>
## 9.19 Global Resource

A Resource may be globally discoverable while remaining conditionally eligible.

<a id="section-9-20"></a>
## 9.20 Project Resource

A Project Resource is intended for one Project or defined Project set.

<a id="section-9-21"></a>
## 9.21 Tenant Resource

A Tenant Resource may be shared among authorised Projects within one Tenant.

<a id="section-9-22"></a>
## 9.22 Personal Resource

A Personal Resource belongs to one user.

Personal ownership shall not make it available to Projects automatically.

<a id="section-9-23"></a>
## 9.23 Environment Scope

Resource definitions shall distinguish:

- development,

- test,

- staging,

- production,

- recovery,

- and other governed Environments.

<a id="section-9-24"></a>
## 9.24 Cross-Environment Use

A production Plan shall not use a development Resource merely because schemas are compatible.

<a id="section-9-25"></a>
## 9.25 Resource State

Every Resource shall have a lifecycle state.

<a id="section-9-26"></a>
## 9.26 Canonical Resource Lifecycle

States may include:

- discovered,

- proposed,

- registered,

- validating,

- qualified,

- active,

- degraded,

- suspended,

- deprecated,

- retired,

- revoked,

- unavailable,

- and archived.

<a id="section-9-27"></a>
## 9.27 Discovered

The Resource has been observed but not admitted.

<a id="section-9-28"></a>
## 9.28 Proposed

The Resource is being considered for registration.

<a id="section-9-29"></a>
## 9.29 Registered

The Resource exists in the canonical Registry.

<a id="section-9-30"></a>
## 9.30 Validating

Technical and governance validation is in progress.

<a id="section-9-31"></a>
## 9.31 Qualified

Required baseline checks have passed.

<a id="section-9-32"></a>
## 9.32 Active

The Resource may become eligible when contextual policy permits.

<a id="section-9-33"></a>
## 9.33 Degraded

The Resource remains partially usable but has known limitations.

<a id="section-9-34"></a>
## 9.34 Suspended

The Resource shall not receive new production work until reviewed.

<a id="section-9-35"></a>
## 9.35 Deprecated

The Resource remains supported temporarily but should not receive new adoption.

<a id="section-9-36"></a>
## 9.36 Retired

The Resource shall not receive new work.

<a id="section-9-37"></a>
## 9.37 Revoked

The Resource has lost authority, trust or access and is explicitly blocked.

<a id="section-9-38"></a>
## 9.38 Unavailable

The Resource cannot currently execute.

Unavailability is operational rather than necessarily governance-related.

<a id="section-9-39"></a>
## 9.39 Archived

The Resource remains available for historical interpretation only.

<a id="section-9-40"></a>
## 9.40 Resource Lifecycle Evidence

Every material state transition shall be attributable.

<a id="section-9-41"></a>
## 9.41 Availability

Availability describes whether a Resource can currently receive work.

<a id="section-9-42"></a>
## 9.42 Availability Is Not Lifecycle

An active Resource may be unavailable.

A deprecated Resource may still be technically available.

<a id="section-9-43"></a>
## 9.43 Health

Health describes observed fitness to serve.

<a id="section-9-44"></a>
## 9.44 Health Is Not Eligibility

A healthy Resource may still be ineligible because of:

- privacy,

- Project scope,

- authority,

- Budget,

- rights,

- or policy.

<a id="section-9-45"></a>
## 9.45 Capability Binding

A Capability Binding declares that a Resource may satisfy a canonical Capability under stated conditions.

<a id="section-9-46"></a>
## 9.46 Binding Identity

Every material Capability Binding should have stable identity and Version.

<a id="section-9-47"></a>
## 9.47 Binding Conditions

Conditions may include:

- supported Input types,

- Output types,

- context limits,

- required Runtime,

- required Account,

- Classification maximum,

- side effects,

- cost model,

- and certification.

<a id="section-9-48"></a>
## 9.48 Binding Claim

A Resource owner or Adapter may claim support for a Capability.

Claims do not become trusted production facts without validation.

<a id="section-9-49"></a>
## 9.49 Binding Evidence

Capability Bindings should reference supporting evidence.

<a id="section-9-50"></a>
## 9.50 Unsupported Capability

A Resource shall reject unsupported Capability use before consequential execution.

<a id="section-9-51"></a>
## 9.51 Resource Metadata

Canonical resource metadata should include:

- identity,

- type,

- Version,

- owner,

- scope,

- lifecycle,

- capabilities,

- dependencies,

- Runtime,

- health,

- cost,

- authority requirements,

- side effects,

- Classification limits,

- provenance,

- and certification.

<a id="section-9-52"></a>
## 9.52 Resource Tag

Tags may assist search and administration.

Tags shall not determine authority by themselves.

<a id="section-9-53"></a>
## 9.53 Resource Label

Human-readable labels may change without changing identity.

<a id="section-9-54"></a>
## 9.54 Resource Alias

Aliases may exist for convenience.

Canonical identity shall remain stable.

<a id="section-9-55"></a>
## 9.55 Alias Collision

Aliases shall not create ambiguous resource resolution.

<a id="section-9-56"></a>
## 9.56 Resource Provenance

The Registry should preserve how and when a Resource definition entered Omnira.

<a id="section-9-57"></a>
## 9.57 Resource Source

Sources may include:

- manual registration,

- Adapter discovery,

- MCP discovery,

- local Runtime discovery,

- deployment manifest,

- configuration,

- or migration import.

<a id="section-9-58"></a>
## 9.58 Imported Resource

Imported legacy Resources shall retain import provenance and uncertainty.

<a id="section-9-59"></a>
## 9.59 Agent Resource

An Agent Resource represents a persistent Omnira intelligence actor with:

- identity,

- role,

- policy,

- Memory access,

- Tool access,

- authority boundaries,

- and operational configuration.

<a id="section-9-60"></a>
## 9.60 Agent Identity

Agent identity is owned by Omnira.

<a id="section-9-61"></a>
## 9.61 Agent Identity Independence

Agent identity shall remain independent from:

- Provider,

- Model,

- Deployment,

- Runtime,

- Session,

- Tool set,

- and physical Node.

<a id="section-9-62"></a>
## 9.62 Agent Example

Atlas remains Atlas when execution changes from one external reasoning Model to another.

<a id="section-9-63"></a>
## 9.63 Agent Example Two

Arnold remains Arnold when coaching reasoning moves from cloud inference to a local Model.

<a id="section-9-64"></a>
## 9.64 Agent Definition

An Agent Definition describes the canonical Agent.

It should include:

- agentId,

- name,

- role,

- owner,

- Tenant,

- default Project relationships,

- policy profile,

- Memory Domains,

- Tool policy,

- Authority Level,

- escalation rules,

- lifecycle,

- and Version.

<a id="section-9-65"></a>
## 9.65 Agent Definition Identity

Every Agent Definition shall have stable identity and Version.

<a id="section-9-66"></a>
## 9.66 Agent Role

The role defines the Agent’s intended function.

Examples include:

- executive coordinator,

- coach,

- researcher,

- creative producer,

- reviewer,

- coding Agent,

- and workflow operator.

<a id="section-9-67"></a>
## 9.67 Role Is Not Authority

A descriptive role shall not grant permissions automatically.

<a id="section-9-68"></a>
## 9.68 Agent Version

Material changes to:

- system instructions,

- role policy,

- allowed Tool classes,

- Memory access,

- or operating constraints

should create a new Agent Version.

<a id="section-9-69"></a>
## 9.69 Model Swap

Changing the Model serving an Agent shall not necessarily create a new Agent identity.

<a id="section-9-70"></a>
## 9.70 Agent Session

An Agent Session represents one bounded interaction or execution context.

<a id="section-9-71"></a>
## 9.71 Agent Session Identity

Every material Session should have stable identity.

<a id="section-9-72"></a>
## 9.72 Agent Session State

Session state is temporary unless admitted into governed Memory.

<a id="section-9-73"></a>
## 9.73 Agent Session Scope

Session scope shall include:

- Tenant,

- Project,

- user,

- purpose,

- and current authority context.

<a id="section-9-74"></a>
## 9.74 Agent Runtime

An Agent Runtime is the execution environment hosting the Agent’s current process or inference orchestration.

<a id="section-9-75"></a>
## 9.75 Agent Runtime Mobility

The same Agent may execute on different Runtime Nodes over time.

<a id="section-9-76"></a>
## 9.76 Agent Model Binding

An Agent may have:

- preferred Model classes,

- minimum capabilities,

- prohibited Providers,

- or default Routing Profiles.

These are preferences or constraints, not identity.

<a id="section-9-77"></a>
## 9.77 Agent Provider Binding

Hard binding an Agent identity to one Provider should be avoided unless the user intentionally requires Pinned execution.

<a id="section-9-78"></a>
## 9.78 Agent Tool Access

Tool access shall be represented as governed policy or Grant references.

<a id="section-9-79"></a>
## 9.79 Agent Tool Inventory

The Agent Registry may expose which Tool classes the Agent is potentially eligible to use.

<a id="section-9-80"></a>
## 9.80 Potential Access Is Not Current Permission

Registry metadata showing a Tool relationship does not authorise one invocation.

<a id="section-9-81"></a>
## 9.81 Agent Memory Access

The Agent definition shall identify permitted Memory Domains or retrieval classes.

<a id="section-9-82"></a>
## 9.82 Agent Memory Boundary

The Agent Registry shall not embed raw Memory content.

<a id="section-9-83"></a>
## 9.83 Agent Authority Metadata

The Agent definition may reference:

- default Authority Level,

- permitted action classes,

- required approval classes,

- and maximum operating boundaries.

<a id="section-9-84"></a>
## 9.84 Agent Cannot Self-Modify Authority

An Agent shall not modify its own authority through ordinary execution.

<a id="section-9-85"></a>
## 9.85 Agent Cannot Self-Register Tools

An Agent may propose a discovered Tool.

It shall not make that Tool production-eligible by itself.

<a id="section-9-86"></a>
## 9.86 Agent Cannot Self-Certify

An Agent may produce test evidence.

Certification remains a separate governance process.

<a id="section-9-87"></a>
## 9.87 Agent Lifecycle

Agent lifecycle states may include:

- draft,

- active,

- observe-only,

- suspended,

- degraded,

- retired,

- and archived.

<a id="section-9-88"></a>
## 9.88 Observe-Only Agent

An observe-only Agent may:

- inspect,

- analyse,

- recommend,

- and prepare

without executing consequential actions.

<a id="section-9-89"></a>
## 9.89 Suspended Agent

A suspended Agent shall not initiate new execution.

<a id="section-9-90"></a>
## 9.90 Agent Incident Suspension

An Agent may be suspended after:

- policy violation,

- repeated boundary attempts,

- compromised Runtime,

- or material Incident.

<a id="section-9-91"></a>
## 9.91 Agent Historical Identity

Retired Agents remain resolvable in historical Execution Evidence.

<a id="section-9-92"></a>
## 9.92 External Agent Resource

<a id="section-9-93"></a>
## 9.93 External Agent Is Not Omnira Agent

<a id="section-9-94"></a>
## 9.94 External Agent Definition

- protocol,

- capabilities,

- authentication profile reference,

- trust state,

- data policy,

- and lifecycle.

<a id="section-9-95"></a>
## 9.95 External Agent Capability

Capabilities claimed by an external Agent require validation.

<a id="section-9-96"></a>
## 9.96 External Agent Authority

External Agent access shall be bounded to the exact delegated task.

<a id="section-9-97"></a>
## 9.97 External Agent Output

External Agent output remains untrusted until canonical validation.

<a id="section-9-98"></a>
## 9.98 Agent-to-Agent Delegation

Delegation shall create explicit execution and authority context.

<a id="section-9-99"></a>
## 9.99 Delegation Is Not Identity Transfer

One Agent does not become another Agent because it performs delegated work.

<a id="section-9-100"></a>
## 9.100 Tool Resource

- output schema,

- permissions,

- data limits,

- timeout,

- reliability profile,

<a id="section-9-104"></a>
## 9.104 Tool Definition Identity

## 9.122 Probabilistic Tool

## 9.123 Tool Input Schema

<a id="section-9-124"></a>
## 9.124 Tool Output Schema

<a id="section-9-125"></a>
## 9.125 Tool Description

<a id="section-9-126"></a>
## 9.126 Tool Self-Description

Unknown side effect shall be treated restrictively.

<a id="section-9-722"></a>
## 9.722 Closing Statement

The Intelligence Fabric cannot route, schedule or govern intelligence reliably unless the things capable of doing work have stable canonical identity.

Models are only one class of resource.

Providers are only one class of resource.

Agents, Tools, Runtimes, Nodes, humans and execution infrastructure are equally important parts of the operational intelligence system.

The Agent Registry ensures that Atlas, Arnold and future Agents retain persistent Omnira identity independently from whatever Model happens to serve them.

The Tool Registry ensures that useful operations become explicit, bounded and reviewable instead of appearing as arbitrary capabilities inside prompts or protocols.

The Execution Resource Registry ensures that Omnira understands where work can actually run, what dependencies exist, what capacity is available and which environments are safe for each workload.

The Runtime Node gives compute a stable identity.

The Runtime Service describes the software that exposes execution.

The Model Deployment binds intelligence to a concrete execution environment.

The Tool Instance binds an operation to a concrete Runtime.

The Human Resource makes manual intelligence and review truthful.

The Human-Assisted Resource allows Omnira to govern workflows that are not yet fully automated.

The External Agent Resource allows future Agent ecosystems to participate without receiving automatic trust.

The Resource Pool creates schedulable groups without hiding member identity.

The Capability Binding describes what each Resource may be able to do.

The Health Observation describes whether it appears capable of doing it now.

The Conformance evidence describes whether the implementation has been verified.

Policy determines whether it may do it for this Request.

Authority determines whether the action may occur.

Routing determines which eligible Resource should be selected.

Execution creates the actual Attempt.

Evidence records what really happened.

For Familje-Stunden, this means that:

- Nova and Pling remain Project Assets rather than Provider concepts,

- image generation remains a Tool or Model Capability,

- Voice production remains separately governed,

- publication remains a distinct Tool class,

- human creative review remains visible,

- and no Provider can become the owner of the Project’s creative identity.

For The Prompt, this means that:

- search,

- reasoning,

- visual generation,

- browser operations,

- and publication

can be composed from different registered Resources while retaining Project scope and source evidence.

For GainPilot, this means that:

- Arnold remains Arnold across Model changes,

- local health-sensitive reasoning can use approved Nodes,

- Project Tools remain isolated,

- programme mutation can be separated from ordinary read access,

- and no local or external resource gains broader health-data access merely because it is technically capable.

For Atlas, this means that:

- Atlas can discover what Omnira is capable of without learning raw infrastructure details,

- it can request Capabilities rather than endpoints,

- it can receive governed Tool Views rather than unrestricted Tool inventories,

- and it can change Models, Providers and execution locations without changing its identity.

For Omnira, this creates one common language for every actor and mechanism capable of participating in intelligence work.

No Agent without identity.

No Tool without a contract.

No Operation without side-effect classification.

No Runtime without scope.

No Node without ownership.

No discovered Resource without admission.

No admitted Resource without qualification where required.

No healthy Resource without contextual eligibility.

No Resource without lifecycle.

No Resource drift without evidence.

No Human-Assisted work without truth.

No external Agent without bounded delegation.

No execution Resource without governance.

The user retains authority.

The Project retains scope.

The Agent retains identity.

The Tool retains bounded purpose.

The Runtime retains operational identity.

Omnira retains canonical resource truth.

The Fabric may choose among intelligence resources without allowing the resources themselves to determine who they are allowed to serve, what they are allowed to access or what they are allowed to do.
