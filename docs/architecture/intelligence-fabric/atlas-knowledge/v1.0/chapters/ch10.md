# Chapter 10 — Intelligence Planning and Execution Graphs

<a id="section-10-1"></a>
## 10.1 Chapter Status

This chapter defines the canonical architecture, governance model, lifecycle, contracts and operational responsibilities for Intelligence Planning and Execution Graphs within the Omnira Intelligence Fabric.

It establishes:

- how validated Capability Requests become executable plans,

- how complex intent is decomposed into bounded work,

- how execution dependencies are represented,

- how mandatory, optional, conditional and fallback paths are modelled,

- how models, providers, tools, local resources and human steps are combined,

- how budgets, authority, data classification, rights and quality remain attached throughout planning,

- how parallelism and sequencing are determined,

- how iterative refinement and retries remain bounded,

- how side effects and irreversible actions are isolated,

- how plans are versioned, approved, activated, revised and retired,

- how partial execution and unknown outcomes are reconciled,

- how planning remains separate from execution,

- and how Stage 1 shall implement a minimal but trustworthy planning architecture.

The Intelligence Planner transforms approved intent into a governed description of how work may proceed.

The Planner does not receive authority to change the user’s objective.

It does not receive permission to weaken mandatory policy.

It does not receive unlimited budget.

It does not receive the right to perform every step it can imagine.

The Planner may select and organise eligible implementation paths only inside the boundaries of the Capability Request, Authority Envelope, Budget Envelope, Quality Contract and current policy.

This chapter is normative after formal approval.

Implementation and conformance must be verified separately.

<a id="section-10-2"></a>
## 10.2 Purpose of Intelligence Planning

A Capability Request describes what Omnira is expected to achieve.

A Provider call describes one technical operation.

Complex work usually requires something between them.

That intermediate layer is the Execution Plan.

The Execution Plan determines:

- which capabilities are required,

- how they depend on one another,

- which resources are eligible,

- where approvals are required,

- how much cost may be consumed,

- how quality will be evaluated,

- how failure will be handled,

- and what evidence proves completion.

Without a planning layer, complex intent would become:

- one oversized prompt,

- hard-coded provider workflow,

- uncontrolled agent improvisation,

- or a sequence of disconnected API calls.

The planning layer allows Omnira to preserve human intent while adapting implementation.

<a id="section-10-3"></a>
## 10.3 Planning Is Not Execution

Planning determines what may be attempted.

Execution performs the approved work.

A Planner may:

- analyse requirements,

- decompose work,

- identify dependencies,

- compare resources,

- estimate cost,

- propose fallback,

- and define checkpoints.

Planning shall not:

- consume production credits unnecessarily,

- publish content,

- mutate canonical Assets,

- send external messages,

- modify production systems,

- or perform another consequential side effect

unless that operation is itself an explicitly authorised planning-stage capability.

A plan may be complete while no execution has begun.

<a id="section-10-4"></a>
## 10.4 Planning Is Not Intent

Intent describes the desired outcome.

Planning describes one permitted implementation of that outcome.

Several valid plans may satisfy the same Intent.

For example, a Nova and Pling episode may be produced through:

- premium scene-by-scene video generation,

- lower-cost image animation plus local composition,

- motion-comic production,

- or a human-assisted creative workflow.

The Intent may remain unchanged while the selected plan changes.

<a id="section-10-5"></a>
## 10.5 Planning Is Not Authority

The existence of a technically valid plan does not authorise execution.

The plan must remain inside the effective Authority Envelope.

A Planner may identify that publication would complete a production.

It shall not add publication authority when the request authorises only generation.

A Planner may estimate that an additional premium retry would improve quality.

It shall not increase the retry budget without approval.

<a id="section-10-6"></a>
## 10.6 Planning Is Not Routing

Planning defines the required work and candidate structure.

Routing selects eligible resources for specific Execution Steps.

Planning may identify:

- required Capability,

- resource constraints,

- preferred execution pattern,

- and fallback class.

Routing evaluates current:

- Provider Accounts,

- Models,

- Deployments,

- cost,

- health,

- capacity,

- quality evidence,

- and policy.

Planning and routing may interact iteratively.

They shall remain conceptually distinct.

<a id="section-10-7"></a>
## 10.7 Planning Is Not Workflow Definition

A Workflow Definition is a reusable governed template.

An Execution Plan is a request-specific plan created for one Capability Request, Production or Workflow Run.

The Workflow may define:

- expected steps,

- decision points,

- dependencies,

- and policies.

The Execution Plan resolves:

- current Inputs,

- current resource candidates,

- current budget,

- current approvals,

- and current operational state.

<a id="section-10-8"></a>
## 10.8 Planning Is Not Agent Autonomy

An Agent may assist with planning.

The canonical plan remains an Omnira-governed object.

Agent reasoning shall not become invisible runtime authority.

The plan must expose:

- steps,

- constraints,

- dependencies,

- cost,

- authority,

- and completion requirements

in a form that can be validated independently of the Agent’s internal reasoning.

<a id="section-10-9"></a>
## 10.9 Intelligence Planner

The Intelligence Planner is the Fabric component or governed service responsible for constructing Execution Plans.

The Planner may use:

- deterministic rules,

- reusable templates,

- graph algorithms,

- policy evaluation,

- cost estimation,

- resource discovery,

- AI-assisted decomposition,

- historical evidence,

- and human input.

The Planner shall have a stable Service Principal identity.

It shall operate with limited authority.

It shall not directly own Provider credentials.

<a id="section-10-10"></a>
## 10.10 Planner Responsibilities

The Planner is responsible for:

- receiving a validated Capability Request,

- resolving applicable planning templates,

- decomposing the request,

- identifying required and optional Capability Steps,

- attaching Inputs and Output Contracts,

- defining dependencies,

- defining approval boundaries,

- defining evaluation requirements,

- allocating budget,

- identifying eligible resource classes,

- estimating cost and latency,

- defining retry and fallback policies,

- defining Completion Contract,

- and producing a versioned Execution Plan.

The Planner shall preserve all mandatory request constraints.

<a id="section-10-11"></a>
## 10.11 Planner Non-Responsibilities

The Planner is not responsible for:

- owning Project strategy,

- approving its own budget expansion,

- accepting Provider terms,

- creating unrestricted credentials,

- overriding Data Classification,

- granting publication authority,

- or declaring output accepted without evaluation.

These responsibilities belong to other governed components or human authorities.

<a id="section-10-12"></a>
## 10.12 Planning Input

The Planner shall receive a canonical Planning Input Package.

The package should include:

- Capability Request ID and Version,

- Intent reference,

- caller,

- initiator,

- Tenant,

- Project,

- Environment,

- Authority Envelope,

- Policy Decisions,

- Routing Profile,

- Budget Envelope,

- Capability Requirements,

- Input references,

- Output Contract,

- Quality Contract,

- Completion Contract,

- rights and consent references,

- deadline,

- priority,

- and permitted assumptions.

The Planner shall not reconstruct authoritative constraints from informal conversation when canonical request data exists.

<a id="section-10-13"></a>
## 10.13 Planning Context

Planning Context may also include:

- Capability Registry Snapshot,

- Model Registry Snapshot,

- Provider Registry Snapshot,

- Tool Registry Snapshot,

- available Workflow templates,

- historical performance evidence,

- current quotas,

- current capacity,

- and relevant governed learning.

Planning Context shall declare freshness.

Stale operational information may support estimation.

It must not be represented as current certainty.

<a id="section-10-14"></a>
## 10.14 Planning Output

The primary output of planning is an Execution Plan.

Planning may also produce:

- Plan Alternatives,

- Cost Estimates,

- Latency Estimates,

- Resource Requirements,

- Approval Requests,

- Capability Gap Records,

- Planning Warnings,

- Assumption Register,

- and Human Decision Points.

A failed planning attempt shall produce evidence explaining why no valid plan could be created.

<a id="section-10-15"></a>
## 10.15 Execution Plan

An Execution Plan is a versioned canonical object describing how one request may be fulfilled.

It shall include or reference:

- planId,

- planVersion,

- requestId,

- requestVersion,

- Tenant,

- Project,

- Environment,

- objective,

- plan status,

- planning strategy,

- Execution Graph,

- step definitions,

- dependency definitions,

- resource requirements,

- selected or deferred resources,

- budget allocation,

- expected cost,

- expected latency,

- approval points,

- quality gates,

- retry policies,

- fallback policies,

- compensation policies,

- Completion Contract,

- assumptions,

- warnings,

- and provenance.

<a id="section-10-16"></a>
## 10.16 Plan Identity

Every persistent Execution Plan shall have stable identity.

Plan identity shall remain separate from:

- Capability Request,

- Workflow,

- Execution,

- and plan version.

One Capability Request may have several competing or sequential plans.

<a id="section-10-17"></a>
## 10.17 Plan Version

Material changes shall create a new Plan Version.

A Plan Version shall preserve:

- exact request version,

- policy context,

- registry snapshots,

- assumptions,

- estimated cost,

- step graph,

- and approval state.

Executions shall reference the Plan Version under which they were created.

<a id="section-10-18"></a>
## 10.18 Plan Revision

A Plan Revision may correct non-semantic metadata such as:

- display description,

- formatting,

- or documentation.

A change affecting:

- steps,

- resources,

- budget,

- authority,

- quality,

- data placement,

- or Completion Contract

requires a new Plan Version.

<a id="section-10-19"></a>
## 10.19 Plan Alternative

A Plan Alternative is one possible implementation path for the same request.

Alternatives may differ by:

- providers,

- cost,

- quality,

- privacy,

- latency,

- automation maturity,

- or operational risk.

Alternatives should remain comparable through structured trade-offs.

<a id="section-10-20"></a>
## 10.20 Preferred Plan

The Preferred Plan is the currently recommended valid plan.

It is not necessarily approved.

Preference may be based on:

- Routing Profile,

- quality evidence,

- cost,

- deadline,

- privacy,

- and reliability.

<a id="section-10-21"></a>
## 10.21 Approved Plan

An Approved Plan has received any required human or policy approval for its exact version and boundaries.

Approval does not guarantee resource availability at execution time.

Current eligibility must still be revalidated.

<a id="section-10-22"></a>
## 10.22 Active Plan

An Active Plan is the Plan Version currently governing one or more Executions.

A Capability Request should normally have one active Plan Version at a time unless the architecture explicitly permits parallel alternatives.

<a id="section-10-23"></a>
## 10.23 Superseded Plan

A Superseded Plan has been replaced for future execution.

Executions already created under it remain historically valid.

Supersession does not erase prior evidence.

<a id="section-10-24"></a>
## 10.24 Abandoned Plan

An Abandoned Plan was considered but intentionally not selected.

The reason may include:

- excessive cost,

- insufficient quality,

- unavailable Provider,

- policy conflict,

- deadline,

- or user preference.

Abandoned alternatives may support future explanation and learning.

<a id="section-10-25"></a>
## 10.25 Rejected Plan

A Rejected Plan was explicitly denied by an approver or policy.

Rejection evidence shall remain immutable.

<a id="section-10-26"></a>
## 10.26 Execution Graph

The Execution Graph is the canonical dependency graph within an Execution Plan.

It represents:

- work units,

- data dependencies,

- control dependencies,

- approval boundaries,

- evaluation gates,

- fallback branches,

- compensation paths,

- and completion logic.

The Execution Graph shall be machine-readable and human-explainable.

<a id="section-10-27"></a>
## 10.27 Graph Node

A Graph Node represents one bounded planning element.

Node types may include:

- Capability Step,

- Data Transformation,

- Resource Selection,

- Approval,

- Human Action,

- Evaluation,

- Decision,

- Wait,

- Side Effect,

- Compensation,

- Aggregation,

- Publication,

- Notification,

- or Completion Gate.

Each Node shall have stable identity within the Plan Version.

<a id="section-10-28"></a>
## 10.28 Graph Edge

A Graph Edge represents a relationship between Nodes.

Edge types may include:

- depends on,

- provides input to,

- triggers,

- conditional on,

- fallback from,

- compensates,

- waits for,

- aggregates,

- approves,

- rejects,

- or completes.

Edge meaning shall be explicit.

<a id="section-10-29"></a>
## 10.29 Directed Graph

The Execution Graph shall normally be directed.

Direction represents control or data progression.

The graph need not be strictly linear.

It may contain:

- branches,

- joins,

- parallel groups,

- bounded loops,

- and conditional paths.

<a id="section-10-30"></a>
## 10.30 Acyclic Default

The default planning structure should be acyclic.

Cycles may exist only when they represent explicitly bounded behaviour such as:

- retry,

- iterative refinement,

- review correction,

- or repeated polling.

Unbounded cycles are prohibited.

<a id="section-10-31"></a>
## 10.31 Bounded Loop

A Bounded Loop shall define:

- entry condition,

- maximum iterations,

- budget limit,

- deadline,

- exit condition,

- and failure behaviour.

A loop shall not expand its own limit.

<a id="section-10-32"></a>
## 10.32 Execution Step

An Execution Step is a Node representing one bounded unit of governed work.

It shall include:

- stepId,

- planId,

- step type,

- Capability Requirement,

- Input references,

- Output Contract,

- Quality Contract,

- Authority requirement,

- Data Classification,

- rights requirement,

- Resource Requirement,

- budget allocation,

- retry policy,

- fallback policy,

- timeout,

- dependencies,

- and Completion Criteria.

<a id="section-10-33"></a>
## 10.33 Step Identity

Step identity shall remain stable within one Plan Version.

A revised Plan may retain logical continuity through:

- predecessorStepId,

- supersedesStepId,

- or equivalent relationship.

Executions shall reference the exact Step definition used.

<a id="section-10-34"></a>
## 10.34 Step Type

Canonical Step Types may include:

- intelligence execution,

- tool execution,

- deterministic transformation,

- human review,

- approval,

- wait,

- evaluation,

- side effect,

- aggregation,

- reconciliation,

- and compensation.

<a id="section-10-35"></a>
## 10.35 Intelligence Execution Step

An Intelligence Execution Step invokes a Model or External Agent Resource through a canonical Capability.

Examples include:

- reasoning,

- script generation,

- image generation,

- speech synthesis,

- video generation,

- embedding,

- reranking,

- or multimodal evaluation.

<a id="section-10-36"></a>
## 10.36 Tool Execution Step

A Tool Execution Step invokes a governed Tool.

Examples include:

- file conversion,

- repository read,

- frame extraction,

- audio mixing,

- storage ingestion,

- or publication submission.

Tool permissions shall remain explicit.

<a id="section-10-37"></a>
## 10.37 Deterministic Transformation Step

A Deterministic Transformation Step performs a predictable operation such as:

- schema conversion,

- resizing,

- document parsing,

- checksum generation,

- format conversion,

- or metadata extraction.

Deterministic does not mean risk-free.

The operation may still modify data or create side effects.

<a id="section-10-38"></a>
## 10.38 Human Action Step

A Human Action Step requires a person to perform a defined task.

It shall include:

- responsible role,

- instructions,

- Inputs,

- expected Output or decision,

- deadline,

- evidence requirement,

- and escalation.

Human-assisted work shall remain visible in the graph.

<a id="section-10-39"></a>
## 10.39 Approval Step

An Approval Step pauses progression until a valid Approval Decision exists.

It shall define:

- approver class,

- approval subject,

- summary,

- scope,

- budget,

- conditions,

- validity,

- and rejection path.

<a id="section-10-40"></a>
## 10.40 Evaluation Step

An Evaluation Step assesses an Output or intermediate result.

It shall define:

- target,

- criteria,

- evaluator,

- method,

- thresholds,

- failure path,

- and acceptance authority.

<a id="section-10-41"></a>
## 10.41 Wait Step

A Wait Step pauses execution until:

- a time,

- callback,

- external state,

- dependency,

- human response,

- or condition

is satisfied.

Wait Steps shall be durable.

They must not rely on one process remaining active.

<a id="section-10-42"></a>
## 10.42 Decision Step

A Decision Step chooses among defined branches.

It shall include:

- decision inputs,

- decision logic,

- authority,

- possible outcomes,

- and evidence.

A Decision Step may be:

- deterministic,

- policy-driven,

- model-assisted,

- or human.

<a id="section-10-43"></a>
## 10.43 Aggregation Step

An Aggregation Step combines several Outputs.

Examples include:

- join scene videos,

- combine research findings,

- merge evaluation results,

- assemble a document,

- or summarise batch status.

Aggregation shall preserve provenance from all source Outputs.

<a id="section-10-44"></a>
## 10.44 Side-Effect Step

A Side-Effect Step changes external or durable state.

Examples include:

- publish,

- send,

- commit,

- delete,

- modify configuration,

- create Provider Asset,

- or charge a transaction.

Side effects require explicit authority, idempotency and verification.

<a id="section-10-45"></a>
## 10.45 Compensation Step

A Compensation Step reverses or mitigates an earlier side effect.

It shall define:

- triggering condition,

- target action,

- authority,

- expected restoration,

- residual risk,

- and evidence.

Compensation may fail.

It must not be represented as guaranteed rollback.

<a id="section-10-46"></a>
## 10.46 Reconciliation Step

A Reconciliation Step compares Omnira state with an external system.

It may resolve:

- unknown Provider job,

- uncertain publication,

- cost discrepancy,

- missing Asset,

- or callback failure.

<a id="section-10-47"></a>
## 10.47 Completion Gate

A Completion Gate determines whether the request or parent step satisfies its Completion Contract.

It shall inspect:

- mandatory Outputs,

- Evaluation Results,

- Approval Decisions,

- cost,

- unresolved unknown outcomes,

- and required side-effect verification.

<a id="section-10-48"></a>
## 10.48 Node Input

Every executable Node shall define its Inputs.

Inputs may reference:

- request Inputs,

- Outputs from predecessor Nodes,

- Assets,

- Data Items,

- governed memory,

- policy results,

- human decisions,

- or external events.

Input lineage shall remain traceable.

<a id="section-10-49"></a>
## 10.49 Node Output

Every executable Node shall define its expected Output.

Outputs may be:

- data,

- Asset candidate,

- decision,

- approval,

- receipt,

- status,

- cost,

- or side-effect evidence.

Output existence does not automatically mean acceptance.

<a id="section-10-50"></a>
## 10.50 Data Edge

A Data Edge identifies Output from one Node as Input to another.

It shall define:

- source Output,

- destination Input,

- transformation,

- classification,

- rights inheritance,

- and version.

<a id="section-10-51"></a>
## 10.51 Control Edge

A Control Edge determines execution order without necessarily transferring data.

Examples include:

- execute after approval,

- execute after deadline,

- or execute only when evaluation passes.

<a id="section-10-52"></a>
## 10.52 Conditional Edge

A Conditional Edge is traversed only when a defined condition is satisfied.

The condition shall be:

- explicit,

- machine-evaluable where possible,

- versioned,

- and evidenced.

<a id="section-10-53"></a>
## 10.53 Fallback Edge

A Fallback Edge leads to an alternative step or resource after defined failure or ineligibility.

It shall preserve mandatory request constraints.

<a id="section-10-54"></a>
## 10.54 Compensation Edge

A Compensation Edge identifies which corrective action follows a failed or cancelled side effect.

<a id="section-10-55"></a>
## 10.55 Join Edge

A Join waits for defined predecessor conditions.

Join policies may include:

- all mandatory predecessors,

- any one predecessor,

- minimum count,

- quorum,

- or explicitly selected subset.

<a id="section-10-56"></a>
## 10.56 Split Edge

A Split creates parallel or conditional branches.

Split conditions shall define:

- branch count,

- budget allocation,

- and later join behaviour.

<a id="section-10-57"></a>
## 10.57 Mandatory Step

A Mandatory Step must complete according to its Completion Criteria for the parent request to complete.

The Planner shall not silently remove it.

<a id="section-10-58"></a>
## 10.58 Optional Step

An Optional Step may improve output or create derivatives.

Its omission shall be allowed by the parent Completion Contract.

Optional Steps shall still have cost and authority boundaries.

<a id="section-10-59"></a>
## 10.59 Conditional Step

A Conditional Step becomes active only when a defined condition is true.

Examples include:

- premium retry after failed quality evaluation,

- translation when target language differs,

- human review for child-facing output,

- or external search when internal sources are insufficient.

<a id="section-10-60"></a>
## 10.60 Deferred Step

A Deferred Step is defined but not yet scheduled because:

- a decision is pending,

- a future Input is missing,

- budget is not yet approved,

- or a prior result determines its necessity.

<a id="section-10-61"></a>
## 10.61 Disabled Step

A Disabled Step remains in the Plan for history or possible future activation but cannot execute under the current Plan Version.

<a id="section-10-62"></a>
## 10.62 Composite Step

A Composite Step contains a subgraph.

It may represent:

- one scene production,

- one research package,

- one publication package,

- or one software-delivery phase.

Composite Steps support hierarchical planning.

<a id="section-10-63"></a>
## 10.63 Atomic Step

An Atomic Step is the smallest unit the current Planner schedules independently.

Atomic does not mean one provider call.

An Adapter may internally perform bounded technical operations.

Material governance boundaries must remain visible at Plan level.

<a id="section-10-64"></a>
## 10.64 Hierarchical Execution Graph

Complex Plans may use a hierarchy:

- Plan,

- Phase,

- Composite Step,

- Atomic Step,

- Execution,

- Attempt.

Hierarchy supports explanation without losing detail.

<a id="section-10-65"></a>
## 10.65 Phase

A Phase groups Steps with a shared purpose.

Example phases may include:

- preparation,

- research,

- generation,

- evaluation,

- assembly,

- approval,

- publication,

- and verification.

Phase names are organisational.

Step contracts remain authoritative.

<a id="section-10-66"></a>
## 10.66 Planning Template

A Planning Template is a reusable structure for common requests.

It may define:

- standard Steps,

- dependencies,

- approvals,

- Quality Gates,

- retry limits,

- and Completion Contract.

Templates shall be versioned and scoped.

<a id="section-10-67"></a>
## 10.67 Project Planning Template

Projects may define specialised templates.

Examples include:

- Familje-Stunden monthly episode,

- The Prompt news segment,

- GainPilot short-form reel,

- Omnira code audit.

Templates shall reference canonical Capabilities.

<a id="section-10-68"></a>
## 10.68 Platform Planning Template

Platform templates may define reusable patterns such as:

- research and verification,

- generate and evaluate,

- preview then premium,

- draft and human review,

- or side-effect with verification.

<a id="section-10-69"></a>
## 10.69 Template Instantiation

Instantiating a Template creates a request-specific Plan.

The Plan shall resolve:

- Inputs,

- Project,

- budget,

- current policies,

- resource requirements,

- deadlines,

- and approvals.

The Template itself is not an active Plan.

<a id="section-10-70"></a>
## 10.70 Template Version

Plans shall reference the exact Template Version used.

A Template update shall not rewrite active Plans.

<a id="section-10-71"></a>
## 10.71 Template Override

A request may override approved Template fields.

Overrides shall remain within:

- authority,

- policy,

- and schema.

Material overrides may require review.

<a id="section-10-72"></a>
## 10.72 Planning Strategy

A Plan shall identify the strategy used.

Strategies may include:

- template-based,

- deterministic decomposition,

- AI-assisted decomposition,

- hybrid,

- manually authored,

- imported,

- or recovery-generated.

<a id="section-10-73"></a>
## 10.73 Deterministic Planning

Deterministic Planning uses predefined rules and templates.

It is suitable when:

- request type is stable,

- steps are known,

- and variation is limited.

It offers strong predictability.

<a id="section-10-74"></a>
## 10.74 AI-Assisted Planning

AI-Assisted Planning may interpret complex intent and propose Steps.

Its output shall be validated against:

- Capability Registry,

- authority,

- policy,

- budget,

- and graph rules.

The AI Planner cannot create new authority.

<a id="section-10-75"></a>
## 10.75 Hybrid Planning

Hybrid Planning combines:

- deterministic boundaries,

- reusable templates,

- and AI-generated detail.

This is likely appropriate for many Omnira workflows.

<a id="section-10-76"></a>
## 10.76 Manual Planning

An authorised human may create or edit a Plan.

Manual Plans remain subject to the same validation and evidence requirements.

<a id="section-10-77"></a>
## 10.77 Imported Plan

A Plan may be imported from:

- external workflow system,

- provider agent,

- code package,

- or partner integration.

Imported Plans shall be treated as untrusted until validated.

<a id="section-10-78"></a>
## 10.78 Plan Validation

Before approval or activation, the Plan shall be validated.

Validation should include:

- graph structure,

- Capability existence,

- scope,

- Inputs,

- authority,

- policy,

- budget,

- data placement,

- rights,

- quality,

- side effects,

- retry,

- fallback,

- and Completion Contract.

<a id="section-10-79"></a>
## 10.79 Structural Graph Validation

Structural validation shall detect:

- missing Node,

- invalid Edge,

- unreachable mandatory Step,

- orphaned Step,

- unbounded cycle,

- impossible join,

- duplicate identifier,

- and invalid dependency.

<a id="section-10-80"></a>
## 10.80 Semantic Plan Validation

Semantic validation shall detect conflicts such as:

- publication before acceptance,

- evaluation before Output exists,

- narration before final script when sequence requires final text,

- Local Only Input routed to external step,

- or deletion without target.

<a id="section-10-81"></a>
## 10.81 Scope Validation

Every Step shall remain within the request’s permitted Tenant, Project and Environment scope.

Cross-Project Steps require explicit authority.

<a id="section-10-82"></a>
## 10.82 Authority Validation

Each Step shall identify the authority required.

The Plan shall not rely on one broad approval when action-specific authority is required.

<a id="section-10-83"></a>
## 10.83 Policy Validation

Current policies shall be evaluated against:

- Step Capability,

- selected or candidate resource,

- Inputs,

- Outputs,

- data class,

- rights,

- and side effects.

<a id="section-10-84"></a>
## 10.84 Budget Validation

The sum of planned maximum spending shall fit within the Budget Envelope.

The Plan shall account for:

- mandatory Steps,

- approved optional Steps,

- retries,

- fallbacks,

- evaluation,

- post-processing,

- and Provider minimum charges.

<a id="section-10-85"></a>
## 10.85 Budget Allocation

The Planner may allocate budget by:

- Step,

- Phase,

- modality,

- Provider class,

- retry pool,

- or reserve.

Allocation shall not exceed the parent envelope.

<a id="section-10-86"></a>
## 10.86 Hard Step Budget

A Hard Step Budget is the maximum amount one Step may consume.

The Executor shall stop before knowingly exceeding it.

<a id="section-10-87"></a>
## 10.87 Shared Retry Budget

Several Steps may share one retry reserve.

The Plan shall define:

- total reserve,

- allocation rules,

- priority,

- and exhaustion behaviour.

<a id="section-10-88"></a>
## 10.88 Contingency Reserve

A Plan may reserve budget for:

- fallback,

- correction,

- or uncertain Provider pricing.

Unused reserve shall be released.

<a id="section-10-89"></a>
## 10.89 Cost Estimate

The Plan shall include an estimated cost or cost range.

The estimate should identify:

- assumptions,

- pricing versions,

- expected usage,

- retry allowance,

- and uncertainty.

<a id="section-10-90"></a>
## 10.90 Minimum Cost Plan

A Minimum Cost Plan represents the cheapest currently valid execution path.

It must still satisfy mandatory requirements.

<a id="section-10-91"></a>
## 10.91 Expected Cost Plan

An Expected Cost Plan represents likely cost under ordinary success and expected retries.

<a id="section-10-92"></a>
## 10.92 Maximum Authorised Cost

Maximum Authorised Cost is the hard approved boundary.

It shall remain distinct from expected cost.

<a id="section-10-93"></a>
## 10.93 Cost Uncertainty

Cost uncertainty may be:

- low,

- moderate,

- high,

- or unknown.

High uncertainty may require conservative reservation or stronger approval.

<a id="section-10-94"></a>
## 10.94 Latency Estimate

The Plan should estimate:

- queue time,

- execution time,

- review time,

- retry time,

- and final delivery.

Latency estimates must remain distinct from guarantees.

<a id="section-10-95"></a>
## 10.95 Critical Path

The Critical Path is the longest dependency path determining earliest completion.

The Planner may optimise the Critical Path through:

- parallelism,

- resource choice,

- preparation,

- or early validation.

<a id="section-10-96"></a>
## 10.96 Deadline Feasibility

The Plan shall evaluate whether the request deadline is feasible.

It should include:

- Provider latency,

- human review,

- fallback,

- and final verification.

An impossible deadline shall be reported before unnecessary spending.

<a id="section-10-97"></a>
## 10.97 Earliest Start

Some Steps may have an earliest start based on:

- schedule,

- Input availability,

- human availability,

- Provider window,

- or policy.

<a id="section-10-98"></a>
## 10.98 Latest Start

A Step may have a latest start to preserve the request deadline.

Missing the latest start may trigger:

- escalation,

- degraded alternative,

- or failure.

<a id="section-10-99"></a>
## 10.99 Step Timeout

Each external or long-running Step should define a timeout.

Timeout does not always mean failure.

It may produce unknown outcome.

<a id="section-10-100"></a>
## 10.100 Plan Expiry

A Plan may expire because:

- approval expires,

- registry state changes materially,

- pricing becomes stale,

- deadline passes,

- Inputs change,

- or Provider terms change.

Expired Plans shall not start new execution without revalidation.

<a id="section-10-101"></a>
## 10.101 Resource Requirement

A Resource Requirement defines the properties needed for a Step.

It may include:

- Capability Version,

- mandatory Features,

- modality,

- quality floor,

- data placement,

- Provider restrictions,

- Model restrictions,

- region,

- context capacity,

- latency,

- cost,

- rights,

- and integration maturity.

<a id="section-10-102"></a>
## 10.102 Resource Candidate

A Resource Candidate combines the operational objects needed to execute a Step.

It may include:

- Provider,

- Provider Account,

- Model Version,

- Model Deployment,

- Adapter,

- Connection,

- Runtime Node,

- Tool,

- or External Agent Resource.

<a id="section-10-103"></a>
## 10.103 Candidate Generation

The Planner or Router may generate candidates from the current registries.

Candidate generation shall exclude resources that are structurally incompatible.

Full eligibility remains a separate decision.

<a id="section-10-104"></a>
## 10.104 Candidate Eligibility

Eligibility shall consider:

- Capability compatibility,

- policy,

- data class,

- rights,

- authority,

- Account,

- Connection,

- health,

- capacity,

- quota,

- budget,

- and deadline.

<a id="section-10-105"></a>
## 10.105 Candidate Ranking

Only eligible candidates may be ranked.

Ranking may use:

- quality,

- cost,

- latency,

- reliability,

- privacy,

- and Routing Profile.

<a id="section-10-106"></a>
## 10.106 Selected Resource

A Plan may contain:

- fully selected Resource Candidate,

- ranked candidate set,

- deferred selection,

- or pinned resource.

The choice depends on how far in advance the Plan is created.

<a id="section-10-107"></a>
## 10.107 Early Binding

Early Binding selects a resource during planning.

It may be useful for:

- fixed Provider contract,

- exact reproducibility,

- reserved capacity,

- unique Capability,

- or approval clarity.

<a id="section-10-108"></a>
## 10.108 Late Binding

Late Binding selects the resource near execution time.

It allows the Fabric to use current:

- health,

- pricing,

- quota,

- capacity,

- and quality evidence.

<a id="section-10-109"></a>
## 10.109 Hybrid Binding

A Plan may bind:

- Provider class early,

- Account during approval,

- and exact Model Deployment at execution.

Binding level shall be explicit.

<a id="section-10-110"></a>
## 10.110 Resource Pinning

A Step may pin:

- Provider,

- Account,

- Model,

- Deployment,

- Adapter,

- Tool,

- or Node.

Pinning shall identify:

- reason,

- fallback,

- validity,

- and whether the pin is mandatory.

<a id="section-10-111"></a>
## 10.111 Resource Reservation

The Plan may reserve:

- local compute,

- Provider capacity,

- budget,

- or human review slot.

Reservation state shall remain separate from execution.

<a id="section-10-112"></a>
## 10.112 Resource Unavailability

If a selected resource becomes unavailable before execution, the Plan shall follow its:

- fallback policy,

- replanning policy,

- approval policy,

- or failure path.

<a id="section-10-113"></a>
## 10.113 Planning With Unknown Resource

A Plan may define a Resource Requirement without identifying a current eligible resource.

Such a Plan may remain:

- incomplete,

- blocked,

- or awaiting Capability gap resolution.

It shall not be activated as executable.

<a id="section-10-114"></a>
## 10.114 Capability Gap During Planning

A Capability Gap exists when no valid resource path can satisfy a mandatory Step.

The Planner shall produce:

- missing Capability or support,

- conflicting constraint,

- possible alternatives,

- and whether human-assisted execution is available.

<a id="section-10-115"></a>
## 10.115 Human-Assisted Alternative

A human-assisted path may bridge a Capability Gap.

It shall define:

- operator,

- Provider or Tool,

- manual instructions,

- cost,

- evidence,

- and quality review.

<a id="section-10-116"></a>
## 10.116 Plan Decomposition

Decomposition divides a broad request into bounded Steps.

The Planner should decompose when:

- different Capabilities are required,

- different authority applies,

- different data placement applies,

- separate quality evaluation is needed,

- different resources are optimal,

- or partial completion has value.

<a id="section-10-117"></a>
## 10.117 Decomposition Boundary

A boundary should be created when one part of work has a distinct:

- identity,

- lifecycle,

- authority,

- budget,

- Input,

- Output,

- side effect,

- or failure behaviour.

<a id="section-10-118"></a>
## 10.118 Over-Decomposition

A Plan is over-decomposed when trivial technical details become separate governed Steps without meaningful boundary.

Over-decomposition increases:

- latency,

- state complexity,

- cost,

- and failure surface.

<a id="section-10-119"></a>
## 10.119 Under-Decomposition

A Plan is under-decomposed when materially different work is hidden inside one opaque Step.

Under-decomposition weakens:

- authority,

- provenance,

- cost,

- evaluation,

- and recovery.

<a id="section-10-120"></a>
## 10.120 Provider Call Boundary

One Step may result in several Provider calls when the Adapter performs bounded internal operations.

Material calls involving separate:

- cost,

- authority,

- output,

- or retry

should normally remain visible as separate Executions or Attempts.

<a id="section-10-121"></a>
## 10.121 Multi-Provider Plan

A Plan may use several Providers.

Each Step shall preserve:

- Provider eligibility,

- Account,

- cost,

- terms,

- data transfer,

- and provenance.

<a id="section-10-122"></a>
## 10.122 Local and External Composition

A Plan may combine:

- local preprocessing,

- external premium generation,

- local evaluation,

- and human review.

Data Classification shall determine what may cross each boundary.

<a id="section-10-123"></a>
## 10.123 Data Localisation Step

A Plan may include a Step to:

- redact,

- summarise,

- anonymise,

- extract,

- or transform data locally

before external use.

Transformation must not automatically lower classification without policy.

<a id="section-10-124"></a>
## 10.124 Data Transfer Boundary

Every transfer between custody or processing locations should be explicit when material.

The Plan should identify:

- source location,

- destination,

- classification,

- rights,

- encryption,

- and retention.

<a id="section-10-125"></a>
## 10.125 Context Assembly Step

A Context Assembly Step builds the bounded context used by a Model or Agent.

It may include:

- retrieved memory,

- selected Assets,

- request instructions,

- evidence,

- and policy summaries.

The resulting Context Package shall be scoped and classified.

<a id="section-10-126"></a>
## 10.126 Retrieval Step

A Retrieval Step obtains relevant information from:

- Project data,

- Memory,

- Intelligence Graph,

- external search,

- or Provider storage.

Retrieval authority and freshness remain explicit.

<a id="section-10-127"></a>
## 10.127 Prompt Construction Step

Prompt construction may be represented when it materially affects:

- provenance,

- quality,

- privacy,

- or reproducibility.

Prompt Templates and runtime substitutions shall be versioned.

<a id="section-10-128"></a>
## 10.128 Prompt Adaptation

Adapters may transform canonical instructions into Provider-specific format.

Material omissions or changes shall be evidenced.

<a id="section-10-129"></a>
## 10.129 Output Ingestion Step

External Provider output may require ingestion into Omnira-controlled storage.

The Step shall verify:

- file integrity,

- type,

- checksum,

- classification,

- provenance,

- and storage destination.

<a id="section-10-130"></a>
## 10.130 Output Normalisation Step

Output may require:

- schema conversion,

- encoding conversion,

- media conversion,

- or metadata normalisation.

Normalisation must preserve original evidence where relevant.

<a id="section-10-131"></a>
## 10.131 Quality Gate

A Quality Gate blocks progression until defined criteria pass.

It shall identify:

- target Output,

- criteria,

- evaluator,

- threshold,

- and failure path.

<a id="section-10-132"></a>
## 10.132 Deterministic Quality Gate

A deterministic gate may test:

- schema,

- file format,

- dimensions,

- duration,

- compilation,

- type checking,

- or unit tests.

<a id="section-10-133"></a>
## 10.133 Model-Based Quality Gate

A Model-based gate may assess:

- relevance,

- style,

- factual support,

- visual consistency,

- or safety.

Evaluator identity and Version shall be preserved.

<a id="section-10-134"></a>
## 10.134 Human Quality Gate

A Human Quality Gate requires an authorised reviewer.

The Plan shall define:

- reviewer role,

- checklist,

- decision options,

- and correction path.

<a id="section-10-135"></a>
## 10.135 Composite Quality Gate

A Composite Gate combines several evaluations.

It may require:

- all mandatory checks,

- minimum score,

- and human approval.

<a id="section-10-136"></a>
## 10.136 Gate Failure

When a Quality Gate fails, the Plan may:

- retry,

- refine,

- use fallback,

- route to human correction,

- accept partial result if permitted,

- or fail.

<a id="section-10-137"></a>
## 10.137 Revision Loop

A Revision Loop may:

1. evaluate Output,

2. identify defects,

3. refine instructions,

4. execute again,

5. re-evaluate.

The loop shall have bounded:

- iterations,

- budget,

- time,

- and authority.

<a id="section-10-138"></a>
## 10.138 Same-Resource Retry

The Plan may retry the same resource for transient failure or stochastic variation.

Retry must remain idempotency- and cost-aware.

<a id="section-10-139"></a>
## 10.139 Resource Fallback

The Plan may switch to another eligible resource.

The fallback may alter:

- cost,

- quality,

- latency,

- or reproducibility.

Material changes require disclosure or approval according to policy.

<a id="section-10-140"></a>
## 10.140 Capability Alternative Fallback

The Plan may switch to an alternative Capability path.

Example:

- premium image-to-video fails,

- motion-comic composition becomes the approved alternative.

The alternative must still satisfy the Completion Contract or produce approved degradation.

<a id="section-10-141"></a>
## 10.141 Human Escalation

Repeated failure may escalate to a human.

Escalation should present:

- failed Steps,

- Outputs,

- cost,

- remaining budget,

- alternatives,

- and required decision.

<a id="section-10-142"></a>
## 10.142 Retry Policy

Each retryable Step shall have a Retry Policy defining:

- retryable conditions,

- non-retryable conditions,

- maximum attempts,

- backoff,

- idempotency,

- budget,

- deadline,

- and unknown-outcome handling.

<a id="section-10-143"></a>
## 10.143 Failure Category

Retry decisions shall distinguish:

- validation failure,

- policy rejection,

- authentication failure,

- rate limit,

- Provider outage,

- timeout,

- quality failure,

- rights restriction,

- safety refusal,

- and internal defect.

<a id="section-10-144"></a>
## 10.144 Transient Failure

Transient failures may include:

- temporary outage,

- rate limit,

- short network interruption,

- or temporary capacity issue.

They may permit bounded retry.

<a id="section-10-145"></a>
## 10.145 Permanent Failure

Permanent failures may include:

- unsupported Capability,

- policy prohibition,

- expired rights,

- missing consent,

- or retired Model.

They shall not be retried without changed conditions.

<a id="section-10-146"></a>
## 10.146 Unknown Outcome

Unknown outcome means the system cannot confirm whether an operation completed.

The Plan shall not automatically retry a non-idempotent or paid Step.

It may require reconciliation first.

<a id="section-10-147"></a>
## 10.147 Unknown-Outcome Branch

A Plan should define a branch for uncertain external operations.

The branch may include:

- Provider status lookup,

- Asset listing,

- billing inspection,

- delayed callback wait,

- human verification,

- or Incident.

<a id="section-10-148"></a>
## 10.148 Retry Backoff

Retry timing may use:

- fixed delay,

- exponential backoff,

- jitter,

- Provider guidance,

- or scheduled retry.

Backoff shall respect deadlines.

<a id="section-10-149"></a>
## 10.149 Retry Budget

Retry cost shall be reserved or bounded.

The system shall stop when the retry budget is exhausted.

<a id="section-10-150"></a>
## 10.150 Attempt Limit

Attempt limit shall count all relevant Attempts across:

- same resource,

- fallback resource,

- and revision loops

according to the Plan’s defined semantics.

<a id="section-10-151"></a>
## 10.151 Infinite Retry Prohibition

No Plan may retry indefinitely.

Every retry path requires a terminal or escalation state.

<a id="section-10-152"></a>
## 10.152 Fallback Policy

A Fallback Policy defines:

- trigger,

- candidate alternatives,

- ordering,

- quality floor,

- budget,

- data policy,

- approval,

- and disclosure.

<a id="section-10-153"></a>
## 10.153 Fallback Eligibility Revalidation

Fallback resources shall be evaluated under current conditions.

Previous eligibility does not guarantee current eligibility.

<a id="section-10-154"></a>
## 10.154 Fallback Ordering

Fallback may be ordered by:

- same Model different Deployment,

- same Provider different Model,

- different Provider same Capability,

- local resource,

- human-assisted path,

- or approved degraded Capability.

<a id="section-10-155"></a>
## 10.155 No Policy Escape

Fallback shall not weaken:

- data classification,

- rights,

- consent,

- authority,

- or hard budget.

<a id="section-10-156"></a>
## 10.156 Degradation Plan

A Degradation Plan defines a reduced outcome that may be offered when full completion is impossible.

Examples include:

- lower resolution,

- fewer variants,

- delayed completion,

- partial episode,

- manual review,

- or draft-only delivery.

Material degradation requires approval where policy demands it.

<a id="section-10-157"></a>
## 10.157 Graceful Degradation

Graceful degradation shall preserve:

- truth,

- minimum value,

- and mandatory safety.

The system shall not claim full completion.

<a id="section-10-158"></a>
## 10.158 Partial Completion

A Plan may permit partial completion.

The Completion Contract shall define:

- which Steps are mandatory,

- minimum output count,

- acceptable omissions,

- and approval requirements.

<a id="section-10-159"></a>
## 10.159 Partial Output Preservation

Successful Outputs should remain preserved when later Steps fail, unless retention policy prohibits it.

They shall be marked with truthful lifecycle state.

<a id="section-10-160"></a>
## 10.160 Partial Cost

Cost incurred by partial work shall remain recorded.

Failure does not erase spending.

<a id="section-10-161"></a>
## 10.161 Parent Completion Logic

A Parent Plan or Composite Step may complete when:

- all mandatory children pass,

- defined optional threshold is met,

- required approval exists,

- and no blocking unknown outcomes remain.

<a id="section-10-162"></a>
## 10.162 Child Failure Propagation

A Child Step failure may:

- fail the parent,

- trigger fallback,

- create partial completion,

- or remain isolated.

Propagation rules shall be explicit.

<a id="section-10-163"></a>
## 10.163 Parallel Execution

Independent Steps may run in parallel.

Parallelism can reduce latency.

It may increase:

- concurrent cost,

- quota pressure,

- complexity,

- and partial-state handling.

<a id="section-10-164"></a>
## 10.164 Parallel Group

A Parallel Group defines Steps allowed to execute concurrently.

It shall include:

- concurrency limit,

- shared budget,

- join condition,

- and cancellation behaviour.

<a id="section-10-165"></a>
## 10.165 Concurrency Limit

Concurrency may be limited by:

- Project,

- Provider Account,

- Model Deployment,

- Runtime Node,

- Capability,

- budget,

- or Workflow.

<a id="section-10-166"></a>
## 10.166 Parallel Cost Reservation

The Plan shall reserve enough budget for concurrently launched paid work.

It must not assume later Steps can be cancelled without cost.

<a id="section-10-167"></a>
## 10.167 Speculative Execution

Speculative Execution runs several alternatives before one is known to be necessary.

It may improve latency or quality.

It also increases cost.

Speculation requires explicit policy and budget.

<a id="section-10-168"></a>
## 10.168 Candidate Race

A Candidate Race submits the same bounded task to several eligible resources and selects the best accepted result.

It shall define:

- maximum candidates,

- budget,

- evaluation,

- cancellation,

- and provenance.

Candidate races should not be default behaviour.

<a id="section-10-169"></a>
## 10.169 Hedged Request

A Hedged Request submits a second attempt after the first exceeds a latency threshold.

Hedging requires:

- idempotency analysis,

- cost allowance,

- and duplicate-result handling.

<a id="section-10-170"></a>
## 10.170 Sequential Execution

Sequential Steps execute in dependency order.

Sequence should be used when:

- Output is required,

- authority boundary exists,

- or cost should be deferred until prior validation passes.

<a id="section-10-171"></a>
## 10.171 Preview-First Strategy

Preview-first planning generates a cheaper or lower-resolution result before full production.

It may reduce waste for:

- image,

- video,

- voice,

- design,

- and long-form media.

<a id="section-10-172"></a>
## 10.172 Premium-Escalation Strategy

A Plan may start with an economical resource and escalate to premium only when:

- quality fails,

- importance warrants it,

- and budget permits.

The escalation threshold shall be explicit.

<a id="section-10-173"></a>
## 10.173 Premium-First Strategy

Critical outputs may use a premium resource immediately when:

- quality risk is high,

- retries are expensive,

- deadline is tight,

- or failure consequence is significant.

<a id="section-10-174"></a>
## 10.174 Local-First Strategy

A Local-First Plan prefers local or private resources.

External fallback shall remain prohibited unless the request permits it.

<a id="section-10-175"></a>
## 10.175 Free-Capacity-First Strategy

A Plan may prefer:

- included credits,

- free tiers,

- or local resources

before paid execution.

The strategy shall still respect quality, rights and reliability.

<a id="section-10-176"></a>
## 10.176 Mixed-Tier Strategy

A production may use:

- premium resources for master Assets,

- economical resources for derivatives,

- local resources for conversion,

- and human review for acceptance.

<a id="section-10-177"></a>
## 10.177 Planning for Human Review

Human review shall be scheduled as a real dependency.

The Plan should estimate:

- reviewer availability,

- review duration,

- and correction cycle.

<a id="section-10-178"></a>
## 10.178 Reviewer Assignment

The Plan may identify:

- named reviewer,

- reviewer role,

- reviewer pool,

- or Project owner.

Assignment shall respect scope and authority.

<a id="section-10-179"></a>
## 10.179 Review Timeout

A Human Review Step may have:

- reminder,

- escalation,

- expiry,

- and cancellation behaviour.

No decision shall be fabricated when the reviewer does not respond.

<a id="section-10-180"></a>
## 10.180 Conditional Approval

The Plan may receive approval with conditions.

Conditions shall become enforceable Plan constraints.

<a id="section-10-181"></a>
## 10.181 Plan Approval Summary

Before approval, the Plan should present:

- objective,

- phases,

- providers or resource classes,

- data transfers,

- expected cost,

- maximum cost,

- retries,

- expected duration,

- quality gates,

- human steps,

- side effects,

- and prohibited actions.

<a id="section-10-182"></a>
## 10.182 Plan Approval Granularity

Approval may cover:

- complete Plan,

- one Phase,

- one expensive branch,

- one Provider,

- one side effect,

- or one retry envelope.

Granularity shall be explicit.

<a id="section-10-183"></a>
## 10.183 Plan Approval Version Binding

Approval shall bind to the exact Plan Version.

Material replanning may invalidate it.

<a id="section-10-184"></a>
## 10.184 Approval Invalidation

Approval may become invalid after:

- budget increase,

- Provider change,

- data-placement change,

- publication addition,

- new side effect,

- rights change,

- or expanded retry.

<a id="section-10-185"></a>
## 10.185 Bounded Plan Autonomy

An approved Plan may allow autonomous execution within:

- defined Steps,

- budget,

- Providers,

- retry limits,

- deadline,

- and quality gates.

Autonomy ends at the Plan boundary.

<a id="section-10-186"></a>
## 10.186 Plan Activation

A Plan may activate only when:

- validation passes,

- required approval exists,

- required Inputs exist,

- budget can be reserved,

- and no blocking policy conflict remains.

<a id="section-10-187"></a>
## 10.187 Activation Record

Activation shall record:

- Plan Version,

- actor,

- time,

- approvals,

- budget reservation,

- registry snapshots,

- and initial state.

<a id="section-10-188"></a>
## 10.188 Plan Execution State

Plan states may include:

- draft,

- constructing,

- validating,

- awaiting clarification,

- awaiting approval,

- approved,

- activating,

- active,

- paused,

- replanning,

- partially completed,

- completed,

- failed,

- cancelled,

- expired,

- superseded,

- and archived.

<a id="section-10-189"></a>
## 10.189 Draft Plan

Draft means the Plan is still being edited and cannot execute.

<a id="section-10-190"></a>
## 10.190 Constructing Plan

Constructing means decomposition, candidate generation or cost estimation is underway.

<a id="section-10-191"></a>
## 10.191 Validating Plan

Validating means structural, semantic and governance checks are running.

<a id="section-10-192"></a>
## 10.192 Awaiting Clarification Plan

The Plan requires additional authoritative information.

<a id="section-10-193"></a>
## 10.193 Awaiting Approval Plan

The Plan is valid but lacks required approval.

<a id="section-10-194"></a>
## 10.194 Approved Plan State

Approved means the current Plan Version may proceed when activation conditions are satisfied.

<a id="section-10-195"></a>
## 10.195 Activating Plan

Activating means:

- budget,

- resources,

- queues,

- and execution records

are being prepared.

<a id="section-10-196"></a>
## 10.196 Active Plan State

Active means at least one Step may execute or wait according to the graph.

<a id="section-10-197"></a>
## 10.197 Paused Plan

A Plan may pause because of:

- approval,

- budget,

- Incident,

- human review,

- Provider outage,

- or user action.

<a id="section-10-198"></a>
## 10.198 Replanning State

Replanning means current execution conditions require a new Plan Version or adjusted future Steps.

<a id="section-10-199"></a>
## 10.199 Partially Completed Plan

Some Outputs satisfy parts of the Completion Contract.

Remaining mandatory work is incomplete or blocked.

<a id="section-10-200"></a>
## 10.200 Completed Plan

Completed means the Plan-level Completion Contract is satisfied.

Completion does not imply every optional Step executed.

<a id="section-10-201"></a>
## 10.201 Failed Plan

Failed means the Plan cannot fulfil its mandatory Completion Contract under current approved boundaries.

<a id="section-10-202"></a>
## 10.202 Cancelled Plan

Cancelled means an authorised Principal stopped future progression.

Running external jobs may remain subject to reconciliation.

<a id="section-10-203"></a>
## 10.203 Expired Plan

Expired means the Plan is no longer valid for new execution.

<a id="section-10-204"></a>
## 10.204 Superseded Plan State

A new Plan Version governs future work.

Existing Executions remain linked to the old Version.

<a id="section-10-205"></a>
## 10.205 Plan Pause

Pause shall prevent new Steps from starting.

It may allow:

- in-flight jobs to complete,

- reconciliation,

- safe cancellation,

- or compensation

according to policy.

<a id="section-10-206"></a>
## 10.206 Hard Pause

A Hard Pause stops all possible activity immediately.

It may be required for:

- security Incident,

- rights violation,

- credential compromise,

- or severe budget anomaly.

<a id="section-10-207"></a>
## 10.207 Soft Pause

A Soft Pause stops new work while allowing current safe operations to settle.

<a id="section-10-208"></a>
## 10.208 Plan Resume

Resume requires:

- valid Plan Version,

- current authority,

- current policy,

- valid credentials,

- budget,

- and resolved pause reason.

<a id="section-10-209"></a>
## 10.209 Plan Cancellation

Cancellation shall define:

- which Steps stop,

- which external jobs are cancelled,

- which Outputs are retained,

- whether compensation runs,

- and how cost is reconciled.

<a id="section-10-210"></a>
## 10.210 User Cancellation

A user with authority may cancel the Plan.

The system shall report what cannot be undone.

<a id="section-10-211"></a>
## 10.211 Automatic Cancellation

Policy may automatically cancel after:

- approval expiry,

- deadline,

- severe Incident,

- or repeated failure.

Automatic cancellation rules shall be explicit.

<a id="section-10-212"></a>
## 10.212 Replanning

Replanning creates a new Plan Version when the active plan can no longer continue as designed.

Triggers may include:

- Provider unavailability,

- cost change,

- quality failure,

- changed Input,

- deadline risk,

- policy change,

- or user amendment.

<a id="section-10-213"></a>
## 10.213 Replanning Boundary

Replanning shall preserve completed work where safe.

It shall not rewrite prior Executions.

<a id="section-10-214"></a>
## 10.214 Material Replanning

Material replanning changes:

- Provider class,

- budget,

- data placement,

- quality,

- side effects,

- mandatory Step,

- or Completion Contract.

It may require renewed approval.

<a id="section-10-215"></a>
## 10.215 Non-Material Replanning

Non-material replanning may adjust:

- queue order,

- equivalent Deployment,

- or timing

within the approved envelope.

<a id="section-10-216"></a>
## 10.216 Replanning Decision

A Replanning Decision shall record:

- trigger,

- old Plan Version,

- new Plan Version,

- preserved Steps,

- cancelled Steps,

- cost impact,

- approval impact,

- and actor.

<a id="section-10-217"></a>
## 10.217 Mid-Execution Resource Change

A future Step may use a different resource without changing completed history.

The new selection shall remain evidenced.

<a id="section-10-218"></a>
## 10.218 Input Change During Execution

Material Input changes may invalidate:

- downstream Steps,

- Evaluations,

- Outputs,

- and approval.

The Planner shall determine the affected subgraph.

<a id="section-10-219"></a>
## 10.219 Selective Invalidation

Only Steps dependent on changed information should be invalidated where safe.

Selective invalidation reduces unnecessary cost.

<a id="section-10-220"></a>
## 10.220 Output Reuse

Accepted Outputs from a superseded Plan may be reused when:

- Inputs remain valid,

- classification permits,

- quality remains sufficient,

- and provenance is preserved.

<a id="section-10-221"></a>
## 10.221 Cached Result Reuse

A cached Output may satisfy a Step only when:

- request semantics match,

- Project and Tenant scope permit,

- freshness is valid,

- rights permit,

- and provenance is complete.

<a id="section-10-222"></a>
## 10.222 Plan Determinism

The same Planning Input may produce different valid Plans when:

- current resources differ,

- prices change,

- health changes,

- or AI-assisted planning is non-deterministic.

The Planner shall preserve the actual Plan Version and decision evidence.

<a id="section-10-223"></a>
## 10.223 Planning Reproducibility

Reproduction may require:

- request version,

- policy versions,

- registry snapshots,

- planning strategy,

- template version,

- assumptions,

- and Planner version.

<a id="section-10-224"></a>
## 10.224 Planner Version

<a id="section-10-225"></a>

- decomposition rules,

- approval rules,

- retry defaults,

- and fallback defaults.

- request,

- template,

- registry snapshots,

- policy,

- assumptions,

- cost sources,

- and revision history.

- Why were these resource classes considered?

- What assumptions were made?

- What may the Plan cost?

## 10.317 Applied Example — Nova and Pling Episode Plan

A Familje-Stunden monthly episode Plan may contain:

Phase 1 — Preparation

1. Resolve approved story manuscript.

2. Resolve canonical Nova and Pling Asset Versions.

3. Validate scene illustration completeness.

4. Validate commercial rights and child-facing policy.

5. Assemble Project Instruction Set.

Phase 2 — Scene Planning

6. Segment story into scenes.

7. Match narration to scene duration.

8. Classify scenes by complexity.

9. Identify character-critical scenes.

10. Estimate preview and production cost.

Phase 3 — Approval

11. Present Production Plan.

12. Approve maximum budget.

13. Approve Providers or Provider classes.

14. Confirm no publication authority.

Phase 4 — Preview Generation

15. Generate low-cost preview for each complex scene.

16. Evaluate Nova consistency.

17. Evaluate Pling consistency.

18. Evaluate child-appropriate motion.

19. Route failed previews to revision.

Phase 5 — Final Scene Production

20. Use economical accepted previews where quality permits.

21. Escalate character-critical failed scenes to premium resource.

22. Ingest Provider videos.

23. Verify format, duration and integrity.

Phase 6 — Narration and Audio

24. Generate or ingest approved Swedish narration.

25. Validate pronunciation.

26. Generate or select approved sound.

27. Mix audio.

Phase 7 — Composition

28. Assemble master video.

29. Add titles and captions.

30. Validate sequence and timing.

Phase 8 — Review

31. Automated technical evaluation.

32. Human child-facing review.

33. Human brand and story review.

34. Revision loop within approved budget.

Phase 9 — Derivatives

35. Create trailer.

36. Create five short clips.

37. Create thumbnail candidates.

38. Preserve derivative provenance.

Phase 10 — Delivery

## 10.387 Closing Statement

The Intelligence Planner is the component that turns governed intent into governed action structure.

It allows Omnira to move beyond isolated prompts and provider calls without surrendering control to opaque agent autonomy.

The user defines the objective.

The Capability Request defines what the Fabric may attempt.

The Planner decomposes the work.

The Execution Graph defines dependencies.

The Steps define bounded operations.

The Resource Requirements define what implementation is needed.

Routing chooses the eligible resources.

The Budget Envelope limits spending.

The Authority Envelope limits action.

The Quality Gates define acceptance.

The Retry Policies define bounded recovery.

The Fallback Policies define eligible alternatives.

The Completion Gate determines whether the promised result was actually achieved.

For Familje-Stunden, this architecture allows one Nova and Pling episode to coordinate story, scene planning, character references, video, voice, sound, composition, evaluation and human review without handing the entire Project to one Provider.

For The Prompt, it keeps research, verification, editorial reasoning, media creation and publication as separate governed responsibilities.

For GainPilot, it enables economical mixed-resource production without creating a second orchestration architecture.

For Omnira, it allows code, research, media, local Models, external Providers, human work and future agent systems to participate in one versioned execution structure.

The Plan may change.

The Provider may change.

The Model may change.

The user’s approved objective and authority boundary remain stable.

No complex execution without a Plan.

No Plan without scope.

No Step without purpose.

No side effect without authority.

No retry without a bound.

No fallback without policy.

No completion without evidence.

The user retains direction.

Omnira retains orchestration.

The Fabric turns intention into governed execution.
