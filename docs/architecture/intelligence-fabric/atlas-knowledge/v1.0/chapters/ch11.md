# Chapter 11 — Routing Profiles and Selection Policy

<a id="section-11-1"></a>
## 11.1 Chapter Status

This chapter defines the canonical architecture, governance model, decision order, lifecycle, contracts and operational responsibilities for routing within the Omnira Intelligence Fabric.

It establishes:

- how eligible intelligence resources are discovered,

- how mandatory constraints are separated from preferences,

- how Providers, Provider Accounts, Models, Deployments, Tools, local resources, External Agent Resources and human-assisted paths are compared,

- how the canonical Routing Profiles Economy, Balanced, Premium, Private and Pinned behave,

- how security, privacy, data classification, rights, authority, quality, deadline and budget outrank ordinary optimisation,

- how local, user-owned and Omnira-managed capacity coexist,

- how resource candidates are excluded, ranked, selected and substituted,

- how profile defaults and Project-specific policy are applied,

- how current health, quotas, credits, latency and capacity affect decisions,

- how fallback and retry remain governed,

- how routing decisions remain explainable,

- how commercial conflicts of interest are controlled,

- how routing learning is admitted without creating unbounded self-modification,

- and how Stage 1 shall implement a bounded but extensible routing system.

Routing is the process through which the Fabric selects an eligible execution path for a specific bounded Step or request.

Routing does not determine the user’s intent.

Routing does not define Capability meaning.

Routing does not create execution authority.

Routing does not lower Data Classification.

Routing does not grant commercial rights.

Routing does not approve spending.

Routing operates only after mandatory eligibility conditions have been resolved.

This chapter is normative after formal approval.

Runtime implementation and conformance must be verified separately.

<a id="section-11-2"></a>
## 11.2 Purpose of Routing

The Intelligence Fabric may have many ways to fulfil the same Capability.

A text Capability may be available through:

- a local Model,

- a user-owned external subscription,

- an Omnira-managed Provider Account,

- a specialist external Provider,

- or a human-assisted workflow.

A video Capability may be available through:

- one economical Model,

- one premium Provider,

- one Provider-managed router,

- one local composition workflow,

- or one manually operated creative platform.

Without a canonical routing layer, resource selection would tend to become:

- hard-coded in Project code,

- embedded inside Agent prompts,

- determined by whichever Provider was connected first,

- chosen manually for every task,

- based on Provider popularity,

- or driven by hidden commercial incentives.

The routing architecture exists to choose the best eligible path for the current request while preserving:

- user control,

- Project isolation,

- quality,

- cost,

- privacy,

- rights,

- reliability,

- deadline,

- and truthful evidence.

<a id="section-11-3"></a>
## 11.3 Routing Is Not Planning

Planning defines:

- which Steps are required,

- what Capabilities they need,

- what dependencies exist,

- what budgets apply,

- and what Completion Contract must be satisfied.

Routing selects the current eligible resource for a Step.

A Plan may state:

Generate one Swedish narration track using speech.synthesise.

Routing determines whether that Step uses:

- a local speech Model,

- ElevenLabs,

- another Provider,

- an Omnira-managed voice service,

- or a human-assisted path.

The Plan defines the need.

Routing selects the implementation.

<a id="section-11-4"></a>
## 11.4 Routing Is Not Capability Resolution

Capability Resolution determines which canonical operation is required.

Routing occurs only after the Capability is known.

The Router shall not replace:

video.image_to_video

with:

image.generate

merely because an image Model is cheaper.

A materially different Capability path requires:

- approved alternative,

- replanning,

- or degraded-outcome approval.

<a id="section-11-5"></a>
## 11.5 Routing Is Not Authority

A Router may identify a technically attractive Provider.

It shall not select that Provider if:

- the Principal lacks authority,

- the Provider Account is outside Project scope,

- spending is unapproved,

- or the requested side effect is prohibited.

Routing cannot expand the Authority Envelope.

<a id="section-11-6"></a>
## 11.6 Routing Is Not Policy Creation

Routing applies current policy.

It does not invent policy dynamically.

The Router may produce a Policy Gap when rules are incomplete.

It shall not assume that missing policy means permission.

<a id="section-11-7"></a>
## 11.7 Routing Is Not Provider Preference

A Provider Preference may influence ranking.

It is not the same as routing.

Routing considers all applicable mandatory and optimisation dimensions.

<a id="section-11-8"></a>
## 11.8 Routing Is Not Model Popularity

A widely known or expensive Model is not automatically the correct resource.

Suitability depends on:

- Capability,

- Inputs,

- Quality Contract,

- Project,

- privacy,

- rights,

- budget,

- latency,

- and current evidence.

<a id="section-11-9"></a>
## 11.9 Routing Is Not Global Best-Resource Selection

There is no universal best resource.

A resource may be best for:

- Swedish technical reasoning,

- but not image editing;

- low-cost captioning,

- but not child-facing narration;

- local confidential analysis,

- but not premium video production.

Routing decisions shall remain request-specific.

<a id="section-11-10"></a>
## 11.10 Intelligence Router

The Intelligence Router is the Fabric component or governed service responsible for selecting eligible Resource Candidates.

The Router may use:

- deterministic policy,

- Registry data,

- current operational state,

- cost estimates,

- quality evidence,

- routing profile,

- historical outcomes,

- and bounded learned preferences.

The Router shall operate as an identifiable Service Principal.

It shall not own unrestricted Provider credentials.

<a id="section-11-11"></a>
## 11.11 Router Responsibilities

The Router is responsible for:

- receiving a Routing Request,

- resolving applicable policy,

- generating Resource Candidates,

- evaluating hard eligibility,

- excluding incompatible candidates,

- scoring eligible candidates,

- selecting a candidate or ranked set,

- identifying fallback candidates,

- preserving decision evidence,

- and returning a Selection Decision.

The Router shall distinguish:

- eligible,

- ineligible,

- conditionally eligible,

- unavailable,

- and unresolved candidates.

<a id="section-11-12"></a>
## 11.12 Router Non-Responsibilities

The Router is not responsible for:

- changing the user objective,

- creating new Capabilities,

- accepting Provider terms,

- granting credentials,

- raising the budget,

- lowering the Quality Floor,

- changing Data Classification,

- granting publication authority,

- or declaring an Output accepted.

These responsibilities remain outside routing.

<a id="section-11-13"></a>
## 11.13 Routing Request

A Routing Request is a canonical request to select one or more eligible execution resources.

It shall include or reference:

- routingRequestId,

- Capability Requirement,

- Plan Version,

- Step ID,

- Tenant,

- Project,

- Environment,

- initiating Principal,

- Authority Envelope,

- Data Classification,

- Rights Profile,

- Consent requirements,

- Quality Contract,

- Budget allocation,

- deadline,

- latency requirement,

- Routing Profile,

- Provider constraints,

- Model constraints,

- placement constraints,

- required Features,

- Inputs,

- output requirements,

- retry context,

- and policy versions.

<a id="section-11-14"></a>
## 11.14 Routing Request Identity

Every material Routing Request shall have stable identity.

A Step may produce several Routing Requests because of:

- initial selection,

- retry,

- fallback,

- replanning,

- or changed operational conditions.

Each decision shall remain traceable.

<a id="section-11-15"></a>
## 11.15 Routing Context

Routing Context may include:

- Capability Registry Snapshot,

- Model Registry Snapshot,

- Provider Registry Snapshot,

- Tool Registry Snapshot,

- Connection state,

- Credential state,

- Provider Account state,

- Runtime Node state,

- current pricing,

- current quota,

- current credit balance,

- current health,

- benchmark evidence,

- Project preferences,

- and governed learning.

Every operational input shall declare freshness.

<a id="section-11-16"></a>
## 11.16 Routing Output

The primary routing output is a Selection Decision.

Routing may also produce:

- ranked candidates,

- exclusions,

- warnings,

- approval requirement,

- budget conflict,

- no-route result,

- degraded alternatives,

- and fallback chain.

<a id="section-11-17"></a>
## 11.17 Selection Decision

A Selection Decision shall include or reference:

- selectionDecisionId,

- routingRequestId,

- selected Resource Candidate,

- selected Provider,

- Provider Account,

- Connection,

- Model Version or Tool,

- Deployment or Runtime Node,

- Adapter,

- Capability Version,

- Routing Profile,

- eligibility results,

- score components,

- expected cost,

- expected latency,

- quality evidence,

- privacy and rights status,

- fallback set,

- decision time,

- data freshness,

- and provenance.

<a id="section-11-18"></a>
## 11.18 Decision Version

Material changes to routing logic or candidate state may produce a new Selection Decision.

The execution shall reference the exact Selection Decision used when the Provider operation began.

<a id="section-11-19"></a>
## 11.19 Decision Finality

A Selection Decision is valid only for a bounded time and context.

It may become invalid because of:

- Provider outage,

- Account exhaustion,

- credential expiry,

- price change,

- policy change,

- Model retirement,

- or deadline shift.

The Executor shall revalidate material conditions before use.

<a id="section-11-20"></a>
## 11.20 Selection Window

A Selection Window defines how long a decision may be used without full rerouting.

The window should reflect:

- operational volatility,

- cost sensitivity,

- Provider health,

- and request consequence.

<a id="section-11-21"></a>
## 11.21 Early Routing

Early Routing selects resources during planning or approval.

It may be appropriate when:

- the exact Provider must be approved,

- the resource is pinned,

- capacity must be reserved,

- or cost must be known.

Early Routing is more exposed to stale operational state.

<a id="section-11-22"></a>
## 11.22 Late Routing

Late Routing selects resources shortly before execution.

It can use current:

- health,

- pricing,

- quota,

- and capacity.

Late Routing may be unsuitable when the user expects exact Provider disclosure before approval.

<a id="section-11-23"></a>
## 11.23 Hybrid Routing

Hybrid Routing may decide:

- Provider class during planning,

- Account during approval,

- Model Family during scheduling,

- and exact Deployment at execution.

The binding level shall remain explicit.

<a id="section-11-24"></a>
## 11.24 Candidate Resource

A Candidate Resource is a complete or partial path capable of performing the requested Step.

A Candidate may include:

- Provider,

- Provider Account,

- Connection,

- Model Version,

- Model Deployment,

- Adapter,

- Tool,

- External Agent Resource,

- Runtime Node,

- human-assisted process,

- or composed resource path.

<a id="section-11-25"></a>
## 11.25 Complete Resource Candidate

A Complete Resource Candidate contains every operational object required to execute the Step.

For an external Model request, this may include:

- Provider,

- Provider Account,

- Connection,

- Model Version,

- Deployment,

- Adapter,

- and pricing reference.

<a id="section-11-26"></a>
## 11.26 Partial Candidate

A Partial Candidate lacks one or more unresolved elements.

Examples include:

- Provider selected but exact Model late-bound,

- local Model selected but Runtime Node unavailable,

- human-assisted path without assigned operator,

- or Model known but no active Connection.

Partial Candidates shall not be executed until complete.

<a id="section-11-27"></a>
## 11.27 Composite Candidate

A Composite Candidate satisfies one Step through several resources.

For example:

- local document extraction,

- external reasoning,

- local validation,

- and human review.

Composite candidates may require replanning when the composition changes the Step boundary materially.

<a id="section-11-28"></a>
## 11.28 Human-Assisted Candidate

A Human-Assisted Candidate includes one or more required human operations.

It shall declare:

- operator,

- Provider Account,

- manual action,

- expected cost,

- output handoff,

- and evidence.

It shall not be scored as fully autonomous.

<a id="section-11-29"></a>
## 11.29 Simulated Candidate

A Simulated Candidate exists only for:

- testing,

- cost comparison,

- or policy simulation.

It shall not be selected for production execution.

<a id="section-11-30"></a>
## 11.30 Candidate Generation

Candidate Generation discovers resources that may structurally support the requested Capability.

It may query:

- Capability Registry,

- Model Registry,

- Provider Registry,

- Tool Registry,

- Runtime Node Registry,

- and approved human-assisted procedures.

Candidate Generation is broad.

Eligibility evaluation narrows the set.

<a id="section-11-31"></a>
## 11.31 Candidate Discovery Scope

Candidate discovery shall respect:

- Tenant,

- Project,

- Environment,

- visibility,

- and administrative restrictions.

A private Tenant resource shall not appear as a candidate for another Tenant.

<a id="section-11-32"></a>
## 11.32 Candidate Set

The Candidate Set is the complete set considered by the Router for one decision.

The decision record should preserve:

- candidates discovered,

- candidates excluded before scoring,

- candidates scored,

- and candidates selected.

<a id="section-11-33"></a>
## 11.33 Candidate Deduplication

Equivalent candidate paths may appear through:

- aliases,

- duplicate Model records,

- several Adapter views,

- or Provider routing products.

The Router should deduplicate only when equivalence is sufficiently established.

<a id="section-11-34"></a>
## 11.34 Eligibility Before Ranking

The Router shall evaluate eligibility before optimisation.

A resource that violates a mandatory constraint shall not receive a score that could overcome the violation.

The decision sequence is:

1. Resolve mandatory policy.

2. Generate candidates.

3. Evaluate hard eligibility.

4. Exclude ineligible candidates.

5. Score eligible candidates.

6. Select according to profile.

7. preserve fallback.

8. revalidate before execution.

<a id="section-11-35"></a>
## 11.35 Hard Constraint

A Hard Constraint is a requirement that cannot be traded away through scoring.

Examples include:

- Local Only processing,

- valid commercial rights,

- mandatory consent,

- required Capability Feature,

- explicit Provider deny,

- maximum authorised cost,

- production-approved Connection,

- and required publication authority.

<a id="section-11-36"></a>
## 11.36 Soft Constraint

A Soft Constraint expresses preference rather than absolute eligibility.

Examples include:

- prefer local,

- prefer included credits,

- prefer lower latency,

- prefer one Provider,

- or prefer higher quality.

Soft constraints may influence ranking.

<a id="section-11-37"></a>
## 11.37 Mandatory Requirement

A Mandatory Requirement shall fail closed when unsatisfied.

The Router must not convert a mandatory requirement into a preference because few candidates remain.

<a id="section-11-38"></a>
## 11.38 Preferred Requirement

A Preferred Requirement should influence ranking.

The decision record should show when a preferred requirement was not satisfied and why.

<a id="section-11-39"></a>
## 11.39 Optional Feature

An Optional Feature may improve suitability.

Its absence shall not create ineligibility unless the request marks it mandatory.

<a id="section-11-40"></a>
## 11.40 Eligibility Result

Candidate eligibility may be:

- eligible,

- eligible with conditions,

- ineligible,

- unavailable,

- unresolved,

- approval required,

- or requires replanning.

<a id="section-11-41"></a>
## 11.41 Eligible Candidate

An Eligible Candidate satisfies all hard constraints under current evidence.

<a id="section-11-42"></a>
## 11.42 Conditionally Eligible Candidate

A Conditionally Eligible Candidate may be used only when defined conditions are satisfied.

Conditions may include:

- human review,

- separate approval,

- lower data class,

- limited duration,

- or bounded retry.

<a id="section-11-43"></a>
## 11.43 Ineligible Candidate

An Ineligible Candidate violates at least one mandatory condition.

Its exclusion reason shall be recorded.

<a id="section-11-44"></a>
## 11.44 Unavailable Candidate

An Unavailable Candidate may be structurally and policy compatible but cannot currently execute because of:

- outage,

- quota,

- credits,

- capacity,

- authentication,

- or maintenance.

<a id="section-11-45"></a>
## 11.45 Unresolved Candidate

An Unresolved Candidate lacks sufficient evidence for a safe decision.

Unknown shall not be treated as eligible.

<a id="section-11-46"></a>
## 11.46 Approval-Required Candidate

A Candidate may be otherwise eligible but require:

- Provider approval,

- cost approval,

- data-placement approval,

- voice consent,

- or premium escalation approval.

The Router shall return the required approval boundary.

<a id="section-11-47"></a>
## 11.47 Replanning-Required Candidate

A Candidate requires a materially different Capability path or graph structure.

Routing shall not perform that substitution silently.

<a id="section-11-48"></a>
## 11.48 Policy Precedence

Mandatory policy shall be applied before optimisation.

The canonical precedence order is:

1. Law and mandatory external obligations.

2. Platform security and safety policy.

3. Tenant isolation and Project scope.

4. Data Classification and privacy.

5. Rights, consent and commercial-use requirements.

6. Authority and approval.

7. Capability and Feature compatibility.

8. Quality Floor and mandatory evaluation.

9. Hard deadline and operational feasibility.

10. Maximum budget and cost authority.

11. Provider, Model and placement restrictions.

12. Routing Profile.

13. Project and user preferences.

14. Learned optimisation.

15. Tie-breaking policy.

A lower level shall not override a higher mandatory level.

<a id="section-11-49"></a>
## 11.49 Legal Constraint

Where a legal or contractual requirement is known and applicable, it shall be enforced before routing preference.

The Fabric shall not invent legal conclusions.

Unresolved legal uncertainty may require human review.

<a id="section-11-50"></a>
## 11.50 Security Constraint

Security policy may exclude resources because of:

- compromised Credential,

- unsafe Model artefact,

- untrusted Adapter,

- active Provider Incident,

- or excessive administrative scope.

<a id="section-11-51"></a>
## 11.51 Tenant Isolation Constraint

A resource belonging to another Tenant is ineligible unless an explicit managed shared-service architecture permits isolated use.

<a id="section-11-52"></a>
## 11.52 Project Scope Constraint

A Project-owned Account, Asset, Credential or local Node shall not be used by another Project without explicit authority.

<a id="section-11-53"></a>
## 11.53 Data Classification Constraint

The Candidate shall be compatible with the effective Data Classification.

The Router shall use the most restrictive unresolved classification.

<a id="section-11-54"></a>
## 11.54 Privacy Constraint

Privacy may require:

- Local Only execution,

- approved region,

- no training use,

- zero or bounded retention,

- private Deployment,

- or user-controlled infrastructure.

<a id="section-11-55"></a>
## 11.55 Rights Constraint

The Candidate shall support required:

- commercial use,

- modification,

- distribution,

- attribution,

- and derivative rights.

<a id="section-11-56"></a>
## 11.56 Consent Constraint

Voice, likeness or personal-data use may require valid consent.

No score may compensate for missing consent.

<a id="section-11-57"></a>
## 11.57 Authority Constraint

The acting Principal and Plan shall have authority for:

- Capability,

- Project,

- Provider class,

- cost,

- side effect,

- and retry.

<a id="section-11-58"></a>
## 11.58 Capability Compatibility Constraint

The Candidate shall support the exact Capability Version or an approved compatible version.

<a id="section-11-59"></a>
## 11.59 Feature Compatibility Constraint

Mandatory Features shall be supported.

A base-capability claim is insufficient.

<a id="section-11-60"></a>
## 11.60 Quality Floor Constraint

The Candidate shall have sufficient evidence to meet the minimum Quality Floor.

Unknown quality may be treated as:

- experimental,

- approval required,

- or ineligible

depending on consequence.

<a id="section-11-61"></a>
## 11.61 Deadline Constraint

The Candidate shall have a feasible chance of meeting a Hard Deadline.

Routing shall include:

- queue,

- execution,

- review,

- and fallback time.

<a id="section-11-62"></a>
## 11.62 Budget Constraint

Expected and maximum candidate cost shall remain inside the approved Step and Plan budgets.

<a id="section-11-63"></a>
## 11.63 Provider Restriction

Provider allowlists, denylists and pinning shall be enforced.

<a id="section-11-64"></a>
## 11.64 Model Restriction

Model Family, Version, ownership class or licence restrictions shall be enforced.

<a id="section-11-65"></a>
## 11.65 Placement Restriction

Execution may be restricted to:

- local Node,

- user-managed Provider,

- approved region,

- Omnira-managed cloud,

- or external Provider class.

<a id="section-11-66"></a>
## 11.66 Integration Maturity Constraint

Production work may require:

- production API,

- production MCP,

- local production,

- or approved human-assisted process.

An experimental connection may remain ineligible.

<a id="section-11-67"></a>
## 11.67 Evidence Sufficiency

Eligibility requires sufficient evidence.

The required evidence strength shall increase with:

- consequence,

- cost,

- privacy,

- public exposure,

- and irreversibility.

<a id="section-11-68"></a>
## 11.68 Fail-Closed Routing

When a mandatory eligibility property cannot be resolved, the Router shall fail closed.

It may:

- request clarification,

- request approval,

- recommend a safer Candidate,

- or return no route.

<a id="section-11-69"></a>
## 11.69 No-Route Result

A No-Route Result means no current Candidate satisfies all mandatory conditions.

It shall identify:

- violated constraints,

- unavailable resources,

- unresolved evidence,

- and possible next actions.

<a id="section-11-70"></a>
## 11.70 No-Route Is Not Failure of Intent

The user’s Intent may remain valid when no route exists.

The request may:

- wait,

- amend constraints,

- add Provider access,

- use human assistance,

- or be deferred.

<a id="section-11-71"></a>
## 11.71 Routing Profile

A Routing Profile is a canonical policy preset describing how eligible candidates should be optimised.

The canonical profiles are:

- Economy,

- Balanced,

- Premium,

- Private,

- and Pinned.

A Routing Profile applies only after mandatory eligibility.

<a id="section-11-72"></a>
## 11.72 Profile Identity

Every Routing Profile shall have stable canonical identity and version.

The profile shall define:

- objective,

- weighting,

- tie-breaking,

- permissible strategies,

- fallback behaviour,

- and disclosure requirements.

<a id="section-11-73"></a>
## 11.73 Profile Version

Material changes to profile behaviour require a new Profile Version.

Executions shall preserve which profile version influenced selection.

<a id="section-11-74"></a>
## 11.74 Profile Inheritance

A Routing Profile may be selected through:

- request-explicit setting,

- Production Envelope,

- Project policy,

- Tenant policy,

- user preference,

- Workflow Template,

- or safe platform default.

<a id="section-11-75"></a>
## 11.75 Profile Resolution Order

The effective profile should be resolved in this order:

1. Request-explicit profile.

2. Approved Production Envelope.

3. Workflow or Plan requirement.

4. Project default.

5. Tenant default.

6. User preference.

7. Platform safe default.

Mandatory policy may override any profile behaviour.

<a id="section-11-76"></a>
## 11.76 Default Profile

Balanced should normally be the default for ordinary governed production unless Project or Tenant policy defines another default.

The default shall be explicit.

Missing profile shall not create undefined behaviour.

<a id="section-11-77"></a>
## 11.77 Profile Override

A user or authorised system may override the default profile within policy.

The override shall preserve:

- actor,

- reason where material,

- scope,

- and validity.

<a id="section-11-78"></a>
## 11.78 Profile Restriction

A Project may prohibit certain profiles.

Examples include:

- Premium prohibited for routine tasks,

- Pinned prohibited without architecture reason,

- External Balanced prohibited for Local Only work.

<a id="section-11-79"></a>
## 11.79 Profile Combination

One Step shall have one effective primary Routing Profile.

Additional constraints such as:

- local-first,

- included-credit preference,

- or approved Provider preference

may be expressed separately.

Profiles shall not be combined ambiguously.

<a id="section-11-80"></a>
## 11.80 Economy Profile

Economy optimises for the lowest expected total eligible cost.

Economy shall preserve:

- Quality Floor,

- privacy,

- rights,

- authority,

- deadline,

- reliability minimum,

- and required evidence.

Economy does not mean:

- lowest advertised unit price,

- free at any quality,

- unlimited local execution,

- or skipping evaluation.

<a id="section-11-81"></a>
## 11.81 Economy Objective

The Economy objective is:

Select the lowest expected total-cost Candidate that satisfies all mandatory constraints and has acceptable reliability.

<a id="section-11-82"></a>
## 11.82 Economy Cost Definition

Total expected cost may include:

- direct Provider charge,

- expected retry cost,

- post-processing cost,

- human correction cost,

- transfer cost,

- local compute estimate,

- and deadline risk.

The cheapest initial generation may not be the cheapest completed result.

<a id="section-11-83"></a>
## 11.83 Economy Candidate Preference

Economy may prefer:

- included subscription capacity,

- free eligible quota,

- local resources,

- lower-cost Providers,

- smaller Models,

- fewer variants,

- reusable Outputs,

- and preview-first strategies.

<a id="section-11-84"></a>
## 11.84 Economy Quality Rule

Economy shall not lower the Quality Floor.

It may accept lower performance above the floor when the user has not requested premium optimisation.

<a id="section-11-85"></a>
## 11.85 Economy Reliability Rule

A very cheap Candidate with high expected failure or retry rate may be more expensive overall.

Economy scoring shall consider reliability.

<a id="section-11-86"></a>
## 11.86 Economy Latency Rule

Economy may accept slower execution when the deadline permits.

It shall not miss a Hard Deadline merely to save cost.

<a id="section-11-87"></a>
## 11.87 Economy Privacy Rule

Economy shall not route protected data to a cheaper but ineligible external Provider.

<a id="section-11-88"></a>
## 11.88 Economy Included-Credit Rule

Included credits may be preferred when:

- Capability and quality are sufficient,

- rights are valid,

- and the credits belong to the authorised Account.

<a id="section-11-89"></a>
## 11.89 Economy Local Rule

Local execution may receive a preference for zero marginal Provider charge.

The Router shall still consider:

- local quality,

- energy,

- hardware occupancy,

- and completion time.

<a id="section-11-90"></a>
## 11.90 Economy Optional-Work Rule

Economy may omit Optional Steps when the Completion Contract permits it.

The omission shall remain visible.

<a id="section-11-91"></a>
## 11.91 Economy Premium Escalation

Economy may escalate to a higher-cost Candidate only when:

- cheaper eligible paths failed,

- the Quality Floor remains unmet,

- remaining budget permits,

- and policy authorises the escalation.

<a id="section-11-92"></a>
## 11.92 Economy Fallback

Economy fallback should ordinarily proceed from lower expected total cost to higher cost while preserving eligibility.

<a id="section-11-93"></a>
## 11.93 Balanced Profile

Balanced optimises across:

- quality,

- expected total cost,

- latency,

- reliability,

- privacy,

- and operational fit.

Balanced is intended for ordinary production where no single dimension dominates.

<a id="section-11-94"></a>
## 11.94 Balanced Objective

The Balanced objective is:

Select the eligible Candidate with the strongest overall expected value for the current request.

<a id="section-11-95"></a>
## 11.95 Balanced Weighting

Balanced weighting shall be versioned.

A representative weighting may consider:

- quality,

- cost,

- reliability,

- latency,

- privacy,

- operational maturity,

- and Project evidence.

Exact weights belong to implementation policy.

<a id="section-11-96"></a>
## 11.96 Balanced Quality Rule

Balanced should prefer resources with stronger evidence when the expected benefit justifies the cost difference.

<a id="section-11-97"></a>
## 11.97 Balanced Cost Rule

Balanced shall avoid unnecessary premium spending.

It may select a more expensive Candidate when expected:

- acceptance,

- reliability,

- or deadline performance

is materially better.

<a id="section-11-98"></a>
## 11.98 Balanced Latency Rule

Balanced should avoid both:

- slow inexpensive paths that threaten delivery,

- and fast premium paths with little added value.

<a id="section-11-99"></a>
## 11.99 Balanced Reliability Rule

Candidates with stable:

- API,

- callbacks,

- Account state,

- and historical success

may outrank less reliable alternatives.

<a id="section-11-100"></a>
## 11.100 Balanced Privacy Rule

Privacy may influence ranking even when several candidates are legally eligible.

A local or low-retention Candidate may receive a preference.

<a id="section-11-101"></a>
## 11.101 Balanced Project Evidence

Project-specific evidence may influence selection.

For Familje-Stunden, character consistency may receive greater weight.

For The Prompt, factual grounding may receive greater weight.

For GainPilot, economical short-form completion may receive greater weight.

<a id="section-11-102"></a>
## 11.102 Balanced Fallback

Balanced fallback should preserve overall expected value rather than follow cost or quality alone.

<a id="section-11-103"></a>
## 11.103 Premium Profile

Premium optimises for the strongest justified expected quality within the approved budget and deadline.

Premium does not mean:

- highest price,

- unlimited variants,

- unlimited retries,

- or automatic use of the most famous Provider.

<a id="section-11-104"></a>
## 11.104 Premium Objective

The Premium objective is:

Select the eligible Candidate with the strongest expected ability to satisfy or exceed the Quality Target while remaining inside the approved envelope.

<a id="section-11-105"></a>
## 11.105 Premium Quality Rule

Premium shall prioritise:

- task-specific benchmark evidence,

- Project acceptance evidence,

- stronger Features,

- and lower quality-failure risk.

<a id="section-11-106"></a>
## 11.106 Premium Budget Rule

Premium remains bounded by:

- Step budget,

- Plan budget,

- retry budget,

- and maximum authorised cost.

<a id="section-11-107"></a>
## 11.107 Premium Reliability Rule

A premium resource shall not be selected merely for advertised quality when operational reliability is inadequate.

<a id="section-11-108"></a>
## 11.108 Premium Latency Rule

Premium may accept additional latency when the deadline permits and expected quality improvement is meaningful.

<a id="section-11-109"></a>
## 11.109 Premium Candidate Count

Premium may permit:

- additional variants,

- candidate races,

- or independent evaluation

only when explicitly included in budget and policy.

<a id="section-11-110"></a>
## 11.110 Premium Evaluation

Premium production may require stronger evaluation to ensure the additional cost produced additional value.

<a id="section-11-111"></a>
## 11.111 Premium Fallback

Fallback should prefer the next strongest eligible quality path.

Material quality reduction shall be disclosed.

<a id="section-11-112"></a>
## 11.112 Premium for Master Assets

Premium routing may be appropriate for:

- canonical character Assets,

- master video,

- high-visibility campaign,

- critical architecture reasoning,

- or reusable commercial output.

<a id="section-11-113"></a>
## 11.113 Premium for Derivatives

Derivatives should not automatically inherit Premium.

A lower-cost profile may be used when the derivative Quality Contract permits it.

<a id="section-11-114"></a>
## 11.114 Private Profile

Private optimises for approved privacy, custody and placement.

The meaning of Private shall be resolved explicitly.

Private may require:

- Local Only execution,

- user-managed infrastructure,

- Tenant-controlled server,

- specified region,

- no Provider retention,

- no training use,

- or private contractual Provider path.

<a id="section-11-115"></a>
## 11.115 Private Objective

The Private objective is:

Select the most private eligible execution path satisfying the request’s required Capability and Quality Floor.

<a id="section-11-116"></a>
## 11.116 Private Is Not One Location

Private does not always mean local device.

Depending on policy, Private may include:

- local Runtime Node,

- home server,

- Tenant server,

- private cloud Deployment,

- enterprise zero-retention API,

- or Omnira-managed isolated environment.

<a id="section-11-117"></a>
## 11.117 Private Placement Definition

The request or Project policy shall define acceptable placement classes.

The Router shall not infer that any encrypted cloud service satisfies Private.

<a id="section-11-118"></a>
## 11.118 Private Data Rule

Private routing shall preserve the effective Data Classification.

Local Only data normally requires user- or Tenant-controlled execution.

<a id="section-11-119"></a>
## 11.119 Private Quality Rule

Private shall not pretend that a weak local resource satisfies a stronger Quality Floor.

When no private Candidate meets quality, the Router shall return:

- no route,

- human-assisted private path,

- or request for revised authority.

<a id="section-11-120"></a>
## 11.120 Private Cost Rule

Private may select a more expensive resource when privacy is the primary profile objective.

The maximum budget remains binding.

<a id="section-11-121"></a>
## 11.121 Private External Fallback

External fallback is prohibited unless the Private profile definition explicitly includes eligible external private services.

<a id="section-11-122"></a>
## 11.122 Private Local-First Rule

Where several private candidates exist, the Router may prefer:

- user-controlled local,

- Tenant-controlled private,

- Omnira-managed isolated,

- and approved external private

according to Project policy.

<a id="section-11-123"></a>
## 11.123 Private Evidence Rule

Privacy eligibility shall rely on:

- Deployment,

- Account,

- region,

- retention,

- training use,

- and contract evidence.

Provider brand reputation is insufficient.

<a id="section-11-124"></a>
## 11.124 Private Logging Rule

Private execution may require reduced or local evidence storage.

Routing evidence shall still preserve enough information for governance.

<a id="section-11-125"></a>
## 11.125 Private Fallback

Fallback shall remain inside the accepted privacy class.

It shall not silently route protected data to ordinary external Providers.

<a id="section-11-126"></a>
## 11.126 Pinned Profile

Pinned requires or strongly prefers a specified resource.

The pin may target:

- Provider,

- Provider Account,

- Product,

- Model,

- Model Version,

- Deployment,

- Tool,

- Adapter,

- Runtime Node,

- or human-assisted procedure.

<a id="section-11-127"></a>
## 11.127 Pinned Objective

The Pinned objective is:

Use the specified resource when it remains eligible under all mandatory policy and request constraints.

<a id="section-11-128"></a>
## 11.128 Mandatory Pin

A Mandatory Pin prohibits substitution.

If the pinned resource is unavailable or ineligible, the result is:

- wait,

- fail,

- request amendment,

- or reapproval.

No silent fallback is permitted.

<a id="section-11-129"></a>
## 11.129 Preferred Pin

A Preferred Pin influences ranking but permits substitution under defined conditions.

<a id="section-11-130"></a>
## 11.130 Pin Reason

Every material Pin should preserve a reason such as:

- reproducibility,

- unique Capability,

- contractual requirement,

- existing Provider Asset,

- user choice,

- benchmark,

- or migration constraint.

<a id="section-11-131"></a>
## 11.131 Pin Scope

A Pin shall define whether it applies to:

- one request,

- one Step,

- one Workflow,

- one Production,

- one Project,

- or one time period.

<a id="section-11-132"></a>
## 11.132 Pin Validity

Pins may expire after:

- Model update,

- benchmark review,

- Project milestone,

- Provider migration,

- or defined date.

<a id="section-11-133"></a>
## 11.133 Pinned Moving Alias

Pinning to a moving Provider alias shall preserve:

- drift risk,

- observed target,

- and reproducibility uncertainty.

<a id="section-11-134"></a>
## 11.134 Pinned Provider Account

A Pin may require one Account because of:

- credits,

- Assets,

- terms,

- or Project ownership.

The Account must still have valid budget and credentials.

<a id="section-11-135"></a>
## 11.135 Pinned Local Node

A request may require execution on one local Node.

Node availability and capacity must be validated.

<a id="section-11-136"></a>
## 11.136 Pinned Failure

When a mandatory Pin fails, the Router shall explain:

- unavailability,

- policy conflict,

- cost conflict,

- or Capability mismatch.

<a id="section-11-137"></a>
## 11.137 Pinned Fallback

Fallback exists only when the Pin explicitly permits it.

<a id="section-11-138"></a>
## 11.138 Profile Priority

Routing Profiles guide optimisation.

They do not outrank:

- security,

- privacy requirements,

- rights,

- authority,

- Quality Floor,

- deadline,

- or budget maximum.

<a id="section-11-139"></a>
## 11.139 Profile Conflict

A profile may conflict with request constraints.

Examples include:

- Economy with mandatory premium-only Feature,

- Private with external-only Capability,

- Pinned with denied Provider,

- Premium with insufficient budget.

The Router shall surface the conflict.

<a id="section-11-140"></a>
## 11.140 Profile Degradation

The Router shall not silently reinterpret one profile as another.

A proposed profile change requires:

- disclosure,

- approval where material,

- and new Selection Decision.

<a id="section-11-141"></a>
## 11.141 Resource-Origin Classes

Omnira shall recognise several resource-origin classes:

- local user-controlled,

- user-owned external,

- Project-owned external,

- Tenant-owned external,

- Omnira-managed,

- shared managed,

- human-assisted,

- and public or free service.

<a id="section-11-142"></a>
## 11.142 Local User-Controlled Resource

A Local User-Controlled Resource runs on infrastructure controlled by the user.

It may receive preference for:

- privacy,

- ownership,

- offline use,

- and low marginal charge.

<a id="section-11-143"></a>
## 11.143 User-Owned External Resource

A User-Owned External Resource uses the user’s Provider Account or subscription.

Use shall preserve:

- explicit permission,

- Project scope,

- and cost attribution.

<a id="section-11-144"></a>
## 11.144 Project-Owned External Resource

A Project-Owned Resource should be preferred when:

- the work belongs to that Project,

- the Account terms are suitable,

- and sufficient capacity exists.

<a id="section-11-145"></a>
## 11.145 Tenant-Owned External Resource

A Tenant-owned Account may serve several Projects.

Routing shall preserve Project attribution and policy.

<a id="section-11-146"></a>
## 11.146 Omnira-Managed Resource

An Omnira-managed resource may be selected when:

- the user has allocated managed credits,

- the Provider is eligible,

- and the Project or Tenant permits it.

<a id="section-11-147"></a>
## 11.147 Shared Managed Resource

Shared resources require strong:

- Tenant isolation,

- Project attribution,

- quotas,

- and privacy controls.

<a id="section-11-148"></a>
## 11.148 Human-Assisted Resource

A human-assisted path may be selected when:

- no automation exists,

- quality is superior,

- Provider access is manual,

- or the user requires direct creative control.

Human effort and delay shall be included in scoring.

<a id="section-11-149"></a>
## 11.149 Free Public Resource

Free or unauthenticated resources may be considered only when:

- terms are acceptable,

- data is eligible,

- rights are adequate,

- reliability is sufficient,

- and evidence can be preserved.

<a id="section-11-150"></a>
## 11.150 Resource-Origin Preference

Project or user policy may define an order such as:

1. Local eligible capacity.

2. Included Project capacity.

3. User-owned Account.

4. Omnira-managed credits.

5. Paid external on-demand.

6. Human-assisted alternative.

This order is a preference, not a universal law.

<a id="section-11-151"></a>
## 11.151 Cost Ownership

Routing shall identify who bears the cost:

- user,

- Project,

- Tenant,

- Omnira,

- customer,

- or included subscription.

A cheaper resource for Omnira may be more expensive for the user.

The cost owner must remain explicit.

<a id="section-11-152"></a>
## 11.152 User-Owned Credit Protection

The Router shall not use user-owned credits as silent fallback when another Account is exhausted.

<a id="section-11-153"></a>
## 11.153 Project Budget Preference

A Project-owned budget should normally fund Project work.

Cross-Project budget use requires explicit authority.

<a id="section-11-154"></a>
## 11.154 Managed Credit Preference

Managed credits may be preferred when:

- they reduce user friction,

- remain transparent,

- and do not create hidden Provider bias.

<a id="section-11-155"></a>
## 11.155 Included Capacity Preference

Subscription-included capacity may be used before metered charges when it remains the best eligible path.

<a id="section-11-156"></a>
## 11.156 Credit Expiry Preference

Credits nearing expiry may influence ranking only when:

- quality remains acceptable,

- use is authorised,

- and selection still serves user value.

Avoiding credit waste shall not override Project needs.

<a id="section-11-157"></a>
## 11.157 Local Capacity Cost

Local capacity may have:

- no direct Provider charge,

- but real compute, energy and opportunity cost.

The scoring model may use an internal estimate.

<a id="section-11-158"></a>
## 11.158 Total Expected Cost

Total Expected Cost should include:

- initial execution,

- likely retries,

- required evaluation,

- post-processing,

- human correction,

- transfer,

- storage,

- and likely fallback.

<a id="section-11-159"></a>
## 11.159 Cost Confidence

Cost estimates shall include confidence or uncertainty.

Opaque Provider pricing reduces routing certainty.

<a id="section-11-160"></a>
## 11.160 Cost Normalisation

Different Provider billing units shall be normalised into comparable expected cost.

The original units shall remain preserved.

<a id="section-11-161"></a>
## 11.161 Currency Normalisation

Where currencies differ, the Router may use a current exchange rate or budget conversion.

The conversion source and time shall be preserved.

<a id="section-11-162"></a>
## 11.162 Quality Evidence

Quality scoring shall rely on Capability-specific evidence.

Evidence may include:

- internal benchmark,

- external benchmark,

- Project acceptance rate,

- human review,

- retry rate,

- and recent operational outcomes.

<a id="section-11-163"></a>
## 11.163 Quality Confidence

Quality evidence shall include:

- scope,

- freshness,

- sample size,

- and confidence.

Sparse evidence shall not be represented as certainty.

<a id="section-11-164"></a>
## 11.164 Quality Floor

The Quality Floor is mandatory.

A candidate below the floor is ineligible.

<a id="section-11-165"></a>
## 11.165 Quality Target

The Quality Target influences ranking above the floor.

Premium routing may weight it strongly.

<a id="section-11-166"></a>
## 11.166 Expected Acceptance Probability

The Router may estimate the probability that a candidate will pass required evaluation.

This estimate should be evidence-based.

<a id="section-11-167"></a>
## 11.167 Correction Cost

A candidate with low initial price but frequent manual correction may have high total cost.

<a id="section-11-168"></a>
## 11.168 Project-Specific Quality

Project evidence may outweigh generic benchmarks when:

- the evidence is sufficient,

- current,

- and relevant.

Nova and Pling consistency tests are more relevant to Familje-Stunden video routing than generic cinematic benchmark scores.

<a id="section-11-169"></a>
## 11.169 User Preference Evidence

A user may prefer a Provider’s output style.

Preference may influence ranking after mandatory quality.

<a id="section-11-170"></a>
## 11.170 Reliability Evidence

Reliability may include:

- success rate,

- Provider uptime,

- callback reliability,

- unknown-outcome rate,

- retry rate,

- and Account stability.

<a id="section-11-171"></a>
## 11.171 Reliability Floor

High-consequence work may require a minimum reliability level.

<a id="section-11-172"></a>
## 11.172 Provider Reliability

Provider-level reliability and Model-level quality shall remain distinct.

<a id="section-11-173"></a>
## 11.173 Account Reliability

One Provider Account may have:

- exhausted quota,

- authentication issues,

- or lower tier

while another Account remains healthy.

<a id="section-11-174"></a>
## 11.174 Connection Reliability

A Provider may be healthy while one MCP or API Connection is degraded.

<a id="section-11-175"></a>
## 11.175 Deployment Reliability

A Model Deployment may be unavailable while another Deployment remains eligible.

<a id="section-11-176"></a>
## 11.176 Local Reliability

Local reliability may depend on:

- Node power,

- hardware health,

- storage,

- Runtime,

- and network.

<a id="section-11-177"></a>
## 11.177 Human-Assisted Reliability

Human-assisted execution may have strong quality but uncertain availability and latency.

<a id="section-11-178"></a>
## 11.178 Latency Evidence

Latency shall consider:

- queue,

- first response,

- total execution,

- upload,

- download,

- evaluation,

- and human handoff.

<a id="section-11-179"></a>
## 11.179 Latency Floor

Interactive and real-time Capabilities may require a maximum latency.

<a id="section-11-180"></a>
## 11.180 Deadline Risk

The Router may score the probability of meeting the deadline.

A high-quality candidate with high queue risk may be unsuitable.

<a id="section-11-181"></a>
## 11.181 Queue-Aware Routing

Current Provider queue state may influence selection.

Queue evidence shall declare freshness.

<a id="section-11-182"></a>
## 11.182 Warm-Resource Preference

A loaded local Model or warm Deployment may outperform a theoretically faster cold resource.

<a id="section-11-183"></a>
## 11.183 Capacity-Aware Routing

The Router shall consider:

- concurrency,

- quota,

- rate limits,

- GPU capacity,

- and reserved workload.

<a id="section-11-184"></a>
## 11.184 Load Balancing

Several equivalent resources may be balanced to improve:

- throughput,

- resilience,

- and quota utilisation.

Load balancing shall preserve cost and Project policy.

<a id="section-11-185"></a>
## 11.185 Sticky Routing

Some workflows may prefer the same resource across related Steps for:

- style consistency,

- context continuity,

- or Provider Asset reuse.

Sticky routing shall be explicit.

<a id="section-11-186"></a>
## 11.186 Non-Sticky Routing

Related Steps may use different resources when:

- Capabilities differ,

- cost improves,

- privacy differs,

- or quality evidence supports specialisation.

<a id="section-11-187"></a>
## 11.187 Session Affinity

Provider threads or real-time sessions may require affinity to one Deployment or Account.

Affinity shall not become permanent Agent identity.

<a id="section-11-188"></a>
## 11.188 Asset Affinity

A Provider-side character, voice or Project Asset may require routing to the Provider or Account holding it.

The lock-in implication shall remain visible.

<a id="section-11-189"></a>
## 11.189 Context Affinity

A persistent Provider context may reduce cost or improve continuity.

It shall not override Project isolation or memory governance.

<a id="section-11-190"></a>
## 11.190 Privacy Score

Eligible candidates may receive a privacy score based on:

- custody,

- region,

- retention,

- training use,

- contractual controls,

- and user control.

<a id="section-11-191"></a>
## 11.191 Privacy Score Limitation

Privacy scoring occurs only after mandatory privacy requirements.

A high privacy score cannot make an otherwise prohibited candidate eligible.

<a id="section-11-192"></a>
## 11.192 Rights Score

Candidates may differ in:

- commercial clarity,

- attribution burden,

- watermarking,

- and output ownership.

Rights may influence ranking after mandatory eligibility.

<a id="section-11-193"></a>
## 11.193 Operational Maturity Score

Production API or local production resources may outrank experimental integrations.

Maturity may include:

- conformance,

- monitoring,

- support,

- and recovery.

<a id="section-11-194"></a>
## 11.194 Automation Maturity Score

Fully governed automation may reduce human effort.

Human-assisted routes may still win when quality or unique Capability justifies them.

<a id="section-11-195"></a>
## 11.195 Portability Score

Candidates may be compared by:

- output export,

- open format,

- Asset portability,

- and lock-in.

Portability may influence long-term routing.

<a id="section-11-196"></a>
## 11.196 Strategic Dependency Score

A Candidate creating severe single-source dependency may receive a penalty where alternatives exist.

<a id="section-11-197"></a>
## 11.197 Energy and Resource Score

Local and managed compute may consider:

- energy,

- device battery,

- heat,

- and resource contention.

This may be important for mobile or edge routing.

<a id="section-11-198"></a>
## 11.198 Routing Score

The Routing Score is a calculated value used to rank eligible candidates.

It may combine:

- quality,

- cost,

- reliability,

- latency,

- privacy,

- rights,

- maturity,

- portability,

- and preference.

The score shall not include ineligible candidates.

<a id="section-11-199"></a>
## 11.199 Score Component

Every material score component should have:

- value,

- weight,

- evidence,

- confidence,

- and version.

<a id="section-11-200"></a>
## 11.200 Score Normalisation

Different dimensions shall be normalised consistently.

Normalisation logic shall be versioned.

<a id="section-11-201"></a>
## 11.201 Profile Weights

Each Routing Profile shall define how dimensions are weighted.

Weights may be adjusted by:

- Capability,

- Project,

- consequence,

- and deadline

within governed limits.

<a id="section-11-202"></a>
## 11.202 Hard Constraint Exclusion

A candidate excluded by hard constraint shall not receive an overall score.

<a id="section-11-203"></a>
## 11.203 Score Explainability

The decision should explain the dominant reasons for selection.

Example:

Selected Candidate B because it met the mandatory multi-character Feature, had the strongest recent Familje-Stunden consistency score, remained within budget and had acceptable queue time.

<a id="section-11-204"></a>
## 11.204 Score Uncertainty

When evidence is weak, the Router should expose uncertainty.

It may choose:

- safer known candidate,

- bounded experiment,

- human review,

- or no route.

<a id="section-11-205"></a>
## 11.205 Deterministic Tie-Breaking

When candidates have equivalent scores, tie-breaking should be deterministic where practical.

Possible order:

1. Stronger privacy.

2. Lower expected total cost.

3. Higher reliability.

4. Lower latency.

5. Existing Project Account.

6. Greater portability.

7. Stable canonical identifier.

<a id="section-11-206"></a>
## 11.206 Randomised Tie-Breaking

Randomised selection may be used for:

- experiments,

- load distribution,

- or evidence gathering

only when explicitly governed.

<a id="section-11-207"></a>
## 11.207 Exploration

Exploration selects a less-proven eligible Candidate to gather evidence.

It shall use:

- low-risk tasks,

- bounded budget,

- explicit experiment policy,

- and mandatory evaluation.

<a id="section-11-208"></a>
## 11.208 Exploitation

Exploitation selects the strongest currently evidenced Candidate.

Ordinary production should usually favour exploitation.

<a id="section-11-209"></a>
## 11.209 Exploration Budget

Exploration shall consume a separately bounded budget or experiment allowance.

<a id="section-11-210"></a>
## 11.210 Production Exploration

High-consequence production should not be used as uncontrolled experimentation.

<a id="section-11-211"></a>
## 11.211 A/B Routing

A/B Routing may compare Candidates across equivalent tasks.

It shall define:

- population,

- metrics,

- duration,

- budget,

- and user-impact controls.

<a id="section-11-212"></a>
## 11.212 Shadow Routing

Shadow Routing evaluates a Candidate without using its Output for the production result.

It may estimate:

- quality,

- latency,

- or compatibility.

Shadow execution still consumes resources and data.

It requires authority.

<a id="section-11-213"></a>
## 11.213 Offline Evaluation

Offline evaluation may compare historical Outputs without new Provider execution.

<a id="section-11-214"></a>
## 11.214 Routing Experiment

Every Routing Experiment shall have:

- experimentId,

- hypothesis,

- scope,

- candidates,

- metrics,

- data policy,

- budget,

- start,

- end,

- and approval.

<a id="section-11-215"></a>
## 11.215 Learned Routing

Learned Routing uses governed historical evidence to adjust candidate ranking.

It may improve:

- cost,

- quality,

- reliability,

- and Project fit.

<a id="section-11-216"></a>
## 11.216 Learned Routing Boundary

Learned Routing shall not change:

- mandatory policy,

- authority,

- Data Classification,

- rights,

- budget maximum,

- or Quality Floor.

<a id="section-11-217"></a>
## 11.217 Routing Learning Candidate

A Learning Candidate may state:

Provider Resource A performs better for Capability X under Project Y conditions.

It shall include:

- evidence,

- scope,

- confidence,

- validity,

- and review status.

<a id="section-11-218"></a>
## 11.218 Learning Admission

Routing learning shall enter production only after governed admission.

Raw outcome correlation shall not automatically rewrite routing policy.

<a id="section-11-219"></a>
## 11.219 Learning Scope

Learning may be:

- global,

- Tenant,

- Project,

- Capability,

- Provider Account,

- Model Version,

- or Workflow-specific.

<a id="section-11-220"></a>
## 11.220 Learning Expiry

Routing learning shall expire or be reviewed after:

- Model change,

- Adapter change,

- Provider update,

- terms change,

- Project style change,

- or defined time.

<a id="section-11-221"></a>
## 11.221 Negative Learning

The Fabric may learn that a Candidate performs poorly under defined conditions.

Negative learning shall not become an unjustified global ban.

<a id="section-11-222"></a>
## 11.222 Confidence Decay

Confidence may decay as evidence becomes stale.

<a id="section-11-223"></a>
## 11.223 Model Drift

Model drift may invalidate routing evidence.

The Router shall reduce confidence or trigger revalidation.

<a id="section-11-224"></a>
## 11.224 Provider Drift

Provider changes in:

- queue,

- pricing,

- terms,

- or routing

may change suitability.

<a id="section-11-225"></a>
## 11.225 Project Drift

Project requirements may evolve.

Old routing preferences may no longer match current quality standards.

<a id="section-11-226"></a>
## 11.226 Feedback Signal

Routing feedback may include:

- accepted Output,

- rejected Output,

- retry,

- user override,

- cost variance,

- latency,

- Incident,

- and publication outcome.

<a id="section-11-227"></a>
## 11.227 Explicit User Feedback

Explicit feedback should normally receive greater weight than inferred satisfaction.

It shall remain scoped.

<a id="section-11-228"></a>
## 11.228 Implicit Feedback

Implicit signals such as reuse or acceptance may help.

They shall not be overinterpreted.

<a id="section-11-229"></a>
## 11.229 Human Reviewer Feedback

Reviewer decisions may improve routing evidence.

Reviewer identity and criteria shall be preserved.

<a id="section-11-230"></a>
## 11.230 Business Outcome Feedback

Long-term outcomes such as engagement or conversion may inform routing only when causation is treated carefully.

<a id="section-11-231"></a>
## 11.231 Cost Feedback

Estimated versus actual cost shall calibrate future decisions.

<a id="section-11-232"></a>
## 11.232 Latency Feedback

Actual queue and completion time shall update routing evidence.

<a id="section-11-233"></a>
## 11.233 Reliability Feedback

Timeouts, unknown outcomes and Provider errors shall update reliability.

<a id="section-11-234"></a>
## 11.234 Routing Override

An authorised user may override the selected Candidate.

The override shall remain subject to mandatory eligibility.

<a id="section-11-235"></a>
## 11.235 Override Reason

Material overrides should preserve a reason such as:

- creative preference,

- known Provider strength,

- contractual obligation,

- or experiment.

<a id="section-11-236"></a>
## 11.236 Unsafe Override

The system shall reject an override that violates mandatory policy.

<a id="section-11-237"></a>
## 11.237 Override Learning

An override shall not automatically become a permanent preference.

Repeated accepted overrides may create a Learning Candidate.

<a id="section-11-238"></a>
## 11.238 User Preference

A user may express preferences for:

- local,

- Provider,

- Model,

- price,

- quality,

- privacy,

- or speed.

Preferences shall remain distinguishable from pins and policies.

<a id="section-11-239"></a>
## 11.239 Project Preference

A Project may define preferred:

- Providers,

- Models,

- Accounts,

- regions,

- and routing profiles.

<a id="section-11-240"></a>
## 11.240 Tenant Preference

Tenant preferences may optimise shared capacity and Provider relationships.

<a id="section-11-241"></a>
## 11.241 Preference Conflict

When preferences conflict, the Router should apply:

1. mandatory policy,

2. request-explicit preference,

3. Production Envelope,

4. Project preference,

5. Tenant preference,

6. user global preference,

7. platform default.

The effective source shall be recorded.

<a id="section-11-242"></a>
## 11.242 Provider Bias Control

The Router shall not favour a Provider because:

- it was integrated first,

- its Adapter is easier,

- it has stronger marketing,

- or Omnira receives commercial benefit.

<a id="section-11-243"></a>
## 11.243 Commercial Conflict of Interest

A commercial relationship may include:

- commission,

- margin,

- affiliate payment,

- bundled credits,

- or strategic partnership.

The relationship shall be visible to governance.

<a id="section-11-244"></a>
## 11.244 Conflict Disclosure

Where a commercial relationship materially influences recommendation, it shall be disclosed.

<a id="section-11-245"></a>
## 11.245 User-Value Priority

Routing shall optimise user and Project value within policy.

Provider or Omnira financial benefit is subordinate.

<a id="section-11-246"></a>
## 11.246 Managed-Margin Routing

Future Omnira-managed credits may include margin.

Margin shall not permit lower-quality or more expensive routing when a better eligible path exists under the user’s chosen profile.

<a id="section-11-247"></a>
## 11.247 Neutral Candidate Evaluation

Candidates should be evaluated through consistent canonical dimensions.

<a id="section-11-248"></a>
## 11.248 Provider-Specific Exception

A Provider-specific routing exception requires:

- explicit reason,

- scope,

- validity,

- and review.

<a id="section-11-249"></a>
## 11.249 Routing Policy

Routing Policy defines mandatory and optimisation rules.

It may exist at:

- platform,

- Tenant,

- Project,

- Capability,

- Provider,

- Workflow,

- Production,

- and request level.

<a id="section-11-250"></a>
## 11.250 Policy Composition

Effective Routing Policy is the composition of all applicable rules.

The most restrictive mandatory rule shall prevail.

<a id="section-11-251"></a>
## 11.251 Policy Conflict

Conflicting mandatory rules shall produce:

- no route,

- clarification,

- or governance escalation.

The Router shall not choose one silently.

<a id="section-11-252"></a>
## 11.252 Policy Rule

A Routing Policy Rule may include:

- ruleId,

- scope,

- condition,

- effect,

- priority,

- version,

- owner,

- effective period,

- and provenance.

<a id="section-11-253"></a>
## 11.253 Allow Rule

An Allow Rule permits a Candidate class when all other requirements are satisfied.

Allow does not override higher restrictions.

<a id="section-11-254"></a>
## 11.254 Deny Rule

A Deny Rule excludes a Candidate.

Deny rules shall propagate through fallback.

<a id="section-11-255"></a>
## 11.255 Require Rule

A Require Rule mandates:

- Provider class,

- region,

- privacy level,

- review,

- or another property.

<a id="section-11-256"></a>
## 11.256 Prefer Rule

A Prefer Rule influences ranking.

<a id="section-11-257"></a>
## 11.257 Penalise Rule

A Penalise Rule lowers ranking without creating ineligibility.

<a id="section-11-258"></a>
## 11.258 Approval Rule

An Approval Rule marks a Candidate or profile transition as requiring approval.

<a id="section-11-259"></a>
## 11.259 Budget Rule

A Budget Rule may limit:

- cost,

- profile,

- Provider,

- Model tier,

- or retry.

<a id="section-11-260"></a>
## 11.260 Time Rule

A Time Rule may apply during:

- business hours,

- maintenance,

- campaign period,

- or scheduled window.

<a id="section-11-261"></a>
## 11.261 Environment Rule

An Environment Rule may prohibit production resources in development.

<a id="section-11-262"></a>
## 11.262 Data-Class Rule

A Data-Class Rule maps classifications to permitted placement and Provider types.

<a id="section-11-263"></a>
## 11.263 Capability Rule

A Capability Rule may require:

- evaluation,

- minimum Model class,

- or specific Provider maturity.

<a id="section-11-264"></a>
## 11.264 Child-Facing Rule

Child-facing media may require:

- approved Provider set,

- stronger visual evaluation,

- and human review.

<a id="section-11-265"></a>
## 11.265 Code Rule

Code execution may require:

- private Provider,

- no repository mutation,

- or separate credentials.

<a id="section-11-266"></a>
## 11.266 Publication Rule

Publication routing requires:

- approved target Account,

- publication Connection,

- idempotency,

- and verification.

<a id="section-11-267"></a>
## 11.267 Voice Rule

Voice routing may require:

- approved Voice Asset,

- consent,

- and cloning restriction.

<a id="section-11-268"></a>
## 11.268 Local-Only Rule

Local Only data shall route only to approved local or private resources.

<a id="section-11-269"></a>
## 11.269 Policy Version

Every Selection Decision shall reference relevant policy versions.

<a id="section-11-270"></a>
## 11.270 Policy Effective Time

Rules may have:

- future start,

- expiry,

- or temporary Incident window.

<a id="section-11-271"></a>
## 11.271 Emergency Routing Policy

During Incident response, emergency policy may:

- disable Provider,

- force local,

- prohibit publication,

- or require human approval.

Emergency rules shall be attributable and reviewed.

<a id="section-11-272"></a>
## 11.272 Routing Lifecycle

Routing lifecycle states may include:

- requested,

- evaluating,

- awaiting data,

- awaiting approval,

- candidate set ready,

- selected,

- revalidating,

- invalidated,

- superseded,

- failed,

- and archived.

<a id="section-11-273"></a>
## 11.273 Requested State

A Routing Request has been created.

<a id="section-11-274"></a>
## 11.274 Evaluating State

Candidates and policies are being evaluated.

<a id="section-11-275"></a>
## 11.275 Awaiting Data State

Fresh operational or governance data is missing.

<a id="section-11-276"></a>
## 11.276 Awaiting Approval State

One or more Candidates require approval.

<a id="section-11-277"></a>
## 11.277 Candidate-Set-Ready State

Eligible candidates have been resolved and may be scored.

<a id="section-11-278"></a>
## 11.278 Selected State

A Selection Decision exists.

<a id="section-11-279"></a>
## 11.279 Revalidating State

The selected Candidate is being checked before execution.

<a id="section-11-280"></a>
## 11.280 Invalidated State

The decision can no longer be used.

<a id="section-11-281"></a>
## 11.281 Superseded State

A newer Selection Decision applies.

<a id="section-11-282"></a>
## 11.282 Failed State

No valid decision could be produced.

<a id="section-11-283"></a>
## 11.283 Archived State

The routing record is retained for history.

<a id="section-11-284"></a>
## 11.284 Pre-Execution Revalidation

Before Provider execution, the system shall revalidate:

- selected resource lifecycle,

- Account,

- Connection,

- Credential,

- health,

- quota,

- budget,

- authority,

- and policy.

<a id="section-11-285"></a>
## 11.285 Lightweight Revalidation

For low-risk immediate execution, revalidation may use cached state within a defined freshness window.

<a id="section-11-286"></a>
## 11.286 Full Revalidation

High-risk or delayed execution may require full current-state evaluation.

<a id="section-11-287"></a>
## 11.287 Selection Invalidation

A decision may invalidate when:

- Candidate disabled,

- Credential revoked,

- Account exhausted,

- price exceeds budget,

- policy changes,

- or deadline becomes infeasible.

<a id="section-11-288"></a>
## 11.288 Rerouting

Rerouting creates a new Selection Decision for the same Step.

It shall preserve:

- previous decision,

- invalidation reason,

- and cost impact.

<a id="section-11-289"></a>
## 11.289 Rerouting Without Replanning

Equivalent resource substitution inside the approved Plan may occur without replanning when all material boundaries remain unchanged.

<a id="section-11-290"></a>
## 11.290 Rerouting With Replanning

A different Capability path, privacy class, quality contract or side effect requires replanning.

<a id="section-11-291"></a>
## 11.291 Retry Routing

A retry may route to:

- the same Candidate,

- another Deployment,

- another Model,

- another Provider,

- or human-assisted path.

The Retry Policy determines permitted options.

<a id="section-11-292"></a>
## 11.292 Same-Candidate Retry

Same-Candidate retry may be suitable for:

- transient failure,

- stochastic variation,

- or rate limit after delay.

<a id="section-11-293"></a>
## 11.293 Same-Provider Fallback

The Router may change:

- Model,

- Deployment,

- Account,

- region,

- or Product

inside one Provider.

<a id="section-11-294"></a>
## 11.294 Cross-Provider Fallback

Cross-Provider fallback changes:

- terms,

- processing location,

- Account,

- pricing,

- and operational evidence.

It requires full eligibility evaluation.

<a id="section-11-295"></a>
## 11.295 Local Fallback

External failure may route locally only when local quality and policy are sufficient.

<a id="section-11-296"></a>
## 11.296 External Fallback

Local failure may route externally only when classification and authority permit it.

<a id="section-11-297"></a>
## 11.297 Human-Assisted Fallback

Automation failure may route to a human-assisted path within budget and deadline.

<a id="section-11-298"></a>
## 11.298 No-Fallback Condition

Fallback may be prohibited by:

- mandatory Pin,

- Local Only policy,

- rights,

- user instruction,

- or unique Capability.

<a id="section-11-299"></a>
## 11.299 Fallback Chain

A Fallback Chain defines ordered eligible alternatives.

It shall include:

- trigger,

- maximum depth,

- approval conditions,

- and quality implications.

<a id="section-11-300"></a>
## 11.300 Fallback Depth

Fallback depth shall be bounded.

The system shall not cycle through unlimited resources.

<a id="section-11-301"></a>
## 11.301 Fallback Cost

Fallback cost counts against the approved budget.

<a id="section-11-302"></a>
## 11.302 Fallback Disclosure

Material fallback shall be disclosed when it affects:

- Provider,

- privacy,

- quality,

- cost,

- or user expectation.

<a id="section-11-303"></a>
## 11.303 Hedged Routing

Hedged Routing may launch a second Candidate after a delay to reduce tail latency.

It requires:

- budget,

- idempotency,

- cancellation,

- and duplicate handling.

<a id="section-11-304"></a>
## 11.304 Speculative Routing

Speculative Routing launches several Candidates before one is known to be necessary.

It shall not be used by default.

<a id="section-11-305"></a>
## 11.305 Candidate Race

A Candidate Race may be permitted for:

- premium creative selection,

- high-value reasoning,

- or latency-critical work.

It requires explicit limits.

<a id="section-11-306"></a>
## 11.306 Multi-Resource Voting

Several Models may produce or evaluate responses.

Voting shall be represented as a composite Plan, not hidden Router behaviour when it materially changes cost or evidence.

<a id="section-11-307"></a>
## 11.307 Router-Managed Micro-Fallback

The Router or Adapter may perform bounded micro-fallback only when:

- alternatives are semantically equivalent,

- cost remains inside the Step budget,

- policy permits,

- and evidence preserves the substitution.

Material Provider changes should remain visible.

<a id="section-11-308"></a>
## 11.308 Provider Router

A Provider-managed router may choose an underlying Model.

The Fabric shall represent:

- routing opacity,

- declared candidates,

- quality evidence,

- and reproducibility limits.

<a id="section-11-309"></a>
## 11.309 Omnira Meta-Router

The Omnira Router may choose between Provider routers and fixed resources.

It shall not claim control over the Provider’s hidden internal choice.

<a id="section-11-310"></a>
## 11.310 Routing Explainability

Every meaningful Selection Decision should be explainable.

The explanation should answer:

- Which resource was selected?

- Why was it eligible?

- Which candidates were excluded?

- Which Routing Profile applied?

- What is the expected cost?

- What quality evidence mattered?

- What privacy and rights conditions apply?

- Which fallback is permitted?

<a id="section-11-311"></a>
## 11.311 Human-Readable Explanation

User-facing explanation should be concise and consequence-focused.

Example:

Balanced routing selected the Project-owned voice Provider because it supports approved Swedish narration, uses included credits, has stronger recent pronunciation scores and remains within the approved budget.

<a id="section-11-312"></a>
## 11.312 Machine-Readable Explanation

The canonical decision shall expose structured:

- rules,

- exclusions,

- scores,

- evidence,

- and versions.

<a id="section-11-313"></a>
## 11.313 Exclusion Explanation

Material candidate exclusions should identify the exact reason.

Examples include:

- Local Only conflict,

- commercial rights unknown,

- insufficient quality evidence,

- expired Credential,

- or cost above limit.

<a id="section-11-314"></a>
## 11.314 Profile Explanation

The system should explain what the selected profile optimised.

Economy:

Lowest expected total eligible cost.

Balanced:

Best overall expected value.

Premium:

Strongest expected quality within budget.

Private:

Strongest eligible privacy and placement.

Pinned:

Specified resource subject to mandatory policy.

<a id="section-11-315"></a>
## 11.315 Uncertainty Explanation

When routing evidence is weak, the decision should state uncertainty.

<a id="section-11-316"></a>
## 11.316 Approval Explanation

When approval is required, the system should explain:

- what changes,

- why it matters,

- and the maximum consequence.

<a id="section-11-317"></a>
## 11.317 Routing Receipt

A Routing Receipt may provide a durable summary containing:

- request,

- Plan Step,

- profile,

- candidates,

- exclusions,

- selected Candidate,

- expected cost,

- fallback,

- and decision provenance.

<a id="section-11-318"></a>
## 11.318 Routing Provenance

Routing provenance should include:

- Router version,

- profile version,

- policy versions,

- Registry snapshots,

- pricing sources,

- health observations,

- quality evidence,

- and learning references.

<a id="section-11-319"></a>
## 11.319 Router Version

The Selection Decision shall identify the Router implementation version.

<a id="section-11-320"></a>
## 11.320 Scoring Version

Material changes to score calculation require a new scoring version.

<a id="section-11-321"></a>
## 11.321 Policy Snapshot

The decision should preserve the policy state used.

<a id="section-11-322"></a>
## 11.322 Registry Snapshot

The decision should preserve the relevant Registry versions or identifiers.

<a id="section-11-323"></a>
## 11.323 Health Snapshot

Current health observations used in selection should be referenced.

<a id="section-11-324"></a>
## 11.324 Pricing Snapshot

Expected cost should reference pricing evidence.

<a id="section-11-325"></a>
## 11.325 Quality Snapshot

Quality scoring should reference benchmark and operational evidence.

<a id="section-11-326"></a>
## 11.326 Routing Audit

Routing audit should allow reconstruction of:

- candidates,

- rules,

- scores,

- decision,

- and later substitution.

<a id="section-11-327"></a>
## 11.327 Routing Privacy

Routing evidence may contain sensitive:

- Account,

- Project,

- Provider,

- and cost information.

Access shall be scoped.

<a id="section-11-328"></a>
## 11.328 Redacted Routing View

A redacted view may hide:

- exact Account,

- confidential Inputs,

- or internal scoring detail.

- profile usage,

<a id="section-11-339"></a>

- accepted quality,

- total cost,

- latency,

- and human effort.

<a id="section-11-340"></a>
## 11.340 Profile Effectiveness

<a id="section-11-341"></a>
## 11.341 Routing Incident

A Routing Incident may involve:

- ineligible Provider selection,

- wrong Project Account,

- privacy violation,

- cost overrun,

- hidden fallback,

- wrong Model,

- or commercial bias.

<a id="section-11-342"></a>
## 11.342 Selection Incident

A Selection Incident occurs when the decision itself was invalid.

<a id="section-11-343"></a>
## 11.343 Execution Incident

An execution may fail despite a valid selection.

<a id="section-11-344"></a>
## 11.344 Wrong-Account Incident

Using the wrong Provider Account is a routing or execution-control Incident even if the output quality is correct.

<a id="section-11-345"></a>
## 11.345 Wrong-Project Incident

Using another Project’s Account, Asset or local resource is a severe isolation defect.

<a id="section-11-346"></a>
## 11.346 Privacy Routing Incident

Protected data sent to an ineligible Provider is a privacy Incident.

<a id="section-11-347"></a>
## 11.347 Rights Routing Incident

Selecting a Provider with incompatible commercial terms is a rights Incident.

<a id="section-11-348"></a>
## 11.348 Budget Routing Incident

Selecting a Candidate whose expected cost exceeds approved limits is a budget Incident.

<a id="section-11-349"></a>
## 11.349 Hidden-Fallback Incident

Substituting a materially different Provider or privacy class without evidence is an Incident.

<a id="section-11-350"></a>
## 11.350 Routing Incident Containment

- disable Candidate,

- block Provider,

- freeze profile,

- require manual routing,

- revoke Connection,

- or pause affected Plans.

<a id="section-11-351"></a>
## 11.351 Routing Incident Recovery

Recovery should include:

- corrected policy,

- evidence review,

- affected Executions,

- cost and privacy impact,

- tests,

- and controlled reactivation.

<a id="section-11-352"></a>
## 11.352 Routing Policy Rollback

A faulty policy or scoring update may require rollback.

Historical Selection Decisions shall remain linked to the faulty version.

<a id="section-11-353"></a>
## 11.353 Routing Canary

New routing logic may be tested on:

- low-risk requests,

- limited Projects,

- or shadow evaluation.

Canary use shall be bounded.

<a id="section-11-354"></a>
## 11.354 Routing Feature Flag

Routing features may be enabled by:

- Tenant,

- Project,

- Capability,

- or environment.

Flags shall not bypass canonical policy.

<a id="section-11-355"></a>
## 11.355 Routing Cache

- source,

- version,

- freshness,

- and invalidation.

<a id="section-11-356"></a>
## 11.356 Eligibility Cache

- policy,

- Account,

- credential,

- and resource state remain sufficiently stable.

<a id="section-11-357"></a>
## 11.357 Health Cache

<a id="section-11-358"></a>
## 11.358 Pricing Cache

<a id="section-11-359"></a>
## 11.359 Quality Cache

<a id="section-11-360"></a>
## 11.360 Routing Consistency

The system shall define consistency requirements for:

- Provider disable,

- credential revocation,

- budget exhaustion,

- and policy changes.

<a id="section-11-361"></a>
## 11.361 Routing Availability

The Router itself is a critical Fabric service.

Its failure must not cause Agents to bypass routing.

<a id="section-11-362"></a>
## 11.362 Router Failure

- use a recently valid pinned Decision,

- pause execution,

- or use a narrowly approved emergency route.

Direct Provider calls are not the safe default.

<a id="section-11-363"></a>
## 11.363 Emergency Static Route

It shall remain:

- bounded,

- versioned,

- monitored,

- and policy-compliant.

<a id="section-11-364"></a>
## 11.364 Router Recovery

Recovery shall preserve pending Routing Requests and avoid duplicate execution.

<a id="section-11-365"></a>
## 11.365 Routing Idempotency

Dynamic state may legitimately produce a new decision.

<a id="section-11-366"></a>

- requestId,

- planId,

- stepId,

- executionId where created,

- correlationId,

<a id="section-11-369"></a>

- Capability,

## 11.492 Routing Conformance Requirements

An implementation conforms to this chapter only when:

- mandatory eligibility occurs before ranking,

- profiles guide optimisation rather than authority,

- all selected external paths identify Provider Account and Connection,

- local and external resources use one decision model,

- Project and Tenant scope are enforced,

- cost and quality remain Capability-specific,

- privacy and rights fail closed,

- fallback is revalidated,

- routing decisions are versioned and explainable,

- and no commercial incentive silently controls selection.

A Provider dropdown is not a routing architecture.

A weighted score alone is not a routing architecture.

A canonical Router must enforce eligibility, policy, evidence and bounded optimisation.

<a id="section-11-501"></a>
## 11.501 Closing Statement

Routing is the decision layer through which the Intelligence Fabric turns interchangeable resource potential into a specific governed execution path.

The Capability defines what must be done.

The Plan defines where the work belongs.

The Routing Request defines the constraints.

The Candidate Set defines what may be possible.

Eligibility removes what is not permitted.

The Routing Profile defines how the remaining candidates should be optimised.

The Selection Decision defines which resource shall be used now.

The Executor performs the bounded work.

The Evaluation system determines whether the result is acceptable.

The Evidence Plane records what happened.

For Familje-Stunden, routing allows one Nova and Pling production to use:

- premium character-aware video for critical scenes,

- economical motion for backgrounds,

- approved Swedish voice,

- local media composition,

- and human child-facing review

without permanently binding the Project to one Provider.

For The Prompt, routing keeps:

- current search,

- factual verification,

- editorial reasoning,

- voice,

- avatar,

- and media production

assigned to the resources best suited to each responsibility.

For GainPilot, routing allows routine content to use economical local and external resources while preserving quality and commercial rights.

For Omnira, routing allows:

- local Models,

- user-owned subscriptions,

- Project Accounts,

- Omnira-managed credits,

- external specialists,

- private infrastructure,

- Tools,

- MCP servers,

- and human-assisted providers

to coexist under one policy-controlled decision model.

Economy shall reduce completed cost.

Balanced shall optimise total value.

Premium shall pursue justified quality.

Private shall preserve custody and placement.

Pinned shall preserve deliberate resource choice.

None shall override:

- security,

- scope,

- privacy,

- rights,

- authority,

- Quality Floor,

- deadline,

- or budget.

The Provider may change.

The Model may change.

The Account may change.

The current health may change.

The user’s approved constraints remain binding.

No routing before eligibility.

No scoring before policy.

No profile above authority.

No fallback outside scope.

No selection without explanation.

No execution without a traceable path.

The user retains preference.

The Project retains its boundaries.

Omnira retains neutrality.

The Fabric selects intelligence without surrendering governance.
