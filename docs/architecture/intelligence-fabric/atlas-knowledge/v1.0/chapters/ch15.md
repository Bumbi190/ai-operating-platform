# Chapter 15 — Latency, Capacity, Scheduling and Quotas

<a id="section-15-1"></a>
## 15.1 Chapter Status

This chapter defines the canonical architecture, governance model, lifecycle, contracts and operational responsibilities for latency, capacity, scheduling, admission control, concurrency, quotas and workload prioritisation within the Omnira Intelligence Fabric.

It establishes:

- how latency is measured across complete intelligence work rather than only Provider response time,

- how deadlines, target completion times and service objectives remain distinct,

- how interactive, real-time, batch, background, scheduled and long-running workloads are classified,

- how available, reserved, committed and effective capacity remain distinct,

- how Provider, Account, Connection, Deployment, Runtime Node, Tool, queue and human capacity are represented,

- how work is admitted, queued, prioritised, scheduled, paused, resumed and cancelled,

- how Project and Tenant fairness are preserved,

- how concurrency limits prevent overload and economic harm,

- how rate limits, quotas, credits and Budgets remain separate,

- how scarce local and external resources are reserved,

- how scheduling remains subordinate to authority, privacy, rights, quality and Budget,

- how deadline-aware and priority-aware scheduling operate without creating starvation,

- how queue backpressure and load shedding preserve critical work,

- how capacity forecasts support planning without being treated as guarantees,

- how scheduled and recurring work revalidates its conditions before execution,

- how latency and capacity evidence influence routing,

- how human-review and manual-assisted capacity are represented,

- how degraded capacity is handled truthfully,

- and how Stage 1 shall implement the smallest trustworthy scheduling and capacity foundation.

The Intelligence Fabric shall not treat every request as equally urgent.

It shall not treat every available Provider slot as authorised capacity.

It shall not treat subscription quota as Budget.

It shall not treat a queue as infinite storage.

It shall not treat a deadline as permission to bypass governance.

It shall not create high priority merely because an Agent requests it.

It shall not allow one Project, Tenant, Provider or Workflow to consume all shared capacity by convenience.

This chapter is normative after formal approval.

Implementation and operational conformance must be verified separately.

<a id="section-15-2"></a>
## 15.2 Purpose of Latency and Capacity Governance

Intelligence work consumes bounded resources.

These resources may include:

- Provider request capacity,

- Model Deployment concurrency,

- token throughput,

- image-generation slots,

- video-generation jobs,

- speech-synthesis characters,

- search queries,

- queue workers,

- local CPU,

- local GPU,

- device battery,

- memory,

- storage,

- network bandwidth,

- human review time,

- and Project operating Budget.

Demand may exceed available capacity.

Capacity may also change without warning because of:

- Provider outages,

- quota exhaustion,

- rate limits,

- Account suspension,

- local device shutdown,

- competing Projects,

- scheduled maintenance,

- cost policy,

- or degraded Model Deployment.

The scheduling architecture exists to determine:

- whether work may start,

- when it should start,

- which resource should receive it,

- how much capacity it may consume,

- how long it may wait,

- whether it should be delayed, rerouted or rejected,

- and how other work remains protected.

<a id="section-15-3"></a>
## 15.3 Scheduling Is Not Planning

Planning defines:

- required Steps,

- dependencies,

- resource requirements,

- deadlines,

- Budgets,

- and Completion Contracts.

Scheduling determines when a Ready Step may use eligible capacity.

The Scheduler shall not:

- add new Steps,

- remove mandatory Steps,

- increase Budget,

- weaken quality,

- or change Capability meaning.

Scheduling changes time and allocation.

It does not change intent.

<a id="section-15-4"></a>
## 15.4 Scheduling Is Not Routing

Routing selects an eligible Resource Candidate.

Scheduling allocates time and capacity to that Candidate or to an eligible candidate class.

Routing may select:

- one external Provider Deployment,

- one local Runtime Node,

- or one human-assisted process.

Scheduling determines when the selected path can execute.

Late scheduling may trigger rerouting when the selected resource is no longer feasible.

<a id="section-15-5"></a>
## 15.5 Scheduling Is Not Authority

A high-priority or urgent request does not create:

- Provider permission,

- spending authority,

- publication authority,

- cross-Project access,

- or privacy exception.

The Scheduler may reorder eligible work.

It shall not grant authority.

<a id="section-15-6"></a>
## 15.6 Scheduling Is Not Economic Governance

Budget determines whether economic value may be consumed.

Scheduling determines when capacity may be used.

A request may have Budget but no capacity.

A resource may have capacity but no approved Budget.

Both conditions may be required.

<a id="section-15-7"></a>
## 15.7 Scheduling Is Not Reliability

Reliability governs:

- failure,

- retry,

- fallback,

- recovery,

- and continuity.

Scheduling governs:

- admission,

- order,

- capacity allocation,

- and timing.

The two systems interact.

They shall remain conceptually distinct.

<a id="section-15-8"></a>
## 15.8 Scheduling Is Not Provider Queueing

A Provider may maintain its own internal queue.

Omnira shall still maintain its own canonical scheduling and execution state.

Provider queue position is external evidence.

It is not the complete scheduling model.

<a id="section-15-9"></a>
## 15.9 Latency

Latency is the elapsed time between defined points in a request or execution lifecycle.

Latency shall always identify:

- start event,

- end event,

- scope,

- and measurement source.

Without those properties, a latency value is ambiguous.

<a id="section-15-10"></a>
## 15.10 End-to-End Latency

End-to-End Latency measures the complete user- or system-observed time from request acceptance to defined completion.

It may include:

- validation,

- policy evaluation,

- approval,

- planning,

- routing,

- queue wait,

- Provider processing,

- retries,

- ingestion,

- evaluation,

- human review,

- and final delivery.

<a id="section-15-11"></a>
## 15.11 Execution Latency

Execution Latency measures the time spent performing a specific Execution.

It may exclude:

- planning,

- approval,

- and earlier queue delay.

<a id="section-15-12"></a>
## 15.12 Attempt Latency

Attempt Latency measures one Attempt from dispatch to terminal or unknown state.

<a id="section-15-13"></a>
## 15.13 Provider Latency

Provider Latency measures the time attributable to the external Provider operation.

It may include:

- request transport,

- Provider queue,

- processing,

- and response delivery.

<a id="section-15-14"></a>
## 15.14 Queue Latency

Queue Latency is the time between a Step becoming eligible for scheduling and the start of execution.

<a id="section-15-15"></a>
## 15.15 Planning Latency

Planning Latency is the time required to create and validate an Execution Plan.

<a id="section-15-16"></a>
## 15.16 Routing Latency

Routing Latency is the time required to create a Selection Decision.

<a id="section-15-17"></a>
## 15.17 Approval Latency

Approval Latency is the time spent awaiting valid human or policy approval.

<a id="section-15-18"></a>
## 15.18 Evaluation Latency

Evaluation Latency is the time required to produce mandatory Evaluation Results and Acceptance Decisions.

<a id="section-15-19"></a>
## 15.19 Human Latency

Human Latency is the time spent awaiting or performing a Human Action or Review Step.

<a id="section-15-20"></a>
## 15.20 Ingestion Latency

Ingestion Latency is the time required to retrieve, validate and store external Output after Provider completion.

<a id="section-15-21"></a>
## 15.21 Callback Latency

Callback Latency is the time from external state change to receipt and processing of the corresponding callback.

<a id="section-15-22"></a>
## 15.22 Publication Latency

Publication Latency is the time from authorised publication submission to verified external visibility or confirmed target state.

<a id="section-15-23"></a>
## 15.23 Time to First Result

Time to First Result measures when the first usable partial result becomes available.

<a id="section-15-24"></a>
## 15.24 Time to Final Result

Time to Final Result measures when the complete defined Completion Contract is satisfied.

<a id="section-15-25"></a>
## 15.25 Time to Accepted Result

Time to Accepted Result includes required evaluation and approval.

It is often more meaningful than Provider completion time.

<a id="section-15-26"></a>
## 15.26 Time to Durable Result

Time to Durable Result includes required ingestion, storage and evidence preservation.

<a id="section-15-27"></a>
## 15.27 Time to Verified Side Effect

Time to Verified Side Effect includes external submission and reconciliation.

For consequential actions, verification is part of completion.

<a id="section-15-28"></a>
## 15.28 Latency Distribution

Latency shall be understood as a distribution rather than one average.

Relevant measures may include:

- median,

- p75,

- p90,

- p95,

- p99,

- maximum,

- and timeout rate.

<a id="section-15-29"></a>
## 15.29 Average Latency Limitation

Average latency may hide:

- long-tail delays,

- starvation,

- queue spikes,

- and severe outliers.

Tail latency shall be measured where consequence warrants it.

<a id="section-15-30"></a>
## 15.30 Latency Confidence

Latency estimates shall include confidence based on:

- sample size,

- freshness,

- workload similarity,

- resource identity,

- and operational volatility.

<a id="section-15-31"></a>
## 15.31 Latency Freshness

Historical latency may become stale after:

- Model update,

- Provider capacity change,

- Account tier change,

- local hardware change,

- Adapter change,

- or queue-policy change.

<a id="section-15-32"></a>
## 15.32 Latency Objective

A Latency Objective defines a desired completion or response time.

It may be:

- target,

- percentile objective,

- or bounded range.

<a id="section-15-33"></a>
## 15.33 Latency Requirement

A Latency Requirement defines a mandatory time constraint.

Examples include:

- interactive response within five seconds,

- first audio chunk within one second,

- final episode by a specific publication window,

- or code analysis before a meeting.

<a id="section-15-34"></a>
## 15.34 Latency Target

A Latency Target is preferred but may be missed without automatic request failure.

<a id="section-15-35"></a>
## 15.35 Hard Deadline

A Hard Deadline is a latest completion time after which the result no longer satisfies the request.

Hard deadlines shall be explicit.

<a id="section-15-36"></a>
## 15.36 Soft Deadline

A Soft Deadline is a preferred completion time.

Missing it may reduce value but does not automatically invalidate the Output.

<a id="section-15-37"></a>
## 15.37 Start Deadline

A Start Deadline defines the latest time by which work may begin to remain feasible.

<a id="section-15-38"></a>
## 15.38 Completion Deadline

A Completion Deadline defines the latest acceptable completion time.

<a id="section-15-39"></a>
## 15.39 Publication Window

A Publication Window defines an approved time interval for external release.

It does not by itself grant publication authority.

<a id="section-15-40"></a>
## 15.40 Scheduling Window

A Scheduling Window defines when a Step may be started.

Examples include:

- overnight local processing,

- business hours,

- low-cost Provider window,

- or user-presence requirement.

<a id="section-15-41"></a>
## 15.41 Expiry Time

Expiry defines when a request, Plan, approval, Reservation or scheduled action is no longer valid.

<a id="section-15-42"></a>
## 15.42 Deadline Feasibility

The Fabric shall evaluate whether the complete request can meet its deadline.

The estimate should include:

- queue time,

- execution,

- retries,

- fallback,

- evaluation,

- human review,

- ingestion,

- and verification.

<a id="section-15-43"></a>
## 15.43 Deadline Infeasibility

When a deadline is not feasible, the system shall:

- explain the conflict,

- propose a valid alternative,

- request revised scope,

- degrade only if permitted,

- or reject admission.

It shall not pretend that the deadline remains achievable.

<a id="section-15-44"></a>
## 15.44 Deadline Does Not Override Policy

A deadline shall never justify bypassing:

- privacy,

- authority,

- rights,

- consent,

- Quality Floor,

- or Budget.

<a id="section-15-45"></a>
## 15.45 Deadline and Quality

The user may approve a lower Quality Target to meet a deadline only when:

- the mandatory Quality Floor remains satisfied,

- the Completion Contract permits it,

- and the change is explicit.

<a id="section-15-46"></a>
## 15.46 Deadline and Cost

Faster execution may require a more expensive Candidate.

The increased cost requires available Budget and authority.

<a id="section-15-47"></a>
## 15.47 Deadline and Reliability

A deadline-aware Plan should preserve enough time for:

- retry,

- fallback,

- and evaluation.

Selecting a resource with fast median latency but severe tail risk may be inappropriate.

<a id="section-15-48"></a>
## 15.48 Capacity

Capacity is the bounded amount of work a resource or system can perform within a defined interval and condition.

Capacity shall identify:

- resource,

- unit,

- period,

- scope,

- availability,

- reservation,

- and confidence.

<a id="section-15-49"></a>
## 15.49 Capacity Is Not Availability

A resource may be available but have no remaining capacity.

A resource may have theoretical capacity but be unavailable.

Both conditions matter.

<a id="section-15-50"></a>
## 15.50 Capacity Is Not Quota

Capacity describes actual or estimated ability to perform work.

Quota describes an imposed limit on permitted or available usage.

A system may have unused technical capacity but exhausted Provider quota.

<a id="section-15-51"></a>
## 15.51 Capacity Is Not Budget

Capacity answers:

Can the work be performed now or within the required period?

Budget answers:

May the economic value be consumed?

<a id="section-15-52"></a>
## 15.52 Capacity Is Not Concurrency

Concurrency is the number of operations that may run simultaneously.

Capacity may also include:

- throughput,

- memory,

- total daily jobs,

- tokens per minute,

- or human hours.

<a id="section-15-53"></a>
## 15.53 Capacity Unit

Capacity units may include:

- requests per second,

- requests per minute,

- tokens per second,

- tokens per minute,

- images per hour,

- video seconds per day,

- concurrent jobs,

- GPU minutes,

- CPU cores,

- gigabytes,

- queue slots,

- human review minutes,

- or generic workload units.

<a id="section-15-54"></a>
## 15.54 Capacity Record

A Capacity Record shall include or reference:

- capacityRecordId,

- resource,

- Capability,

- unit,

- total capacity,

- available capacity,

- reserved capacity,

- committed capacity,

- effective period,

- observedAt,

- source,

- confidence,

- and provenance.

<a id="section-15-55"></a>
## 15.55 Capacity Identity

Every material Capacity Record shall have stable identity or versioned observation identity.

<a id="section-15-56"></a>
## 15.56 Total Capacity

Total Capacity is the maximum known or configured capacity under defined conditions.

<a id="section-15-57"></a>
## 15.57 Available Capacity

Available Capacity is the portion currently usable for new eligible work.

<a id="section-15-58"></a>
## 15.58 Reserved Capacity

Reserved Capacity is held for future or pending work.

<a id="section-15-59"></a>
## 15.59 Committed Capacity

Committed Capacity is allocated to active work.

<a id="section-15-60"></a>
## 15.60 Effective Capacity

Effective Capacity is the usable capacity after accounting for:

- health,

- policy,

- maintenance,

- reliability reserve,

- concurrency,

- and workload overhead.

<a id="section-15-61"></a>
## 15.61 Theoretical Capacity

Theoretical Capacity is a maximum under ideal conditions.

It shall not be represented as ordinary production capacity.

<a id="section-15-62"></a>
## 15.62 Sustainable Capacity

Sustainable Capacity is the workload level that can be maintained without unacceptable degradation.

<a id="section-15-63"></a>
## 15.63 Burst Capacity

Burst Capacity is temporary capacity above the sustainable level.

It shall define:

- duration,

- recovery,

- cost,

- and risk.

<a id="section-15-64"></a>
## 15.64 Reserved Reliability Capacity

Some capacity may be withheld to support:

- retries,

- recovery,

- critical work,

- or Provider failover.

This reserve shall remain visible to governance.

<a id="section-15-65"></a>
## 15.65 Provider Capacity

Provider Capacity may depend on:

- Product,

- Account tier,

- region,

- Model,

- queue,

- and Provider-wide demand.

<a id="section-15-66"></a>
## 15.66 Provider Account Capacity

One Account may have specific:

- concurrency,

- rate limit,

- queue priority,

- credit balance,

- or contractual capacity.

<a id="section-15-67"></a>
## 15.67 Connection Capacity

A Connection may impose:

- transport limits,

- Adapter worker limits,

- or protocol-specific concurrency.

<a id="section-15-68"></a>
## 15.68 Model Capacity

Model capacity may include:

- maximum concurrent requests,

- token throughput,

- context limits,

- and generation throughput.

<a id="section-15-69"></a>
## 15.69 Deployment Capacity

The same Model Version may have different capacity across Deployments.

<a id="section-15-70"></a>
## 15.70 Local Runtime Capacity

Local Runtime capacity may depend on:

- CPU,

- GPU,

- memory,

- thermal state,

- battery,

- storage,

- Model size,

- and competing workloads.

<a id="section-15-71"></a>
## 15.71 Runtime Node Capacity

A Runtime Node may expose multiple resource pools.

Examples include:

- CPU pool,

- GPU pool,

- memory pool,

- storage pool,

- and network pool.

<a id="section-15-72"></a>
## 15.72 Tool Capacity

Tools may have capacity limits such as:

- worker count,

- file-size limit,

- process limit,

- or licensed-seat limit.

<a id="section-15-73"></a>
## 15.73 Queue Capacity

Queue Capacity includes:

- message count,

- storage,

- throughput,

- retention,

- and consumer capacity.

<a id="section-15-74"></a>
## 15.74 Human Capacity

Human Capacity represents bounded availability for:

- review,

- approval,

- manual Provider operation,

- creative direction,

- or Incident response.

<a id="section-15-75"></a>
## 15.75 Human Capacity Is Not Infinite

A Workflow shall not assume immediate human response.

Human scheduling shall account for:

- working hours,

- role,

- availability,

- expertise,

- and workload.

<a id="section-15-76"></a>
## 15.76 Approval Capacity

Approval queues may become a bottleneck.

The system should distinguish:

- approval waiting,

- review work,

- and decision authority.

<a id="section-15-77"></a>
## 15.77 Evaluation Capacity

Evaluator capacity may include:

- Model throughput,

- Tool workers,

- or human reviewers.

<a id="section-15-78"></a>
## 15.78 Storage Capacity

Storage capacity affects:

- Output ingestion,

- checkpointing,

- Asset retention,

- and recovery.

<a id="section-15-79"></a>
## 15.79 Network Capacity

Network bandwidth and latency may constrain:

- media upload,

- local-to-cloud transfer,

- and remote Model execution.

<a id="section-15-80"></a>
## 15.80 Composite Capacity

A complex Step may depend on several capacity dimensions.

Its effective capacity is constrained by the required bottleneck resource.

<a id="section-15-81"></a>
## 15.81 Bottleneck

A Bottleneck is the resource or dependency limiting throughput or completion time.

<a id="section-15-82"></a>
## 15.82 Bottleneck Identification

The Fabric should identify whether delay originates from:

- queue,

- Provider,

- local compute,

- approval,

- evaluation,

- storage,

- or another dependency.

<a id="section-15-83"></a>
## 15.83 Bottleneck Shift

Optimising one component may move the bottleneck elsewhere.

Capacity planning shall consider end-to-end flow.

<a id="section-15-84"></a>
## 15.84 Capacity Observation

Capacity observations may come from:

- Provider headers,

- official limits,

- current queue,

- local telemetry,

- configured limits,

- historical throughput,

- or manual records.

<a id="section-15-85"></a>
## 15.85 Capacity Confidence

Capacity confidence may be:

- exact,

- high,

- moderate,

- low,

- inferred,

- or unknown.

<a id="section-15-86"></a>
## 15.86 Unknown Capacity

Unknown capacity shall be treated conservatively for:

- expensive,

- high-priority,

- or consequential work.

<a id="section-15-87"></a>
## 15.87 Capacity Freshness

Operational capacity may change rapidly.

Every observation shall include freshness.

<a id="section-15-88"></a>
## 15.88 Capacity Forecast

A Capacity Forecast predicts future availability or demand.

It shall include:

- horizon,

- assumptions,

- expected demand,

- expected supply,

- uncertainty,

- and source data.

<a id="section-15-89"></a>
## 15.89 Forecast Is Not Reservation

A forecast does not guarantee capacity.

Reservations or contracts may be required.

<a id="section-15-90"></a>
## 15.90 Capacity Planning

Capacity Planning determines whether expected future demand can be served.

It may include:

- workload forecast,

- Provider contracts,

- local hardware planning,

- subscription tier review,

- and human staffing.

<a id="section-15-91"></a>
## 15.91 Short-Term Capacity Planning

Short-term planning may cover:

- current day,

- current week,

- active Production,

- or campaign window.

<a id="section-15-92"></a>
## 15.92 Long-Term Capacity Planning

Long-term planning may support:

- hardware acquisition,

- Provider diversification,

- managed service design,

- or Tenant growth.

<a id="section-15-93"></a>
## 15.93 Capacity Headroom

Capacity Headroom is unused sustainable capacity held for:

- spikes,

- retries,

- recovery,

- and uncertainty.

<a id="section-15-94"></a>
## 15.94 Minimum Headroom

Critical services may require a minimum headroom percentage or absolute reserve.

<a id="section-15-95"></a>
## 15.95 Capacity Saturation

Saturation occurs when demand approaches or exceeds sustainable capacity.

<a id="section-15-96"></a>
## 15.96 Saturation Indicators

Indicators may include:

- queue growth,

- latency increase,

- timeout increase,

- rate limiting,

- memory pressure,

- thermal throttling,

- or human backlog.

<a id="section-15-97"></a>
## 15.97 Capacity Overcommitment

Overcommitment allocates more logical demand than physical capacity.

It may be safe only when usage patterns and risk are understood.

<a id="section-15-98"></a>
## 15.98 Unsafe Overcommitment

Overcommitment is unsafe when:

- deadlines are hard,

- workloads peak together,

- cancellation is costly,

- or side effects are consequential.

<a id="section-15-99"></a>
## 15.99 Capacity Degradation

Capacity may be degraded by:

- Incident,

- maintenance,

- reduced Account tier,

- local battery,

- high temperature,

- or competing work.

<a id="section-15-100"></a>
## 15.100 Capacity Recovery

Recovered capacity shall be validated before full scheduling resumes.

<a id="section-15-101"></a>
## 15.101 Scheduler

The Scheduler is the Fabric component or governed service responsible for assigning eligible work to time, queue and capacity.

The Scheduler shall have a stable Service Principal identity.

It shall operate only on validated canonical state.

<a id="section-15-102"></a>
## 15.102 Scheduler Responsibilities

The Scheduler is responsible for:

- receiving schedulable Steps,

- evaluating admission,

- resolving effective priority,

- selecting queue or resource pool,

- reserving required capacity,

- ordering Ready work,

- enforcing concurrency and quota,

- dispatching eligible work,

- delaying infeasible work,

- handling cancellation,

- and preserving scheduling evidence.

<a id="section-15-103"></a>
## 15.103 Scheduler Non-Responsibilities

The Scheduler shall not:

- create Capability authority,

- alter Data Classification,

- approve spending,

- lower Quality Floor,

- retrieve raw credentials,

- or mark business outcomes complete.

<a id="section-15-104"></a>
## 15.104 Scheduling Request

A Scheduling Request is a canonical request to allocate time and capacity to one Step or operation.

It shall include or reference:

- schedulingRequestId,

- Plan Version,

- Step ID,

- Tenant,

- Project,

- Environment,

- Capability,

- selected or eligible Candidate,

- workload class,

- effective priority,

- earliest start,

- deadline,

- expected duration,

- capacity requirements,

- concurrency requirements,

- Budget Reservation,

- approval state,

- and policy versions.

<a id="section-15-105"></a>
## 15.105 Scheduling Request Identity

Every material Scheduling Request shall have stable identity.

Material changes shall create a new version or superseding request.

<a id="section-15-106"></a>
## 15.106 Scheduling Decision

A Scheduling Decision shall include or reference:

- schedulingDecisionId,

- Scheduling Request,

- selected queue,

- selected resource pool,

- scheduled start,

- expected completion,

- capacity reservation,

- priority,

- policy,

- fairness decision,

- and provenance.

<a id="section-15-107"></a>
## 15.107 Scheduling Decision Validity

A Scheduling Decision may become invalid because of:

- resource failure,

- deadline change,

- Plan amendment,

- quota exhaustion,

- capacity loss,

- or Budget invalidation.

<a id="section-15-108"></a>
## 15.108 Scheduling Lifecycle

Scheduling states may include:

- proposed,

- validating,

- admitted,

- queued,

- scheduled,

- dispatching,

- running,

- delayed,

- blocked,

- preempted,

- cancelled,

- expired,

- completed,

- failed,

- and archived.

<a id="section-15-109"></a>
## 15.109 Proposed Scheduling State

The work has been submitted but not evaluated for admission.

<a id="section-15-110"></a>
## 15.110 Validating Scheduling State

The system is verifying:

- dependencies,

- authority,

- Budget,

- policy,

- and capacity requirements.

<a id="section-15-111"></a>
## 15.111 Admitted State

The work is permitted to enter the scheduling system.

<a id="section-15-112"></a>
## 15.112 Queued State

The work awaits capacity or its permitted start time.

<a id="section-15-113"></a>
## 15.113 Scheduled State

A future dispatch time or resource allocation has been selected.

<a id="section-15-114"></a>
## 15.114 Dispatching State

The Scheduler is transferring responsibility to the execution worker or external resource.

<a id="section-15-115"></a>
## 15.115 Running State

Execution has begun.

<a id="section-15-116"></a>
## 15.116 Delayed State

Work has been intentionally postponed.

The delay reason shall be explicit.

<a id="section-15-117"></a>
## 15.117 Blocked State

A required condition remains missing.

<a id="section-15-118"></a>
## 15.118 Preempted State

Execution or queue position has been interrupted for higher-priority or emergency work according to policy.

<a id="section-15-119"></a>
## 15.119 Cancelled State

Future scheduling has been stopped by authority or policy.

<a id="section-15-120"></a>
## 15.120 Expired State

<a id="section-15-121"></a>
## 15.121 Completed Scheduling State

The Scheduler’s responsibility for the dispatch has completed.

This does not imply the business request completed.

<a id="section-15-122"></a>
## 15.122 Admission Control

Admission Control determines whether new work may enter the scheduling system.

It protects:

- capacity,

- deadlines,

- reliability,

- Budgets,

- and fairness.

<a id="section-15-123"></a>
## 15.123 Admission Decision

An Admission Decision may be:

- admit,

- admit with conditions,

- defer,

- reject,

- require approval,

- require replanning,

- or require rerouting.

<a id="section-15-124"></a>
## 15.124 Admission Requirements

Admission should evaluate:

- valid Plan and Step,

- current authority,

- current policy,

- required Inputs,

- Budget Reservation,

- resource eligibility,

- capacity feasibility,

- deadline feasibility,

- quota,

- and concurrency.

<a id="section-15-125"></a>
## 15.125 Conditional Admission

Work may be admitted under conditions such as:

- wait until a window,

- use reduced concurrency,

- use a specific queue,

- or require human review.

<a id="section-15-126"></a>
## 15.126 Deferred Admission

Deferred Admission postpones entry until:

- capacity returns,

- approval exists,

- Budget renews,

- quota resets,

- or a scheduled time arrives.

<a id="section-15-127"></a>
## 15.127 Rejected Admission

Rejection occurs when the work cannot safely or feasibly enter the system under current conditions.

<a id="section-15-128"></a>
## 15.128 Admission Is Not Execution

Admitted work may still wait.

Admission only confirms that the system accepts responsibility for scheduling it.

<a id="section-15-129"></a>
## 15.129 Admission Overload Protection

When capacity is saturated, the system shall not continue accepting unlimited work without:

- queue limit,

- delay,

- load shedding,

- or rejection.

<a id="section-15-130"></a>
## 15.130 Admission and Deadline

Work should not be admitted when available evidence shows that the Hard Deadline cannot be met, unless the user explicitly accepts delayed or degraded delivery.

<a id="section-15-131"></a>
## 15.131 Admission and Budget

Paid work shall not be admitted without required economic protection.

<a id="section-15-132"></a>
## 15.132 Admission and Human Capacity

A Plan requiring human review should not claim feasible completion when no qualified reviewer is available before the deadline.

<a id="section-15-133"></a>
## 15.133 Workload Class

A Workload Class describes the timing and interaction characteristics of work.

Canonical classes may include:

- real-time,

- interactive,

- near-interactive,

- asynchronous,

- batch,

- background,

- scheduled,

- recurring,

- long-running,

- maintenance,

- recovery,

- and emergency.

<a id="section-15-134"></a>
## 15.134 Real-Time Workload

Real-time work requires continuous or near-continuous response within a strict latency boundary.

Examples include:

- live voice interaction,

- streaming interpretation,

- or real-time control.

Real-time work requires specialised capacity and fallback.

<a id="section-15-135"></a>
## 15.135 Interactive Workload

Interactive work is user-facing and expects a response within seconds or a short period.

Examples include:

- chat reasoning,

- search assistance,

- or approval support.

<a id="section-15-136"></a>
## 15.136 Near-Interactive Workload

Near-interactive work may take tens of seconds or several minutes while the user remains engaged.

<a id="section-15-137"></a>
## 15.137 Asynchronous Workload

Asynchronous work may complete later without holding an active user session.

Examples include:

- video generation,

- document processing,

- or large code analysis.

<a id="section-15-138"></a>
## 15.138 Batch Workload

Batch work processes a bounded collection of items.

It may optimise throughput over immediate latency.

<a id="section-15-139"></a>
## 15.139 Background Workload

Background work has low urgency and may use spare capacity.

Examples include:

- reindexing,

- benchmark runs,

- or non-urgent derivative generation.

<a id="section-15-140"></a>
## 15.140 Scheduled Workload

Scheduled work should begin within an approved time or window.

<a id="section-15-141"></a>
## 15.141 Recurring Workload

Recurring work repeats according to a governed schedule.

Each occurrence shall receive fresh validation.

<a id="section-15-142"></a>
## 15.142 Long-Running Workload

Long-running work may span:

- minutes,

- hours,

- days,

- or multiple human interactions.

It requires durable scheduling and state.

<a id="section-15-143"></a>
## 15.143 Maintenance Workload

Maintenance includes:

- registry refresh,

- cache rebuild,

- cleanup,

- or model download.

Maintenance shall not silently disrupt higher-priority work.

<a id="section-15-144"></a>
## 15.144 Recovery Workload

Recovery work restores valid operation or state.

It may receive elevated priority under Incident policy.

<a id="section-15-145"></a>
## 15.145 Emergency Workload

Emergency work addresses severe active harm.

Emergency priority shall be tightly governed and attributable.

<a id="section-15-146"></a>
## 15.146 Workload Class Is Not Priority

Workload class describes timing behaviour.

Priority determines relative scheduling preference.

A background recovery verification may be higher priority than an interactive optional request.

<a id="section-15-147"></a>
## 15.147 Priority

Priority is the governed relative importance of work within a scheduling scope.

Priority shall be explicit, bounded and attributable.

<a id="section-15-148"></a>
## 15.148 Priority Level

Canonical levels may include:

- emergency,

- critical,

- high,

- normal,

- low,

- background,

- and best effort.

<a id="section-15-149"></a>
## 15.149 Emergency Priority

Emergency priority is reserved for active severe incidents, safety or security containment.

It shall not be available to ordinary Agents by default.

<a id="section-15-150"></a>
## 15.150 Critical Priority

Critical priority may apply to:

- essential production deadline,

- recovery,

- or user-blocking operation.

<a id="section-15-151"></a>
## 15.151 High Priority

High priority may apply to important time-sensitive work with valid authority.

<a id="section-15-152"></a>
## 15.152 Normal Priority

Normal is the default for ordinary work.

<a id="section-15-153"></a>
## 15.153 Low Priority

Low-priority work may wait behind ordinary work.

<a id="section-15-154"></a>
## 15.154 Background Priority

Background work should consume spare capacity and yield to higher priorities.

<a id="section-15-155"></a>
## 15.155 Best-Effort Priority

Best-effort work may be delayed, cancelled or omitted when capacity is scarce.

<a id="section-15-156"></a>
## 15.156 Priority Source

Priority may derive from:

- explicit user request,

- Project policy,

- Workflow,

- Incident,

- deadline,

- or system maintenance.

The source shall remain visible.

<a id="section-15-157"></a>
## 15.157 Priority Authority

Only authorised Principals or policies may assign elevated priority.

<a id="section-15-158"></a>
## 15.158 Agent Priority Limitation

An Agent shall not mark its own work critical merely to reduce latency.

<a id="section-15-159"></a>
## 15.159 Priority Escalation

Priority escalation shall be:

- reasoned,

- scoped,

- time-bounded,

- and attributable.

<a id="section-15-160"></a>
## 15.160 Priority De-Escalation

Priority may decrease when:

- deadline passes,

- Incident resolves,

- or urgency changes.

<a id="section-15-161"></a>
## 15.161 Priority Inversion

Priority Inversion occurs when high-priority work waits behind lower-priority work due to shared locks, capacity or dependencies.

<a id="section-15-162"></a>
## 15.162 Priority-Inversion Mitigation

Mitigation may include:

- priority inheritance,

- reserved capacity,

- narrow locks,

- or separate queues.

<a id="section-15-163"></a>
## 15.163 Priority Inheritance

A lower-priority dependency may temporarily inherit higher scheduling importance when it blocks critical work.

The inheritance shall be bounded.

<a id="section-15-164"></a>
## 15.164 Priority Abuse

Repeated unjustified high priority shall be detected and governed.

<a id="section-15-165"></a>
## 15.165 Starvation

Starvation occurs when work waits indefinitely because higher-priority work continually arrives.

<a id="section-15-166"></a>
## 15.166 Starvation Prevention

Controls may include:

- ageing,

- fair-share allocation,

- maximum delay,

- reserved low-priority capacity,

- or escalation.

<a id="section-15-167"></a>
## 15.167 Priority Ageing

Waiting work may gradually gain scheduling weight.

Ageing shall not raise it above mandatory emergency classes without policy.

<a id="section-15-168"></a>
## 15.168 Fairness

Fairness ensures that shared capacity is allocated according to governed policy rather than arbitrary arrival, power or implementation order.

<a id="section-15-169"></a>
## 15.169 Tenant Fairness

One Tenant shall not monopolise shared Omnira-managed capacity.

<a id="section-15-170"></a>
## 15.170 Project Fairness

One Project shall not consume all capacity needed by other authorised Projects.

<a id="section-15-171"></a>
## 15.171 User Fairness

Multi-user Tenants may require fair allocation among users or roles.

<a id="section-15-172"></a>
## 15.172 Capability Fairness

High-volume media jobs shall not indefinitely block text, approvals or recovery.

<a id="section-15-173"></a>
## 15.173 Fairness Weight

A fairness policy may assign weights based on:

- subscription,

- Project importance,

- reserved capacity,

- or contractual entitlement.

Weights shall be explicit.

<a id="section-15-174"></a>
## 15.174 Weighted Fair Scheduling

Weighted Fair Scheduling allocates proportional capacity among eligible classes.

<a id="section-15-175"></a>
## 15.175 Equal Fairness

Equal share may be appropriate when all participants have equivalent entitlement.

<a id="section-15-176"></a>
## 15.176 Reserved Share

A Tenant or Project may hold a reserved capacity share.

<a id="section-15-177"></a>
## 15.177 Borrowed Share

Unused reserved capacity may be borrowed by others when policy permits.

Borrowing shall be revocable.

<a id="section-15-178"></a>
## 15.178 Fairness Window

Fairness may be measured over a defined time window rather than every individual dispatch.

<a id="section-15-179"></a>
## 15.179 Fairness Versus Priority

Priority may temporarily override fair share for urgent work.

Long-term starvation remains prohibited.

<a id="section-15-180"></a>
## 15.180 First-In-First-Out

First-In-First-Out scheduling orders work by arrival.

It is simple but may be unsuitable when:

- deadlines differ,

- workloads vary greatly,

- or priority matters.

<a id="section-15-181"></a>
## 15.181 Shortest-Job-First

Shortest-Job-First may reduce average wait time.

It can starve long work and relies on duration estimates.

<a id="section-15-182"></a>
## 15.182 Earliest-Deadline-First

Earliest-Deadline-First prioritises the nearest deadline.

It requires realistic duration and feasibility estimates.

<a id="section-15-183"></a>
## 15.183 Priority Queue

Priority queues order work by effective priority.

They require starvation prevention.

<a id="section-15-184"></a>
## 15.184 Weighted Queue

Weighted queues allocate service across workload classes.

<a id="section-15-185"></a>
## 15.185 Round-Robin

Round-Robin rotates among queues or Projects.

It may improve fairness.

<a id="section-15-186"></a>
## 15.186 Deficit Round-Robin

Deficit Round-Robin can support workloads with different sizes while preserving fair share.

<a id="section-15-187"></a>
## 15.187 Hybrid Scheduling

Omnira may combine:

- admission control,

- priority,

- fairness,

- deadline,

- and resource fit.

The algorithm shall be versioned and explainable.

<a id="section-15-188"></a>
## 15.188 Scheduling Policy

Scheduling Policy defines how admitted work is ordered and allocated.

It shall include:

- scope,

- workload classes,

- priorities,

- fairness,

- concurrency,

- quotas,

- ageing,

- preemption,

- and load shedding.

<a id="section-15-189"></a>
## 15.189 Scheduling Policy Identity

<a id="section-15-190"></a>
## 15.190 Policy Scope

Scheduling policies may exist at:

- Platform,

- Tenant,

- Project,

- Environment,

- Capability,

- Provider,

- queue,

- and workload-class level.

<a id="section-15-191"></a>
## 15.191 Policy Composition

Effective policy is the composition of applicable rules.

Mandatory isolation and safety rules outrank convenience.

<a id="section-15-192"></a>
## 15.192 Scheduling Algorithm Version

Every material Scheduling Decision shall preserve the algorithm or policy version used.

<a id="section-15-197"></a>
## 15.197 Project Queue

<a id="section-15-198"></a>
## 15.198 Provider Queue

Provider-specific queues isolate external capacity and failure.

<a id="section-15-199"></a>
## 15.199 Capability Queue

- text,

- image,

- video,

- voice,

- code,

Consequential operations should use separate queues or dispatch controls.

<a id="section-15-201"></a>

- required role,

- and assignment state.

- priorities,

<a id="section-15-206"></a>

<a id="section-15-207"></a>

- expected queue wait,

- execution,

- evaluation,

<a id="section-15-208"></a>
## 15.208 Queue Wait Limit

A Queue Item may have a maximum permitted waiting time.

<a id="section-15-209"></a>
## 15.209 Queue Expiry

Expired work shall not dispatch without revalidation.

<a id="section-15-210"></a>
## 15.210 Queue Cancellation

Cancellation shall remove future dispatch while preserving history.

<a id="section-15-211"></a>
## 15.211 Queue Reprioritisation

<a id="section-15-212"></a>
## 15.212 Queue Migration

Work may move between queues after:

- rerouting,

- priority change,

- or Continuity Mode.

<a id="section-15-213"></a>
## 15.213 Queue Compaction

Completed and expired records may be archived.

## 15.214 Queue Backlog

## 15.215 Backlog Age

<a id="section-15-217"></a>
## 15.217 Queue Size Limitation

A queue shall have bounded capacity or explicit spillover behaviour.

<a id="section-15-218"></a>
## 15.218 Queue Overflow

Overflow may cause:

- rejection,

- alternate queue,

- durable spillover,

- or load shedding.

<a id="section-15-219"></a>
## 15.219 Infinite Queue Prohibition

Infinite logical queues create hidden failure and unbounded delay.

Every queue requires bounded operational policy.

<a id="section-15-220"></a>
## 15.220 Backpressure

Backpressure slows or rejects new work when downstream capacity is constrained.

<a id="section-15-221"></a>
## 15.221 Backpressure Signal

Signals may include:

- queue depth,

- wait time,

- memory pressure,

- Provider rate limit,

- or worker saturation.

<a id="section-15-222"></a>
## 15.222 Producer Backpressure

Upstream systems should reduce work submission when the Scheduler signals saturation.

<a id="section-15-223"></a>
## 15.223 Agent Backpressure

Agents shall not create unlimited child requests when the Fabric reports constrained capacity.

<a id="section-15-224"></a>
## 15.224 Workflow Backpressure

Workflow fan-out shall respect downstream queue and Budget limits.

<a id="section-15-225"></a>
## 15.225 Provider Backpressure

Provider rate-limit or queue signals shall reduce dispatch.

<a id="section-15-226"></a>
## 15.226 Human Backpressure

Large review backlogs shall reduce new work requiring the same reviewer class where feasible.

<a id="section-15-227"></a>

<a id="section-15-228"></a>

1. speculative work,

2. duplicate alternatives,

3. optional derivatives,

4. background benchmarks,

5. best-effort work,

6. low-priority work,

7. normal work where unavoidable.

Critical and emergency work should be protected according to policy.

<a id="section-15-229"></a>

- affected work,

- trigger,

- priority,

- user impact,

- and recovery path.

<a id="section-15-230"></a>
## 15.230 Silent Load Shedding Prohibition

Dropped work shall receive truthful state.

It shall not disappear.
