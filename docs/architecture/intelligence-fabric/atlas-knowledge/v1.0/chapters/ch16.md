# Chapter 16 — Adapter and Connector Architecture

<a id="section-16-1"></a>
## 16.1 Chapter Status

This chapter defines the canonical architecture, governance model, object model, lifecycle, boundaries and conformance requirements for Adapters, Connectors, Connections and integration-facing execution resources within the Omnira Intelligence Fabric.

It establishes:

- how Provider-specific systems are translated into canonical Fabric contracts,

- how Adapters remain separate from Providers, Models, Accounts, Credentials and Connections,

- how Connectors expose governed integration capabilities,

- how external APIs, MCP servers, webhooks, asynchronous queues, local runtimes, tools, browser-assisted systems and human-assisted systems coexist,

- how request and response translation remain deterministic, versioned and observable,

- how capability support is mapped without leaking Provider-specific assumptions into Projects or Agents,

- how Provider-specific identifiers and lifecycle states are preserved,

- how errors, usage, cost, latency, quality and execution evidence are normalised,

- how idempotency, retries, streaming, pagination, callbacks and long-running jobs cross integration boundaries,

- how Assets and multimodal payloads are transferred safely,

- how schema evolution and protocol drift are handled,

- how Provider-managed routing and hidden implementation choices are represented truthfully,

- how security, privacy, Project isolation and authority remain enforceable across every integration,

- how connector health and maturity influence routing,

- how testing, certification, simulation and sandboxing are performed,

- how integration failure is contained,

- how manual-assisted integration paths remain canonical without pretending to be automated,

- and how Stage 1 shall implement the smallest trustworthy adapter and connector foundation.

Adapters and Connectors exist to isolate external variation from Omnira’s canonical architecture.

A Provider-specific API shall not define Omnira’s internal object model.

An MCP server shall not become unrestricted platform authority.

A local tool shall not bypass policy because it runs on a trusted machine.

A browser-assisted Provider shall not be represented as an API.

A webhook shall not be trusted merely because it arrived at an Omnira endpoint.

A Connector shall not contain raw credentials.

An Adapter shall not own Agent identity.

A Provider SDK shall not become the canonical execution contract.

This chapter is normative after formal approval.

Protocol-specific implementation details are expanded in Chapter 17.

Credential, secret and identity mechanics are expanded in Chapter 18.

Implementation and conformance must be verified separately.

<a id="section-16-2"></a>
## 16.2 Purpose of the Integration Architecture

The Intelligence Fabric must communicate with systems that differ in:

- protocol,

- authentication,

- schema,

- terminology,

- lifecycle,

- error handling,

- billing,

- media formats,

- streaming behaviour,

- job semantics,

- callback design,

- versioning,

- and operational maturity.

Examples may include:

- external language-model APIs,

- image and video generation Providers,

- voice and audio services,

- local Ollama runtimes,

- NVIDIA-hosted or local Models,

- MCP servers,

- search services,

- file-processing tools,

- repository tools,

- publication platforms,

- browser-only creative tools,

- human-assisted production paths,

- and future Agent-to-Agent protocols.

Without a canonical integration layer, Project code would become tightly coupled to:

- Provider model names,

- SDK types,

- endpoint URLs,

- raw API errors,

- Provider billing units,

- callback payloads,

- and hidden Provider assumptions.

That coupling would make it difficult to:

- replace Providers,

- add local resources,

- enforce uniform policy,

- preserve Project isolation,

- compare costs,

- route by Capability,

- recover from failure,

- and maintain truthful provenance.

The Adapter and Connector architecture exists to absorb that variation while preserving canonical semantics.

<a id="section-16-3"></a>
## 16.3 Integration Boundary

The Integration Boundary is the controlled interface between canonical Omnira objects and external or implementation-specific systems.

The boundary shall define:

- what enters,

- what leaves,

- which identity is used,

- which policy applies,

- which data may cross,

- which side effects may occur,

- and which evidence must return.

Every external or local execution path shall cross an explicit Integration Boundary.

<a id="section-16-4"></a>
## 16.4 Canonical Side

The canonical side uses Omnira-owned objects such as:

- Capability Request,

- Intent Envelope,

- Execution Plan,

- Step,

- Routing Decision,

- Execution,

- Attempt,

- Output,

- Asset,

- Cost Record,

- Evaluation Result,

- and Incident.

Canonical objects shall remain independent from one Provider’s schema.

<a id="section-16-5"></a>
## 16.5 Integration Side

The integration side may contain:

- Provider request objects,

- SDK calls,

- HTTP requests,

- MCP messages,

- process invocations,

- local runtime commands,

- browser instructions,

- queue messages,

- webhook payloads,

- or human task packages.

Provider-specific objects shall remain inside the integration boundary unless preserved as evidence.

<a id="section-16-6"></a>
## 16.6 Integration Translation

Integration Translation converts between:

- canonical request and implementation-specific operation,

- implementation-specific response and canonical Output,

- Provider error and canonical Error Classification,

- Provider usage and canonical Usage Record,

- Provider job state and canonical Execution state,

- Provider Asset and canonical Asset reference,

- and Provider metadata and canonical provenance.

Translation shall not change user intent silently.

<a id="section-16-7"></a>
## 16.7 Adapter

An Adapter is a versioned software component that translates between canonical Fabric contracts and one implementation-specific interface.

An Adapter may support:

- one Provider API,

- one Provider Product,

- one local runtime,

- one Tool protocol,

- one MCP server family,

- one queue system,

- one file format,

- or one human-assisted procedure.

An Adapter is an implementation component.

It is not the Provider itself.

<a id="section-16-8"></a>
## 16.8 Connector

A Connector is a governed integration capability exposed to the Fabric.

A Connector combines or references:

- one or more Adapters,

- supported Connections,

- Capability mappings,

- policy,

- health,

- maturity,

- and operational constraints.

A Connector describes how Omnira may interact with a resource class.

It is broader than one translation library.

<a id="section-16-9"></a>
## 16.9 Connection

A Connection is a configured operational relationship between Omnira and a specific external or local target.

A Connection may identify:

- Provider Account,

- endpoint,

- region,

- workspace,

- Runtime Node,

- repository,

- MCP server,

- queue,

- browser profile,

- or human operator channel.

A Connection is an instance.

A Connector is a governed integration type.

An Adapter is a translating implementation.

<a id="section-16-10"></a>
## 16.10 Provider

A Provider is the organisation or system offering a Product or service.

A Provider may expose several:

- Products,

- APIs,

- Models,

- regions,

- Accounts,

- and protocols.

Provider identity shall remain separate from Adapter and Connector identity.

<a id="section-16-11"></a>
## 16.11 Provider Product

A Provider Product is one commercial or technical offering.

Examples include:

- text-generation API,

- image-generation workspace,

- voice-synthesis API,

- search product,

- or managed Agent platform.

One Provider may require several Connectors for different Products.

<a id="section-16-12"></a>
## 16.12 Model

A Model is an intelligence resource.

A Model may be exposed through:

- several Providers,

- several Products,

- several Deployments,

- or several Adapters.

Model identity shall not be embedded into Connector identity unnecessarily.

<a id="section-16-13"></a>
## 16.13 Model Deployment

A Model Deployment is one executable placement of a Model.

The Adapter may need deployment-specific translation.

The Connector shall preserve the distinction between:

- Model,

- Model Version,

- Deployment,

- and Provider-managed alias.

<a id="section-16-14"></a>
## 16.14 Tool

A Tool is an executable resource that performs a bounded operation.

A Tool may be integrated through:

- local process,

- API,

- MCP,

- SDK,

- queue,

- or human-assisted procedure.

Tool identity shall remain separate from the Connector used to invoke it.

<a id="section-16-15"></a>
## 16.15 Runtime Node

A Runtime Node is a machine or environment capable of running local Models or Tools.

A local Connector may target one or more Runtime Nodes.

Node identity and health shall remain explicit.

<a id="section-16-16"></a>
## 16.16 External Agent Resource

An External Agent Resource is an external system that performs multi-step or agentic work.

It shall not be treated as an Omnira Agent identity.

Its external autonomy shall remain bounded by:

- Capability,

- Connection,

- data policy,

- authority,

- and evidence.

<a id="section-16-17"></a>
## 16.17 Human-Assisted Integration

A Human-Assisted Integration uses a person to operate or mediate an external system.

It remains a valid canonical integration path when:

- no API exists,

- creative direction requires a human,

- login or interface restrictions prevent automation,

- or production maturity is insufficient.

It shall be labelled honestly.

<a id="section-16-18"></a>
## 16.18 Integration Object Model

The canonical integration object model should include or reference:

- Adapter,

- Adapter Version,

- Connector,

- Connector Version,

- Connection,

- Connection Profile,

- Endpoint,

- Protocol Profile,

- Capability Mapping,

- Feature Mapping,

- Parameter Mapping,

- Schema Mapping,

- State Mapping,

- Error Mapping,

- Usage Mapping,

- Asset Mapping,

- Callback Mapping,

- Integration Policy,

- Integration Test Suite,

- Conformance Result,

- Integration Incident,

- and Manual Procedure.

<a id="section-16-19"></a>
## 16.19 Adapter Identity

Every Adapter shall have stable identity.

The identity shall remain stable across implementation versions.

Example:

adapter.openart.director

may have several Versions.

<a id="section-16-20"></a>
## 16.20 Adapter Version

Every material Adapter release shall have a distinct Version.

Version changes may reflect:

- Provider API change,

- schema change,

- SDK update,

- new Capability support,

- changed error mapping,

- changed cost mapping,

- or security correction.

<a id="section-16-21"></a>
## 16.21 Adapter Version Immutability

Historical Executions shall preserve the exact Adapter Version used.

A new deployment shall not rewrite historical integration evidence.

<a id="section-16-22"></a>
## 16.22 Connector Identity

Every Connector shall have stable canonical identity.

Connector identity should describe the governed integration boundary rather than a temporary endpoint.

Examples may include:

- connector.provider.text-api,

- connector.local.ollama,

- connector.mcp.repository,

- connector.human.openart-director.

<a id="section-16-23"></a>
## 16.23 Connector Version

Material changes to:

- Capability mappings,

- supported protocols,

- policy,

- maturity,

- or connection requirements

shall create a new Connector Version.

<a id="section-16-24"></a>
## 16.24 Connection Identity

Every persistent Connection shall have stable identity.

Connection identity shall remain separate from:

- credential,

- Provider Account,

- endpoint,

- and Adapter Version.

<a id="section-16-25"></a>
## 16.25 Connection Version

Material configuration changes should create:

- new Connection Version,

- attributable amendment,

- or new Connection

according to consequence.

<a id="section-16-26"></a>
## 16.26 Connection Profile

A Connection Profile defines reusable configuration requirements for one Connector.

It may include:

- protocol,

- endpoint class,

- authentication mechanism,

- region,

- timeout defaults,

- callback requirements,

- supported Environments,

- and health checks.

<a id="section-16-27"></a>
## 16.27 Endpoint

An Endpoint is a specific address or invocation target.

An Endpoint may be:

- HTTP URL,

- WebSocket address,

- local socket,

- process command,

- queue topic,

- MCP server address,

- repository path,

- or browser application location.

Endpoint identity shall not be treated as Provider identity.

<a id="section-16-28"></a>
## 16.28 Endpoint Environment

Endpoints may be classified as:

- development,

- sandbox,

- staging,

- production,

- local,

- or recovery.

Environment mismatch shall block execution.

<a id="section-16-29"></a>
## 16.29 Endpoint Region

Region shall remain explicit where relevant to:

- data residency,

- latency,

- pricing,

- and failure domains.

<a id="section-16-30"></a>
## 16.30 Protocol Profile

A Protocol Profile defines the communication model used by a Connector.

Protocol classes may include:

- synchronous API,

- asynchronous API,

- streaming API,

- MCP,

- webhook,

- queue,

- local process,

- local runtime,

- file exchange,

- browser-assisted,

- human-assisted,

- or future Agent protocol.

<a id="section-16-31"></a>
## 16.31 Protocol Version

Protocol Version shall remain explicit where the external system defines one.

<a id="section-16-32"></a>
## 16.32 Protocol Maturity

Protocol maturity may be:

- experimental,

- preview,

- production,

- deprecated,

- legacy,

- or unsupported.

<a id="section-16-33"></a>
## 16.33 Adapter Responsibility

An Adapter is responsible for:

- validating canonical invocation inputs,

- resolving Provider-specific parameters,

- serialising requests,

- invoking the target through an approved Connection,

- preserving correlation identifiers,

- parsing responses,

- mapping lifecycle state,

- mapping errors,

- extracting usage,

- extracting Provider identifiers,

- normalising Outputs,

- and emitting evidence.

<a id="section-16-34"></a>
## 16.34 Adapter Non-Responsibility

An Adapter shall not:

- decide user intent,

- grant authority,

- select unrestricted Providers,

- increase Budget,

- lower classification,

- approve Outputs,

- create Agent identity,

- or hide external side effects.

<a id="section-16-35"></a>
## 16.35 Connector Responsibility

A Connector is responsible for defining:

- supported Capability mappings,

- required Connection properties,

- permitted protocol modes,

- operational maturity,

- policy restrictions,

- health checks,

- conformance expectations,

- and supported Adapter Versions.

<a id="section-16-36"></a>
## 16.36 Connector Non-Responsibility

A Connector shall not:

- own business logic,

- own Project memory,

- own Provider billing authority,

- or become the canonical source of Model identity.

<a id="section-16-37"></a>
## 16.37 Connection Responsibility

A Connection defines the exact configured path used for execution.

It shall identify or reference:

- Connector,

- Adapter Version,

- Provider Account,

- endpoint,

- Environment,

- region,

- Credential Reference,

- allowed Projects,

- allowed Capabilities,

- and lifecycle.

<a id="section-16-38"></a>
## 16.38 Connection Non-Responsibility

A Connection shall not contain:

- raw API key,

- raw password,

- payment-card data,

- unrestricted account session,

- or hidden cross-Project authority.

<a id="section-16-39"></a>
## 16.39 Integration Separation of Concerns

The canonical separation is:

Provider

offers a service.

Product

defines an offering.

Model or Tool

performs intelligence or action.

Deployment

places the resource.

Connector

defines the governed integration capability.

Adapter

translates canonical contracts.

Connection

configures one operational path.

Credential Reference

allows authorised authentication.

Routing Decision

selects the path.

Execution

uses the path.

Evidence

records what happened.

<a id="section-16-40"></a>
## 16.40 Capability Mapping

A Capability Mapping declares that a Connector and resource path can support one canonical Capability or Capability Version.

It shall include or reference:

- capabilityMappingId,

- Connector Version,

- canonical Capability,

- supported Features,

- constraints,

- implementation operation,

- maturity,

- evidence,

- and lifecycle.

<a id="section-16-41"></a>
## 16.41 Capability Mapping Identity

Every persistent Capability Mapping shall have stable identity and Version.

<a id="section-16-42"></a>
## 16.42 Exact Capability Mapping

An Exact Mapping supports the canonical Capability directly.

<a id="section-16-43"></a>
## 16.43 Composite Capability Mapping

A Composite Mapping satisfies one Capability through several implementation operations.

Material composition should normally be represented in the Plan rather than hidden inside the Adapter.

<a id="section-16-44"></a>
## 16.44 Approximate Capability Mapping

An Approximate Mapping does not fully implement the canonical Capability.

It shall be marked:

- degraded,

- conditional,

- experimental,

- or unsuitable for certain use.

<a id="section-16-45"></a>
## 16.45 Unsupported Capability

Unsupported Capability shall fail explicitly.

The Adapter shall not approximate silently.

<a id="section-16-46"></a>
## 16.46 Capability Version Mapping

A Connector may support:

- exact canonical Version,

- compatible Version range,

- or Provider-specific subset.

Compatibility shall be versioned.

<a id="section-16-47"></a>
## 16.47 Feature Mapping

A Feature Mapping relates canonical Features to implementation-specific options.

Examples include:

- tool calling,

- structured output,

- reference image,

- voice selection,

- streaming,

- seed,

- transparent background,

- or asynchronous callback.

<a id="section-16-48"></a>
## 16.48 Mandatory Feature Mapping

Mandatory Features shall map to verified implementation support.

An ignored or unsupported parameter shall not be represented as supported.

<a id="section-16-49"></a>
## 16.49 Optional Feature Mapping

Optional Features may be:

- omitted,

- downgraded,

- or emulated

only when the request permits it.

<a id="section-16-50"></a>
## 16.50 Feature Evidence

Feature support shall be based on:

- Provider documentation,

- conformance tests,

- production evidence,

- or verified manual procedure.

<a id="section-16-51"></a>
## 16.51 Feature Drift

Provider updates may change Feature behaviour.

Feature mappings shall be reviewed after material Provider change.

<a id="section-16-52"></a>
## 16.52 Parameter Mapping

A Parameter Mapping translates canonical execution parameters into implementation-specific values.

It shall include:

- canonical parameter,

- target field,

- conversion rule,

- default,

- valid range,

- omission behaviour,

- and Version.

<a id="section-16-53"></a>
## 16.53 Canonical Parameter

Canonical parameters express Fabric semantics.

Examples include:

- output format,

- maximum duration,

- quality tier,

- deterministic seed preference,

- response schema,

- reference Asset,

- or streaming preference.

<a id="section-16-54"></a>
## 16.54 Provider Parameter

Provider parameters remain implementation-specific.

They shall not leak into Project or Agent contracts unless explicitly pinned.

<a id="section-16-55"></a>
## 16.55 Parameter Default

Default values shall be explicit.

The Adapter shall distinguish:

- canonical default,

- Provider default,

- Connection default,

- and request-explicit value.

<a id="section-16-56"></a>
## 16.56 Provider Default Risk

Provider defaults may change.

Critical behaviour should not rely on undocumented defaults.

<a id="section-16-57"></a>
## 16.57 Parameter Validation

The Adapter shall validate ranges and combinations before dispatch where possible.

<a id="section-16-58"></a>
## 16.58 Parameter Rejection

Unsupported or unsafe parameters shall fail before Provider invocation.

They shall not be dropped silently.

<a id="section-16-59"></a>
## 16.59 Parameter Normalisation

Units may require conversion.

Examples include:

- milliseconds to seconds,

- pixels to aspect ratio,

- characters to Provider credits,

- or language code transformation.

<a id="section-16-60"></a>
## 16.60 Unit Preservation

Original canonical units and Provider units shall remain available in evidence.

<a id="section-16-61"></a>
## 16.61 Schema Mapping

A Schema Mapping translates between canonical and implementation-specific data structures.

It may apply to:

- request,

- response,

- callback,

- error,

- usage,

- Asset metadata,

- or Tool input.

<a id="section-16-62"></a>
## 16.62 Schema Mapping Version

Every material Schema Mapping shall be versioned.

<a id="section-16-63"></a>
## 16.63 Required Field Mapping

Every canonical mandatory field shall either:

- map directly,

- be derived transparently,

- be unavailable and reject the operation,

- or be satisfied elsewhere in the Plan.

<a id="section-16-64"></a>
## 16.64 Derived Field

A derived field shall preserve:

- derivation rule,

- source fields,

- confidence where relevant,

- and provenance.

<a id="section-16-65"></a>
## 16.65 Ignored Field

Ignored canonical fields shall be prohibited for mandatory semantics.

Optional ignored fields shall produce evidence or warning.

<a id="section-16-66"></a>
## 16.66 Unknown Provider Field

Unknown Provider fields shall not enter canonical objects without validation.

<a id="section-16-67"></a>
## 16.67 Schema Validation

Both outbound and inbound payloads shall be validated.

<a id="section-16-68"></a>
## 16.68 Provider Schema Drift

Unexpected schema changes shall produce:

- Adapter error,

- degraded state,

- Incident,

- or controlled compatibility handling.

They shall not be accepted silently.

<a id="section-16-69"></a>
## 16.69 Response Normalisation

Response Normalisation converts Provider output into canonical Output structures.

It shall preserve:

- Provider response ID,

- job ID,

- Model identity where known,

- timing,

- usage,

- finish reason,

- content,

- Asset references,

- warnings,

- and raw-evidence reference.

<a id="section-16-70"></a>
## 16.70 Output Type Mapping

The Adapter shall map Provider outputs to canonical types such as:

- Text Output,

- Structured Output,

- Code Output,

- Image Output,

- Audio Output,

- Video Output,

- Tool Result,

- Search Result,

- or External Action Result.

<a id="section-16-71"></a>
## 16.71 Output Type Integrity

A Provider response shall not be labelled as a canonical type when mandatory properties are missing.

<a id="section-16-72"></a>
## 16.72 Text Normalisation

Text normalisation may include:

- encoding,

- line endings,

- Unicode handling,

- and Provider wrapper removal.

It shall not rewrite meaning.

<a id="section-16-73"></a>
## 16.73 Structured Output Normalisation

Structured Outputs shall preserve:

- raw Provider text where relevant,

- parsed object,

- schema-validation result,

- and parse error.

<a id="section-16-74"></a>
## 16.74 Code Output Normalisation

Code output shall preserve:

- language,

- file context,

- patch format,

- and Provider metadata.

Code shall not be applied automatically by the Adapter.

<a id="section-16-75"></a>
## 16.75 Image Output Normalisation

Image output shall preserve:

- Provider Asset ID,

- URL or binary reference,

- dimensions,

- format,

- generation metadata,

- and expiry.

<a id="section-16-76"></a>
## 16.76 Audio Output Normalisation

Audio output shall preserve:

- format,

- sample rate,

- duration,

- channels,

- Voice Asset,

- and Provider metadata.

<a id="section-16-77"></a>
## 16.77 Video Output Normalisation

Video output shall preserve:

- duration,

- dimensions,

- frame rate where known,

- Provider job,

- Asset reference,

- and processing state.

<a id="section-16-78"></a>
## 16.78 Search Output Normalisation

Search output shall preserve:

- query,

- result identity,

- source URL or source reference,

- title,

- snippet,

- retrieval time,

- ranking,

- and Provider.

<a id="section-16-79"></a>
## 16.79 Tool Result Normalisation

Tool results shall preserve:

- Tool identity,

- Tool Version,

- input fingerprint,

- output,

- side effects,

- exit state,

- and logs reference.

<a id="section-16-80"></a>
## 16.80 Finish Reason Mapping

Provider finish reasons may include:

- completed,

- length limit,

- content filter,

- tool call,

- cancellation,

- error,

- or unknown.

They shall map to canonical state without losing Provider detail.

<a id="section-16-81"></a>
## 16.81 Provider Warning

Provider warnings shall be preserved.

Warnings may affect:

- quality,

- rights,

- safety,

- cost,

- or future availability.

<a id="section-16-82"></a>
## 16.82 Raw Response Preservation

The complete raw response may be retained as protected evidence when policy permits.

Canonical operation shall not depend on indefinite raw retention.

<a id="section-16-83"></a>
## 16.83 Raw Response Redaction

Secrets, tokens, personal data or restricted Provider fields may require redaction before evidence storage.

<a id="section-16-84"></a>
## 16.84 State Mapping

State Mapping converts implementation-specific lifecycle states into canonical Execution or Provider Job states.

It shall preserve both:

- canonical interpretation,

- and original external state.

<a id="section-16-85"></a>
## 16.85 Canonical Job States

Representative canonical states may include:

- submitted,

- accepted,

- queued,

- running,

- partially complete,

- succeeded,

- failed,

- cancelled,

- cancellation pending,

- expired,

- unknown,

- and reconciliation required.

<a id="section-16-86"></a>
## 16.86 Provider-Specific Job State

Provider state names shall be stored as evidence.

They shall not replace canonical state.

<a id="section-16-87"></a>
## 16.87 Ambiguous State Mapping

When a Provider state cannot be mapped safely, the canonical state shall be:

- unknown,

- unresolved,

- or provider-specific pending

rather than an invented completion.

<a id="section-16-88"></a>
## 16.88 Terminal State

A Provider terminal state does not automatically imply canonical Completion.

Required Output ingestion, cost, evaluation and verification may remain.

<a id="section-16-89"></a>
## 16.89 Cancellation Mapping

Cancellation states shall distinguish:

- cancellation requested,

- cancellation accepted,

- cancelled,

- and cancellation unknown.

<a id="section-16-90"></a>
## 16.90 Expired Provider Job

Provider expiry may mean:

- result deleted,

- job cancelled,

- status unavailable,

- or access expired.

The Adapter shall not assume one interpretation.

<a id="section-16-91"></a>
## 16.91 Error Mapping

An Error Mapping converts implementation-specific failures into canonical Error Classification.

It shall include:

- Provider error code,

- HTTP or protocol status,

- message pattern,

- canonical category,

- retryability,

- severity,

- and Version.

<a id="section-16-92"></a>
## 16.92 Error Mapping Identity

Every reusable Error Mapping shall have stable identity or versioned rule identity.

<a id="section-16-93"></a>
## 16.93 Authentication Error Mapping

Authentication failures shall remain distinct from:

- Account suspension,

- missing permission,

- expired session,

- and Provider outage.

<a id="section-16-94"></a>
## 16.94 Authorisation Error Mapping

Permission errors shall identify:

- Principal,

- Connection,

- Account,

- resource,

- and required scope where known.

<a id="section-16-95"></a>
## 16.95 Rate-Limit Error Mapping

2. Every Adapter release SHALL have an explicit Version.

3. Every Adapter SHALL reference a governed Connector.

4. Every Adapter SHALL identify its target Product, protocol, runtime or procedure.

5. Every Adapter SHALL translate canonical requests deterministically where practical.

6. Every Adapter SHALL validate mandatory canonical fields.

7. Every Adapter SHALL preserve request correlation.

8. Every Adapter SHALL preserve Provider or external identifiers.

9. Every Adapter SHALL normalise responses into canonical Output types.

10. Every Adapter SHALL map errors into canonical categories.

11. Every Adapter SHALL preserve Provider-native error evidence.

12. Every Adapter SHALL map usage where available.

13. Missing usage SHALL remain unknown.

14. Every Adapter SHALL preserve Adapter Version in execution evidence.

15. Adapters SHALL NOT own Agent identity.

16. Adapters SHALL NOT choose unrestricted fallback resources.

17. Adapters SHALL NOT grant authority.

18. Adapters SHALL NOT contain raw credentials.

19. Adapters SHALL NOT silently alter Capability meaning.

20. Historical Adapter Versions SHALL remain resolvable.

<a id="section-16-641"></a>
## 16.641 Closing Statement

The Adapter and Connector architecture is the boundary that allows Omnira to use many forms of intelligence without allowing any one Provider, protocol or tool to define the platform.

The Capability defines what must be achieved.

The Plan defines which bounded operation is required.

The Routing Decision selects an eligible resource path.

The Connector defines the governed integration capability.

The Connection identifies the exact operational target.

The Adapter translates canonical meaning into implementation-specific action.

The Provider, Tool, Runtime or human operator performs the work.

The Adapter translates the result back into canonical evidence.

The Asset system preserves durable Outputs.

The Cost system reconciles usage.

The Quality system determines acceptance.

The Reliability system handles uncertainty and recovery.

For Familje-Stunden, this architecture allows Nova and Pling production to combine:

- an external image Provider,

- an asynchronous video Provider,

- an approved voice service,

- local media tools,

- and human creative review

without embedding those Provider interfaces into the Project’s canonical design.

For The Prompt, it allows:

- current search,

- source retrieval,

- reasoning,

- voice,

- avatar,

- composition,

- and publication

to remain separate governed integrations.

For GainPilot, it allows economical local and external resources to be substituted without rewriting the Project’s workflows.

For Omnira, it allows:

- APIs,

- MCP,

- local Models,

- local Tools,

- webhooks,

- queues,

- browser-assisted systems,

- human-assisted Providers,

- and future Agent protocols

to coexist behind one canonical boundary.

The Provider may change.

The endpoint may change.

The SDK may change.

The protocol may change.

The Model may change.

The Provider Account may change.

The user’s intent and Omnira’s governance shall not.

No integration without a boundary.

No boundary without identity.

No Connection without scope.

No Adapter without Version.

No Capability claim without evidence.

No external action without authority.

No response without validation.

No Asset without provenance.

No manual work without truth.

The user retains control.

The Project retains its architecture.

Omnira retains canonical meaning.

The Fabric connects intelligence without becoming owned by its integrations.
