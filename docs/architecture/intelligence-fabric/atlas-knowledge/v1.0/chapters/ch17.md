# Chapter 17 — APIs, MCP, Webhooks and Asynchronous Jobs

<a id="section-17-1"></a>
## 17.1 Chapter Status

This chapter defines the canonical architecture, governance model, object model, lifecycle, contracts and operational responsibilities for APIs, Model Context Protocol integrations, webhooks, event delivery, polling, streaming and asynchronous jobs within the Omnira Intelligence Fabric.

It establishes:

- how synchronous and asynchronous integration patterns remain distinct,

- how API operations are described independently from Provider SDKs,

- how canonical request, response, command, event and callback envelopes are represented,

- how long-running Provider jobs are submitted, tracked, reconciled and completed,

- how polling and callbacks cooperate without duplicating state,

- how webhooks are authenticated, validated, deduplicated and ordered,

- how MCP servers, Tools, Resources and prompts remain governed external capabilities,

- how MCP discovery remains separate from MCP authority,

- how sessions, transports and server inventory changes are handled,

- how queue and event delivery semantics are represented truthfully,

- how at-least-once delivery is made safe through idempotency and deduplication,

- how correlation, causation, tracing and provenance cross protocol boundaries,

- how pagination, rate limits, quotas and backpressure are handled,

- how streaming results remain partial until finalisation,

- how asynchronous work survives worker, service and network failure,

- how unknown outcomes remain explicit,

- how callbacks and events remain subordinate to canonical state machines,

- how external payloads are treated as untrusted data,

- how Project, Tenant, Environment and authority scope remain preserved,

- how protocol versioning and schema evolution are governed,

- how APIs, MCP, webhooks and queues remain implementation mechanisms rather than business architecture,

- and how Stage 1 shall implement the smallest trustworthy protocol foundation.

An API response is not automatically an accepted Output.

A webhook is not automatically trusted.

A callback is not automatically unique.

A successful HTTP status is not automatically business success.

A timeout is not automatically Provider failure.

A queued external job is not automatically durable inside Omnira.

An MCP Tool is not automatically authorised because a server exposes it.

An event is not automatically current merely because it arrived later.

A retried message is not automatically a new logical operation.

A streaming fragment is not automatically a final result.

This chapter is normative after formal approval.

Credential, identity and secret mechanics are defined in Chapter 18.

Implementation and conformance must be verified separately.

<a id="section-17-2"></a>
## 17.2 Purpose of Protocol Governance

The Intelligence Fabric communicates with:

- external AI Providers,

- local Model runtimes,

- MCP servers,

- search services,

- media-generation platforms,

- repository systems,

- publication platforms,

- internal platform services,

- human-assisted procedures,

- queues,

- event buses,

- and future Agent protocols.

Those systems use different interaction patterns.

Some return immediately.

Some stream partial data.

Some create jobs that finish minutes or hours later.

Some send callbacks.

Some require polling.

Some expose discovered Tools.

Some deliver duplicate events.

Some lose callbacks.

Some return temporary Asset URLs.

Some change schemas without warning.

Some retry automatically.

Some provide incomplete usage or billing evidence.

The protocol architecture exists to ensure that these differences do not weaken:

- authority,

- policy,

- cost control,

- reliability,

- Project isolation,

- quality,

- provenance,

- or truthful state.

<a id="section-17-3"></a>
## 17.3 Protocol Is Not Capability

A protocol describes how communication occurs.

A Capability describes what can be achieved.

The same Capability may be accessed through:

- synchronous API,

- asynchronous API,

- streaming API,

- MCP Tool,

- local process,

- queue,

- browser-assisted procedure,

- or human-assisted operation.

The protocol shall not become the Capability identity.

<a id="section-17-4"></a>
## 17.4 Protocol Is Not Provider

One Provider may expose several protocols.

Several Providers may expose equivalent protocol patterns.

Protocol identity and Provider identity shall remain separate.

<a id="section-17-5"></a>
## 17.5 Protocol Is Not Authority

A technically callable endpoint does not create permission to use it.

A discovered MCP Tool does not create authority.

A valid webhook signature does not grant permission to perform a downstream action.

Authority remains governed by Omnira.

<a id="section-17-6"></a>
## 17.6 Protocol Is Not Completion

A transport-level success indicates only that one communication phase succeeded.

Canonical completion may still require:

- external processing,

- Output retrieval,

- Asset ingestion,

- usage capture,

- quality evaluation,

- approval,

- side-effect verification,

- and reconciliation.

<a id="section-17-7"></a>
## 17.7 Protocol Is Not Reliability

HTTP, WebSocket, MCP, queue and webhook mechanisms expose different reliability characteristics.

The protocol alone does not guarantee:

- delivery,

- ordering,

- uniqueness,

- durability,

- or completion.

- GET,

<a id="section-17-26"></a>
## 17.26 API Path

<a id="section-17-27"></a>
## 17.27 Read Operation

A Read Operation retrieves state without intended external mutation.

Read operations may still create:

- Provider usage,

- logs,

- rate-limit consumption,

- or data exposure.

<a id="section-17-28"></a>
## 17.28 Write Operation

A Write Operation creates or changes external state.

It requires explicit side-effect classification.

<a id="section-17-29"></a>
## 17.29 Delete Operation

A Delete Operation is consequential.

It shall require:

- exact target identity,

- authority,

- idempotency where possible,

- and verification.

<a id="section-17-30"></a>
## 17.30 Submission Operation

A Submission Operation sends work for immediate or deferred execution.

Provider acceptance does not imply completion.

<a id="section-17-31"></a>
## 17.31 Status Operation

A Status Operation retrieves current or historical state for an existing external job or object.

<a id="section-17-32"></a>
## 17.32 Cancellation Operation

A Cancellation Operation requests that external work stop.

Cancellation request and confirmed cancellation shall remain distinct.

<a id="section-17-33"></a>
## 17.33 Result Operation

A Result Operation retrieves the completed Output or references after external execution.

<a id="section-17-34"></a>
## 17.34 API Side-Effect Class

An API Operation shall declare whether it may:

- read,

- create,

- update,

- delete,

- publish,

- send,

- purchase,

- subscribe,

- unsubscribe,

- or execute code.

<a id="section-17-35"></a>
## 17.35 Safe Operation

A Safe Operation does not intend to alter external state.

Safe does not mean free of privacy or cost consequence.

<a id="section-17-36"></a>
## 17.36 Idempotent Operation

An idempotent operation may be repeated without creating additional unintended effect under defined conditions.

<a id="section-17-37"></a>
## 17.37 Non-Idempotent Operation

A non-idempotent operation may create repeated effects.

Retry requires stronger controls.

## 17.38 API Schema

## 17.43 API Versioning

## 17.45 Unversioned API

<a id="section-17-80"></a>
## 17.80 Event Immutability

<a id="section-17-81"></a>
## 17.81 Event Correction

A correction Event shall reference the Event or state it corrects.

<a id="section-17-82"></a>
## 17.82 Event Retraction

<a id="section-17-83"></a>
## 17.83 Event Completeness

An Event may provide:

- complete state,

- partial change,

- or notification requiring a follow-up read.

<a id="section-17-84"></a>
## 17.84 Notification Event

A notification Event indicates that something changed but may not contain authoritative state.

<a id="section-17-85"></a>
## 17.85 State-Carrying Event

<a id="section-17-86"></a>
## 17.86 Event Trust

External Events shall be treated as untrusted until:

- source is authenticated,

- schema is validated,

- scope is resolved,

- and semantic checks pass.

<a id="section-17-87"></a>

- correlationId,

- requestId,

- planId,

- stepId,

- executionId,

- attemptId,

- jobId,

- sessionId,

- and traceId.

<a id="section-17-88"></a>
## 17.88 Correlation Identity

Correlation identifiers shall remain stable across retries and callbacks where they represent the same logical operation.

<a id="section-17-89"></a>
## 17.89 Causation Context

Causation identifies which prior command, request, event or decision caused the current interaction.

<a id="section-17-90"></a>
## 17.90 Trace Context

Trace Context supports distributed observability.

Trace propagation shall not expose protected data.

<a id="section-17-91"></a>
## 17.91 External Correlation ID

Provider correlation identifiers shall be preserved exactly where supplied.

<a id="section-17-92"></a>
## 17.92 Correlation Loss

If an external callback lacks direct correlation, the system may resolve through:

- Provider job ID,

- Account,

- Asset ID,

- idempotency key,

- or controlled lookup.

Ambiguous correlation shall remain unresolved.

<a id="section-17-93"></a>
## 17.93 Synchronous API

A Synchronous API attempts to return its primary response during the initiating connection.

It is appropriate when:

- execution is short,

- response size is bounded,

- timeout risk is acceptable,

- and no long-lived Provider state is required.

<a id="section-17-94"></a>
## 17.94 Synchronous Request Lifecycle

Representative states include:

- prepared,

- dispatched,

- acknowledged,

- responding,

- received,

- parsed,

- failed,

- timed out,

- or unknown.

<a id="section-17-95"></a>
## 17.95 Synchronous Success

Synchronous success means the expected transport response arrived and passed protocol validation.

It does not automatically mean:

- Quality accepted,

- Asset durable,

- cost confirmed,

- or business complete.

<a id="section-17-96"></a>
## 17.96 Synchronous Timeout

Timeout after dispatch may create unknown outcome when the operation has side effects or Provider work may continue.

<a id="section-17-97"></a>
## 17.97 Synchronous Retry

Retry is permitted only when:

- operation semantics allow it,

- idempotency is preserved,

- Budget remains,

- and external completion ambiguity is resolved.

<a id="section-17-98"></a>
## 17.98 Long Work Through Synchronous API

Long-running work should not be forced through a synchronous connection merely for implementation convenience.

<a id="section-17-99"></a>
## 17.99 Asynchronous API

An Asynchronous API accepts work and returns an external job or operation reference before final completion.

<a id="section-17-101"></a>

<a id="section-17-102"></a>

- external response,

<a id="section-17-636"></a>
## 17.636 Closing Statement

APIs, MCP, webhooks, queues, streams and asynchronous jobs are the communication mechanisms through which the Intelligence Fabric reaches the systems that perform work.

They are not the architecture of intent.

They are not the source of authority.

They are not proof of quality.

They are not proof of completion.

The Capability Request defines what is needed.

The Plan defines what shall occur.

The Routing Decision selects an eligible resource path.

The Adapter translates canonical meaning.

The API Operation or MCP Invocation carries the request.

The Request Envelope preserves scope and identity.

The external system accepts, rejects or processes the work.

The Asynchronous Job preserves long-running state.

The callback, webhook, poll or stream provides new evidence.

The Event Envelope preserves what was observed.

The Queue preserves durable delivery where required.

The deduplication and idempotency systems prevent repeated harm.

The Asset system preserves durable Outputs.

The Quality system determines acceptance.

The Reliability system resolves uncertainty.

For Familje-Stunden, this architecture ensures that:

- Nova and Pling video jobs survive worker restarts,

- duplicate completion callbacks do not create duplicate Assets,

- temporary URLs are ingested before expiry,

- and Provider completion never bypasses character review.

For The Prompt, it ensures that:

- search responses remain source evidence rather than truth,

- scheduled publication callbacks are verified,

- and current-news Workflows do not publish from stale or uncorrelated Events.

For GainPilot, it allows batch production, voice generation and publication work to flow through bounded queues without duplicate spend or side effects.

For Omnira, it allows:

- synchronous text requests,

- asynchronous media jobs,

- local streaming Models,

- MCP repository Tools,

- webhook callbacks,

- event-driven Workflows,

- scheduled polling,

- and future Agent protocols

to coexist within one canonical execution model.

The API may return.

The callback may arrive.

The queue may redeliver.

The stream may break.

The MCP inventory may change.

The Provider may complete after Omnira timed out.

The Fabric must still know what it requested, what it observed, what it can prove and what remains unknown.

No API without a Contract.

No request without an Envelope.

No asynchronous job without durable identity.

No callback without validation.

No webhook without replay protection.

No poll without bounds.

No stream without finalisation.

No queue consumer without idempotency.

No MCP Tool without governed admission.

No Event without source, subject and Version.

No external delivery without canonical state validation.

The user retains authority.

The Project retains scope.

Omnira retains protocol truth.

The Fabric communicates across systems without surrendering control to the mechanisms of communication.
