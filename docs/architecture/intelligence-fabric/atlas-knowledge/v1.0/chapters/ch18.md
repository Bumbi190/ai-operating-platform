# Chapter 18 — Credentials, Identity and Secret Management

<a id="section-18-1"></a>
## 18.1 Chapter Status

This chapter defines the canonical identity, authentication, authorisation, Credential, Secret, Session, Account-binding and protected-access architecture for the Omnira Intelligence Fabric.

It establishes:

- how human, Agent, service, device, Tenant and Project identity remain distinct,

- how authentication remains separate from authorisation,

- how authorisation remains separate from Approval,

- how Credentials remain separate from authority,

- how Secrets remain separate from Credential metadata,

- how Provider Accounts remain separate from Credentials,

- how Connections bind Accounts, Credentials, Adapters and scope,

- how Agent identity remains Omnira-owned,

- how Agent identity survives Model, Provider and Runtime changes,

- how API keys, OAuth, Tokens, certificates, service Accounts, Sessions and browser credentials are represented,

- how raw Secret material is prevented from entering Agent context,

- how Secret values are resolved only at the appropriate execution boundary,

- how user-owned, Project-owned, Tenant-owned and Omnira-managed Credentials coexist,

- how local and remote workloads authenticate,

- how MCP, browser, webhook, queue, repository, database and publication identities are governed,

- how Credential lifecycle, rotation, revocation, expiry and compromise are handled,

- how privileged access is constrained,

- how break-glass and recovery access are represented,

- how environment separation is preserved,

- how service-to-service identity operates,

- how Credential usage becomes auditable without recording Secret values,

- how Stage 1 implements the minimum viable protected-access architecture,

- and how future workload identity and Secretless integration can evolve without weakening the canonical model.

The central doctrine is:

Credentials establish technical access.

Credentials do not create business authority.

Possession of a Credential does not mean an Agent is permitted to use it.

Possession of a Provider Account does not mean every Project may use it.

Successful authentication does not mean an operation is authorised.

Successful authorisation does not replace Approval where Approval is required.

A Secret is not identity.

A Token is not identity.

A Session is not identity.

An Account is not identity.

A Connection is not identity.

A Model is not Agent identity.

A Provider is not Agent identity.

No raw Secret material shall be required inside Atlas, another Agent, an Execution Plan, a prompt, Model context, queue message, ordinary Event, Memory Item or ordinary Execution Receipt.

Secret material shall be resolved as late as practical and as close as practical to the exact execution boundary that requires it.

This chapter is normative after formal approval.

<a id="section-18-2"></a>
## 18.2 Purpose

The Intelligence Fabric must interact with systems that require proof of identity and protected technical access.

Examples include:

- Model Providers,

- cloud platforms,

- local Nodes,

- databases,

- queues,

- repositories,

- publication platforms,

- MCP servers,

- browser Sessions,

- email Accounts,

- object storage,

- vector stores,

- webhook systems,

- payment or billing systems,

- and internal Omnira services.

Without a canonical identity and Secret architecture, Omnira could:

- leak API keys into prompts,

- store passwords in configuration,

- confuse Account ownership with Project permission,

- let one Project reuse another Project’s Credential,

- allow Atlas to learn raw Secret material,

- retain revoked Tokens in long-lived caches,

- silently use the wrong publication Account,

- restore compromised Credentials from backups,

- share personal browser Sessions with Project automation,

- or assume that technical access creates user authority.

The architecture exists to prevent those failures.

## 18.3 Identity

Identity is the canonical representation of who or what an actor is.

<a id="section-18-4"></a>
## 18.4 Principal

A Principal is a canonical identity capable of participating in authentication, authorisation, ownership, assignment or execution.

<a id="section-18-5"></a>
## 18.5 Principal Identity

Every Principal shall have stable canonical identity.

<a id="section-18-6"></a>
## 18.6 Principal Types

Canonical Principal types include:

- Human Principal,

- Service Principal,

- Agent Principal,

- Device Principal,

- External Principal,

- Tenant Principal,

- and Project Principal.

<a id="section-18-7"></a>
## 18.7 Human Principal

A Human Principal represents one person.

<a id="section-18-8"></a>
## 18.8 Service Principal

A Service Principal represents a non-human service or workload.

<a id="section-18-9"></a>
## 18.9 Agent Principal

An Agent Principal represents one persistent Omnira Agent identity.

<a id="section-18-10"></a>
## 18.10 Device Principal

A Device Principal represents a registered device or Runtime Node identity where authentication requires it.

<a id="section-18-11"></a>
## 18.11 External Principal

An External Principal represents an authenticated identity controlled outside Omnira.

<a id="section-18-12"></a>
## 18.12 Tenant Principal

A Tenant Principal may represent one Tenant as an authority or resource owner where appropriate.

<a id="section-18-13"></a>
## 18.13 Project Principal

A Project Principal may represent Project-owned automation or resources where appropriate.

<a id="section-18-14"></a>
## 18.14 Principal Versus User Account

A Principal is canonical identity.

A user Account on an external service is an External Identity or Provider Account binding.

<a id="section-18-15"></a>
## 18.15 Principal Stability

A Principal should survive changes to:

- email address,

- display name,

- Provider,

- Model,

- Runtime,

- device,

- and Session.

<a id="section-18-16"></a>
## 18.16 Principal Deletion

Deletion or deactivation of a Principal shall not erase historical accountability.

<a id="section-18-17"></a>
## 18.17 Principal Lifecycle

Principal states may include:

- proposed,

- active,

- suspended,

- disabled,

- revoked,

- departed,

- retired,

- and archived.

<a id="section-18-18"></a>
## 18.18 Principal Suspension

A suspended Principal shall not receive new authority or initiate new execution.

<a id="section-18-19"></a>
## 18.19 Principal Revocation

Revocation invalidates active access according to applicable Credential and Session semantics.

<a id="section-18-20"></a>
## 18.20 External Identity

An External Identity is an identity asserted by an external identity system.

<a id="section-18-21"></a>
## 18.21 External Identity Examples

Examples include:

- Google identity,

- Microsoft identity,

- GitHub identity,

- Provider user identity,

- cloud IAM identity,

- enterprise directory identity,

- and platform-specific operator identity.

<a id="section-18-22"></a>
## 18.22 External Identity Is Not Principal

An External Identity shall map to a Principal through an explicit Identity Binding.

<a id="section-18-23"></a>
## 18.23 Identity Binding

An Identity Binding links one canonical Principal to one external identity representation.

<a id="section-18-24"></a>
## 18.24 Identity Binding Identity

Every material Identity Binding shall have stable identity.

<a id="section-18-25"></a>
## 18.25 Identity Binding Fields

It should include:

- bindingId,

- Principal,

- issuer,

- subject identifier,

- External Identity,

- verification state,

- createdAt,

- lastVerifiedAt,

- lifecycle,

- and Version.

<a id="section-18-26"></a>
## 18.26 Identity Binding Uniqueness

One external identity subject shall not map ambiguously to several unrelated Principals.

<a id="section-18-27"></a>
## 18.27 Mutable External Labels

Email, display name and username shall not be used as immutable identity keys where stronger subject identifiers exist.

<a id="section-18-28"></a>
## 18.28 Identity Provider

An Identity Provider authenticates and asserts external identity.

<a id="section-18-29"></a>
## 18.29 Issuer Identity

Every accepted identity assertion shall identify its issuer.

<a id="section-18-30"></a>
## 18.30 Subject Identity

External authentication shall preserve the issuer-scoped subject identifier where available.

<a id="section-18-31"></a>
## 18.31 Authentication

Authentication determines whether an actor can prove control of an asserted identity or Credential.

<a id="section-18-32"></a>
## 18.32 Authentication Is Not Authorisation

Successful authentication does not imply permission to perform an operation.

<a id="section-18-33"></a>
## 18.33 Authentication Method

An Authentication Method describes how a Principal proves identity.

<a id="section-18-34"></a>
## 18.34 Authentication Method Types

Methods may include:

- password,

- passkey,

- hardware key,

- OTP,

- authenticator app,

- OAuth,

- OpenID Connect,

- certificate,

- SSH key,

- API key,

- workload identity,

- signed challenge,

- device key,

- and recovery method.

<a id="section-18-35"></a>
## 18.35 Authentication Method Identity

Every governed Authentication Method should have stable identity where persistent.

<a id="section-18-36"></a>
## 18.36 Authentication Strength

Authentication methods may carry assurance or strength metadata.

<a id="section-18-37"></a>
## 18.37 Authentication Strength Is Contextual

A method sufficient for ordinary read access may be insufficient for high-risk Credential or authority changes.

<a id="section-18-38"></a>
## 18.38 Step-Up Authentication

High-risk actions may require stronger or more recent authentication.

<a id="section-18-39"></a>
## 18.39 Reauthentication

Reauthentication may be required before:

- Credential export,

- break-glass activation,

- publication Account change,

- security-policy change,

- authority escalation,

- or destructive Secret operation.

<a id="section-18-40"></a>
## 18.40 Authentication Event

An Authentication Event records one authentication attempt or result.

<a id="section-18-41"></a>
## 18.41 Authentication Event Identity

Every material Authentication Event shall have stable identity.

<a id="section-18-42"></a>
## 18.42 Authentication Event Fields

It should include:

- authenticationEventId,

- Principal,

- issuer,

- method,

- time,

- result,

- assurance,

- Session,

- device or Node,

- and bounded failure metadata.

<a id="section-18-43"></a>
## 18.43 Authentication Failure

Authentication failure shall not reveal unnecessary sensitive detail to untrusted callers.

<a id="section-18-44"></a>
## 18.44 Authentication Logging

Authentication logs shall never contain passwords, private keys, raw Tokens or reusable Secret material.

<a id="section-18-45"></a>
## 18.45 Authorisation

Authorisation determines whether an authenticated Principal may perform one action within one scope.

<a id="section-18-46"></a>
## 18.46 Authorisation Is Not Authentication

Identity proof and permission Decision remain separate.

<a id="section-18-47"></a>
## 18.47 Authorisation Is Not Approval

A Principal may have general technical permission while still requiring user Approval for a specific consequential action.

<a id="section-18-48"></a>
## 18.48 Authorisation Decision

An Authorisation Decision determines whether one action is:

- allowed,

- denied,

- conditionally allowed,

- approval required,

- or indeterminate.

<a id="section-18-49"></a>
## 18.49 Authorisation Decision Identity

Every material Authorisation Decision should have stable identity.

<a id="section-18-50"></a>
## 18.50 Authorisation Decision Inputs

Inputs may include:

- Principal,

- Tenant,

- Project,

- action,

- target,

- Resource,

- Role,

- Grants,

- Mandates,

- Approval,

- Classification,

- Environment,

- time,

- and policy Version.

<a id="section-18-51"></a>
## 18.51 Default Deny

Access shall default to denied when required authority cannot be established.

<a id="section-18-52"></a>
## 18.52 Least Privilege

Every Principal shall receive only the minimum access required for the intended task.

<a id="section-18-53"></a>
## 18.53 Just-Enough Access

Privilege should be constrained to the exact operations required.

<a id="section-18-54"></a>
## 18.54 Just-In-Time Access

Elevated access should be issued near the time of use and expire quickly where practical.

<a id="section-18-55"></a>
## 18.55 Persistent Privilege

Long-lived high privilege shall be avoided.

<a id="section-18-56"></a>
## 18.56 Role

A Role groups intended responsibilities or permission patterns.

<a id="section-18-57"></a>
## 18.57 Role Identity

Every canonical Role shall have stable identity and Version.

<a id="section-18-58"></a>
## 18.58 Role Is Not Principal

A Role is assigned to a Principal.

It is not identity itself.

<a id="section-18-59"></a>
## 18.59 Role Is Not Approval

A Role does not replace action-specific Approval.

<a id="section-18-60"></a>
## 18.60 Role Assignment

Role assignment shall be attributable and scoped.

<a id="section-18-61"></a>
## 18.61 Role Scope

A Role may be scoped to:

- Tenant,

- Project,

- Environment,

- Resource class,

- or operation class.

<a id="section-18-62"></a>
## 18.62 Role Inheritance

Role inheritance shall be explicit and bounded.

<a id="section-18-63"></a>
## 18.63 Group

A Group is a collection of Principals for governance or access management.

<a id="section-18-64"></a>
## 18.64 Group Identity

Every governed Group shall have stable identity.

<a id="section-18-65"></a>
## 18.65 Membership

Membership links a Principal to a Group.

<a id="section-18-66"></a>
## 18.66 Membership Lifecycle

Membership shall have:

- effective time,

- expiry where applicable,

- state,

- and revocation.

<a id="section-18-67"></a>
## 18.67 Group Membership Is Not Universal Authority

Group access remains limited to the permissions assigned to the Group.

<a id="section-18-68"></a>
## 18.68 Authority Grant

An Authority Grant permits one Principal or group to perform defined actions within a defined scope.

<a id="section-18-69"></a>
## 18.69 Authority Grant Identity

Every Authority Grant shall have stable identity.

<a id="section-18-70"></a>
## 18.70 Grant Fields

A Grant should include:

- grantId,

- grantee,

- grantor,

- Tenant,

- Project,

- actions,

- Resources,

- conditions,

- effectiveAt,

- expiresAt,

- revocation,

- and Version.

<a id="section-18-71"></a>
## 18.71 Grant Scope

A Grant shall be as narrow as practical.

<a id="section-18-72"></a>
## 18.72 Grant Delegation

Delegation shall not exceed the delegator’s own authority.

<a id="section-18-73"></a>
## 18.73 Delegation

Delegation transfers bounded ability to act to another Principal.

<a id="section-18-74"></a>
## 18.74 Delegation Identity

Every material Delegation shall have stable identity.

<a id="section-18-75"></a>
## 18.75 Delegation Chain

The Fabric should be able to reconstruct the authority chain for material consequential actions.

<a id="section-18-76"></a>
## 18.76 Delegation Expiry

Delegated authority shall expire according to policy.

<a id="section-18-77"></a>
## 18.77 Delegation Revocation

Revocation shall stop future use and invalidate derived active access where practical.

<a id="section-18-78"></a>
## 18.78 Separation of Duties

Critical operations may require different Principals for:

- request,

- approval,

- execution,

- and review.

<a id="section-18-79"></a>
## 18.79 Dual Control

Selected high-risk actions may require two independent authorised Principals.

<a id="section-18-80"></a>
## 18.80 Self-Approval Prohibition

An Agent shall not create and approve its own authority expansion.

<a id="section-18-81"></a>
## 18.81 Credential

A Credential is an artefact or mechanism used to establish authenticated technical access.

<a id="section-18-82"></a>
## 18.82 Credential Is Not Identity

The Principal using a Credential remains distinct from the Credential itself.

<a id="section-18-83"></a>
## 18.83 Credential Is Not Authority

Possession of a Credential does not create business permission.

<a id="section-18-84"></a>
## 18.84 Credential Is Not Provider Account

A Credential may authenticate access to one Provider Account.

The Account remains a separate object.

<a id="section-18-85"></a>
## 18.85 Credential Is Not Secret

A Credential has identity, metadata and lifecycle.

Some Credentials contain or reference Secret material.

<a id="section-18-86"></a>
## 18.86 Credential Identity

Every governed Credential shall have stable canonical identity.

<a id="section-18-87"></a>
## 18.87 Credential Version

Credential rotation or material Secret replacement shall create or reference a Credential Version.

<a id="section-18-88"></a>
## 18.88 Credential Reference

A Credential Reference is a non-secret pointer to a governed Credential or current eligible Credential Version.

<a id="section-18-89"></a>
## 18.89 Credential Reference Safety

A Credential Reference may appear in:

- Connection metadata,

- Execution configuration,

- Plans,

- and audit

because it shall not contain the Secret value.

<a id="section-18-90"></a>
## 18.90 Credential Reference Resolution

Secret resolution shall occur only inside an approved execution or authentication boundary.

<a id="section-18-91"></a>
## 18.91 Credential Types

Canonical Credential types include:

- API Key Credential,

- OAuth Credential,

- Access Token Credential,

- Refresh Token Credential,

- Password Credential,

- Passkey Credential,

- Certificate Credential,

- SSH Credential,

- Signing Key Credential,

- Encryption Key Credential,

- Service Account Credential,

- Device Credential,

- Workload Identity Credential,

- Session Credential,

- Recovery Credential,

- and Break-Glass Credential.

<a id="section-18-92"></a>
## 18.92 Credential Owner

Every Credential shall identify an owner or controlling Principal.

<a id="section-18-93"></a>
## 18.93 Credential Custodian

A Credential Custodian is responsible for secure storage or operational maintenance.

<a id="section-18-94"></a>
## 18.94 Owner Versus Custodian

The owner determines legitimate use.

The custodian may manage Secret material operationally.

<a id="section-18-95"></a>
## 18.95 Credential Scope

Credential scope shall identify:

- Provider or system,

- Account,

- Tenant,

- Project,

- Environment,

- Resource,

- operations,

- and data where relevant.

<a id="section-18-96"></a>
## 18.96 Credential Sharing

Shared Credential use shall be explicit.

Implicit cross-Project sharing is prohibited.

<a id="section-18-97"></a>
## 18.97 Credential State

Credential states may include:

- proposed,

- active,

- rotating,

- expiring,

- expired,

- suspended,

- revoked,

- compromised,

- recovery-only,

- and archived.

<a id="section-18-98"></a>
## 18.98 Credential Active

Active means technically available subject to current authorisation.

<a id="section-18-99"></a>
## 18.99 Credential Expiring

Expiring indicates that renewal or rotation is required soon.

<a id="section-18-100"></a>
## 18.100 Credential Expired

Expired Credentials shall not authenticate new work.

<a id="section-18-101"></a>
## 18.101 Credential Suspended

Suspended Credentials shall not be resolved for new execution.

<a id="section-18-102"></a>
## 18.102 Credential Revoked

Revoked Credentials shall fail immediately for future resolution.

<a id="section-18-103"></a>
## 18.103 Credential Compromised

Compromised Credentials require urgent containment and replacement.

<a id="section-18-104"></a>
## 18.104 Credential Archive

Archived Credentials remain historical metadata only.

<a id="section-18-105"></a>
## 18.105 Credential Metadata

Credential metadata may include:

- credentialId,

- type,

- owner,

- custodian,

- Provider,

- Account,

- Environment,

- createdAt,

- expiresAt,

- rotation policy,

- Secret Store reference,

- state,

- and Version.

<a id="section-18-106"></a>
## 18.106 Secret

A Secret is confidential material whose disclosure could enable unauthorised access, impersonation, decryption, signing or privilege.

<a id="section-18-107"></a>
## 18.107 Secret Examples

Examples include:

- API key values,

- passwords,

- private keys,

- refresh Tokens,

- bearer Tokens,

- webhook signing Secrets,

- encryption keys,

- database passwords,

- session cookies,

- and recovery codes.

<a id="section-18-108"></a>
## 18.108 Secret Identity

A Secret may have stable metadata identity separate from its value.

<a id="section-18-109"></a>
## 18.109 Secret Value

The Secret value shall be treated as highly restricted data.

<a id="section-18-110"></a>
## 18.110 Secret Metadata

Secret metadata may be stored separately from the Secret value.

<a id="section-18-111"></a>
## 18.111 Secret Value Prohibition

Raw Secret values shall not be stored in:

- Agent Memory,

- prompt templates,

- Execution Plans,

- ordinary database records,

- Registry records,

- queue messages,

- Event payloads,

- ordinary logs,

- traces,

- analytics,

- screenshots,

- canonical Evidence summaries,

- source code,

- or documentation.

<a id="section-18-112"></a>
## 18.112 Secret Store

<a id="section-18-113"></a>
## 18.113 Secret Store Identity

Every production Secret Store shall have stable configuration identity.

<a id="section-18-114"></a>
## 18.114 Secret Store Responsibilities

The Secret Store shall support as applicable:

- encrypted storage,

- access control,

- versioning,

- audit,

- rotation,

- revocation,

- and short-lived retrieval.

<a id="section-18-115"></a>
## 18.115 Secret Store Non-Responsibilities

The Secret Store does not decide Project business authority.

<a id="section-18-116"></a>
## 18.116 Secret Encryption

Secrets shall be encrypted at rest according to Environment and threat model.

<a id="section-18-117"></a>
## 18.117 Secret Transport

Secrets shall use protected transport when crossing process or network boundaries.

<a id="section-18-118"></a>
## 18.118 Secret Access

Secret access shall require explicit authenticated workload identity.

<a id="section-18-119"></a>
## 18.119 Secret Access Scope

One workload shall receive only the Secret required for its exact operation.

<a id="section-18-120"></a>
## 18.120 Secret Resolution

Secret Resolution converts a Credential Reference into temporarily usable Secret material.

<a id="section-18-121"></a>
## 18.121 Resolution Boundary

Resolution shall occur at the narrowest practical boundary.

Examples include:

- Provider Adapter process,

- database Connector,

- publication Connector,

- webhook verifier,

- local Tool Runtime,

- or service client.

<a id="section-18-122"></a>
## 18.122 Just-In-Time Resolution

Secrets should be resolved immediately before use where practical.

<a id="section-18-123"></a>
## 18.123 Resolution Lifetime

Resolved Secret material shall remain available only as long as needed.

<a id="section-18-124"></a>
## 18.124 Resolution Cache

Temporary in-memory Secret caching may be permitted when:

- scope is narrow,

- lifetime is short,

- process is trusted,

- cache is non-persistent,

- and revocation can be respected.

<a id="section-18-125"></a>
## 18.125 Long-Lived Secret Cache

Long-lived caches of raw Secret material should be prohibited.

<a id="section-18-126"></a>
## 18.126 Secret Copy Minimisation

Secret values should be copied as few times as possible.

<a id="section-18-127"></a>
## 18.127 Secret Serialization

Secrets shall not be serialized into ordinary application state.

<a id="section-18-128"></a>
## 18.128 Secret Exception Handling

Errors involving Secret resolution shall not include the Secret value.

<a id="section-18-129"></a>
## 18.129 Secret Metrics

Metrics may record:

- resolution count,

- denial count,

- expiry,

- or latency.

They shall not record values.

<a id="section-18-130"></a>
## 18.130 Secret Trace

Tracing shall use Credential identity or reference, never the Secret itself.

<a id="section-18-131"></a>
## 18.131 Secret Lease

A Secret Lease grants temporary access to Secret material or temporary Credentials.

<a id="section-18-132"></a>
## 18.132 Secret Lease Identity

Every governed Secret Lease should have stable identity.

<a id="section-18-133"></a>
## 18.133 Secret Lease Fields

## 18.134 Dynamic Secret

A Dynamic Secret is generated on demand with bounded lifetime.

<a id="section-18-135"></a>
## 18.135 Dynamic Secret Preference

Dynamic Credentials are preferred over static long-lived Secrets where supported.

<a id="section-18-136"></a>
## 18.136 Secret Version

Secret values may have Versions for rotation.

<a id="section-18-137"></a>
## 18.137 Secret Version Identity

Every active Secret Version shall be distinguishable.

<a id="section-18-138"></a>

<a id="section-18-140"></a>

## 18.802 Closing Statement

Identity is the foundation of accountable execution.

Credentials are the technical mechanisms through which authenticated access becomes possible.

Secrets are the protected material that may enable those mechanisms.

Accounts define external ownership and service context.

Connections bind those Accounts to exact Credentials, Adapters, Environments and Projects.

Authority determines whether access may actually be exercised.

Approval determines whether a consequential action may proceed now.

These concepts must remain separate.

For Atlas, this means that Atlas can request intelligence without carrying API keys, passwords, Tokens or Provider Sessions in its reasoning context.

Atlas retains its own Omnira identity regardless of which Model, Provider or Runtime performs the work.

For Arnold, this means that switching between local and external Models does not change Arnold's identity, authority or Project boundaries.

For Familje-Stunden, this means that image, Voice, publication and creative-platform Accounts can remain isolated from private personal Accounts and from unrelated Projects.

For The Prompt, this means that research, generation and publishing may use several external services without giving any one Agent unrestricted Credential access.

For local intelligence, this means that Nodes, Runtimes and Tools authenticate as their own Principals while Local Only policy continues to govern where data may travel.

For Omnira-managed infrastructure, this means that centrally managed Provider access can serve several Projects while retaining Project attribution, isolation and user-visible governance.

The Principal identifies the actor.

The Authentication Method proves identity.

The Authorisation Decision establishes permission.

The Approval establishes bounded user authority where required.

The Credential establishes technical access.

The Secret Store protects Secret material.

The Credential Reference allows the Fabric to reason about access without carrying the Secret.

The Provider Account identifies the external service context.

The Connection binds that context to one exact Credential, Adapter, Environment and scope.

The Credential Use Record proves when protected access was exercised.

The Rotation Plan changes access material safely.

The Revocation Record terminates access.

The Compromise Record preserves security truth.

The Recovery Credential restores legitimate access.

The Break-Glass Grant handles exceptional emergency conditions without turning emergency privilege into normal operation.

No identity without a Principal.

No authentication without an issuer.

No authorisation without scope.

No Credential without ownership.

No Secret without protected storage.

No Connection without exact Account binding.
