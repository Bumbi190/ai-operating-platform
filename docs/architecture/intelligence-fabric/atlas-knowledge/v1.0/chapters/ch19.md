# Chapter 19 — Local, Private, Edge and Self-Hosted Intelligence

<a id="section-19-1"></a>
## 19.1 Chapter Status

This chapter defines the canonical architecture, governance model, object model, lifecycle, trust boundaries and conformance requirements for local, private, edge and self-hosted intelligence within the Omnira Intelligence Fabric.

It establishes:

- how local, private, edge, offline, on-premises and self-hosted execution remain distinct,

- how user-owned, Tenant-owned, Project-owned and Omnira-managed infrastructure coexist,

- how Runtime Nodes, execution environments, local Model Deployments and private Tools are represented,

- how placement policy selects where work may execute,

- how data custody and processing location remain explicit,

- how local execution remains subject to authority, policy, quality, cost and provenance,

- how Nodes are enrolled, identified, attested, restricted, suspended and retired,

- how Models, Tools and runtime packages are installed, verified, updated and removed,

- how local Model identity remains separate from filenames, aliases and runtime tags,

- how quantisation, fine-tuning, compilation and hardware configuration affect Deployment identity,

- how private and self-hosted resources enter the Capability, Model, Provider and execution-resource Registries,

- how hardware capacity, energy, thermal state, battery, memory, storage and network constraints influence execution,

- how local and edge work is scheduled without degrading the user’s device unexpectedly,

- how confidential and Local Only data is prevented from leaving approved boundaries,

- how offline execution and delayed synchronisation remain canonical,

- how local Assets, logs, caches, Model weights and temporary files are governed,

- how local Tools and runtimes are sandboxed,

- how distributed user-owned Nodes coordinate without becoming one unrestricted trust domain,

- how private clusters and cloud-hosted self-managed infrastructure remain distinguishable,

- how local failure, device loss, corruption and stale state are recovered,

- how local cost, energy and hardware depreciation remain visible,

- how private inference, local retrieval, embeddings, speech, vision and media processing are integrated,

- how local training, fine-tuning and adaptation remain governed,

- how future mobile, workstation, server and edge Nodes participate in Omnira,

- and how Stage 1 shall implement the smallest trustworthy local and private execution foundation.

Local is not automatically private.

Private is not automatically secure.

Self-hosted is not automatically user-owned.

User-owned is not automatically trusted.

Offline is not automatically authorised.

A local Model is still a Model resource.

A local Runtime is still an execution dependency.

A private Node is still subject to identity, policy, cost, quality and evidence.

A downloaded Model file is not automatically an admitted Model Version.

A runtime tag is not automatically canonical Model identity.

A machine that is online is not automatically ready.

A Node with technical access to data does not automatically have authority to process it.

This chapter is normative after formal approval.

Implementation and operational conformance must be verified separately.

<a id="section-19-2"></a>
## 19.2 Purpose of Local and Private Intelligence

Omnira shall support intelligence resources that do not depend exclusively on external managed Providers.

These resources may run on:

- the user’s laptop,

- a desktop workstation,

- a private GPU rig,

- a home server,

- a mobile device,

- a local network appliance,

- an organisation-owned server,

- an on-premises cluster,

- a dedicated hosted server,

- a self-managed cloud virtual machine,

- a confidential-compute environment,

- or a future edge device.

Local and private resources may provide:

- stronger data custody,

- lower marginal execution cost,

- reduced Provider dependence,

- offline capability,

- lower latency for some workloads,

- custom Model support,

- private retrieval,

- controlled Tool execution,

- hardware reuse,

- and continuity during external Provider disruption.

They may also create risks involving:

- insecure configuration,

- unpatched software,

- malicious Model packages,

- insufficient hardware,

- device loss,

- broad file access,

- cross-Project leakage,

- unavailable backups,

- inaccurate Model identity,

- poor quality,

- hidden energy cost,

- or unsupported operational burden.

The architecture exists to preserve the benefits without hiding the risks.

<a id="section-19-3"></a>
## 19.3 Local

Local means that execution occurs on a device or Node physically or logically controlled near the user or organisation.

Local may include:

- personal laptop,

- workstation,

- home server,

- local mobile device,

- or local network server.

Local does not necessarily mean:

- offline,

- isolated,

- user-owned,

- or safe.

<a id="section-19-4"></a>
## 19.4 Private

Private means that execution and data handling occur within a defined restricted trust and custody boundary.

A private boundary may be:

- one user device,

- one Tenant network,

- one isolated cluster,

- one dedicated hosted environment,

- or one confidential-compute boundary.

Private shall be defined through evidence and policy.

It shall not be inferred from marketing language.

<a id="section-19-5"></a>
## 19.5 Edge

Edge means execution occurs on or near the device, user, sensor, data source or operational environment that produces or consumes the data.

Edge execution may reduce:

- latency,

- network dependence,

- data transfer,

- and central infrastructure load.

Edge does not automatically mean Local Only.

<a id="section-19-6"></a>
## 19.6 Self-Hosted

Self-hosted means the user, Tenant, Project or Omnira operates the runtime or service rather than relying entirely on a Provider-managed execution service.

Self-hosted infrastructure may run:

- locally,

- on premises,

- in rented dedicated hardware,

- or in public cloud infrastructure.

Self-hosted does not necessarily mean user-owned hardware.

<a id="section-19-7"></a>
## 19.7 On-Premises

On-premises means infrastructure is operated within facilities or networks controlled by the user or organisation.

On-premises does not prove:

- security,

- isolation,

- maintenance,

- or data residency

without further evidence.

<a id="section-19-8"></a>
## 19.8 Offline

Offline means the Node can perform the defined work without an active external network connection.

Offline execution may still require:

- local credentials,

- cached policy,

- local Models,

- local data,

- and later synchronisation.

<a id="section-19-9"></a>
## 19.9 Air-Gapped

Air-gapped means the execution environment is deliberately isolated from ordinary network communication.

Air-gapped environments require controlled:

- import,

- export,

- update,

- evidence transfer,

- and recovery procedures.

<a id="section-19-10"></a>
## 19.10 Dedicated Hosted

Dedicated Hosted means infrastructure is rented from an external operator but dedicated to one user, Tenant or defined scope.

The hosting Provider remains part of the trust and physical control boundary.

<a id="section-19-11"></a>
## 19.11 Self-Managed Cloud

Self-Managed Cloud means the user, Tenant or Omnira operates software and execution policy on cloud infrastructure.

The cloud infrastructure Provider still controls underlying physical and virtualisation layers.

<a id="section-19-12"></a>
## 19.12 Confidential Compute

Confidential Compute uses hardware or platform mechanisms intended to protect data during processing.

Actual guarantees shall be evidenced through:

- supported hardware,

- attestation,

- threat model,

- key release policy,

- and implementation review.

<a id="section-19-13"></a>
## 19.13 Local Only

Local Only is a Data Classification and placement restriction.

It means data or work shall remain within approved local or private execution boundaries.

Local Only shall not be weakened automatically because a local resource is unavailable.

<a id="section-19-14"></a>
## 19.14 Private Routing Profile

The Private Routing Profile prefers or requires resources meeting defined custody and placement constraints.

Private is not merely a cost preference.

It may exclude otherwise superior external resources.

<a id="section-19-15"></a>
## 19.15 Execution Placement

Execution Placement determines the physical, virtual and trust location where work is performed.

Placement shall be:

- explicit,

- policy-conformant,

- attributable,

- and preserved in evidence.

<a id="section-19-16"></a>
## 19.16 Placement Is Not Routing Alone

Routing selects an eligible intelligence or execution resource.

Placement determines where that resource operates.

A Model may have several Deployments with different placement properties.

<a id="section-19-17"></a>
## 19.17 Placement Is Not Ownership

A user-owned Model Deployment may run on rented infrastructure.

A self-hosted service may run on Omnira-managed hardware.

Ownership and placement shall remain separate.

<a id="section-19-18"></a>
## 19.18 Placement Is Not Trust

A resource may be local but untrusted.

A remote dedicated Node may be approved for certain confidential work.

Trust shall be evaluated independently.

<a id="section-19-19"></a>
## 19.19 Placement Is Not Data Classification

Data Classification defines protection requirements.

Placement Policy determines which locations satisfy them.

<a id="section-19-20"></a>
## 19.20 Local Execution Is Not Governance Bypass

Local resources shall still require:

- Capability eligibility,

- Model or Tool registration,

- authority,

- Budget where applicable,

- scheduling,

- evidence,

- evaluation,

- and Incident handling.

## 19.23 Execution Zone

An Execution Zone is a governed location or infrastructure boundary in which work may execute.

Examples include:

- user laptop zone,

- private workstation zone,

- home-server zone,

- mobile-device zone,

- Tenant on-premises zone,

- dedicated-hosting zone,

- self-managed cloud zone,

- confidential-compute zone,

- and external managed Provider zone.

<a id="section-19-783"></a>
## 19.783 Closing Statement

Local, private, edge and self-hosted intelligence allow Omnira to use compute that is closer to the user, more private, more controllable and less dependent on external managed Providers.

Those benefits exist only when the local boundary is represented truthfully.

The Execution Zone defines where work may occur.

The Placement Policy defines where it is permitted to occur.

The Runtime Node defines the machine or virtual environment.

The Node Trust Profile defines what may be trusted about it.

The Runtime Deployment defines the software that executes work.

The Local Model Package defines the verified Model artefacts.

The Model Deployment defines the exact Model, package, Runtime, Node and configuration.

The Tool Deployment defines the local operation and its permissions.

The Sandbox limits access.

The Scheduler allocates bounded capacity.

The Resource Lease protects ownership of scarce hardware.

The Local Execution Receipt preserves what happened.

The Synchronisation Record reconciles offline and connected state.

The Quality system determines whether the Output is acceptable.

The Cost system preserves the real economic impact.

The Incident system handles compromise, loss and failure.

For Familje-Stunden, this architecture allows:

- local page composition,

- local media processing,

- private storage of Nova and Pling Assets,

- local review tools,

- and private drafting

without exposing Project data unnecessarily or bypassing final quality review.

For The Prompt, it allows:

- private archives,

- local semantic search,

- local script drafting,

- and local media processing

while preserving the need for current external source verification.

For GainPilot, it allows:

- local structured content generation,

- economical batch drafting,

- private user-data analysis,

- and local embeddings

without turning private health and training data into shared Provider context.

For Omnira, it allows:

- laptops,

- workstations,

- mobile devices,

- private GPU rigs,

- home servers,

- dedicated hosted Nodes,

- self-managed cloud infrastructure,

- local Model runtimes,

- private Tools,

- offline work,

- and future federated devices

to participate in one governed Intelligence Fabric.

The hardware may belong to the user.

The Runtime may be open source.

The Model may be downloaded.

The Node may be offline.

The data may remain private.

The execution must still have identity, authority, policy, evidence and quality.

No local execution without a Node.

No Node without identity.

No private placement without policy.

No Model Deployment without package provenance.

No Tool without bounded permissions.

No offline work without expiring authority.

No synchronisation without conflict handling.

No Local Only fallback to external processing.

No private claim without evidence.

No self-hosting without operational responsibility.

The user retains custody.

The Project retains isolation.

Omnira retains governance.

The Fabric brings intelligence closer to the user without allowing proximity to replace trust.
