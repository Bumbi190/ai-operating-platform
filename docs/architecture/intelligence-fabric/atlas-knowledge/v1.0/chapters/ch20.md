# Chapter 20 — Multimodal Production Architecture

<a id="section-20-1"></a>
## 20.1 Chapter Status

This chapter defines the canonical architecture, governance model, object model, lifecycle, planning semantics, quality boundaries and conformance requirements for multimodal production within the Omnira Intelligence Fabric.

It establishes:

- how text, image, audio, voice, music, video, animation, document and interactive media production coexist,

- how multimodal production remains Capability-driven and Provider-independent,

- how creative intent is translated into structured Production Specifications,

- how canonical Assets, references, characters, Voices, styles, scenes, timelines and compositions are represented,

- how generation, transformation, editing, assembly, rendering, review and publication remain distinct operations,

- how multimodal Plans become explicit Production Graphs,

- how reference Assets guide identity, style, composition and continuity,

- how character and visual identity remain stable across generated outputs,

- how voice identity, pronunciation, timing and consent remain governed,

- how image, video, audio and document variants are generated and compared,

- how asynchronous Provider jobs and local processing coexist,

- how intermediate Outputs remain distinct from accepted Assets,

- how deterministic and stochastic stages are represented,

- how creative iteration remains bounded by Budget, quality and approval,

- how multimodal quality is evaluated through modality-specific and cross-modal criteria,

- how continuity is maintained across scenes, pages, episodes, campaigns and Projects,

- how technical specifications such as dimensions, duration, codecs, loudness, frame rate and file formats are enforced,

- how rights, licences, attribution, consent and provenance remain attached throughout production,

- how child-facing, public-facing and brand-sensitive content receives stronger review,

- how local, private and external resources are combined without hidden data movement,

- how publication packages are assembled without bypassing final approval,

- how failed or partial media jobs are recovered,

- how multimodal production integrates with Assets, Registries, Scheduling, Cost, Quality, Memory and the Intelligence Graph,

- and how Stage 1 shall implement the smallest trustworthy multimodal production foundation.

A generated Output is not automatically an Asset.

An Asset is not automatically approved.

A reference image is not automatically consent.

A Provider preset is not automatically a canonical style.

A character name is not automatically character identity.

A Voice ID is not automatically voice ownership.

A successful render is not automatically production completion.

A technically valid file is not automatically creatively acceptable.

A scene that looks correct in isolation is not automatically continuous with the surrounding work.

A Provider project or workspace is not automatically the canonical Production Project.

A multimodal pipeline shall not hide which steps were human-assisted.

This chapter is normative after formal approval.

Asset rights, provenance, consent and ownership are expanded in Chapter 21.

Implementation and conformance must be verified separately.

<a id="section-20-2"></a>
## 20.2 Purpose of Multimodal Production Architecture

Omnira Projects may produce:

- written content,

- structured data,

- illustrations,

- photographs,

- diagrams,

- voice narration,

- sound effects,

- music,

- video,

- animation,

- social-media clips,

- printable documents,

- ebooks,

- web graphics,

- application Assets,

- and composite publication packages.

These Outputs often require several intelligence and Tool resources.

A single finished video may require:

- script generation,

- factual review,

- scene planning,

- image generation,

- image selection,

- character consistency review,

- animation,

- voice synthesis,

- audio cleaning,

- music selection,

- subtitle generation,

- composition,

- rendering,

- quality review,

- and publication packaging.

Without a canonical multimodal architecture, each Project would become dependent on:

- one Provider’s workspace model,

- one editor’s file naming,

- one Tool’s timeline format,

- one image generator’s prompt language,

- or one person’s memory of prior creative decisions.

The architecture exists to make multimodal production:

- repeatable,

- explainable,

- Provider-independent,

- quality-governed,

- rights-aware,

- recoverable,

- and suitable for increasing automation.

<a id="section-20-3"></a>
## 20.3 Multimodal Production

Multimodal Production is the governed process of creating, transforming, combining, evaluating and delivering Outputs involving one or more media modalities.

It may contain:

- one modality,

- several coordinated modalities,

- or a composite deliverable.

<a id="section-20-4"></a>
## 20.4 Modality

A Modality is a canonical category of content representation.

Canonical modalities may include:

- text,

- structured data,

- code,

- image,

- document,

- audio,

- voice,

- music,

- video,

- animation,

- three-dimensional content,

- interactive content,

- and mixed media.

<a id="section-20-5"></a>
## 20.5 Primary Modality

The Primary Modality is the dominant form of the final deliverable.

Examples include:

- video for a reel,

- document for a printable activity,

- image for a social post,

- audio for a narrated story,

- or interactive media for an application experience.

<a id="section-20-6"></a>
## 20.6 Supporting Modality

A Supporting Modality contributes to the final deliverable.

Examples include:

- script supporting video,

- narration supporting animation,

- subtitles supporting audio,

- reference images supporting image generation,

- or metadata supporting publication.

<a id="section-20-7"></a>
## 20.7 Composite Deliverable

A Composite Deliverable contains several coordinated Assets.

Examples include:

- video plus thumbnail plus caption,

- PDF plus cover image plus preview images,

- audio story plus transcript plus chapter markers,

- social campaign package,

- or application media bundle.

<a id="section-20-8"></a>
## 20.8 Production Project

A Production Project is a governed creative-production context within an Omnira Project.

It may represent:

- one book,

- one episode,

- one campaign,

- one monthly theme,

- one video series,

- one application release,

- or one publication package.

<a id="section-20-9"></a>
## 20.9 Production Project Identity

Every persistent Production Project shall have stable canonical identity.

<a id="section-20-10"></a>
## 20.10 Production Project Scope

A Production Project shall identify:

- Tenant,

- Omnira Project,

- owner,

- audience,

- purpose,

- brand or creative system,

- deliverables,

- schedule,

- Budget,

- rights context,

- and lifecycle.

<a id="section-20-11"></a>
## 20.11 Production Project Is Not Provider Workspace

A Provider workspace may support execution.

It shall not replace the canonical Production Project.

<a id="section-20-12"></a>
## 20.12 Production Unit

A Production Unit is one bounded creative item inside a Production Project.

Examples include:

- scene,

- page,

- exercise animation,

- reel,

- audio chapter,

- thumbnail,

- or publication post.

<a id="section-20-13"></a>
## 20.13 Production Unit Identity

Every governed Production Unit shall have stable identity.

<a id="section-20-14"></a>
## 20.14 Production Batch

A Production Batch groups several compatible Production Units for coordinated execution.

Batching may improve:

- consistency,

- cost,

- throughput,

- Model warmth,

- and review efficiency.

<a id="section-20-15"></a>
## 20.15 Batch Identity

Every material Production Batch shall have stable identity.

<a id="section-20-16"></a>
## 20.16 Production Version

A Production Version is one immutable material state of a Production Unit or Deliverable.

Material changes shall create a new Version.

<a id="section-20-17"></a>
## 20.17 Draft

A Draft is an incomplete or unaccepted Production Version.

<a id="section-20-18"></a>
## 20.18 Candidate

A Candidate is a Production Version eligible for comparison or review.

<a id="section-20-19"></a>
## 20.19 Selected Candidate

A Selected Candidate has been chosen for further production.

Selection does not automatically mean final acceptance.

<a id="section-20-20"></a>
## 20.20 Accepted Version

An Accepted Version satisfies the applicable Quality and Approval Contracts.

<a id="section-20-21"></a>
## 20.21 Final Version

A Final Version is the accepted version designated for delivery or publication.

Final does not mean immutable forever.

Corrections require a new Version.

## 20.29 Brief Versus Script

<a id="section-20-30"></a>

It does not redefine the entire style unless explicitly Versioned.

An Audience Profile describes intended consumers of the content.

- age group,

- language,

- literacy,

- cultural context,

- accessibility needs,

- platform,

- and sensitivity.

<a id="section-20-32"></a>
## 20.32 Audience Profile Identity

Every reusable Audience Profile shall have stable identity and Version.

## 20.33 Child-Facing Audience

Child-facing production requires stronger controls for:

- safety,

- age appropriateness,

- clarity,

- privacy,

- emotional tone,

- and advertising boundaries.

<a id="section-20-34"></a>
## 20.34 Public Audience

Public-facing content requires review for:

- factual accuracy,

- rights,

- brand,

- privacy,

- and reputational consequence.

<a id="section-20-35"></a>
## 20.35 Internal Audience

Internal content may still contain confidential or strategic data.

- visual motifs,

- tone,

<a id="section-20-37"></a>
## 20.37 Brand System Identity

Every Brand System shall have stable identity and Version.

- wordmark,

- template,

- type treatment,

- approved colour palette,

- title placement,

- or prohibited distortion.

- camera language,

## 20.44 Style Description

- line,

- texture,

- lighting,

A Production Incident is a material production failure affecting:

- safety,

- rights,

- data,

- cost,

- publication,

- identity,

- or operational integrity.

<a id="section-20-623"></a>
## 20.623 Production Incident Examples

Examples include:

- wrong Character published,

- wrong Account used,

- private reference leaked,

- invalid rights,

- duplicate publication,

- runaway generation cost,

- or corrupted Master Asset.

<a id="section-20-624"></a>
## 20.624 Security

Multimodal production processes untrusted Inputs and complex files and shall apply security controls throughout the pipeline.

<a id="section-20-625"></a>
## 20.625 Untrusted Media

Uploaded or Provider-generated files shall be treated as untrusted until validated.

<a id="section-20-626"></a>
## 20.626 File Validation

Validation may include:

- content-type verification,

- size,

- dimensions,

- codec,

- decompression limits,

- and malware scanning where applicable.

<a id="section-20-627"></a>
## 20.627 Malicious Metadata

Embedded metadata shall not be treated as trusted instructions.

<a id="section-20-628"></a>
## 20.628 Prompt Injection in References

Text embedded in documents, webpages or images shall not override Fabric policy.

<a id="section-20-629"></a>
## 20.629 Tool Injection

Generated files shall not automatically trigger scripts, macros or external actions.

<a id="section-20-630"></a>
## 20.630 Document Macro

Macro-enabled documents require explicit handling policy.

<a id="section-20-631"></a>
## 20.631 SVG Security

SVG and other active formats may contain scripts or external references and require safe processing.

<a id="section-20-632"></a>
## 20.632 Media Parser Risk

Complex codecs and parsers should run inside appropriately isolated execution boundaries.

<a id="section-20-633"></a>
## 20.633 External URL Fetch

<a id="section-20-634"></a>
## 20.634 Reference URL Expiry

The following requirements define Multimodal Production:

1. Every governed Production Project SHALL have stable identity.

2. every material Production Unit SHALL have stable identity.

3. every executable Production Specification SHALL have Version.

4. Creative Brief SHALL remain distinct from Provider prompt.

5. Provider prompt SHALL derive from canonical requirements.

6. every generated Candidate SHALL have provenance.

7. Character identity SHALL remain canonical and Provider-independent.

8. Voice identity SHALL remain canonical and Provider-independent.

9. references SHALL use exact Asset Versions.

10. reference use SHALL remain rights- and Consent-governed.

11. Generation, Transformation, Composition, Render, Acceptance and Publication SHALL remain distinct.

12. Production Graph dependencies SHALL be explicit.

13. iterations SHALL remain bounded.

14. Quality SHALL be evaluated before acceptance.

15. accepted Assets SHALL remain Version-specific.

16. composite Assets SHALL preserve source lineage.

17. Packages SHALL contain exact Asset Versions.

18. publication SHALL remain separately authorised.

19. human-assisted Steps SHALL remain truthful.

20. Multimodal production SHALL remain Provider-independent above Adapter boundaries.

<a id="section-20-740"></a>

1. Every governed Character SHALL have stable identity.

2. material design changes SHALL create Character Version.

3. Character Reference Sets SHALL be Versioned.

4. recurring production SHALL reference exact Character Version.

5. Provider prompts SHALL NOT become Character identity.

6. Character names SHALL NOT substitute for references where visual continuity matters.

7. every governed Voice SHALL have stable identity.

8. material Voice changes SHALL create Voice Version.

9. Provider Voice IDs SHALL remain mappings.

10. Voice use SHALL preserve rights and Consent.

11. Voice cloning SHALL require explicit authority.

12. Character and Voice continuity SHALL be evaluated.

13. drift SHALL be recorded.

14. mandatory identity failure SHALL block acceptance.

15. Character Assets SHALL remain Project-scoped unless reuse is authorised.

16. Voice Assets SHALL remain Project-scoped unless reuse is authorised.

17. Model change SHALL NOT change canonical Character identity.

18. Provider change SHALL NOT change canonical Voice identity automatically.

19. historical production SHALL preserve the Versions actually used.

20. Creative identity SHALL remain owned by the Project rather than the Provider.

19. historical acceptance Decisions SHALL remain preserved.

20. Quality SHALL NOT be inferred solely from Provider reputation or technical success.

## 20.746 Closing Statement

Multimodal production is where intelligence becomes visible, audible, interactive and publishable.

It is also where weak architecture becomes expensive.

A single creative deliverable may pass through:

- Scripts,

- references,

- Models,

- Providers,

- human operators,

- generation systems,

- editing systems,

- local Tools,

- Voice services,

- renderers,

- evaluation systems,

- Asset stores,

- and publication platforms.

Without canonical structure, every one of those systems can become an accidental source of truth.

The Creative Brief preserves intent.

The Audience Profile defines who the production exists for.

The Brand System preserves Project identity.

The Style System preserves recurring creative language.

The Character Definition preserves recurring visual identity.

The Voice Definition preserves recurring spoken identity.

The Production Specification converts creative intent into an executable canonical contract.

The Prompt Specification translates that contract toward generative resources without making prompts the owner of creative truth.

The Production Graph makes dependencies explicit.

The Candidate Set makes stochastic generation reviewable.

The Selection Decision makes creative choice attributable.

The Continuity Profile and Continuity Ledger preserve identity and state across scenes, pages, episodes and campaigns.

The Timeline and Composition make multimodal assembly explicit.

The Render Profile makes technical delivery reproducible.

The Quality system determines whether an Output is actually suitable.

The Revision architecture allows defects to be corrected without destroying accepted work.

The Asset system makes temporary Provider results durable.

The provenance system preserves how each Asset came into existence.

The rights and Consent systems determine whether an Asset may be used.

The Production Package binds exact approved Asset Versions for delivery.

The Publication Handoff preserves the boundary between production and consequence.
