# Chapter 23 — Data Classification, Privacy and Isolation

<a id="section-23-1"></a>
## 23.1 Chapter Status

This chapter defines the canonical architecture, object model, policy hierarchy, lifecycle, enforcement boundaries and conformance requirements for data classification, privacy and isolation within the Omnira Intelligence Fabric.

It establishes:

- how every meaningful data object receives a governed protection state,

- how Public, Project Internal, Confidential, Local Only and Prohibited classifications are defined and enforced,

- how data category, sensitivity, classification, handling policy and legal status remain distinct,

- how classification is assigned automatically and tightened by authorised humans,

- how the Fabric is prohibited from lowering classification without explicit authority and evidence,

- how classification propagates through derived data, embeddings, summaries, caches, logs, prompts, Outputs, Assets and Memory,

- how aggregated information may become more sensitive than its individual Inputs,

- how declassification, redaction, anonymisation and disclosure decisions remain governed,

- how purpose limitation and data minimisation constrain collection, processing, storage and retrieval,

- how personal, family, child, health, financial, biometric, location, communication and Credential-related data receive stronger controls,

- how private messages and private correspondence remain outside general Agent access,

- how raw Secrets, passwords, Tokens and private keys remain prohibited from ordinary Model context and Memory,

- how user, Project, Tenant, Agent, Workflow, environment, Node, Provider, Account, storage, cache, index and Memory isolation remain explicit,

- how Tenant and Project boundaries are enforced before routing, retrieval and execution,

- how local execution differs from Local Only classification,

- how data residency, custody, processing location and storage location remain distinct,

- how cross-boundary transfer, Provider upload, remote execution, backup and synchronisation are controlled,

- how access remains purpose-, capability-, role-, Project-, data-type-, device- and time-bounded,

- how privacy-preserving transformation is represented and verified,

- how pseudonymisation differs from anonymisation,

- how re-identification risk is assessed,

- how telemetry, observability, logs, traces, evidence and analytics remain privacy-governed,

- how consent, rights, authority, privacy and classification interact without collapsing into one concept,

- how deletion, retention, revocation and restoration preserve current privacy state,

- how privacy incidents, isolation failures and cross-Project leakage are contained and investigated,

- how Stage 1 shall implement the smallest trustworthy classification, privacy and isolation foundation,

- and how future multi-Tenant growth shall preserve the same canonical guarantees.

Classification is not consent.

Consent is not access authority.

Access authority is not ownership.

Ownership is not permission for every processing purpose.

Privacy is not secrecy alone.

Encryption is not isolation by itself.

Local execution is not automatically Local Only.

Publicly available data is not automatically Public within Omnira.

A redacted copy is not automatically anonymous.

A pseudonym is not anonymity.

An embedding is not non-sensitive merely because it cannot be read directly.

A summary may remain as sensitive as its source.

A log may contain more private data than the operation it describes.

A shared database is not a shared trust domain.

A filtered query is not sufficient Tenant isolation unless enforcement is structural and verified.

An administrator role does not automatically permit unrestricted content access.

A Model context window is a temporary disclosure boundary.

A Provider Account is a custody and policy boundary.

A backup is another copy of the data.

A deleted index entry is not proof that all data copies are deleted.

This chapter is normative after formal approval.

Approval, authority and bounded autonomy are expanded in Chapter 24.

Observability, audit and Incident Response are expanded in Chapter 25.

Implementation, legal applicability and operational conformance must be verified separately.

<a id="section-23-2"></a>
## 23.2 Purpose of Data Classification, Privacy and Isolation

Omnira coordinates intelligence across:

- users,

- Projects,

- Tenants,

- Agents,

- Models,

- Providers,

- Accounts,

- Devices,

- local Nodes,

- cloud services,

- Tools,

- Connectors,

- Assets,

- Memory,

- and external systems.

Those systems may process:

- public source material,

- internal Project plans,

- private family information,

- children’s images,

- training and health records,

- financial information,

- business strategy,

- unpublished media,

- source code,

- Credentials,

- personal communications,

- location information,

- Voice recordings,

- biometric-like identifiers,

- legal documents,

- and confidential customer data.

Without canonical classification and isolation, the Fabric could:

- send Local Only material to an external Provider,

- retrieve one Project’s Memory into another Project,

- expose a family image to a business Agent,

- place raw Credentials in a Model prompt,

- preserve private data in logs after the source was deleted,

- infer sensitive traits and retain them without authority,

- reuse embeddings across Tenants,

- restore revoked data from backup,

- allow one Provider Account to mix several Project libraries,

- or treat administrative convenience as permission.

The architecture exists to ensure that every processing operation can answer:

- What data is involved?

- Which classification applies?

- Which categories and subjects are represented?

- Which purpose permits processing?

- Which Principal, Agent and Project are acting?

- Which Capabilities are required?

- Which environments, Nodes, Providers and Accounts are eligible?

- Where may the data be processed?

- Where may it be stored?

- How long may it remain?

- Which transformations are permitted?

- Which disclosure or transfer is occurring?

- Which evidence supports the Decision?

- Which obligations apply after deletion, revocation or policy change?

<a id="section-23-6"></a>
## 23.6 Classification

Classification is the governed protection level assigned to data according to sensitivity, harm potential, privacy, contractual obligations, policy and intended use.

<a id="section-23-7"></a>
## 23.7 Classification Is Not Data Type

An image may be Public, Confidential or Local Only.

A data type does not determine one universal classification.

<a id="section-23-8"></a>
## 23.8 Classification Is Not Category

Health data is a Data Category.

Confidential may be its Classification.

The two shall remain distinct.

<a id="section-23-9"></a>
## 23.9 Classification Is Not Access Control

Classification defines required protection.

Access Control determines which Principal may perform which action.

<a id="section-23-10"></a>
## 23.10 Classification Is Not Location

Classification may constrain placement.

It does not itself identify where the data is stored.

<a id="section-23-11"></a>
## 23.11 Classification Is Not Encryption

Encryption is one control used to enforce classification requirements.

<a id="section-23-12"></a>
## 23.12 Privacy

Privacy is the governed protection of people, relationships, communications, behaviour, identity and personal context from unnecessary collection, use, disclosure, inference, retention or control.

<a id="section-23-13"></a>
## 23.13 Isolation

Isolation is the enforced separation of data, execution, identity, storage, Memory, Credentials and authority across defined boundaries.

<a id="section-23-14"></a>
## 23.14 Data Boundary

## 23.15 Privacy Boundary

## 23.16 Trust Boundary

## 23.17 Isolation Boundary

<a id="section-23-20"></a>
## 23.20 Canonical Classification Levels

The canonical Data Classification levels are:

1. Public.

2. Project Internal.

3. Confidential.

4. Local Only.

5. Prohibited.

<a id="section-23-21"></a>
## 23.21 Classification Ordering

The canonical levels form an increasing protection ordering for default enforcement:

Public

less restrictive than:

Project Internal

less restrictive than:

Confidential

less externally transferable than:

Local Only.

Prohibited is not merely a higher secrecy level.

It represents data or processing that is disallowed under the applicable policy.

<a id="section-23-22"></a>
## 23.22 Classification Precedence

When several classifications apply, the effective Classification shall be the most restrictive relevant state unless a valid, explicit and evidenced Decision defines otherwise.

<a id="section-23-23"></a>
## 23.23 Public

Public data is approved for public disclosure and ordinary external processing under applicable rights, policy and purpose constraints.

<a id="section-23-24"></a>
## 23.24 Public Does Not Mean Unrestricted

Public data may still have:

- copyright,

- attribution,

- terms,

- accuracy,

- audience,

- retention,

- or platform restrictions.

<a id="section-23-25"></a>
## 23.25 Public Source Material

Material found on a public website is not automatically classified Public within Omnira.

The system shall consider:

- intended use,

- personal data,

- rights,

- context,

- and source restrictions.

<a id="section-23-26"></a>
## 23.26 Public Asset

An Asset becomes Public only after explicit approval or policy-supported classification.

<a id="section-23-27"></a>
## 23.27 Project Internal

Project Internal data is intended for authorised use inside one Project or its approved operational relationships.

It shall not be disclosed publicly or reused across Projects automatically.

<a id="section-23-28"></a>
## 23.28 Project Internal Examples

Examples may include:

- drafts,

- internal notes,

- ordinary plans,

- non-sensitive prompts,

- unpublished scheduling data,

- Project analytics,

- and routine production metadata.

<a id="section-23-29"></a>
## 23.29 Project Internal Boundary

Project Internal data shall remain inside:

- the owning Project,

- authorised Agents,

- approved Providers,

- approved storage,

- and permitted operational systems.

<a id="section-23-30"></a>
## 23.30 Confidential

Confidential data could cause material harm, privacy loss, commercial damage, legal exposure, identity risk or safety impact if accessed or disclosed improperly.

<a id="section-23-31"></a>
## 23.31 Confidential Examples

Examples may include:

- private user data,

- health information,

- financial information,

- confidential strategy,

- customer records,

- unpublished contracts,

- private family images,

- source code with sensitive logic,

- and protected correspondence.

<a id="section-23-32"></a>
## 23.32 Confidential Processing

Confidential processing may require:

- stronger identity,

- least privilege,

- approved Provider terms,

- encrypted storage,

- restricted logging,

- and explicit placement.

<a id="section-23-33"></a>
## 23.33 Local Only

Local Only data shall remain within approved local, private or self-hosted boundaries defined by policy.

It shall not be sent to ordinary external managed Providers.

<a id="section-23-34"></a>
## 23.34 Local Only Is a Placement Restriction

Local Only constrains processing and storage placement.

It may also require:

- restricted network,

- local Model,

- local Tool,

- and local evidence handling.

<a id="section-23-35"></a>
## 23.35 Local Only Is Not Device-Specific Automatically

A Local Only policy may permit:

- one laptop,

- one private rig,

- one on-premises server,

- or a defined private cluster.

The eligible Zones shall be explicit.

<a id="section-23-36"></a>
## 23.36 Local Only Failure

When no eligible local resource exists, the Fabric shall:

- wait,

- request a policy change,

- request an approved private alternative,

- or stop.

It shall not silently route externally.

<a id="section-23-37"></a>
## 23.37 Prohibited

Prohibited data or processing shall not be collected, stored, inferred, transferred, generated or used under the current policy.

<a id="section-23-38"></a>
## 23.38 Prohibited Examples

Examples may include:

- raw passwords in Model context,

- unauthorised private messages,

- prohibited biometric inference,

- unauthorised child sexual content,

- unlawfully obtained data,

- data outside the Project’s legal or policy authority,

- or information explicitly excluded by the user.

<a id="section-23-39"></a>
## 23.39 Prohibited Does Not Mean Delete Immediately in Every Case

Some prohibited content may need temporary isolated handling for:

- Incident response,

- lawful reporting,

- quarantine,

- or deletion verification.

Such handling shall be narrowly authorised.

<a id="section-23-40"></a>
## 23.40 Classification Label

A Classification Label is the machine- and human-readable representation of a Data Classification applied to a Data Object.

<a id="section-23-41"></a>
## 23.41 Classification Label Identity

Every reusable Classification Label shall have stable identity and Version.

<a id="section-23-42"></a>
## 23.42 Classification Assignment

A Classification Assignment binds a Classification Label to one Data Object or scope.

It shall include or reference:

- classificationAssignmentId,

- Data Object,

- assigned Classification,

- source,

- rule,

- classifier,

- confidence,

- effective time,

- expiry or review,

- and provenance.

<a id="section-23-43"></a>
## 23.43 Classification Assignment Identity

Every material Classification Assignment shall have stable identity.

<a id="section-23-44"></a>
## 23.44 Classification Source

Classification may originate from:

- explicit user designation,

- Project policy,

- Tenant policy,

- data category,

- source inheritance,

- automatic classifier,

- Provider metadata,

- legal requirement,

- or human review.

<a id="section-23-45"></a>
## 23.45 Explicit User Tightening

An authorised user may increase protection.

The Fabric shall apply the tighter classification promptly.

<a id="section-23-46"></a>
## 23.46 Automatic Tightening

The Fabric may increase classification automatically when new evidence indicates greater sensitivity.

<a id="section-23-47"></a>
## 23.47 Automatic Lowering Prohibition

The Fabric shall not lower classification automatically merely because:

- content was summarised,

- names were removed,

- a Provider labelled it safe,

- or an embedding was created.

<a id="section-23-48"></a>
## 23.48 Classification Lowering

Lowering classification requires:

- authorised Principal,

- defined purpose,

- transformation evidence,

- risk review,

- and attributable Decision.

<a id="section-23-49"></a>
## 23.49 Classification Confidence

Automatic classification shall preserve confidence and method.

<a id="section-23-50"></a>
## 23.50 Unknown Classification

Unknown classification shall default to a restrictive handling state appropriate to the context.

<a id="section-23-51"></a>
## 23.51 Classification Review

Low-confidence or high-risk classifications shall require review.

<a id="section-23-52"></a>
## 23.52 Classification Conflict

Conflicting assignments shall produce the most restrictive effective handling until resolved.

<a id="section-23-53"></a>
## 23.53 Classification Version

Material classification changes shall be Versioned or recorded as state transitions.

<a id="section-23-54"></a>
## 23.54 Classification Effective Time

Classification may change over time.

Historical processing shall remain linked to the effective Classification at the time.

<a id="section-23-55"></a>
## 23.55 Classification Expiry

Some temporary heightened states may expire after review.

Expiry shall not reduce protection without an explicit governing rule.

<a id="section-23-56"></a>
## 23.56 Classification Rule

A Classification Rule maps evidence, categories or contexts to a Classification.

It shall include or reference:

- classificationRuleId,

- scope,

- conditions,

- assigned level,

- exceptions,

- priority,

- Version,

- and owner.

<a id="section-23-57"></a>
## 23.57 Classification Rule Identity

Every Rule shall have stable identity and Version.

<a id="section-23-58"></a>
## 23.58 Rule Priority

Higher-authority or more-specific Rules shall outrank general defaults.

## 23.707 Closing Statement

Data classification, privacy and isolation determine where Omnira may think, what it may remember, which resources it may use and which boundaries it must never cross.

Classification defines the required protection.

Data Category defines the kind of information involved.

Purpose defines why processing is permitted.

The Handling Profile defines how the data must be protected.

The Access Scope defines who or what may act.

The Tenant Boundary separates organisations.

The Project Boundary separates operational worlds.

The Agent Boundary limits intelligence roles.

The Workflow Boundary limits one execution path.

The Environment Boundary separates development from production.

The Node Boundary limits local access.

The Provider Boundary defines external custody.

The Storage Boundary protects durable copies.

The Cache and Index Boundaries protect derived and accelerated access.

The Data Flow describes where information moves.

The Transfer Decision determines whether that movement is permitted.

The Retention Decision determines how long the data may remain.

The Redaction, Pseudonymisation and Anonymisation Records preserve privacy transformations without overstating their guarantees.

The Privacy Review evaluates high-risk processing before activation.

The Isolation Test proves that architectural boundaries work in practice.

The Privacy Incident preserves accountability when they fail.

For Familje-Stunden, this architecture ensures that:

- private family photos remain private,

- children’s information receives stronger protection,

- Nova and Pling Assets remain Project-scoped,

- child-facing review sees only necessary material,

- and public content does not expose private working sources.

For The Prompt, it ensures that:

- public research remains distinguishable from private source correspondence,

- screenshots are redacted,

- generated visuals remain correctly classified,

- and analytics do not become hidden personal profiling.

For GainPilot, it ensures that:

- health, fitness and body data remain Confidential or Local Only,

- Arnold retrieves only GainPilot-relevant Memory,

- programme history does not leak into unrelated Projects,

- and local processing preferences cannot be overridden silently.

For Atlas, it ensures that:

- broad orchestration authority does not become universal data access,

- Personal Memory remains purpose-limited,

- Project context remains isolated,

- Secrets remain inside Credential systems,

- and current user intent does not cause accidental disclosure of unrelated history.

For Omnira, it ensures that:

- users,

- Tenants,

- Projects,

- Agents,

- workflows,

- Providers,

- Nodes,

- Assets,

- Evidence,

- Memory,

- caches,

- indexes,

- logs,

- and backups

participate in one governed data architecture.

No processing without purpose.

No scope without identity.

No disclosure without eligibility.

No retrieval before isolation.

No transfer before minimisation.

No external Provider for Local Only data.

No Model context containing raw Secrets.

No Project Memory in the wrong Project.
