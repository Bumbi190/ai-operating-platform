# Chapter 26 — Developer Experience, Testing and Conformance

<a id="section-26-1"></a>
## 26.1 Chapter Status

This chapter defines the canonical architecture, object model, workflows, quality gates, lifecycle controls and conformance requirements for developer experience, testing and implementation assurance within the Omnira Intelligence Fabric.

It establishes:

- how developers interact with the Fabric without bypassing its governance,

- how canonical schemas, APIs, SDKs, command-line tools, local environments and documentation remain aligned,

- how implementation contracts become executable tests,

- how component tests, integration tests, contract tests, conformance tests, system tests and acceptance tests remain distinct,

- how Provider, Model, Tool, Adapter, Connector, Agent, workflow and local Node integrations are tested,

- how test data remains isolated from production data,

- how paid Provider tests remain bounded and attributable,

- how publishing, deletion, messaging, purchasing and other external side effects remain disabled or safely redirected during testing,

- how deterministic fixtures coexist with probabilistic Model evaluation,

- how Quality evaluation differs from software correctness,

- how golden tests, benchmark suites, rubrics, statistical tests and human review are governed,

- how test environments preserve Tenant, Project, Credential, data and authority isolation,

- how local development remains representative without requiring unrestricted production access,

- how mocks, stubs, fakes, simulators, emulators, sandboxes and live tests remain distinguishable,

- how Provider-specific behaviour is validated without leaking into canonical business logic,

- how schema and protocol compatibility are tested,

- how API, event, queue, webhook, callback and Tool contracts remain Versioned,

- how retries, timeouts, unknown outcomes, duplicate delivery and partial completion are tested,

- how privacy, rights, consent, classification, authority, Budget and provenance controls receive first-class conformance tests,

- how performance, load, stress, endurance, capacity and latency tests remain bounded,

- how security tests address Secrets, supply chain, Sandbox escape, prompt injection, Tool misuse and cross-scope access,

- how test evidence remains attributable and reviewable,

- how builds, releases, migrations and deployments receive quality gates,

- how failed tests block promotion according to risk,

- how exceptions remain explicit, expiring and approved,

- how conformance certification applies to Adapters, Connectors, Models, Providers, Tools, Agents, workflows and services,

- how external drift invalidates prior certification when necessary,

- how regression suites preserve previously fixed behaviour,

- how developer productivity is improved without weakening architecture,

- how Stage 1 shall implement the smallest trustworthy developer and conformance foundation,

- and how future autonomous development remains bounded by the same evidence and authority model.

A successful build is not proof of correctness.

A passing unit test is not proof of system conformance.

A working demo is not production readiness.

A mock response is not evidence that the Provider behaves the same way.

A Provider sandbox is not always equivalent to production.

A deterministic snapshot is not sufficient for probabilistic intelligence quality.

A Model benchmark is not a software contract test.

A high benchmark score is not proof of policy compliance.

A manual test without recorded evidence is not canonical conformance.

A test environment is not permitted to use production data merely because it is non-public.

A development Credential is not a production Credential.

A test Account is not a user Account.

A successful API response is not proof of external outcome.

A timeout test is incomplete if unknown outcome is not represented.

A retry test is incomplete if cost, idempotency and duplicate side effects are ignored.

A test suite that cannot fail meaningfully is not assurance.

A flaky test is not harmless when it hides real regressions.

A waived test is not permanently removed from governance.

A certification is not eternal.

A release tag is not approval to deploy.

Developer convenience shall never become an implicit exception to privacy, authority or Project isolation.

This chapter is normative after formal approval.

Stage 1 implementation architecture is expanded in Chapter 27.

Rollout, migration, anti-patterns and future evolution are expanded in Chapter 28.

Implementation, tooling and operational conformance must be verified separately.

<a id="section-26-2"></a>
## 26.2 Purpose of Developer Experience, Testing and Conformance

The Intelligence Fabric depends on many independently changing components, including:

- canonical schemas,

- control-plane services,

- Agents,

- Models,

- Providers,

- Adapters,

- Connectors,

- local Runtimes,

- Tools,

- MCP servers,

- queues,

- webhooks,

- Asset stores,

- Memory systems,

- approval services,

- and external publication platforms.

Those components may fail through:

- schema mismatch,

- incorrect mapping,

- stale Provider assumptions,

- broken retry logic,

- missing idempotency,

- unsupported cancellation,

- wrong data classification,

- Credential leakage,

- cross-Project access,

- unbounded cost,

- incorrect rights handling,

- missing provenance,

- false success reporting,

- incompatible Model updates,

- and unsafe developer shortcuts.

Without a canonical developer and conformance architecture, Omnira could:

- implement the same contract differently in several services,

- allow Provider SDKs to bypass the Adapter boundary,

- accept incompatible event Versions,

- test only happy paths,

- use production Accounts for experiments,

- incur uncontrolled Provider spend,

- publish or delete during automated testing,

- treat probabilistic quality as deterministic correctness,

- certify an integration once and never re-evaluate it,

- or ship a release whose observable behaviour contradicts the approved architecture.

The architecture exists to ensure that developers can answer:

- Which canonical contracts govern this component?

- Which schemas and Versions are supported?

- Which test environment is safe?

- Which data and Credentials may be used?

- Which side effects are permitted?

- Which test types are required?

- Which Provider behaviours are simulated?

- Which behaviours are verified live?

- Which failures are covered?

- Which policy invariants are executable?

- Which conformance profile applies?

- Which evidence proves compliance?

- Which exceptions remain open?

- Which release gates must pass?

- Which drift conditions invalidate prior results?

- How can a developer reproduce a failure locally?

- How can a change be rolled back safely?
