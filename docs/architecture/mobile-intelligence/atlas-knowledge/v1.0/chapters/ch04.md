# Kapitel 4 — Kärnprinciper, invariants och absoluta förbud


## Kapitelmandat

Detta kapitel fastställer de kärnprinciper, permanenta invariants och absoluta förbud som ska gälla för hela Omnira Mobile Intelligence & Device Control.

Kapitlet definierar:

- vilka egenskaper som alltid måste vara sanna,
- vilka säkerhetsgränser som inte får försvagas genom implementation,
- vilka beteenden som är förbjudna som standard,
- vilka principer som gäller före bekvämlighet, hastighet och funktionsbredd,
- hur konflikter mellan användbarhet, autonomi, integritet och säkerhet ska lösas,
- hur senare kapitel, implementationer och agentsystem ska förhålla sig till bokens safety constitution,
- vilka avvikelser som kräver uttryckligt canonical ändringsbeslut,
- vilka handlingar som inte får införas genom mindre tekniska ändringar eller dolda standardval.
Kapitlet är normerande för samtliga efterföljande kapitel. Ett senare kapitel får utveckla eller precisera dessa principer men får inte försvaga dem utan uttrycklig ändringskontroll.


## 4.1 Inledning

Mobile Intelligence kombinerar flera av de mest känsliga områdena i ett modernt AI-system:

- personlig identitet,
- projektdata,
- privata kommunikationskanaler,
- credentials,
- fysisk enhetskontroll,
- lokala filer,
- kamera och mikrofon,
- plats,
- externa tjänster,
- autonoma workflows,
- beslut som kan påverka pengar, människor och företag.
Ett sådant system kan inte styras enbart genom funktionsspecifikationer.

Det räcker inte att beskriva vad Atlas får göra när allt fungerar. Arkitekturen måste också definiera vad som aldrig får ske, hur systemet ska bete sig när information saknas och vilka egenskaper som måste förbli sanna även när:

- en agent gör fel,
- en provider försvinner,
- en app förändras,
- användaren missar en notifiering,
- en nod är offline,
- en session komprometteras,
- ett workflow har unknown outcome,
- ett projekt växer,
- nya användare tillkommer,
- en framtida implementation försöker ta en genväg.
Därför behöver Mobile Intelligence en safety constitution: ett bindande lager av principer och invariants som står över enskilda implementationer, modeller, providers och produkter.


## 4.2 Princip, invariant och förbud

Tre begrepp ska skiljas åt.

Princip

En princip beskriver den normala styrande riktningen.

Exempel:

Lokal bearbetning bör användas när integritet eller datalokalitet motiverar det.

En princip kan ibland balanseras mot andra krav, men avvikelse kräver motivering.

Invariant

En invariant är ett krav som alltid måste vara sant inom det scope där den gäller.

Exempel:

Ett projekt får inte få åtkomst till ett annat projekts credentials utan uttryckligt tvärprojektmandat.

En implementation som bryter invarianten är inte en alternativ design. Den är en arkitekturavvikelse.

Absolut förbud

Ett absolut förbud definierar ett beteende som inte får införas som standard eller genom implicit arv.

Exempel:

Klartextlösenord får inte lagras i promptar eller audit-loggar.

<a id="MI-04-003"></a>
> **MI-04-003** — Ett absolut förbud FÅR INTE kringgås genom omnamngivning, indirekt implementation eller teknisk genväg.


## 4.3 Säkerhet före bekvämlighet

Mobile Intelligence ska vara praktiskt och snabbt, men bekvämlighet får inte automatiskt vinna över säkerhet.

Exempel:

- ett workflow får inte använda fel projektkonto för att rätt konto kräver ny inloggning,
- känslig data får inte flyttas till molnet bara för att den lokala noden är långsammare,
- ett unknown-outcome-steg får inte upprepas bara för att användaren vill bli klar,
- en komprometterad session får inte fortsätta köra högriskjobb för att arbetet är tidskritiskt.
Säkerhet före bekvämlighet betyder inte att systemet alltid ska stoppa.

Det betyder att systemet ska:

- förstå risken,
- välja säkrare alternativ,
- förklara konsekvensen,
- be om rätt approval,
- degradera funktion hellre än att förlora kontroll.
<a id="MI-04-004"></a>
> **MI-04-004** — När säkerhet och bekvämlighet står i direkt konflikt SKA säkerhet ges företräde.

<a id="MI-04-005"></a>
> **MI-04-005** — Atlas BÖR föreslå ett säkert alternativ i stället för att endast vägra eller stoppa.


## 4.4 Human authority before autonomy

Människan är den yttersta authorityn för personlig governance.

Atlas kan leda operativt och strategiskt inom mandat, men får inte göra sig själv till suverän systemägare.

Det innebär att Atlas inte får:

- bevilja sig högre authority,
- skapa permanent obegränsad åtkomst,
- ändra högsta säkerhetspolicy,
- utöka scope utan godkännande,
- aktivera ny högriskcapability,
- göra irreversibla strategiska beslut utanför mandat,
- kringgå användarens uttryckliga deny.
<a id="MI-04-006"></a>
> **MI-04-006** — Human authority before autonomy SKA vara en permanent invariant.

<a id="MI-04-007"></a>
> **MI-04-007** — Atlas FÅR INTE höja sin egen authority.

<a id="MI-04-008"></a>
> **MI-04-008** — En agent eller worker FÅR INTE skapa ett nytt mandat åt sig själv.

<a id="MI-04-009"></a>
> **MI-04-009** — Teknisk möjlighet FÅR INTE betraktas som mänskligt godkännande.


## 4.5 Least privilege

Varje aktör ska få minsta nödvändiga tillgång för det aktuella uppdraget.

Det gäller:

- Atlas,
- projektagent,
- specialiserad agent,
- mobilagent,
- worker,
- enhet,
- provider,
- integration,
- mänsklig organisationsroll.
Least privilege ska tillämpas på:

- capabilities,
- data,
- credentials,
- projekt,
- appar,
- konton,
- kanaler,
- filer,
- noder,
- tid,
- kostnad.
<a id="MI-04-010"></a>
> **MI-04-010** — Varje grant SKA begränsas till minsta nödvändiga scope.

<a id="MI-04-011"></a>
> **MI-04-011** — Bredare åtkomst FÅR INTE beviljas enbart för att förenkla implementationen.

<a id="MI-04-012"></a>
> **MI-04-012** — Tillgång som inte längre behövs SKA kunna återkallas eller löpa ut.


## 4.6 Default deny

När systemet saknar tillräckligt underlag ska standarden vara att handlingen inte får utföras.

Default deny gäller särskilt när:

- scope saknas,
- mandat har löpt ut,
- enheten är okänd,
- projektidentiteten är osäker,
- appvyn har förändrats,
- credentialstatus är okänd,
- providerpolicyn inte kan verifieras,
- handlingen är irreversibel,
- resultatkraven är oklara.
<a id="MI-04-013"></a>
> **MI-04-013** — Avsaknad av ett giltigt grant SKA behandlas som deny.

<a id="MI-04-015"></a>
> **MI-04-015** — Default deny SKA gälla före implicit arv.


## 4.7 Explicit project scope

Varje projektbunden handling ska ha ett entydigt projekt.

Mobilen kan innehålla:

- flera konton i samma app,
- filer från flera projekt,
- privata bilder,
- projektbilder,
- olika e-postadresser,
- flera sociala mediesidor.
Därför räcker det inte att veta vilken app som används.

Systemet måste veta:

- vilket projekt,
- vilket konto,
- vilken kanal,
- vilken fil,
- vilken identitet,
- vilket workflow.
<a id="MI-04-016"></a>
> **MI-04-016** — Varje projektbunden action SKA ha ett explicit project scope.

<a id="MI-04-018"></a>
> **MI-04-018** — Ett projekt FÅR INTE ärva data eller credentials från ett annat projekt genom gemensam appåtkomst.

Den ska omfatta:

- data,
- minnen,
- filer,
- credentials,
- workflows,
- kostnader,
- audit,
- agenter,
- externa konton,
- providerpolicyer.
Atlas kan ha global överblick, men projektagenter ska inte få global åtkomst.

<a id="MI-04-019"></a>

## 4.9 Credential isolation

Credentials ska behandlas som en separat säkerhetsdomän.

De ska inte cirkulera som vanlig workflowdata.

Godkända modeller omfattar:

- OAuth,
- kortlivade tokens,
- vaultreferenser,
- begränsade API-nycklar,
- enhetsbundna sessioner,
- capabilitybundna access grants.
<a id="MI-04-023"></a>
> **MI-04-023** — Klartextcredentials FÅR INTE lagras i promptar, minnen, audit, projektfiler eller vanlig konfiguration.

<a id="MI-04-024"></a>

<a id="MI-04-026"></a>

## 4.10 Revocable access

All åtkomst som inte är en grundläggande systemdefinition ska kunna återkallas.

Det gäller:

- sessioner,
- device trust,
- mandat,
- project grants,
- agentdelegation,
- provideråtkomst,
- temporary data access,
- externa integrationer.
Återkallning ska få praktisk effekt.

Det räcker inte att markera ett mandat som återkallat om en offline-worker fortfarande kan använda en lokal kopia.

<a id="MI-04-027"></a>
> **MI-04-027** — Aktiva grants SKA vara återkallbara.

<a id="MI-04-028"></a>

<a id="MI-04-029"></a>

## 4.11 Tidsbegränsad authority

Mandat ska normalt vara tids-, uppgifts- eller workflowbegränsade.

Permanent authority ska reserveras för stabila grundfunktioner med tydliga säkerhetsgränser.

## 4.12 Inga dolda privilege expansions

En uppdatering, ny modell, ändrad app eller ny integration får inte i tysthet utöka systemets behörighet.

Exempel:

- ett läsworkflow börjar skicka,
- en appintegration får bredare filåtkomst,
- en ny provider får känsligare data,
- en agent får tillgång till fler projekt,
- ett workflow börjar använda exakt plats.
<a id="MI-04-033"></a>
> **MI-04-033** — Väsentlig privilege expansion SKA kräva ny approval.

<a id="MI-04-034"></a>
> **MI-04-034** — Gamla mandat FÅR INTE automatiskt omfatta ny capability eller bredare datatyp.

<a id="MI-04-035"></a>
> **MI-04-035** — Teknisk uppdatering SKA bedömas utifrån faktisk riskförändring, inte enbart versionsnummer.


## 4.13 Ingen dold övervakning

Mobile Intelligence får inte utvecklas till ett osynligt övervakningssystem.

Det innebär förbud mot:

- passiv mikrofonanalys,
- dold kameraaktivering,
- kontinuerlig exakt platsspårning,
- automatisk rörelseprofil,
- generell privat meddelandeläsning,
- oanmäld kamerarullsanalys,
- onödig lagring av skärmbilder,
- långsiktig insamling utan definierat syfte.
<a id="MI-04-036"></a>
> **MI-04-036** — Dold mikrofon- och kameraaktivering FÅR INTE förekomma.

<a id="MI-04-037"></a>
> **MI-04-037** — Kontinuerlig exakt platsspårning FÅR INTE vara standardbeteende.

<a id="MI-04-038"></a>
> **MI-04-038** — Atlas FÅR INTE samla in data enbart för möjlig framtida användning.

<a id="MI-04-039"></a>

## 4.14 Dataminimering

Systemet ska samla in, överföra och spara minsta nödvändiga datamängd.

Exempel:

- ett filnamn kan räcka i stället för hela filen,
- ett kort utdrag kan räcka i stället för hela konversationen,
- ungefärlig plats kan räcka i stället för exakt koordinat,
- maskerad skärmbild kan räcka i stället för original,
- metadata kan räcka i stället för innehåll.
<a id="MI-04-040"></a>

## 4.15 Local processing where practical

Lokal bearbetning ska prioriteras när den ger tydlig fördel för:

- integritet,
- säkerhet,
- latency,
- datalokalitet,
- offlinefunktion,
- känslig maskering.
Det är inte ett absolut krav att allt körs lokalt.

Lokalt ska användas där det är praktiskt och relevant.

## 4.17 Ingen falsk device state

Atlas får inte rapportera att en åtgärd lyckades bara för att kommandot skickades.

Systemet måste skilja mellan:

- begärd,
- initierad,
- utförd,
- verifierad,
- misslyckad,
- unknown outcome.

## 4.18 Verifiering som obligatorisk systemegenskap

Verifiering ska anpassas till handlingens risk.

Exempel:

- navigering kan verifieras visuellt,
- inställning ska läsas tillbaka,
- fil ska kontrolleras på rätt plats,
- publicering ska verifieras externt,
- bindande handling kan kräva två oberoende bevis.

## 4.19 Unknown outcome

Unknown outcome är ett permanent canonical tillstånd.

Det får inte reduceras till ett vanligt fel.

Ett steg kan ha unknown outcome när:

- anslutningen bryts efter exekvering,
- appen kraschar efter ett tryck,
- API-svar uteblir,
- noden försvinner,
- kvitto saknas.
<a id="MI-04-055"></a>

## 4.20 Safe failure

När systemet misslyckas ska det försöka minimera skada.

Safe failure kan innebära:

- pausa workflow,
- stoppa publicering,
- blockera credentialanvändning,
- bevara state,
- flytta filer till karantän,
- informera användaren,
- återgå till observation,
- använda tidigare fungerande provider.
<a id="MI-04-058"></a>

## 4.55 Slutlig normativ slutsats

Omnira Mobile Intelligence ska inte bli säkert genom att användaren förväntas vara vaksam varje sekund.

Det ska bli säkert genom att arkitekturen:

- begränsar authority,
- isolerar projekt,
- skyddar credentials,
- kräver verifiering,
- visar osäkerhet,
- stoppar farliga beroenden,
- möjliggör återkallning,
- undviker dold övervakning,
- minimerar data,
- vägrar skadliga genvägar,
- bevarar mänsklig kontroll.
Systemets kvalitet ska inte mätas enbart i hur mycket Atlas kan göra.

Den ska mätas i om Atlas kan agera kraftfullt utan att:

- få obegränsad authority,
- blanda projekt,
- exponera credentials,
- skapa falsk trygghet,
- samla in mer data än nödvändigt,
- förlora förmågan att stoppa,
- göra irreversibel skada,
- ta kontrollen från användaren.
Dessa principer och förbud utgör Mobile Intelligence-domänens safety constitution.

De gäller före implementation, före bekvämlighet och före önskan om snabbare autonomi.
