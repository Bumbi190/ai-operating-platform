# Kapitel 11 — Utgående kommunikation, varumärkesidentitet och mänsklig representation


## Kapitelmandat

Detta kapitel definierar den kanoniska arkitekturen för utgående kommunikation, extern identitet, varumärkesrepresentation och mänsklig representation inom Omnira Mobile Intelligence & Device Control.

Kapitlet fastställer:

- vem eller vad som får representeras externt,
- hur projektidentitet skiljs från Atlas internidentitet,
- hur Atlas, projektagenter och workers får skapa och sända kommunikation,
- hur utkast skiljs från faktisk sändning eller publicering,
- hur avsändaridentitet, konto, kanal, mottagare och innehåll ska verifieras,
- när Atlas får kommunicera autonomt och när human approval krävs,
- hur personlig representation av André ska begränsas,
- hur signaturer, namn, röst, bild, avatar och ton får användas,
- hur varumärken som Familje-Stunden, GainPilot och The Prompt får representeras,
- hur Nova, Pling, Arnold och andra projektidentiteter ska behandlas,
- hur svåra, känsliga, juridiska, ekonomiska och konfliktfyllda ärenden ska eskaleras,
- hur framtida organisationer ska hantera kommunikationsroller, separation of duties och flerpersonsgodkännande,
- hur extern AI-transparens ska styras,
- hur felaktig kommunikation ska verifieras, stoppas, rättas och auditeras.
Kapitlet reglerar inte endast textmeddelanden. Det omfattar även:

- e-post,
- sociala kommentarer,
- direktmeddelanden,
- publicering,
- nyhetsbrev,
- formulärsvar,
- röstkommunikation,
- video,
- avatarer,
- automatiska svar,
- annan extern representation.

## 11.1 Inledning

Utgående kommunikation är en av de mest kraftfulla och riskfyllda capabilities som Atlas kan få.

När Atlas skickar eller publicerar något förändras den externa verkligheten.

Kommunikationen kan:

- påverka en kund,
- skapa ett löfte,
- uttrycka ett pris,
- publicera ett påstående,
- påverka ett varumärke,
- skapa juridisk risk,
- avslöja privat information,
- representera André,
- uppfattas som bindande,
- spridas vidare,
- lagras av mottagaren,
- bli omöjlig att återkalla fullständigt.
Ett utkast är internt och kan normalt korrigeras.

Ett skickat meddelande eller publicerat inlägg har lämnat Omniras direkta kontroll.

Därför ska outbound communication behandlas som en särskild familj av externa och ofta irreversibla handlingar.

Systemet måste före sändning kunna fastställa:

- vem som representeras,
- vilket projekt kommunikationen tillhör,
- vilket konto som används,
- vem mottagaren är,
- vilken kanal som används,
- vilket innehåll som skickas,
- vilken version som godkänts,
- om känsliga data ingår,
- om Atlas har mandat,
- om kommunikationen kan verifieras,
- om handlingen kräver mänsklig granskning.

## 11.2 Normativ definition av outbound communication

Outbound communication är varje handling där information lämnar Omnira eller en privat intern arbetsyta för att bli tillgänglig för en extern människa, organisation, publik, kanal eller plattform.

Det omfattar bland annat:

- send,
- reply,
- forward,
- publish,
- comment,
- direct message,
- newsletter delivery,
- form submission,
- calendar invitation,
- voice call,
- voice message,
- public video,
- support response,
- external file share,
- public status update.
<a id="MI-11-001"></a>
> **MI-11-001** — Outbound communication SKA behandlas som extern stateförändring.

<a id="MI-11-002"></a>
> **MI-11-002** — Utkast SKA hållas åtskilt från skickad eller publicerad kommunikation.

<a id="MI-11-003"></a>
> **MI-11-003** — Outbound action SKA ha en identifierbar avsändare, mottagare eller publik och en verifierbar communication identity.

<a id="MI-11-004"></a>
> **MI-11-004** — Outbound communication FÅR INTE genomföras enbart för att innehållet har genererats färdigt.


## 11.3 Extern identitet

En extern identitet är den person, organisation, produkt, karaktär eller varumärkesyta som mottagaren uppfattar som avsändare.

Exempel:

- Familje-Stunden,
- GainPilot,
- The Prompt,
- Omnira,
- Arnold,
- Nova,
- Pling,
- André Hultgren,
- ett framtida kundföretag,
- en supportfunktion.
Den externa identiteten ska skiljas från:

- Atlas internidentitet,
- agent identity,
- worker identity,
- provider identity,
- device identity,
- credential identity.
<a id="MI-11-005"></a>
> **MI-11-005** — Extern identitet SKA vara explicit definierad för varje outbound channel.

<a id="MI-11-006"></a>
> **MI-11-006** — Den aktör som producerar innehållet FÅR INTE automatiskt bli den externa avsändaridentiteten.

<a id="MI-11-007"></a>
> **MI-11-007** — Worker- eller provideridentitet FÅR INTE synas som extern avsändare om inte det uttryckligen är avsett.


## 11.4 Atlas som intern identitet

Atlas är normalt en intern lednings- och intelligensidentitet.

Atlas ska kunna:

- planera kommunikation,
- skapa utkast,
- granska,
- prioritera,
- verifiera policy,
- välja agent,
- stoppa fel,
- godkänna inom mandat,
- auditera.
Atlas ska normalt inte automatiskt presenteras som extern avsändare.

Undantag kan finnas där Atlas är en uttrycklig del av projektets koncept, exempelvis i The Prompt eller Omnira.

<a id="MI-11-008"></a>
> **MI-11-008** — Atlas SKA vara intern identitet som standard.

<a id="MI-11-009"></a>
> **MI-11-009** — Atlas FÅR synas externt endast när projektets godkända kommunikationskoncept tillåter det.

<a id="MI-11-010"></a>
> **MI-11-010** — Atlas FÅR INTE framställas som mänsklig person om detta är vilseledande.

<a id="MI-11-011"></a>
> **MI-11-011** — Atlas interna systemroll FÅR INTE avslöjas i extern kommunikation när detta saknar relevant syfte.

## 11.68 Primära failure modes

Identity confusion

Fel varumärke, person eller karaktär representeras.

Account confusion

Rätt app men fel konto används.

Utkast skickas utan rätt approval.

Content version mismatch

Fel version skickas.

Recipient mismatch

Fel mottagare eller publik används.

Impersonation drift

Agenten börjar uttrycka sig som André utan mandat.

Promise inflation

Atlas skapar löften eller ekonomiska åtaganden.

Sensitive disclosure

Privat eller projektkänslig information lämnar systemet.

Duplicate communication

Samma meddelande skickas flera gånger.

Silent policy drift

Plattform eller project policy ändras utan revalidation.

AI-transparency failure

Kommunikationen blir vilseledande om mänsklig eller AI-baserad avsändare.

## 11.71 Exempel på canonical outbound-flöden

Exempel A — Familje-Stunden svarar på en enkel kommentar

Kommentaren tillhör rätt projektkonto.

Atlas klassificerar den som låg risk.

Projektpolicyn tillåter standardsvar.

Familje-Stunden är extern identitet.

Ett svar skapas i rätt tonalitet.

Inga känsliga data eller löften ingår.

L4-mandat är aktivt.

Svaret skickas.

Resultatet verifieras i kommentarstråden.

Användaren får initialt en kort eftergranskningsnotis.

Exempel B — GainPilot och Arnold

En användare ställer en vanlig träningsfråga.

Arnold får svara inom GainPilots godkända coachingpolicy.

Om frågan innehåller allvarliga medicinska symtom ska Arnold:

- inte diagnostisera,
- markera osäkerhet,
- eskalera enligt health-safetypolicy,
- inte låtsas vara vårdgivare.
Exempel C — The Prompt-publicering

Innehållet är färdiggranskat.

Källor och fakta är verifierade.

The Prompt är extern identitet.

Rätt konto och kanal verifieras.

Publiceringsmandat och budget är aktiva.

Content version matchar approval.

Inlägget publiceras.

Extern synlighet verifieras.

Dubblettskydd registreras.

Exempel D — Personligt mejl från André

André ber Atlas formulera ett mejl i hans namn.

Atlas får:

- skapa utkast,
- använda personlig tonalitet,
- lägga till hans signatur endast om detta godkänts,
- inte skicka förrän separat approval finns,
- inte använda samma approval för framtida personliga mejl.
Exempel E — Känsligt kundklagomål

Ett klagomål innehåller krav på återbetalning och hot om rättslig åtgärd.

Atlas ska:

- klassificera ärendet som känsligt,
- stoppa standardsvar,
- sammanfatta fakta,
- skapa försiktigt utkast,
- eskalera till André,
- inte lova återbetalning eller erkänna ansvar utan mandat.
Exempel F — Unknown outcome efter publicering

Publiceringsknappen aktiveras och anslutningen bryts.

Atlas ska:

- registrera unknown outcome,
- kontrollera kanalens publicerade innehåll,
- inte publicera igen förrän status fastställts,
- informera användaren om kvarstående osäkerhet.

## 11.74 Slutlig normativ slutsats

Omnira ska aldrig behandla utgående kommunikation som en enkel sista knapptryckning.

Innan något lämnar systemet måste Atlas kunna fastställa:

- vem som representeras,
- vilket projekt som talar,
- vilket konto som används,
- vem mottagaren är,
- vilken version som skickas,
- vilka påståenden som görs,
- vilka löften som skapas,
- om privat information exponeras,
- om mänsklig granskning krävs,
- om resultatet kan verifieras.
Atlas ska kunna vara en mycket kapabel intern ledare och kommunikationsmotor.

Atlas ska kunna låta:

- Familje-Stunden tala som Familje-Stunden,
- Arnold tala som GainPilots coach,
- Nova och Pling fungera som tydliga fiktiva projektkaraktärer,
- The Prompt kommunicera genom sitt varumärke,
- Omnira kommunicera genom sin godkända identitet.
Atlas ska däremot inte automatiskt tala som André.

Den ska inte använda hans namn, signatur, röst eller bild som om han personligen granskat och godkänt något när detta inte har skett.

Kontrollerad outbound communication betyder därför:

- rätt identitet,
- rätt projekt,
- rätt konto,
- rätt mottagare,
- rätt innehåll,
- rätt mandat,
- rätt verifiering,
- rätt ansvar.
När dessa delar är tydliga kan Omnira kommunicera snabbt, konsekvent och autonomt inom säkra ramar.

När någon av dem är oklar ska systemet stanna, fråga, begränsa eller eskalera.

Det är denna disciplin som gör att Atlas kan representera flera projekt professionellt utan att skapa impersonation, identitetsförväxling, falska löften eller oåterkalleliga kommunikationsfel.
