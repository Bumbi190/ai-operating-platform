# Kapitel 23 — Omnira-noder och exekveringsroller


## Kapitelmandat

Detta kapitel definierar den kanoniska arkitekturen för Omnira-noder, nodidentitet, exekveringsroller, trust, kapabiliteter, livscykel och ansvar inom Omnira Mobile Intelligence & Device Control.

Kapitlet fastställer:

- vad en Omnira-node är,
- hur en node skiljs från device, app, service, provider, agent och account,
- vilka nodklasser som ska stödjas,
- hur mobil, laptop, workstation, privat rigg, molnserver, recovery-enhet, klocka och fordon ska modelleras,
- vilka roller en node får bära,
- hur control, approval, execution, data, coordination, recovery och notification roles ska separeras,
- hur node identity, owner, tenant, project access, device relation och physical locality ska beskrivas,
- hur node trust ska etableras, omvärderas, begränsas och återkallas,
- hur capability discovery och capability claims ska verifieras,
- hur Atlas ska välja mellan noder utan att kringgå privacy, authority, data locality eller cost policy,
- hur känsliga lokala jobb ska stanna på rätt node eller vänta när node saknas,
- hur node health, availability, battery, thermal state, storage, network och workload capacity ska påverka exekvering,
- hur en node ska ta ownership över ett jobb,
- hur dubblettexekvering, split-brain, stale leases och felaktiga failovers ska motverkas,
- hur node enrollment, pairing, attestation, quarantine, suspension, revocation, retirement och recovery ska fungera,
- hur offline-noder ska arbeta med begränsade mandat och senare reconcileras,
- hur data, credentials, memory, logs och artifacts får lagras på respektive nodtyp,
- hur node compromise, loss, theft, diskfel och nätverksavbrott ska hanteras,
- hur framtida organisationer ska stödja managed devices, cloud workers, regional execution och tenantisolering,
- vilka absoluta nodförbud och blockerande tester som ska gälla.
Kapitlet är normerande för varje fysisk eller virtuell resurs som kan ta emot data, exekvera kod, köra modeller, visa approvals, leverera notifieringar, lagra state, koordinera workflows eller stödja recovery inom Omnira.


## 23.1 Inledning

Omnira ska inte vara bundet till en enda dator eller telefon.

Systemet ska kunna använda flera typer av resurser:

- mobil,
- laptop,
- stationär dator,
- privat AI-rigg,
- molnserver,
- recovery-enhet,
- smartklocka,
- fordon,
- framtida organisationsnoder.
Men fler noder innebär inte bara mer kapacitet.

Det innebär även fler möjliga fel:

- samma jobb körs på två noder,
- fel node får känslig data,
- en offline node arbetar med utgånget mandat,
- en stulen mobil behåller secrets,
- en lokal rigg antas vara betrodd trots osäker integrity,
- molnet tar över ett local-only-jobb,
- en gammal node skriver över nyare canonical state,
- recovery sker från fel kopia,
- en notifieringsyta får exekveringsauthority,
- en compromise sprids genom sync.
Omnira måste därför behandla noder som governade exekveringsprincipals.

En node är inte säker bara för att den ägs av André.

En node är inte lämplig bara för att den är online.

En node är inte behörig bara för att den kan tekniskt utföra uppgiften.

Atlas ska alltid kunna svara på:

Vilken node ska göra arbetet?

Varför just den?

Vilken data får lämnas till den?

Vilken roll har den?

Är den betrodd?

Har den rätt capabilities?

Har den aktuellt mandat?

Vem äger jobbet?

Hur verifieras resultatet?

Vad händer om noden försvinner mitt i arbetet?


## 23.2 Normativ definition av node

En Omnira-node är en identifierad fysisk eller virtuell exekveringsresurs som kan bära en eller flera governade roller inom Omnira.

En node kan:

- ta emot task,
- exekvera capability,
- lagra data,
- köra modell,
- visa approval,
- leverera notification,
- koordinera workflow,
- verifiera resultat,
- stödja recovery.
<a id="MI-23-001"></a>
> **MI-23-001** — Varje Omnira-node SKA ha en stabil och unik node identity.

<a id="MI-23-002"></a>
> **MI-23-002** — Node identity SKA skiljas från hostname, IP-adress, device name och user-facing label.

<a id="MI-23-003"></a>
> **MI-23-003** — Varje node SKA ha definierad owner, trust state, node class, roles, capabilities och lifecycle state.

<a id="MI-23-004"></a>
> **MI-23-004** — Okänd eller oregistrerad resurs FÅR INTE behandlas som Omnira-node.


## 23.3 Node kontra device

En device är den fysiska eller virtuella enheten.

En node är den governade Omnira-exekveringsidentiteten på eller genom enheten.

Samma device kan i vissa arkitekturer bära:

- en personal node,
- en work-profile node,
- en recovery node,
- en isolerad project worker.
<a id="MI-23-005"></a>
> **MI-23-005** — Device identity och node identity SKA vara separata men länkade.

<a id="MI-23-006"></a>
> **MI-23-006** — En device FÅR bära flera logiskt isolerade nodes endast om identity, storage, credentials och policy hålls separerade.

<a id="MI-23-007"></a>
> **MI-23-007** — Factory reset eller ny enrollment SKA kunna skapa ny node trust lifecycle.

<a id="MI-23-008"></a>
> **MI-23-008** — Device ownership FÅR INTE automatiskt ge node full project- eller tenantaccess.


## 23.4 Node kontra agent

En agent är en logisk intelligens- eller arbetsroll.

En node är platsen där agenten eller dess task exekveras.

Exempel:

Arnold är en agent.

GainPilot-riggen är en node.

Atlas kan koordinera Arnold att köra ett analysjobb på riggen.

<a id="MI-23-009"></a>
> **MI-23-009** — Agent identity och node identity SKA vara separata.

<a id="MI-23-010"></a>

<a id="MI-23-011"></a>

<a id="MI-23-012"></a>
> **MI-23-012** — Varje exekverad task SKA kunna attribueras till både agent och node.


## 23.5 Node kontra provider

En node är en exekveringsresurs.

En lokal node kan köra en lokal provider.

En molnnode kan anropa en extern provider.

<a id="MI-23-013"></a>
> **MI-23-013** — Provider identity SKA skiljas från node identity.

<a id="MI-23-014"></a>

<a id="MI-23-015"></a>
> **MI-23-015** — Provider request SKA fortfarande följa provider-, egress- och credentialpolicy oavsett exekveringsnode.

Nodepolicy finns endast i prompttext.

Node cleanup raderar source, approved artifact eller enda recovery copy.

Locality och cloud region blandas till ett enda otydligt fält.

Node får credential för annat project för att samma provider används.

Omnira kan inte förklara vilken node som gjorde jobbet och varför.

## 23.107 Exempel på canonical nodflöden

Exempel A — Mobil som approval surface

Ett Familje-Stunden-inlägg väntar på approval.

Systemet:

- coordination node skapar approval task,
- mobilen väljs som approval node,
- device trust och recent authentication verifieras,
- mobilen visar project, account och exakt content version,
- André godkänner,
- mobilen exekverar inte publiceringen,
- en project-bound execution node tar emot bounded mandate,
- publicering verifieras separat.
Exempel B — Privat rigg för lokal bildgenerering

Ett känsligt GainPilot-mediajobb är bundet till privat rigg.

Job requirement anger local-only.

Atlas kontrollerar riggens trust, GPU, storage och model capability.

Riggen är offline.

Jobbet blir waiting for node.

Molnfallback blockeras.

André får en lågprioriterad fråga om att starta riggen.

Efter start re-attesteras noden.

Jobbet tilldelas genom lease.

Output valideras och projektderivat sparas.

Temporär modelldata rensas.

Exempel C — Laptop som full control surface

André ändrar global node policy från sin laptop.

Systemet:

- verifierar owner identity,
- kräver step-up authentication,
- laptopnoden används som control surface,
- policyändringen signeras och versioneras,
- laptopnoden ger inte sig själv nya execution roles,
- andra nodes får den nya policyn genom governad sync,
- stale nodes begränsas tills de har reconcilerats.
Exempel D — Mobil med låg batterinivå

Ett större lokalt transkriptionsjobb planeras på mobilen.

Systemet:

- upptäcker låg batterinivå och hög thermal risk,
- kontrollerar om datan får flyttas,
- ser att jobbet är privat men tillåtet på private rig,
- föreslår riggen som execution node,
- om riggen är offline väntar jobbet,
- mobilen behåller endast control och notification role,
- datan skickas inte till moln utan separat policy.
Exempel E — Split-brain under nätverksavbrott

En workstation kör ett jobb och tappar kontakt med coordinator.

Workstationens lease löper ut.

Coordinator tilldelar inte jobbet direkt utan bedömer unknown outcome.

En ny worker får högre fencing token först när failover är godkänt.

Den gamla workstationens write med stale token avvisas.

Eventuella lokala outputs quarantänsätts.

Endast det verifierade attemptet kan promoteras.

Exempel F — Förlorad mobil

André markerar mobilen som förlorad via recovery node.

Systemet:

- sätter node state till lost,
- stoppar token refresh,
- återkallar sessions och delegated credentials,
- återkallar aktiva leases,
- stoppar sensitive sync,
- initierar remote wipe om möjligt,
- behandlar wipe som unknown tills verifiering finns,
- låter inte mobilen återansluta utan re-enrollment.
Exempel G — Ephemeral cloud worker

Ett icke-känsligt batchjobb behöver tillfällig skalning.

En ephemeral worker skapas i godkänd region.

Den får task-bound identity och short-lived credential.

Endast minimerat input skickas.

Workern exekverar en definierad batch.

Output valideras.

Temporary storage rensas.

Credential löper ut.

Worker termination verifieras.

Inget project memory eller secret blir kvar.

Exempel H — Offline geofence-workflow

Mobilnoden är offline men ett godkänt geofence är aktivt.

Mobilen använder device-local policy.

Geofence trigger utvärderas lokalt.

Endast en lokal reminder skapas.

Ingen extern action skickas.

Efter återanslutning synkroniseras triggern.

Current task state kontrolleras.

Dubblettpåminnelse undviks.

Utgångna grants återaktiveras inte.

Exempel I — Storage failure på privat rigg

Riggen rapporterar checksumfel och diskproblem.

Nya writes stoppas.

Senaste verifierade backup identifieras.

Exempel J — Organisationsnode med work profile

## 23.108 Canonical kravsammanfattning

Nodarkitekturen ska:

- skilja node från device, agent, provider och service,
- använda stabil node identity,
- stödja mobil, laptop, workstation, privat rigg, cloud, edge, recovery, wearable, vehicle, managed och ephemeral nodes,
- använda explicita node classes och lifecycle states,
- separera control, approval, execution, data, coordination, verification, notification, sensor, recovery, audit och gateway roles,
- använda versionerade node profiles,
- registrera hardware, software, locality, capacity, storage, network och security posture,
- använda dynamisk node trust,
- etablera trust genom enrollment, credentials och relevant attestation,
- skilja claimed, tested och approved capabilities,
- placera jobs efter capability, trust, locality, project, tenant, cost, capacity och user impact,
- respektera specific-node och local-only constraints,
- använda waiting state när rätt node saknas,
- skydda mobilens batteri, thermal state och användbarhet,
- använda job identities och tydliga job states,
- skilja assignment, acceptance, execution och success,
- använda reservation, leases, fencing och ownership,
- hantera heartbeat loss utan falskt failure-antagande,
- stödja checkpointing, handoff och failover,
- skydda mot split-brain och stale writes,
- govern data, credential, memory och artifact placement,
- begränsa offline nodes och omvärdera queued actions efter reconnect,
- applicera revocations och tombstones före normal sync,
- stödja quarantine, lost node, compromise, storage failure och network partition,
- auditera node selection, ownership, failover och result,
- ge användaren kontroll över enrollment, roles, jobs, revocation och preferred nodes,
- stödja tenant-managed nodes utan att blanda personal profiles,
- använda separation of duties för högriskflöden,
- kräva blockerande wrong-node-, split-brain-, duplicate-, revocation- och offline-reconciliation-tester.

## 23.110 Slutlig normativ slutsats

Omnira ska inte välja en node enbart för att den är online, snabb, billig eller nära användaren.

En node är lämplig först när den:

- är rätt identifierad,
- ägs av rätt principal eller tenant,
- har tillräcklig trust,
- har rätt role,
- har verifierad capability,
- uppfyller data locality,
- har tillräcklig capacity,
- har rätt credentials,
- kan verifiera resultatet,
- kan stoppas och återhämtas säkert.
Mobilen ska kunna vara den primära approvalytan utan att bära alla tunga jobs.

Laptopen ska kunna vara full administrativ control surface utan att varje action använder owner authority.

Den privata riggen ska kunna köra känsliga och kraftfulla lokala workflows utan att bli ett obegränsat gemensamt datalager.

Molnet ska kunna koordinera och skala utan att ta över local-only-data.

Recovery-enheten ska kunna rädda systemet utan att bli en vardagsdator.

Den kanoniska nodprincipen är därför:

Identifiera noden innan den får arbete.

Verifiera trust innan den får data.

Grant:a roller separat.

Placera jobbet där capability, locality, authority och säkerhet samtidigt uppfylls.

Låt local-only-jobb vänta när rätt node saknas.

Använd leases och fencing så att endast rätt owner kan skapa canonical side effects.

Anta aldrig att tystnad från en node betyder att jobbet misslyckades.

Återanslut offline-noder genom reconciliation, inte genom blind sync.

Återkalla en förlorad eller komprometterad node innan recovery eller ersättning.

Låt aldrig samma högrisknode ensam kontrollera, godkänna, exekvera, verifiera och skriva om historiken.

När dessa gränser är verkliga kan Omnira använda en hel väv av mobiler, datorer, privata riggar, molnworkers och framtida organisationsnoder utan att förlora kontrollen över vem som gör arbetet, var datan finns eller vilken state som är canonical.
