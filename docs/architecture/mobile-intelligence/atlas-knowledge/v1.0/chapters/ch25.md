# Kapitel 25 — Nodval, arbetsplacering och providerkontinuitet


## Kapitelmandat

Detta kapitel definierar den kanoniska arkitekturen för nodval, arbetsplacering, resursmatchning, providerkontinuitet, omplacering, väntelägen, failover och exekveringsresiliens inom Omnira Mobile Intelligence & Device Control.

Kapitlet fastställer:

- hur Atlas ska välja rätt node för rätt arbete,
- hur task requirements ska översättas till placeringskrav,
- hur hårda constraints ska skiljas från optimeringspreferenser,
- hur node, surface, provider, model, account, credential, project och tenant ska bindas ihop i ett placeringsbeslut,
- hur capability, trust, locality, privacy, authority, budget, kvalitet, latency, energi och användarpåverkan ska vägas,
- hur arbete ska placeras mellan mobil, laptop, workstation, privat rigg, cloud node och framtida tenantworkers,
- hur local-only-, node-bound-, region-bound- och human-presence-bound-arbete ska skyddas,
- hur Atlas ska agera när ingen node uppfyller alla krav,
- hur waiting for node, waiting for power, waiting for network, waiting for approval, waiting for provider och andra säkra väntelägen ska fungera,
- hur node selection ska skiljas från provider selection,
- hur local model, remote model, provider API och execution node ska kombineras utan sammanblandning,
- hur provider continuity ska bevara task semantics, provenance, project scope, budget och data policy,
- hur providerbyte ska ske utan att data skickas till otillåten destination,
- hur samma task kan flyttas mellan noder utan att duplicera side effects,
- hur checkpointing, resumability, portable task state och normalized outputs ska stödja kontinuitet,
- hur Atlas ska hantera node outage, provider outage, regional outage, model retirement, accountproblem, rate limits och kapacitetsbrist,
- hur planned migration ska skiljas från emergency failover,
- hur work placement ska styras av deadline, cost-quality frontier och current system state,
- hur batcharbete, interaktivt arbete, realtidsarbete och långvariga jobs ska placeras olika,
- hur användarens primära devices ska skyddas från onödig belastning,
- hur placement decisions ska förklaras, auditloggas och testas,
- hur framtida tenants ska kunna styra regioner, managed nodes, approved providers, cost centers och continuity requirements,
- vilka absoluta placerings- och continuityförbud samt blockerande tester som ska gälla.
Kapitlet är normerande för varje beslut där Omnira väljer var, när och genom vilken kombination av node, provider, model, surface och credential ett arbete ska utföras.


## 25.1 Inledning

Att ha flera noder och providers skapar inte automatiskt ett resilient system.

Det kan i stället skapa ett system som:

- skickar jobb till första bästa online-node,
- flyttar känslig data till moln när en lokal rigg är avstängd,
- använder fel provider för att den är snabb,
- startar om samma jobb på flera ställen,
- överbelastar användarens mobil,
- väljer billigast trots otillräcklig kvalitet,
- fastnar i dyr retryloop,
- tappar project context vid handoff,
- använder ett annat account än det som godkändes,
- fortsätter på stale policy efter reconnect,
- byter region utan att användaren vet det,
- kallar teknisk failover för business continuity trots att resultatet inte verifierats.
Rätt arbetsplacering kräver mer än kapacitet.

Den kräver att Atlas samtidigt förstår:

- vad uppgiften innebär,
- vilken data den använder,
- vilken authority den kräver,
- vilken kvalitet som behövs,
- vilken provider som är tillåten,
- vilken node som är betrodd,
- var datan får finnas,
- vilken kostnad som ryms,
- när arbetet måste vara klart,
- vad som händer om execution avbryts.
Det kan därför vara korrekt att:

- köra direkt på mobilen,
- vänta tills laptopen är tillgänglig,
- be André starta den privata riggen,
- använda en godkänd cloud worker,
- byta textprovider,
- fortsätta från checkpoint på annan node,
- pausa hela workflowet.
Den bästa placeringen är inte alltid den snabbaste.

Det är den placering som uppfyller uppgiftens verkliga krav utan att försvaga governance.


## 25.2 Normativ definition av arbetsplacering

Arbetsplacering, eller work placement, är beslutet om var och under vilka exekveringsvillkor en task eller ett execution attempt ska utföras.

Ett placeringsbeslut kan omfatta:

- node,
- surface,
- provider,
- model,
- account,
- credential,
- region,
- network path,
- storage location,
- execution window,
- fallback plan.
<a id="MI-25-001"></a>
> **MI-25-001** — Varje materiell task SKA ha ett explicit placeringsbeslut före execution.

<a id="MI-25-002"></a>
> **MI-25-002** — Placeringsbeslut SKA vara bundet till task identity, project, tenant och aktuell policyversion.

<a id="MI-25-003"></a>
> **MI-25-003** — Placement FÅR INTE reduceras till valet av node enbart.

<a id="MI-25-004"></a>
> **MI-25-004** — Placement SKA kunna rekonstrueras och förklaras i efterhand.


## 25.3 Placering kontra routing

Provider-routing avgör vilken tjänst eller modell som ska användas.

Node placement avgör var tasken eller provideranropet ska exekveras.

Dessa beslut kan kombineras men ska inte sammanblandas.

Exempel:

- en laptopnode anropar en extern textprovider,
- en privat rigg kör en lokal bildmodell,
- en cloud node koordinerar men datan behandlas på en lokal node,
- en mobilnode gör lokal redaktion före provideranrop.
<a id="MI-25-005"></a>
> **MI-25-005** — Node selection och provider selection SKA vara separata men koordinerade beslut.

<a id="MI-25-006"></a>
> **MI-25-006** — Godkänd provider FÅR INTE innebära att alla noder får anropa den.

<a id="MI-25-007"></a>
> **MI-25-007** — Godkänd node FÅR INTE innebära att alla providers får användas därifrån.

<a id="MI-25-008"></a>
> **MI-25-008** — Placement engine SKA verifiera kombinationen node, provider, account, region och credential.

## 25.108 Slutlig normativ slutsats

Omnira ska inte placera arbete där det råkar finnas ledig compute.

Det ska placera arbete där hela exekveringsvägen är korrekt.

Det betyder att rätt placement samtidigt måste uppfylla:

- rätt node,
- rätt surface,
- rätt provider,
- rätt modell,
- rätt account,
- rätt credential,
- rätt project,
- rätt tenant,
- rätt locality,
- rätt kvalitet,
- rätt budget,
- rätt continuitynivå.
När den privata riggen är avstängd kan det korrekta beslutet vara att vänta.

När mobilen har låg batterinivå kan det korrekta beslutet vara att flytta arbetet till laptopen.

När laptopen saknar lagring kan det korrekta beslutet vara att använda riggen.

När providern är nere kan det korrekta beslutet vara att använda en annan godkänd provider.

När fallback förändrar region, account, cost eller rights kan det korrekta beslutet vara att be om nytt approval.

När previous outcome är okänt kan det korrekta beslutet vara att inte göra någonting förrän state är reconcilerad.

Den kanoniska placeringsprincipen är därför:

Definiera taskens krav innan en node väljs.

Filtrera efter tillåtlighet före optimering.

Välj hela exekveringsvägen, inte bara en maskin eller modell.

Låt local-only och node-bound arbete vänta när rätt plats saknas.

Skydda användarens primära devices från onödig belastning.

Bevara task identity, project, provenance och authority genom varje handoff.

Använd checkpoint och portable state innan automatisk failover införs.

Kontrollera previous outcome före retry eller reassignment.

Låt fallback bevara governance, inte kringgå den.

Behandla waiting och degraded mode som legitima, tydliga systemtillstånd.

Kalla inte omstart för continuity om state, resultat eller external effects inte bevarats.

När dessa krav är verkliga kan Atlas fördela arbete mellan mobil, laptop, privat rigg, moln, lokala modeller och externa providers utan att systemet tappar kontrollen över var datan finns, vem som äger jobbet eller vilket resultat som faktiskt är giltigt.
