# Kapitel 26 — Workflowägarskap, samtidighet och dubblettskydd


## Kapitelmandat

Detta kapitel definierar den kanoniska arkitekturen för workflowägarskap, exekveringsansvar, samtidighet, leases, fencing, idempotency, deduplicering, reservations, serialisering, retries och dubblettskydd inom Omnira Mobile Intelligence & Device Control.

Kapitlet fastställer:

- vad ett workflow är inom Omnira,
- hur workflow skiljs från task, job, execution attempt, command, event, action och saga,
- hur ett workflow får en entydig owner,
- hur mänsklig owner, project owner, agent owner, orchestration owner, execution owner och resource owner ska skiljas,
- hur ägarskap ska överföras mellan Atlas, agents, nodes och människor,
- hur flera agents och nodes får arbeta parallellt utan att skapa motstridiga eller duplicerade effekter,
- hur concurrency ska klassificeras som säker, begränsad, exklusiv eller förbjuden,
- hur read concurrency ska skiljas från write concurrency,
- hur entity-, account-, project-, resource- och effect-scoped locks ska fungera,
- hur leases, heartbeats och fencing tokens ska förhindra stale execution,
- hur idempotency keys ska utformas, scope:as, lagras och verifieras,
- hur duplicate delivery ska skiljas från duplicate execution och duplicate external effect,
- hur retries ska hanteras när resultatet är success, failure, partial eller unknown,
- hur Omnira ska förhindra dubbla publiceringar, meddelanden, betalningar, deletioner, filflyttar, bokningar och providerjobb,
- hur workflow state och external state ska reconcileras,
- hur reservations ska användas för budget, lager, providerquota, GPU, tidsslottar och human attention,
- hur optimistic och pessimistic concurrency ska väljas,
- hur compare-and-swap, versionsnummer, conditional writes och transactional outbox ska användas,
- hur distributed locks ska begränsas och kompletteras med fencing,
- hur sagas, compensation och irreversible steps ska styras,
- hur parent-, child- och subworkflowägarskap ska fungera,
- hur fan-out, fan-in, parallel branches och join conditions ska modelleras,
- hur workflows ska pausa, avbrytas, återupptas, migreras och återställas,
- hur offline actions och senare sync ska undvika dubbletter,
- hur human approvals ska bindas till exakt workflow- och stateversion,
- hur emergency stop ska fenca pågående exekvering,
- hur tenant- och projectgränser ska bevaras under concurrent execution,
- hur audit, explainability, testing och incidenthantering ska fungera,
- vilka absoluta workflow-, concurrency- och dubblettförbud som ska gälla.
Kapitlet är normerande för varje process där mer än en actor, agent, node, systemkomponent eller execution attempt kan påverka samma state, resurs eller externa effekt.


## 26.1 Inledning

När Omnira arbetar på flera devices, genom flera agents och mot flera providers uppstår en grundläggande risk:

Fler än en komponent kan tro att den får göra samma sak.

Det kan leda till:

- samma inlägg publiceras två gånger,
- samma e-post skickas flera gånger,
- samma betalning initieras igen,
- samma fil flyttas av två workflows,
- samma möte bokas dubbelt,
- samma providerjobb startas flera gånger,
- två agents uppdaterar samma canonical dokument,
- en gammal node skriver över nyare state,
- ett retry sker trots att den första exekveringen lyckades,
- ett offlinekommando återspelas efter att uppgiften redan slutförts,
- en människa och agenten ändrar samma objekt samtidigt,
- ett workflow fortsätter efter att dess authority återkallats.
Distribuerade system kan inte förlita sig på att varje meddelande levereras exakt en gång.

De kan inte heller förlita sig på att:

- timeout betyder failure,
- svar betyder external success,
- en worker som är tyst har slutat,
- senaste timestamp är korrekt,
- en lock aldrig förloras,
- ett API alltid stöder idempotency,
- en användare aldrig trycker två gånger.
Omnira måste därför utformas för en verklighet där:

- meddelanden kan levereras flera gånger,
- noder kan tappa kontakt,
- svar kan försvinna,
- processer kan krascha efter external effect men före local commit,
- gamla workers kan vakna igen,
- users och agents kan agera samtidigt,
- state kan vara delvis uppdaterad.
Den kanoniska principen är inte:

Försök skicka allt exakt en gång.

Den är:

Designa varje stateförändring så att dubbletter, stale workers och osäkerhet kan upptäckas, blockeras, reconcileras eller kompenseras.


## 26.2 Normativ definition av workflow

Ett workflow är en governad, tillståndsbärande process som koordinerar en eller flera tasks, actions, approvals, nodes, agents, providers och external effects mot ett definierat mål.

Ett workflow ska minst kunna ha:

- workflow ID,
- workflow type,
- owner,
- project,
- tenant,
- initiator,
- goal,
- current state,
- version,
- authority,
- input references,
- child tasks,
- external effects,
- deadlines,
- retry policy,
- cancellation policy,
- verification requirements,
- lifecycle.
<a id="MI-26-001"></a>
> **MI-26-001** — Varje workflow SKA ha globalt unik workflow identity inom relevant systemdomän.

<a id="MI-26-002"></a>
> **MI-26-002** — Workflow identity SKA bevaras genom retries, nodebyten och providerfailover.

<a id="MI-26-003"></a>
> **MI-26-003** — Varje workflow SKA ha exakt definierad owner och project- eller tenantbinding.

<a id="MI-26-004"></a>
> **MI-26-004** — Workflow state SKA vara versionerad och auditbar.

- kontrollera om provider erbjuder undo,
- föreslå korrigeringsmeddelande,
- markera workflowet som completed with follow-up.
Originaleffekten bevaras i audit.

Exempel J — Project hibernate

GainPilot sätts i hibernate.

Project-level stop höjer project fencing epoch.

Nya workflows blockeras.

Queued nonessential tasks canceleras.

Pågående critical storage- och recoveryjobb får explicit policy.

Arnold förlorar nya execution leases.

Ett stale background attempt försöker senare skriva.

Epoch mismatch blockerar write.

Project state förblir hibernate.

## 26.137 Slutlig normativ slutsats

Omnira ska aldrig bygga säkerheten på antagandet att en action endast kommer att försöka utföras en gång.

I ett verkligt distribuerat system kan:

- användaren trycka två gånger,
- samma command levereras två gånger,
- två nodes tro att de äger jobbet,
- en provider utföra en request utan att svaret når tillbaka,
- en gammal worker vakna efter failover,
- en offline device återspela stale commands,
- en agent och människa ändra samma state samtidigt.
Därför ska Omnira alltid kunna svara på:

Vem äger workflowet nu?

Vilken version av state arbetas det mot?

Vilken effect scope skyddas?

Har samma business intent redan registrerats?

Finns ett pågående eller verifierat external result?

Är den här workern fortfarande giltig?

Är retry säkert?

Har commit boundary passerats?

Kan actionen stoppas, reconcileras eller kompenseras?

Den kanoniska workflowprincipen är därför:

Ge varje workflow en owner.

Ge varje attempt en egen identity.

Definiera effect scope innan concurrency tillåts.

Använd versioner, leases och fencing för att stoppa stale writers.

Definiera idempotency på business intent, inte endast requesten.

Behandla duplicate delivery som normalt och duplicate external effect som incident.

Tolka aldrig timeout som verifierat failure.

Reconcila före retry när previous outcome är okänt.

Versionsbind approvals och invalidera gamla beslut när state ändras.

Låt human actions delta i samma concurrencymodell som agents.

Använd compensation ärligt och kalla det inte rollback när världen inte återställts exakt.

Stoppa automatic failover tills ownership, idempotency och duplicate prevention fungerar.

När dessa mekanismer är verkliga kan Atlas, agents, mobilen, laptopen, privata riggen och molnet samarbeta samtidigt utan att samma handling sker två gånger, fel version vinner eller en gammal worker fortsätter styra systemet efter att dess rätt har upphört.
