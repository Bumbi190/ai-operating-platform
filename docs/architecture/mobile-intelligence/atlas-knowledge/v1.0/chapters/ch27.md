# Kapitel 27 — Offlinedrift, synkronisering och canonical state


## Kapitelmandat

Detta kapitel definierar den kanoniska arkitekturen för offlinedrift, lokal state, synkronisering, replikering, konflikthantering, reconciliation och canonical state inom Omnira Mobile Intelligence & Device Control.

Kapitlet fastställer:

- vad offline betyder i ett distribuerat Omnira-system,
- hur offline ska skiljas från degraded, disconnected, partitioned, stale, unavailable och unknown,
- vilka funktioner som får fortsätta lokalt utan nätverk,
- hur authority, approvals, mandates, credentials och policies ska begränsas offline,
- hur mobil, laptop, privat rigg och andra nodes ska bära lokal state,
- hur local state ska skiljas från canonical state,
- hur en node ska veta vilken state som får läsas, ändras, köas eller endast observeras,
- hur local-first och offline-first ska användas utan att skapa parallella sanningar,
- hur commands, events, edits, files, memory, geofences, notifications och workflowstate ska köas,
- hur varje offlineförändring ska identifieras, versionsbindas och dedupliceras,
- hur reconnect ska börja med identity, trust, revocation, policy och tombstones,
- hur sync ska skilja transport, replication, reconciliation, merge och promotion,
- hur conflict detection ska fungera,
- hur last-write-wins ska begränsas,
- hur versionsvektorer, revisionsnummer, causal metadata, operation logs och compare-and-swap kan användas,
- hur olika datatyper ska använda olika merge- och conflictstrategier,
- hur canonical state ska definieras per objekt och systemdomän,
- hur authority över canonical state ska skiljas från lokal writeability,
- hur offline writes ska promoteras eller avvisas,
- hur raderingar och tombstones ska prioriteras,
- hur revoked credentials, expired approvals, suspended projects och emergency stop ska verkställas efter reconnect,
- hur flera offline nodes ska reconcileras,
- hur stale nodes ska hindras från att skriva över nyare state,
- hur duplicate commands och external effects ska förhindras,
- hur partial sync, interrupted sync, clock skew, missing history och corrupted state ska hanteras,
- hur användaren ska kunna förstå vad som är lokalt, osynkat, conflicted eller canonical,
- hur organisationer ska hantera managed offline nodes, regional sync och tenantisolering,
- vilka absoluta offline-, sync- och canonical-state-förbud samt blockerande tester som ska gälla.
Kapitlet är normerande för varje workflow där en node kan arbeta utan full kontakt med Omniras control plane, canonical data source, provider, verifieringsyta eller annan nödvändig systemdel.


## 27.1 Inledning

En mobil kan tappa nätverk.

En laptop kan vara avstängd.

En privat rigg kan vara offline.

Ett moln kan bli otillgängligt.

En provider kan svara långsamt eller inte alls.

Ett lokalt workflow kan fortsätta samtidigt som central state förändras någon annanstans.

Detta innebär att Omnira måste fungera i en värld där alla komponenter inte alltid ser samma state samtidigt.

Det är frestande att lösa detta genom att säga:

Senaste ändringen vinner.

Men det kan orsaka:

- att en gammal mobil återställer raderad data,
- att ett utgånget approval används,
- att en offline node publicerar efter project stop,
- att en filändring skriver över en senare canonical version,
- att ett återkallat credential används efter reconnect,
- att två kalenderbokningar skapas,
- att samma påminnelse visas flera gånger,
- att en tidigare providerrequest skickas igen,
- att lokal cache behandlas som source of truth.
Det är lika fel att säga:

Inget får fungera offline.

Mobilen ska fortfarande kunna:

- visa lokala reminders,
- läsa godkänd cached information,
- registrera notes,
- hantera vissa geofences,
- ta emot bounded user input,
- köa säkra commands,
- utföra device-local actions,
- fortsätta vissa lokala workflows.
Den kanoniska frågan är därför inte:

Är noden online eller offline?

Utan:

Vilken state känner noden till, vilken authority gäller fortfarande, vilka lokala förändringar är säkra och hur återförenas de med canonical state utan att något dupliceras, återuppstår eller skrivs över felaktigt?


## 27.2 Normativ definition av offline

En node är offline när den saknar tillräcklig anslutning till en eller flera nödvändiga Omnira-komponenter för normal synkroniserad drift.

Offline kan avse bristande kontakt med:

- control plane,
- canonical state store,
- identity service,
- credential service,
- provider,
- verification surface,
- audit service,
- annan node.
<a id="MI-27-001"></a>
> **MI-27-001** — Offline SKA definieras relativt till vilka systemdelar som inte kan nås.

<a id="MI-27-002"></a>
> **MI-27-002** — En node FÅR INTE klassas som fullt online enbart för att internetanslutning finns.

<a id="MI-27-003"></a>
> **MI-27-003** — En node FÅR INTE klassas som helt offline om vissa relevanta tjänster fortfarande är nåbara.

<a id="MI-27-004"></a>
> **MI-27-004** — Connectivity state SKA vara explicit och tidsstämplad.


## 27.3 Offline kontra disconnected

Offline betyder att noden inte kan genomföra normal systemfunktion genom tillräckliga länkar.

<a id="MI-27-007"></a>

## 27.4 Offline kontra degraded

<a id="MI-27-011"></a>

## 27.5 Offline kontra partitioned

Detta skapar särskild risk för:

- split ownership,
- parallella writes,
- stale authority,
- duplicate execution.

<a id="MI-27-014"></a>

- local tombstones,

<a id="MI-27-071"></a>

## 27.115 Primära failure modes

Online-flag illusion

Systemet använder en enda boolesk onlineflagga och missar vilka services som faktiskt saknas.

Offline authority inflation

Node fortsätter med bred authority trots stale policy eller revocationrisk.

Cache-as-truth

Lokal replica behandlas som canonical state.

Blind queue replay

Alla queued commands körs efter reconnect utan omvärdering.

Timestamp dominance

Senaste lokala timestamp används som truth.

Tombstone loss

Raderad data återuppstår från offline node eller backup.

Silent merge

Motstridiga changes kombineras utan semantic review.

First-reconnect-wins

Första node som återansluter får skriva över andra.

Partial-sync concealment

Systemet visar sync success trots att object saknas eller konflikter kvarstår.

Stale approval execution

Offline approval används efter att state eller content ändrats.

Revoked credential continuation

Node använder credential som återkallats under offlineperioden.

Lost unsynced work

Cleanup eller device loss raderar user work som aldrig promoterats.

<a id="MI-27-403"></a>
> **MI-27-403** — Offline- och syncarkitekturen SKA uttryckligen skydda mot cache-as-truth, blind queue replay, timestamp dominance, tombstone loss, stale approval execution, revoked credential continuation och lost unsynced work.

## 27.121 Slutlig normativ slutsats

Omnira ska kunna fortsätta fungera när nätverk, moln, provider eller annan node saknas.

Men offlinedrift får aldrig innebära att varje node skapar sin egen sanning.

En mobil får kunna:

- visa cached information,
- skapa notes,
- köra local geofences,
- registrera user actions,
- bygga proposals,
- köa bounded commands.
Den får inte automatiskt:

- publicera,
- betala,
- höja authority,
- återaktivera credentials,
- skriva över canonical state,
- återuppliva raderad data.
Den kanoniska offlineprincipen är därför:

Beskriv exakt vad som är otillgängligt.

Begränsa authority efter offlineperiodens risk.

Märk lokal state som lokal.

Versionsbind varje ändring.

Köa intent, inte blind framtida execution.

Revalidera identity, trust, policy och credentials vid reconnect.

Applicera emergency stop, revocations och tombstones före normal sync.

Reconcila external state före retry.

Låt inte första reconnectande node eller senaste timestamp vinna automatiskt.

Behandla semantic conflict som conflict, inte som mergeproblem.

Skydda unsynced user work.

Promovera endast genom rätt canonical authority.

Säg aldrig “synkroniserad” när state fortfarande är partial, conflicted eller unverified.

När dessa regler är verkliga kan Omnira fungera genom nätverksavbrott, avstängda noder, mobila miljöer och regionala störningar utan att systemet förlorar skillnaden mellan en lokal observation, en pending ändring och den state som faktiskt är canonical.
