# Kapitel 29 — Felhantering, rollback, compensation och nödstopp


## Kapitelmandat

Detta kapitel definierar den kanoniska arkitekturen för felhantering, containment, rollback, compensation, recovery, degraded operation och emergency stop inom Omnira Mobile Intelligence & Device Control.

Kapitlet fastställer:

- vad ett failure är inom Omnira,
- hur failure ska skiljas från error, exception, rejection, cancellation, timeout, degradation, conflict, partial success och unknown_outcome,
- hur fel ska klassificeras efter källa, omfattning, varaktighet, säkerhet, data, authority, project, tenant, cost och external effect,
- hur failures ska isoleras till minsta möjliga scope,
- hur systemet ska välja mellan retry, wait, rollback, compensation, reconciliation, quarantine, failover, degraded mode och human intervention,
- när rollback verkligen är möjlig,
- när rollback är tekniskt eller semantiskt falskt,
- hur compensation ska utformas för redan inträffade external effects,
- hur partial failure ska hanteras i distributed workflows,
- hur irreversible actions och commit boundaries ska styra recovery,
- hur local state, canonical state och external state ska återställas eller reconcileras,
- hur Atlas ska undvika att göra ett fel större genom blind retry, aggressiv failover eller överdriven cleanup,
- hur data corruption, storage failure, provider failure, node failure, network partition, credential failure och policy failure ska hanteras,
- hur högriskincidenter ska stoppa eller begränsa execution,
- hur emergency stop ska kunna scope:as till action, workflow, capability, account, node, provider, project, tenant, region eller hela Omnira,
- hur pågående commands, jobs, leases, queues, credentials och providerrequests ska påverkas av nödstopp,
- hur offline nodes ska ta emot och verkställa ett stopp efter reconnect,
- hur nödstopp ska skiljas från pause, cancellation, suspension, quarantine och shutdown,
- hur emergency stop ska kunna aktiveras av användare, Atlas, policy, incidentdetektion eller recovery authority,
- hur ett nödstopp ska förhindra nya side effects utan att förstöra evidens eller meningsbärande state,
- hur återstart efter stopp ska ske genom kontrollerad revalidation,
- hur recovery plans, runbooks, recovery owners och manual resolution ska definieras,
- hur backup och restore ska användas utan att återintroducera raderad, stale eller komprometterad state,
- hur människan ska informeras om påverkan, osäkerhet, återstående risk och nästa säkra steg,
- hur fel och recovery ska auditloggas utan att systemet blir beroende av full känslig payload,
- hur project- och tenantpolicy ska styra failure tolerance, recovery objectives och emergency powers,
- vilka absoluta failure-, rollback-, compensation- och emergency-stop-förbud samt blockerande tester som ska gälla.
Kapitlet är normerande för varje situation där Omnira inte längre säkert kan fortsätta som planerat, där en handling redan kan ha skapat en effekt eller där fortsatt automation riskerar att öka skadan.


## 29.1 Inledning

Ett pålitligt system definieras inte endast av hur ofta det lyckas.

Det definieras av vad det gör när något går fel.

Ett dåligt felhanterande system kan:

- försöka igen tills kostnaden skenar,
- starta samma publicering på flera noder,
- kalla compensation för rollback,
- skriva över den enda fungerande kopian,
- återställa en backup som återintroducerar raderad data,
- fortsätta använda ett komprometterat credential,
- flytta local-only-data till moln under outage,
- radera evidens i ett försök att “städa”,
- starta om efter nödstopp utan att förstå vad som hände,
- rapportera att allt är återställt fast externa effekter finns kvar.
Ett säkert system måste kunna stanna.

Det måste kunna säga:

- detta steg misslyckades,
- detta steg lyckades delvis,
- detta utfall är fortfarande okänt,
- denna effekt kan återställas exakt,
- denna effekt kan endast kompenseras,
- denna skada kan inte automatiskt repareras,
- denna provider eller node måste isoleras,
- detta workflow får inte fortsätta,
- detta kräver mänskligt beslut.
Det kan ibland vara bättre att pausa ett helt project än att låta ett osäkert workflow fortsätta.

Det kan vara bättre att bevara en felaktig men tydligt quarantänsatt artifact än att radera den och förlora evidens.

Det kan vara bättre att vänta på en auktoritativ external-state-kontroll än att försöka göra samma sak igen.

Den kanoniska felprincipen är därför:

Minimera skadan före optimering av återhämtningen.

Fastställ vad som faktiskt hände före nästa side effect.

Återställ endast det som verkligen kan återställas.

Kompensera öppet när världen inte kan rullas tillbaka exakt.

Stoppa automation när osäkerheten är större än mandatet.


## 29.2 Normativ definition av failure

Ett failure är ett tillstånd där en operation, task, workflow, node, provider, policy eller systemkomponent inte uppfyller en definierad postcondition, serviceförväntan eller säkerhetsinvariant.

<a id="MI-29-001"></a>
> **MI-29-001** — Failure SKA bedömas mot explicit expected behavior eller postcondition.

<a id="MI-29-002"></a>
> **MI-29-002** — Failure SKA vara identifierat med source, scope, time och affected objects.

<a id="MI-29-003"></a>
> **MI-29-003** — Failure FÅR INTE automatiskt likställas med att ingen external effect inträffade.

<a id="MI-29-004"></a>
> **MI-29-004** — Failure state SKA kunna skilja verified failure, partial failure och unknown outcome.


## 29.3 Error kontra failure

Ett error är ett upptäckt felvillkor.

Ett failure är att systemet eller workflowet inte uppnår det avsedda resultatet.

Exempel:

- ett timeout-error kan förekomma trots att external effect lyckades,
- ett valideringsfel kan stoppa execution utan business failure,
- ett internt warning kan vara ofarligt om postconditions ändå uppnås.
<a id="MI-29-005"></a>
> **MI-29-005** — Error och failure SKA modelleras separat.

<a id="MI-29-006"></a>
> **MI-29-006** — Error code FÅR INTE ensam avgöra business outcome.

<a id="MI-29-007"></a>
> **MI-29-007** — Flera errors FÅR förekomma utan full workflow failure om recovery lyckas och postconditions verifieras.


## 29.4 Exception kontra failure

En exception är en teknisk kontrollflödes- eller runtimehändelse.

<a id="MI-29-008"></a>
> **MI-29-008** — Exception SKA klassificeras innan recoverybeslut.

<a id="MI-29-009"></a>
> **MI-29-009** — Unhandled exception SKA kunna stoppa berörd execution path men FÅR INTE automatiskt markera external effect som failed.

<a id="MI-29-010"></a>

## 29.142 Primära failure modes

Retry reflex

Varje fel behandlas med omedelbart nytt försök.

Rollback illusion

Systemet säger rollback trots att external effect eller historik kvarstår.

Compensation concealment

Korrigerande action döljs som om originaleffekten aldrig skett.

Recovery before reconciliation

Systemet försöker återställa utan att veta vad som faktiskt hände.

Destructive cleanup

Evidence eller enda fungerande copy raderas i ett försök att “städa”.

Failover amplification

En lokal failure sprids genom aggressiv node-, provider- eller regionfallback.

Stop without fencing

UI visar stoppat men gamla workers kan fortsätta.

Process-stop illusion

En process dödas men externa requests, queues eller tokens förblir aktiva.

Auto-restart relapse

Systemet startar om direkt in i samma fel.

Backup contamination

Restore återintroducerar raderad, stale eller komprometterad state.

Partial-recovery concealment

Vissa delar återställs men status visas som full recovery.

Human-blame shortcut

Systemiska skyddsbrister beskrivs endast som användarfel.

- klassificera severity F0–F6,
- bedöma scope och blast radius,
- följa lifecycle för detect, classify, contain, preserve evidence, stabilize, recover, verify och restart,
- välja recoverystrategi efter effect, reversibility och evidence,
- inte använda retry som standard,
- använda waiting, resume, restart, failover och manual resolution proportionerligt,
- definiera rollback strikt,
- skilja rollback från compensation, restore och repair,
- behandla compensation som ny external effect,
- definiera reversibility och commit boundaries,
- göra partial failure till first-class state,
- identifiera safe recovery points,
- verifiera checkpoints och backups,
- använda staging för osäker restore,
- skydda tombstones, revocations och current policy vid restore,
- använda repair och rebuild endast för lämplig state,
- använda quarantine utan automatisk deletion,
- stödja read-only, local-only och manual-only degraded modes,
- ha durable emergency-stop-capability,
- skilja emergency stop från pause, cancellation, shutdown och quarantine,
- stödja stop scope från action till globalt,
- tillåta human och policy-driven stop,
- blockera commands, queues, retries, failover, leases, credentials, sync och memory writes,
- verifiera stop enforcement,
- låta stop state överleva restart,

- använda staged controlled restart,
- reconcila queues, credentials, nodes och unknown effects före återstart,
- använda recovery owners, incident commander och runbooks,

- kommunicera fakta och osäkerhet tydligt,
- auditera failure, containment, rollback, compensation och recovery,

## 29.148 Slutlig normativ slutsats

Omnira ska inte försöka dölja fel genom att fortsätta arbeta snabbare.

Det ska inte behandla varje error som ett nytt försök.

Det ska inte kalla en korrigering för rollback när den ursprungliga effekten redan har inträffat.

Det ska inte återställa en backup utan att först förstå vilka senare deletioner, revocations, workflows och external effects som finns.

Det ska inte nöja sig med att stänga en process när queues, providerjobb, credentials och gamla workers fortfarande kan fortsätta.

Den kanoniska failureprincipen är därför:

Klassificera innan recovery.

Begränsa blast radius innan service återställs.

Bevara evidence innan destructive action.

Reconcila unknown outcomes före retry.

Använd rollback endast när tidigare state verkligen kan återställas.

Använd compensation öppet när världen redan har förändrats.

Behandla partial failure som partial.

Låt quarantine isolera utan att automatiskt radera.

Gör emergency stop durable, scope:at och tekniskt enforcebart.

Stoppa retries, failover, queues och stale workers tillsammans.

Verifiera att stoppet faktiskt gäller.

Återstarta stegvis genom read-only, limited mode och canary.

Återaktivera inte credentials, nodes eller queues innan de har reconcilerats.

Kalla inte systemet återställt förrän recovery postconditions är verifierade.

Låt varje materiellt failure förbättra policies, tester, runbooks och capability maturity.

När dessa regler är verkliga kan Omnira misslyckas utan att tappa kontrollen, återhämta sig utan att skriva om sanningen och stoppa sig självt innan ett lokalt fel växer till ett systemfel.
