# Kapitel 31 — Versionering, testning, utrullning och capability expansion


## Kapitelmandat

Detta kapitel definierar den kanoniska arkitekturen för versionering, kompatibilitet, testning, validering, release governance, staged rollout, capability expansion, maturity promotion och kontrollerad avveckling inom Omnira Mobile Intelligence & Device Control.

Kapitlet fastställer:

- vad som ska versionsmärkas inom Omnira,
- hur versionsidentitet ska skiljas från namn, alias, deploytid och marknadsföringsetikett,
- hur kod, schema, policy, prompt, workflow, agent, capability, model, provideradapter, node runtime, mobile app, API, event, auditformat och canonical books ska versioneras,
- hur backward compatibility, forward compatibility, migration och explicit incompatibility ska hanteras,
- hur pinned, minimum, supported, deprecated och forbidden versions ska definieras,
- hur compatibility contracts ska skydda project-, tenant-, device-, provider- och dataflöden,
- hur schema evolution ska bevara identity, provenance, tombstones, approvals, idempotency och audit,
- hur testning ska organiseras från unit tests till end-to-end-, failure-, recovery-, privacy-, security-, offline-, concurrency- och human-factors-tester,
- hur simulation, fixtures, digital twins, shadow mode, canary och staged rollout ska användas,
- hur productionlik testdata ska skapas utan att privata data kopieras obehörigt,
- hur regressioner ska klassificeras och blockera release,
- hur safety invariants och absoluta förbud ska göras till blockerande tester,
- hur test evidence och validation evidence ska lagras och länkas till releasebeslut,
- hur release candidates ska skapas, frysas, signeras, granskas och promoteras,
- hur rollout ska kunna scope:as till user, device, node, project, tenant, provider, capability, region och riskklass,
- hur feature flags, kill switches, emergency stop och policy gates ska samverka,
- hur rollback, roll-forward och compensation ska skiljas vid releaseproblem,
- hur migrationsordning ska styras mellan code, schema, policy, data, credentials, prompts och workflows,
- hur multi-node- och offlinekompatibilitet ska bevaras under stegvis uppgradering,
- hur stale clients och äldre nodes ska begränsas,
- hur forced updates ska användas proportionerligt,
- hur capability expansion ska gå från observation till proposal, test, approval, limited activation och full promotion,
- hur authority, dataåtkomst, external effects och autonomy ska expandera separat,
- hur capability maturity ska mätas och kunna sänkas,
- hur project- och tenantpolicies ska kunna ställa egna releasekrav,
- hur modeller och providers ska valideras före byte eller automatisk aliasuppgradering,
- hur deprecation, retirement, sunset och removal ska ske utan att förlora data, audit eller recoverability,
- hur experiment ska skiljas från productionbeslut,
- hur drift, performance, cost, quality, privacy och user impact ska övervakas under rollout,
- hur en release ska stoppas eller återkallas,
- vilka absoluta versions-, test-, rollout- och capability-expansionförbud samt blockerande tester som ska gälla.
Kapitlet är normerande för varje förändring som kan påverka hur Omnira tolkar policy, använder data, fattar beslut, styr devices, väljer providers, exekverar workflows eller skapar externa effekter.


## 31.1 Inledning

Ett säkert system är inte säkert en gång för alla.

Det förändras.

Kod uppdateras.

Policies revideras.

Prompts förbättras.

Providers byter modeller.

API:er deprecieras.

Devices får nya operativsystem.

Agents får nya tools.

Workflows får fler steg.

Datamodeller migreras.

Capability maturity höjs.

Varje förändring kan vara korrekt isolerat men ändå skapa systemfel i kombination med äldre state, äldre clients eller andra komponenter.

En ny appversion kan:

- förstå ett approval annorlunda,
- skriva ett schema som en gammal node inte kan läsa,
- tolka en tombstone som vanlig metadata,
- använda en ny provider utan rätt regionpolicy,
- återspela en gammal queue,
- dölja ett nytt field i UI,
- visa “klart” för en state som inte längre betyder samma sak.
En provider kan byta modell bakom ett stabilt alias och därmed förändra:

- kvalitet,
- säkerhetsbeteende,
- kostnad,
- context window,
- format,
- kommersiella rättigheter,
- datahantering.
En capability kan fungera hundra gånger i låg-riskläge och ändå vara omogen för:

- payment,
- deletion,
- private communication,
- owner transfer,
- cross-tenant execution.
Därför får Omnira inte behandla förändring som en enkel teknisk deploy.

Varje materiell förändring är ett governat systembeslut.

Den kanoniska förändringsprincipen är:

Versionsmärk allt som påverkar mening, authority, execution eller verifiering.

Testa både normalfall och failure modes.

Rulla ut till minsta säkra scope.

Mät verifierade outcomes, inte enbart teknisk completion.

Höj capability stegvis och separat per riskdimension.

Bevara rollback eller roll-forward innan förändringen aktiveras.

Stoppa expansion när evidensen inte längre stödjer den.

## 31.166 Slutlig normativ slutsats

Omnira ska aldrig förändras på ett sätt som gör att systemet inte längre kan svara på vilken version som fattade ett beslut.

Det ska inte låta:

- en provider ändras bakom ett alias,
- en prompt ändras utan identity,
- en gammal mobil skriva över ny state,
- en feature flag ersätta authoritykontroll,
- en canary expandera utan evidence,
- en capability få större mandat bara för att den fungerat många gånger.
Versionering ska bevara mening.

Testning ska utmana antaganden.

Rollout ska begränsa blast radius.

Capability expansion ska skilja teknisk möjlighet från governad rätt.

Den kanoniska förändringsprincipen är därför:

Versionsmärk allt som kan ändra behavior, policy eller meaning.

Knyt varje execution till exact code, prompt, workflow, provider och policy.

Definiera compatibility uttryckligt.

Migrera data utan att radera source först.

Testa failure, offline, concurrency, privacy och recovery — inte bara happy path.

Låt absoluta förbud bli blockerande tester.

Använd synthetic och minimerad testdata.

Frys releasecandidate före final validation.

Rulla ut stegvis till minsta säkra scope.

Mät verifierad framgång, inte teknisk completion.

Stoppa expansion när unknown outcomes, duplicates eller privacyrisk ökar.

Använd rollback endast där state faktiskt kan återställas.

Hantera external effects separat genom reconciliation och compensation.

Låt feature flags styra aktivering men aldrig ersätta canonical governance.

Höj maturity separat för read, write, external effects, offline och autonomy.

Sänk maturity snabbt när evidensen försämras.

Avveckla gamla versioner utan att förlora historik, audit eller recoverability.

När dessa krav är verkliga kan Omnira utvecklas snabbt utan att varje ny version blir ett nytt okontrollerat system.
