# The Prompt – FactCheck v1 (separate editorial workflow)

**Status: draft / disabled / not registered in the live Omnira workflow engine.** Tracked in GitHub issue #591: https://github.com/Bumbi190/ai-operating-platform/issues/591.

**Decision 28 October 2026:** Fact checking is independent of growth-oriented content quality scoring. A reported 8/10 engagement score is not a fact check, nor is a parser's `passed=true` a factual approval. The original Home Office story was already published with a fabricated QA fallback; incident #586 documents the correction/takedown decision.

## Updated product objective — Nova reviews; the owner handles exceptions

**Decision 28 October 2026, updated:** The user should NOT manually approve every The Prompt story. Nova is the intended autonomous editorial verifier in Omnira/Atlas. She should independently check sources, assess framing, revise a draft when feasible and discard weak stories; only genuine high-impact or unresolved editorial questions should be escalated as concise messages with evidence links. This design explicitly supersedes the earlier assumption that every story needs a human FactCheck approval. Existing human-only decision receipts remain a *temporary production constraint*, not the desired final operating mode.

The proposed default workflow is: source intake → independent semantic verification by a different provider → deterministic claim/citation and risk gates → **Nova auto-clears ordinary fully supported drafts** → verify final audio/on-screen/caption/video version → automated channel gate → audited publication. For uncertainty, Nova researches again first (maximum two source rounds, two reviewer attempts and one automatic manuscript rewrite). Contradicted or unverifiable routine stories are skipped, not pushed to the owner or disguised as verified. Nova asks the owner only for sensitive, credibly sourced judgments that need a human decision; a human "yes" cannot override a claim proven false.

A Nova decision must be stored under a **separate, auditable agent identity** bound to the exact source/story/render/post hashes. It must not masquerade as the project owner's existing `social_content_decisions` or `media_factcheck_editorial_decisions` record. Before automatic public release: stage in preview/shadow mode, validate factual quality with independent samples, implement hard project spending ceilings and an atomic final admission for every publisher route. Current prototype returns `automatic_editorial_candidate` at most, and **canSpend, canRender, canSchedule and canPublish remain false**. No live automation or owner notification is wired. The original `the-prompt.factcheck.v1.json` design blueprint still describes the earlier mandatory human-approval prototype; it is deliberately disabled and must be versioned/replaced before any Nova-autonomy release.

## Desired sequence

1. **Source snapshot:** Fetch the exact original article from the canonical URL, preserve URL, date, publisher, immutable excerpt/source hash, and retrieve the best available primary sources. Reddit and Hacker News can indicate interest, but are not independent verification of a news claim.
2. **Material assertions:** Extract *all* potentially factual statements from hook, script, on-screen captions, CTA, thumbnail and social caption. Bind every assessment to project ID + script ID + revision ID + content SHA-256. Rewrites invalidate older evidence.
3. **Independent evidence search:** Seek confirming **and conflicting** material. Avoid treating syndication, copied press releases, the same parent publisher or the same model's paraphrase as independent confirmation. Use primary material where available and a second independent publisher for autonomous eligibility; otherwise escalate.
4. **Claim-level verification:** For each material sentence, record supported/unsupported/contradicted/misleading/not-factual, with exact source excerpts and explanation. A source's existence cannot prove semantic support; evidence interpretation remains part of the editorial review.
5. **Framing and certainty:** Compare the hook, summary, spoken script and on-screen text against the actual sources. Preserve 'may', 'plans to', 'alleged', 'according to', uncertainty, timelines, relevant denials, and opposing evidence. Do not manufacture false balance by presenting weak and strong evidence as equally credible.
6. **Nova decision:** The future autonomous lane may proceed without individual owner approval only when the complete evidence contract is fulfilled, the independent reviewer supports every material statement, framing is faithful and the risk is ordinary. For a credible sensitive story, Nova requests an explicit human exception decision. Unsupported, stale or contradicted stories are re-researched, rewritten or discarded, not treated as approved. The current code remains preview-only; a model verdict itself NEVER grants social posting authority.
7. **Traceability:** Persist a new immutable report for each content version; show source links, exact citation snippets, decision reasons and reviewer identity in the project UI. Manual actions need operator authorization and an audit trail.

## Deliberate limitation of the first code slice

`apps/web/lib/media/factcheck/contract.ts` provides a read-only evidence/coverage/verdict validation contract. The new `source-collector.ts` accepts only explicitly mapped publisher URLs, checks input and final URL identity, bounds article length, and produces source-hash receipts using an **injected reader**; it does not implement or invoke network access. The new `reviewer-preview.ts` runs an end-to-end **offline fixture rehearsal** with a second reviewer identity, strict source and revision binding, and no authority to generate or publish. It has no real source reader or model adapter attached. There are **no executed** AI/provider calls, database schema changes, executable Atlas action, persistent audit log, scheduling or publish hook. The JSON blueprint alongside this document remains an inactive design, not a deployed Omnira workflow.

The new `safe-https-reader.ts` has a **not-yet-integrated** HTTPS implementation with exact-host allowlisting, conservative public-IPv4 DNS validation, a pinned TLS lookup, redirect denial, response/body size limits and an HTML `article`/`main` extractor. It is deliberately not called by any live route. A public-news fetch still needs authorized preview verification, true egress policy review, reliable publisher/ownership mapping, source licensing review and an end-to-end TypeScript/CI pass. Manually run, read-only probes on the owner's Windows machine retrieved `https://www.gov.uk/robots.txt` (1,097 characters) and extracted **6,870 characters of actual article text plus the correct headline** from `https://www.gov.uk/government/news/britain-steps-up-national-defences-against-growing-ai-risks` (28 October 2026). Both used the pinned IPv4 HTTPS reader with Node's automatic family selection disabled. Another government source, the UK Parliament written-answer page, returned HTTP 403/Cloudflare challenge; this is a **HOLD**, not an instruction to bypass protection. The live probes verify limited TLS/network/HTML extraction, **not** independent article fact-checking, publisher licensing, provenance or general SSRF resistance. No public production route calls this reader; HTML extraction, publisher identification and fail-closed integration still need independent proof.

**New independent model boundary (28 October):** `independent-review.ts` builds a bounded source-grounded instruction payload for `gpt-5.4-mini`, validates the full JSON report, derives the real review run ID and timestamp on the server rather than trusting model output, freezes report/evidence after review, and refuses incomplete, altered or stale evidence. The source/model identity must come from trusted saved execution metadata; it deliberately refuses writers that were themselves OpenAI-based or whose identity cannot be verified. `reviewer-admission.ts` and `governed-reviewer.ts` provide a **dormant, server-only** provider adapter via the existing `openAIChatCompletion` cost and stop boundary. The model feature flag `THE_PROMPT_FACTCHECK_MODEL_ENABLED` must be exactly `true`; `H1_SPEND_GATE=1` must be enforced (advisory spending is refused); the execution must be project-bound with a valid owned RUN_BOUND claim; and the trusted project/script IDs must be database-verified. No production route imports this adapter. **No model request, budget reservation, database update or release took place during development.** The existing full-context budget estimator may refuse this request even when the real prompt is short; never weaken it or raise the ceiling silently just to make the trial succeed.

The rules can confirm that quotes appear in supplied source snapshots, and that different mapped publisher groups are cited. Source snapshots and receipts are runtime-frozen, and byte-identical syndicated texts from different publishers are not accepted as independent corroboration. Near-identical syndication still needs semantic review. These checks do NOT prove source authenticity or that a quote logically supports a claim. The offline runner uses simulated readers/reviewers. A real, separate fact-check model and trusted primary-source reader must still be integrated and audited. High-impact content in **English or Swedish** (asylum/asyl, elections/riksdagsval, health/läkemedel, alleged crimes/åtal, investigations/myndighetsutredning and breaches/dataintrång) receives an additional keyword-based human-review floor, even when an upstream risk field says `standard`; this is defense-in-depth, not complete risk classification. Evidence and citations never automatically grant publish permission.

## FactCheck evidence history — draft schema and read-only UI

A CLI-generated SQL **proposal** `docs/workflows/proposed-migrations/20261028131815_the_prompt_factcheck_evidence_v1.sql` defines the future `public.media_factcheck_reports` table. It was moved out of the active migrations directory because Omnira's canonical production migration-count guard correctly refuses an unapproved new migration. The guard was preserved unchanged. The table is neither deployed nor registered as `created_not_live` in the production catalog snapshot: the SQL is a reviewed design proposal until its own migration approval and controlled database rollout. It stores the exact project, manuscript revision, source text checksums/URLs, per-claim evidence excerpts, reviewer model, human-review requirement and verdict. It intentionally does **not** store entire third-party copyrighted articles. A report represents **review evidence**, not a publish grant. The table has RLS enabled, no anonymous/authenticated grants or policies, only service-role SELECT/INSERT, FORCE RLS, and triggers refusing UPDATE/DELETE/TRUNCATE even for privileged callers. An insertion is refused if the script/version, project or run claim do not match the database.

The project-scoped read-only page at `/projects/ai-media-automation/factcheck` is accessible through The Prompt's media dashboard. It resolves the user-authorized project through the RLS server client **before** a narrowly project-filtered admin read. The screen shows evidence and exact version identifiers, never publication controls or model calls. If reports exist, it separately queries owner decisions under the same project boundary, verifies each decision's script/version, source/content hashes and **current project owner**, and labels an absent/unreadable decision as not verified. It cannot convert `ready_for_editor` into approval. Until the new migration is explicitly reviewed, tested and applied, it shows an unavailable-schema message rather than invented historical reports.

**New, still dormant report writer:** `report-record.ts` builds an immutable evidence candidate from a fresh database-read script, the current claim/lease, source text hashes, publisher identities and the model's source-set digest. It *recomputes* the deterministic claim decision, refuses all swapped/missing evidence and requires an exact database-derived `vN` manuscript revision. `report-writer.ts` is a server-only, unreferenced adapter that can look up The Prompt by slug, reread the current script and claimed run, and submit **one** append-only insert. It is disabled unless `THE_PROMPT_FACTCHECK_REPORT_WRITES_ENABLED=true`, `THE_PROMPT_FACTCHECK_MODEL_ENABLED=true` and the hard spend gate is enforced. Older scripts without explicitly stored `raw_output.writer_model` stay on HOLD; no writer provider is guessed or fabricated. A possibly committed/ambiguous write is not retried automatically. Insertion is backed by a **proposed** SQL trigger that also checks running state, lease expiry and `vN` identity. End-to-end tests use a **simulated database only**: the schema remains uninstalled and no real report was recorded.

**Actual model provenance captured for newly authored scripts (still draft PR):** `script-writer-provenance.ts` extracts the provider/model from the *actual completed SDK response*, rather than trusting the requested model string or the AI-generated script JSON. It binds a SHA-256 digest of the authored hook, script, captions, hashtags, CTA, tone, duration and `vN` version to an explicit server-stamped `writer_model`, `writer_provider`, `writer_provenance=provider_response_v1`, `writer_version` and `writer_content_sha256` in `media_scripts.raw_output`. Anthropic responses must have provider Message type/id and a Claude model; governed OpenAI fallback responses are marked as OpenAI, never mistakenly as Claude. If the actual provider omitted metadata, all provenance fields are **null**, and the independent FactCheck reviewer refuses to proceed. This metadata is traceability, **not proof the claims are correct**.

All existing direct script-generation routes, the final post-rewrite output, breaking news, and manual regenerate write their verified provenance for the final saved text. The workflow `scripts/from-run` route strips forged provenance because free-form workflow JSON cannot prove its author. A human PATCH editing hook/script now increments the version, clears existing writer attribution and quality/render acceptance, and fences concurrent edits by version; the subsequent report writer independently recalculates the stamp against current stored columns. **Legacy scripts stay unverified; never backfill by guessing Anthropic based on the prompt or marketing copy.** No paid model calls were made to implement or test this change, and this draft remains unmerged/disabled.

**Owner-matched editorial decision proposal, physically tested:** the same still-quarantined SQL now proposes a second append-only table, media_factcheck_editorial_decisions, bound by foreign key to a FactCheck report, exact project/owner/script/revision/source digests and a written approve/reject decision. This schema validates that the claimed actor ID equals the current project owner, but **does not itself prove the actor was present**: only a future session-authenticated server writer (with a reviewed human-origin receipt) can establish that. A **dormant, server-only** `owner-decision-writer.ts` adapter is now implemented but is not imported by any route. Its `owner-decision-intent.ts` parser accepts only nine expected client fields, rejects submitted actor/project/approval metadata, and binds the exact report/script/source digests. The adapter requires both `THE_PROMPT_FACTCHECK_OWNER_DECISIONS_ENABLED=true` and `THE_PROMPT_FACTCHECK_REPORT_WRITES_ENABLED=true`, validates the session with `createClient().auth.getUser()` **before** creating an admin client, re-reads the project owner and current report/script in the same project, and inserts exactly one immutable row (never upserts or retries an ambiguous write). Offline session/DB tests cover absent users, foreign projects, fabricated author IDs, stale revisions and unsupported approvals. This still does **not** provide a human-click attestation by itself: a future same-origin/CSRF-protected manual action endpoint and user interface must be reviewed separately. None of these flags was changed and no such live route exists. The database denies non-owner approvals, changed or unverified claims, missing independent per-claim citation groups, short justifications and stale manuscript revisions. Only a narrowly specified sensitive-risk HOLD can receive a preparation-only approval with explicit human acknowledgment; contradictions or missing evidence never qualify. The existing social_content_decisions remains the separate, final per-channel revision approval. Both private tables have RLS/FORCE RLS, zero client grants, service-role SELECT/INSERT only and UPDATE/DELETE/TRUNCATE denial.

**Actual PostgreSQL 17 verification:** the draft SQL, role grants, trigger logic, append-only behavior and positive/negative owner-approval cases were executed successfully inside a dedicated disposable database on an already-running local Postgres test server. A reusable local-only PowerShell runner creates a uniquely named database, runs the fixtures, rolls back the assertions and drops it again; see docs/workflows/factcheck-postgres-isolation-test.md. The test exposed and resolved two privilege mismatches (row-lock UPDATE privileges on source tables, and a missing service-role EXECUTE grant on an internal evidence helper) without changing production access. These are synthetic schema fixtures rather than a full production-schema clone.

**Two-stage offline review policy:** editorial-admission.ts compares current server-stamped author provenance, complete public-facing story digest, source/claim receipt structure and the owner's preproduction FactCheck decision. It then separately checks the existing final social content revision, explicit human decision and video/evidence identities. Even if every check passes, its response is only a review-readiness state: canSpend=false, canRender=false and canPublish=false. There is no external side effect or API route importing the module.

**Not yet activated:** a reviewed same-origin session-authenticated owner approval HTTP route and explicit human-click UI (the dormant adapter alone is not an endpoint or a physical-human attestation), reliable source licence/provenance and live independent semantic reviewer, actual production DB migration, immutable report writes from an approved worker, plus an atomic final render/publisher gate. Never bypass Omnira's canonical migration guard or infer that local SQL fixture success is production authorization.

## Release order and safety

- Keep PR #585's emergency parser fail-closed fix separate from production activation of this **new** workflow. Do not hide failed reviews by lowering thresholds or auto-switching to publish.
- Replace the offline source-reader fixture with an independently reviewed, authenticated, project-scoped adapter. Hermes currently follows its own Playwright read flow and cannot by itself prove a safe final-URL/egress boundary; do **not** connect the collector to Hermes or arbitrary live URLs before network-level SSRF/redirect/DNS rebinding controls, content provenance and real publisher identity are verified. Unavailable/invalid sources must cause HOLD.
- Wire the dormant governed reviewer **only after** verifying the persisted actual script writer/provider, database ownership of the claimed run, authorized independent claim reviewers, enabled operator setting and sufficient hard project-budget headroom. Enforce one dispatch with no retries or ungoverned fallback; inspect the cost ceiling before even considering a live trial. Independent semantic interpretation is still fallible; maintain explicit HOLD/human review.
- Store signed/revision-bound FactCheck reports with RLS; activate **one** verified script through preview and manual editor acceptance before touching production scheduling.
- Hook EVERY legacy and new render/publish route to the same approval identity. A report on an earlier draft must not authorize a new version or an edited video caption.
- Preserve existing image fallback and 10:00/20:00 business goal; fix DST separately in issue #378.
- Review previously published posts containing the historical parse-error placeholder, prioritizing material errors over bulk deletions.
